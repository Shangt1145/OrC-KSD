# 触发器合法性验证 — 需求阐明记录

> 本记录随对齐逐轮增长：记录委托需求的阐明（功能职责、约束、验收标准、已解决歧义与备选方案）。
> 委托：触发器合法性验证（Orc 引擎级，受控变更）。

## 一、需求概述（委托要点）

- Trigger<TView> 新增 public virtual 验证方法（基类默认恒合法、可选覆写）；暴露面＝接收原始引用 → bool（供外部触发前检查）。
- InvokeAsync 内部固定先调用验证（空位：空转检查后、ctx/视图绑定前）；不合法＝仅本次取消（不绑视图、不跑事件、留痕），不传染嵌套链。
- 契约：判定合法 ⇒ 后续错误（含绑定失败）捕获处理、安全结束（返回流＋失败标记）；失败标记＝EventStream 加性属性（三态：正常/验证拒绝/契约兜底失败）。
- 归属 Orc；受控变更管理（绑定失败行为变更＋测试迁移，汇报逐条列出）。

## 二、对齐记录

### 轮 1：【主问题 1】验证方法的输入面与调用语义（委托 Requirements 第 1/2 条）

**问题原文（摘要）**：
- a) 「原始引用」的信息面语义：「引用标识＋存活状态」级（复用 IRefInfo）还是「能到达具体类型的目标对象」（强类型引用）？
- b) 「从触发数据中收集引用」的判定语义：收集标准？是否递归嵌套容器？是否去重？外部预检是否自行组织引用列表？
- c) 验证方法自身抛异常时的语义：按「不合法」处理？按「契约兜底」？直接外抛？

**解答（需求口径）**：

**a) 信息面＝须能到达目标对象本体**（在存活前提下可解引用、读取对象类型与其数据）。依据：合法性判断的典型用途是规则级判断（类型/状态/词条等），仅「引用名＋存活」的通用面不足以支撑；因此公开签名**不得仅用仅标识+存活的信息面**（如仅 IRefInfo），定型候选＝强类型引用列表（`Ref<Entity>` 或等效形态；具体由实现定型并汇报）。「存活判断」仍为一等能力（先查 IsAlive、避免解引用抛出）。

**b) 收集语义**：
- 收集标准＝凡属于**引用类对象**（实现引用信息面的类型）一律收集，**不限目标类型**；
- 范围＝**仅 data 第一层值**（不递归进入嵌套字典/列表——引用需平铺放置为显式契约；避免隐式深遍历的语义不透明与开销）；
- **去重＝按引用相等去重**（验证只关心"涉及哪些引用"；重复出现无信息增量）；
- 顺序＝保持 data 插入序（不排序）；无引用＝空列表（默认恒合法）；
- 外部触发前检查＝调用方**自行组织**引用列表（框架不额外暴露收集工具）；触发内调用与外部调用为**同一方法、无缓存/无短路**（每次完整调用；内外判定源唯一）。

**c) 验证方法自身抛异常＝按契约兜底路径处理**：捕获＋记录＋失败标记＋安全结束（不外传；取消类仍穿透上抛）。**不按「不合法」处理**（预期拒绝与意外错误必须区分：不合法→取消留痕；异常→失败标记）；**不直接外抛**（保持"错误捕获兜底、不把错误炸给调用方"的改进方向；作者编程错误经记录/标记可观测）。

**备选方案与拒绝原因**：
- a 备选：仅「标识＋存活」面（IRefInfo 级）——**拒绝**：不足以支撑规则级判断（无法读取类型/状态/数据），迫使验证者下游绕行取对象，违背"直接接收原始引用"的可用性目标。
- b 备选：递归收集嵌套容器——**拒绝**：语义不透明（层次/顺序解释歧义）、性能不可预期；平铺为显式契约更可控。b 备选：不去重——**拒绝**：重复项无信息增量，徒增验证者负担。
- c 备选：按「不合法」处理——**拒绝**：混淆预期拒绝与程序错误，掩盖作者缺陷。c 备选：直接外抛——**拒绝**：在验证阶段破坏「错误捕获兜底」的整体改进方向；可观测性由标记与记录承担。

**架构审视补充（补充入需求）**：
- 验证方法契约＝**只读、无副作用**（不得改写游戏状态；判定与执行分离）；
- 验证保持轻量（每次触发均被调用）；
- 输入面边界：验证输入以引用为限；如需引用之外的上下文（如资源量等）参与判定，由调用侧在暴露调用中自行组织（或作为后续扩展评估）——不在本委托输入契约内；
- 失败标记三态（正常/验证拒绝/契约兜底失败）为验收锚点（对应委托验收⑤）。

### 轮 2：【主问题 2】契约兜底的边界、失败标记归类与迁移边界（委托 Requirements 第 4/5/6 条）

**问题原文（摘要）**：
- a) 兜底边界与标记归类：①事件处理器内异常是否保持既有「隔离＋继续」语义？②若是，「事件异常但全部跑完」的结局归「正常」还是「契约兜底失败」？③空转执行（不调用验证）的结局归「正常」吗？④失败标记仅属本流自身、不因嵌套子流失败改变祖先流标记？
- b) 记录形态：绑定失败捕获记录是否与现状「总线层捕获记录」保持同构（source＝触发器展示名、Error 级、keywords 含异常类型名），还是切换新关键词体系？「验证拒绝」留痕的级别/关键词/来源约定？
- c) 迁移边界：「总线层捕获绑定失败并记录、广播继续」用例（BusEmitTests）是否纳入受控变更，还是「行为等价、保持通过」并由汇报说明差异？

**解答（需求口径）**：

**a) 四条全部明确**：
1. **事件处理器内异常＝保持既有「隔离＋继续剩余事件」语义**（不改为安全结束）。契约兜底只覆盖「准备阶段/执行链路的结构性错误」（验证之后的绑定失败等）；事件级容错语义维持 S2 已验收行为（隔离记录、继续、非回滚）。「合法 ⇒ 必须捕获处理」由隔离记录满足（错误被处理、不外传）。
2. **「事件异常但全部跑完」结局＝「正常」**。失败标记表达**结构性结局**（未进入执行／执行中途中止）；事件异常隔离是预期内的容错路径，执行流完整完成。**记录与标记分离**：调用方如需感知异常，经事件流条目（既有观察面）查询，而非经标记。
3. **空转执行＝「正常」**（既定正常语义路径：产空流、不验证、无标记）。
4. **失败标记＝本流自身属性，不传染祖先**（与「仅本次取消、不传染」一致）；**记录照常冒泡**（可观察性传播与标记性传播分离——记录可经父流看见、标记不变）。嵌套子流被验证拒绝/契约失败时，祖先流标记同样不变；父事件拿到带标记的子流继续执行。

**b) 记录形态**：
- **绑定失败兜底记录＝与触发器既有隔离记录同构**（复用同一形态，而非沿用「总线层格式」）：level＝Error；source＝触发器展示名（纯展示名、无事件上下文）；keywords 至少含 `exception:{异常类型名}`；data 含 exceptionType/message。
- **不新立 contract/validation 平行体系**；「契约兜底」的区分经**失败标记（本流）**与记录归属表达。
- **验证拒绝留痕**：level＝Warning；keywords 含 `validation:rejected`；source＝触发器展示名；data 最简（可空）。写入**本流**（拒绝路径上流已创建、正常挂载）。
- 总线层故障捕获机制**保留**（防御性、服务未来其他路径），其既有形态不变；但「绑定失败」场景此后不再经该路径。

**c) 迁移裁定（受控变更清单口径）**：
- `TriggerSharedContextTests`「绑定失败原样传播」用例：**纳入受控变更**——断言迁移为：不抛（返回流＋失败标记＝契约兜底失败）；`executed=false` 保持；**写兜底记录**（与旧「不写记录」相反）；逐条列出旧断言与新断言。
- `BusEmitTests`「总线捕获绑定失败并记录、广播继续」用例：**纳入受控变更**——其原断言（root 观察面：恰 2 条 Error、source＝B/BusPayloadView、keywords 含 exception:KeyNotFoundException、广播继续 trace）**保留为观察锚点**（新架构下预期继续通过：记录改由触发器写入本流、经冒泡于 root 可见、source 相同）；**增补新协议断言**（子流失败标记存在；总线捕获未触发该场景；记录不重复）；汇报说明机制变更。
- `ContextViewTests` 的 Binder 直调用用例（KeyNotFound）：**不受影响**（Binder 底层 API 仍抛；契约变更仅作用于 InvokeAsync 路径）。
- 兜底原则：凡断言涉及「记录来源/归属/流」者按上表迁移；「广播继续」「失败不外传」等语义保持不变。

**备选方案与拒绝原因**：
- a②备选：事件异常亦标「契约兜底失败」——**拒绝**：与 S2 隔离语义冲突，混淆「完整执行（含容错）」与「中止」。
- b 备选：切换新关键词体系（contract/validation 系列重写观察面）——**拒绝**：平行体系造成观察面分裂；失败标记已承担区分职责。
- c 备选：BusEmitTests 用例「行为等价、保持通过」不做迁移——**拒绝**：记录归属与路径实际变化（不再由总线捕获），仅说明差异会遗留语义漂移；应显式迁移并增补断言。另：总线 catch 的防御性保留可以人造异常（非绑定失败）覆盖——建议（非强制）。

**架构审视补充**：
- 可诊断性：三种结局（含事件容错记录）须在验收中可断言（对应验收④⑤）——失败标记断言＋记录断言＋流归属断言；
- 兼容性：失败标记为加性属性（既有消费方忽略新属性即旧行为——除绑定失败传播语义外）；
- 兜底边界：兜底不承诺回滚（与既有隔离语义一致；准备阶段本身无状态改写、无回滚需求）。

### 轮 3：【主问题 3】公开面定型与命名口径（class 级收尾）

**问题原文（摘要）**：
- a) 验证方法的公开命名：是否有指定或偏好（Validate／IsValid 风格单方法 bool 形态），还是与失败标记一样「由实现者定型并汇报」？
- b) 输入类型定型确认：拟定型为「强类型框架引用列表」＝`IReadOnlyList<Ref<Entity>>`（依据：库中唯一可达引用类型；IRefInfo 不入签名）——确认该口径；或期望「接口化等效形态」（为未来其它引用目标留扩展余地）？
- c) 公共文档口径：InvokeAsync／EventStream 的 XML 注释同步改写为新契约（验证调用点、绑定失败不再上抛、失败标记三态、记录形态），受控变更以「旧契约 → 新契约」逐条呈现——确认？

**解答（需求口径）**：

**a) 命名定型＝`Validate`**（`public virtual bool Validate(IReadOnlyList<Ref<Entity>> refs)`；外部可直接调用；基类默认恒合法＝可选覆写）。理由：与需求术语「验证（Validation）」直接对应（检索/沟通/文档一致）；单方法 bool 形态确认。如实现中发现同名冲突等硬性障碍，可微调但须在汇报中说明。

**b) 输入类型定型＝`IReadOnlyList<Ref<Entity>>`；本委托不引入接口化抽象**。事实依据（本次已核实）：①库内唯一引用实例化点＝`Entity.Ref`（`new Ref<Entity>(this, Life, name)`；构造库内限定、外部不可自造其它形态）；②`Card : Entity`——实体家族全部经基类视角 `Ref<Entity>` 承载（可解引用到对象本体）；③IRefInfo（标识＋存活）不满足信息面要求、不入签名。「接口化等效形态」不做：与既有「不预埋、用例驱动扩展」口径一致；未来若出现新引用目标，以受控变更扩展（本轮定型不构成该演进的阻塞）。

**c) 文档口径确认 ✅**：XML 文档注释随受控变更同步改写（覆盖：验证方法及其调用点、绑定失败不再上抛、失败标记三态、记录形态）；受控变更以「旧契约 → 新契约」逐条在汇报呈现。补充要求：`Validate` 注释须写明「无副作用契约（覆写不得引入跨调用可变状态）、默认恒合法」；失败标记属性注释须写明三态语义与「记录与标记分离」口径。

**备选方案与拒绝原因**：
- a 备选：`IsValid` 命名——**拒绝**：与需求术语族（Validation）不一致、易与属性式查询混淆；`Validate` 更贴合「作者声明参与验证」的动作语义。
- b 备选：接口化等效形态（`IReadOnlyList<IRef>` 或自定义协变接口）——**拒绝**：当前唯一目标族＝Entity（生命周期根）；提前抽象无用例支撑、无谓扩大公共面。
- c 备选：仅新增成员写注释、既有成员注释不动——**拒绝**：契约已变（绑定失败语义等），旧注释将成误导源；必须同步改写。

**架构审视补充**：
- 可维护性：验证覆写约束（无副作用／不得引入跨调用可变状态）延续 S2「开放继承契约」，写入注释；
- 兼容性口径复述：`Validate` 与失败标记均为**加性**（不改变既有成员签名）；受控变更集中于行为语义与注释；
- 验收检查单补充（四项对齐）：命名／签名定型、注释完备（含无副作用与三态口径）、受控变更「旧→新」呈现、覆盖清单逐条。

## 三、实现记录（实现阶段追加）

> 实现完成；以下为实现定案与验证结果，供验收对照（原对齐记录保持不变）。

### 命名与签名定案（实现者定型并汇报）
- 验证方法：`Trigger<TView>.Validate(IReadOnlyList<Ref<Entity>> refs)` → bool（public virtual；基类默认恒合法）。签名按轮 3 定型（IRefInfo 不入签名）。
- 失败标记：`EventStream.Outcome`（加性属性，internal set）＋枚举 `ExecutionOutcome`：`Normal`（正常，含空转与事件级容错）／`ValidationRejected`（验证拒绝）／`ContractFailure`（契约兜底失败）。
- 验证拒绝留痕：level=Warning；keywords=[validation:rejected]；source=触发器展示名；data 空。
- 契约兜底记录：与既有隔离记录同构（level=Error；source=触发器展示名；keywords 含 exception:{类型名}；data 含 exceptionType/message）。
- 收集规则：data 第一层值、引用类对象（库内唯一形态 Ref<Entity>）收集、按引用相等去重、保持插入序、无引用＝空列表；触发内调用与外部调用为同一方法、无缓存/无短路。

### 受控变更（旧契约 → 新契约）
- 绑定失败（必填缺失/视图声明非法）：原「原样传播（KeyNotFound / Argument 抛出）」→ 新「捕获处理：记录＋Outcome=ContractFailure＋安全结束（返回流）；不外传」。
- 验证自身异常：按契约兜底路径处理（捕获＋记录＋标记；不按「不合法」处理；取消类穿透）。
- 不合法（Validate=false）：仅本次取消（不绑视图、不执行事件、留痕、返回流含标记、不传染嵌套链）。
- 相关测试迁移：TriggerSharedContextTests（绑定失败用例改为捕获＋标记）；BusEmitTests（保留观察锚点＋增补子流标记/记录归属断言）；ContextViewTests 直调用不受影响。
- 总线层捕获机制保留（防御性、形态不变）；事件级容错语义维持（结局仍 Normal）。
