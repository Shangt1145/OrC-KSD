# S4 组件与效果 —— 需求阐明记录

> 委托：S4『组件与效果』（继承 S1~S3 交付）；级别＝类/功能流程级。
> 本记录随 grill 逐轮增长，记录对齐过程与需求阐明（功能职责、约束、验收标准、已解决歧义）。

## 甲、委托要点（已对齐、供实现遵循）

1. **卡牌＝薄容器**：数据放数据组件、逻辑放逻辑组件；容器访问：`AddData` / `GetData<T>`（数据组件）、`AddEffect` / `Effects`（逻辑组件）（拟案已归档；如实现中发现偏差，按汇报反馈）。
2. **效果＝逻辑组件**：一个效果＝一个主触发器（主动/被动）＋附带的逻辑引用；组装默认实例化（继承＝额外注入 handler 的途径）。
3. **装载/卸载行为契约**：①单位放置后效果生效（注入完成）；②效果移除/卡牌销毁后清理完成（不再生效、引用清理）；③顺序：单位初始化逻辑先、效果注入后。
4. **通用流程**：攻击（发起方：反制检查→调用伤害结算→收尾）与伤害结算（承受方：护盾检查结算→伤害生效）**分离**；施放流程：法术＝主动效果，施放→调用伤害结算；具名 band 扩展位（复用 S2 band 机制）。
5. **注入**：handler 经 Register（S2 运行期追加注册）注入流程触发器的具名 band。
6. **验收锚点**：场景 2『攻击时回血』全链路（放置→注入→攻击→回血→移除→清理→不再回血）。

## 乙、第 1 轮对齐：装载链路与 Effect/主触发器关系（2026-10-03）

### 轮 1 问题（子 agent 原文）

**主问题 1：放置/移除/销毁链路的驱动入口与顺序契约的验收口径**
- 1a. 验收测试中"放置"应经什么入口发起？（框架提供卡牌级放置 API？还是测试/调用方直接发出 card.placed 更新、由效果侧响应完成挂载？还是两者组合）"单位初始化逻辑先、效果注入后"中的"单位初始化逻辑"指谁的逻辑（卡牌自身的放置处理？数据初始化？），该顺序期望怎么被观察/断言（可观察信号是什么）？
- 1b. card.placed / effect.removed / card.destroyed 三个更新在链路中的角色与发出方：它们是链路的"驱动信号"（先广播更新→订阅者响应执行挂载/清理），还是链路执行完后的"通知"（框架编排完成挂载后广播）？验收断言应建立在哪一种？
- 1c. 效果"移除"与"卡牌销毁"的入口和范围：移除单个效果的入口是什么（卡牌上的 API？发出 effect.removed 更新？）；卡牌销毁的入口是什么（Destroy？发出 card.destroyed？）；销毁时清理范围＝全部效果吗？销毁后卡牌是否有"不能再攻击/不再受击"等附加契约，还是只要求"清理完成"？

**主问题 2：Effect 基类与"主触发器"的关系及主触发器 hooks 覆盖**
- 2a. 一个效果是否恰有一个"主触发器"？"装载＝挂载这个主触发器＋执行 OnMount"中，挂载动作与 OnMount 的关系是什么（OnMount 里写注入逻辑＝作者把 handler 注入流程触发器；主触发器本身被挂到总线是为了什么——响应后续的放置/移除类更新吗）？
- 2b. 被动效果主触发器的 hooks 应覆盖哪些更新（委托原文"主触发器 hook 放置/移除类更新"）？"放置时注入"与"移除时清理"分别走作者覆写的 OnMount/OnUnmount，还是主触发器的 handler（框架模板骨架）？框架模板骨架（注册/注销）与主触发器的职责边界请明确。
- 2c. 主动效果（法术）的装载差异：S3 约束下主动触发器不可挂载；主动效果在"放置/加入卡牌"时是否有装载动作（如仅进入 Effects 列表），还是其生效完全依赖"施放"时调用主触发器？

### 回复（本轮对齐结论）

**1a. 放置入口与顺序验收口径**
- 放置的驱动入口＝**发射 `card.placed` 更新**（经引擎总线；载荷携带卡牌引用/标识）；本阶段**不引入**游戏流程/棋盘层的放置 API——更新即驱动；框架（效果装载链）对该更新的响应完成挂载。测试可直接发更新（可自封装辅助方法）。
- "单位初始化逻辑"＝**卡牌（单位）自身的放置初始化**（数据/状态就绪），先于效果注入完成；其承载者（框架放置处理或卡牌声明）由实现者设计，但**顺序契约必须成立**。
- 顺序契约的验收口径（推荐①+②组合；允许等价的其它信号）：①**事件流条目次序**——初始化相关条目先于装载/注入条目；②**状态可观察**——OnMount（注入）执行时，初始化产出的数据/状态已可用；③**端到端**——放置处理完成（更新广播及其响应完成）后，效果已生效（"攻击时回血"已可发生）。
- 备选与拒绝：备选＝框架提供卡牌级放置 API（如 `Place()`）→ 拒绝：本阶段不引入游戏流程层（非目标）；更新驱动与既有模型一致、避免新增抽象层。

**1b. 三个更新＝驱动信号（非完成通知）**
- `card.placed`、`effect.removed`、`card.destroyed` 均为**驱动信号**：先广播更新→订阅者响应执行装载/清理；验收断言建立在**行为结果＋事件流**上。
- 备选与拒绝：备选＝"完成通知"模型（框架编排完成后再广播）→ 拒绝：与既有更新模型不符（hook＝对更新作出反应）；驱动模型使行为契约更直接、可测。

**1c. 移除/销毁入口与范围**
- 效果移除：卡牌容器 API（`RemoveEffect`，与 AddEffect 对称）为规范入口，触发该效果的清理链；与低层 `effect.removed` 驱动**收敛于同一清理模板**；测试可经任一路径。
- 卡牌销毁：销毁动作（`Destroy()` 语义）＋发出 `card.destroyed` 更新驱动清理；**`Destroy()` 本身不触发卸载（S3 既有约束）**；清理范围＝该卡牌全部效果。
- 销毁后附加契约：**仅"清理完成"**；**不引入**死亡/胜负等游戏规则语义（非目标）。
- 边界：重复放置＝幂等（不重复装载）；移除不存在的效果＝幂等无操作（不抛错，与总线卸载的幂等语义一致）；重复销毁＝幂等。
- 备选与拒绝：备选＝销毁自动内联触发卸载（`Destroy()` 内部直接卸载）→ 拒绝：与 S3 已定约束冲突（Destroy 只杀不管卸载）；编排归本委托且以更新驱动。

**2a. 效果与主触发器：恰好一个主触发器**
- 一个效果**恰有一个主触发器**（主动/被动）。
- 装载＝【挂载主触发器到总线】→【执行 OnMount（注入）】（框架模板按序完成）；卸载＝【执行 OnUnmount（清理）】→【总线卸载】（保证清理时可安全访问引用）。
- 主触发器＝效果在总线上的**运行时代表**（hooks 挂点）；框架模板负责把生命周期更新与"挂载/卸载＋钩子"接好。
- 时序说明：主触发器挂载与放置更新的先后编排由实现者设计（满足行为契约即可；若强时序模型存在自举问题，允许框架装载链代表放置响应执行首挂——测试以行为为准）。

**2b. hooks 覆盖与职责边界**
- 主触发器 hooks 覆盖**放置类＋移除类**更新（**至少覆盖移除类**：`effect.removed`、`card.destroyed`）。
- 作者逻辑**统一写 OnMount / OnUnmount**（既定 Effect 基类方案）；主触发器与框架模板负责"何时触发"。
- 职责边界：**框架**＝注册/注销模板、挂载/卸载、更新接线、顺序保证、幂等与安全；**主触发器**＝运行时代表（hooks 挂点）；**作者**＝OnMount（注入）/ OnUnmount（清理）。

**2c. 主动效果装载差异**
- 主动效果（法术）：**不挂总线**（S3 约束）；放置/加入时**不做装载动作**（仅存在于 Effects 列表）；生效＝施放时调用其主触发器（施放流程→伤害结算）；一次性/消耗语义不在本期范围。
- 备选与拒绝：备选＝主动效果也走装载链（挂总线后由施放触发）→ 拒绝：与 S3 约束（主动触发器不可挂载）冲突、无必要。

### 父补充：边界与失败模式（对抗性审视）

- **装载/清理失败**：OnMount / OnUnmount 中作者逻辑失败按 S2 异常隔离原则处理——记录进事件流、不阻断其它效果的装载/清理；该效果视为未生效（或清理未完成，以实况计）。
- **执行顺序确定性**：多效果的装载/清理顺序必须确定（建议＝Effects 列表序），可断言。
- **单线程**：并发不在本期（沿用既有单线程语义）。
- **非功能**：无性能指标要求（本期）；可测试性以上述验收口径为准。

## 丁、第 2 轮对齐：注入撤销语义与流程分离验收细目（2026-10-03）

### 轮 2 问题（子 agent 原文）

**主问题 3：注入与撤销的行为验收（效果清理）**
- 3a. "不再生效"的验收口径：清理后"注入的 handler 不再执行"是否要求**实际撤销注入**（后续攻击轮次不再进入该 handler、流程触发器事件表已移除）？还是允许"进入后发现已移除而不动作"的**等价短路行为**？验收断言是否区分两者？
- 3b. 多效果隔离：同一流程触发器上多个效果各自注入 handler 时，移除其中一个是否只清理该效果的注入、其余效果的注入不受影响？此隔离是否为专项验收项？
- 3c. "调用 UnmountOwner 清引用"的指代与移除后边界：①"清引用"是否＝主触发器从总线卸载（总线不再持有该触发器）、以及效果侧对流程触发器/卡牌的引用登记被清除？②移除后卡牌 Effects 列表是否仍包含该效果（还是随之移除）？③效果移除后可否再次 Add 重新装载（复用语义）？④卡牌**已放置后**再 AddEffect 的新效果是否立即装载，还是须等待再次放置驱动？

**主问题 4：流程分离与 band 的验收细目（攻击/伤害结算/施放）**
- 4a. 攻击流程最小行为与位置断言：反制检查 band（如 Counter）与收尾 band（如 Finalize）在 S4 是否作为"空扩展位"（band 存在、可注入、无默认处理器）即可？"回血注入位置语义＝攻击结算完成时"在验收上是否要求"伤害结算先于回血"的明确断言？回血与收尾（Finalize）的先后是否为验收项，还是由实现设计并说明？
- 4b. 伤害结算流程："护盾检查结算"的 S4 最小语义与护盾数据来源（如卡牌数据组件上的护盾值；无护盾＝0 直接伤害）由实现设计即可？"攻击/伤害分离"的验收观测面是什么——伤害结算流程可被独立触发/调用？事件流上的嵌套结构（攻击流下的伤害结算子流）？band 顺序（护盾→伤害生效）以什么信号断言？
- 4c. 施放流程：法术＝主动效果的"施放"最小形态（施放时对目标调用伤害结算流程）——施放流程是否也需要具名 band 扩展位（或仅作为调用链）？验收标准③"流程分离（攻击/伤害结算/施放）"对"施放"的覆盖期望是什么（如：一个法术效果施放造成伤害的测试）？

### 回复（本轮对齐结论）

**3a. 要求实际撤销注入（非短路）**
- 清理的机制要求＝**实际撤销注入**：流程触发器注册表移除该效果的 handler（用户既定"取消注册"）。**不接受**"进入后发现已移除而不动作"的短路作为等价物——短路会残留注册与引用登记，不符合"清理完成／清除引用"的既定语义。
- 现状说明：S2 注册面仅"追加"入口；为支持撤销，允许实现者为触发器增加**注册项移除能力**（对 S2 面的加性/受控扩展，在汇报中标注）。
- 验收口径（区分两者）：**必测＝行为**——清理后攻击（含多轮重复攻击）不再回血、不再进入该 handler；**机制核验＝注册面**——如提供可读查询则断言条目已消失，如未提供则以"移除后重新装载"联动用例佐证。行为断言必须存在；机制核验形式可选。
- 备选与拒绝：备选＝允许"短路"作为等价实现 → 拒绝：残留注册/引用（与"清引用"矛盾）、可观察差异（注册面仍含该效果）、长期累积垃圾。

**3b. 多效果隔离＝专项验收项**
- 是：移除其中一个效果**只清理该效果的注入与装载面**，其它效果的注入不受影响。
- 列为**专项验收项**（用例：同一流程触发器两个效果注入 → 移除其一 → 另一仍正常生效）。
- 备选与拒绝：备选＝不列专项、仅作随机覆盖 → 拒绝：隔离为明确语义、清理波及他者将造成隐性错误，须专项回归。

**3c. "清引用"指代与移除后边界（四问）**
- ① 是。清理完成＝【撤销注入（3a）】＋【总线卸载（UnmountOwner；总线不再持有该触发器）】＋【效果侧登记/引用清除（作者 OnUnmount 的"专属清理"，如清除引用登记）】。
- ② `RemoveEffect` **从 Effects 列表移除**该效果（容器读面与运行态一致）。
- ③ **可**：移除后再次 Add 重新装载（同实例或新实例由实现者定；须保证重新装载后再次生效）。建议列入边界测试。
  - 备选与拒绝：备选＝不承诺复装（移除即终态）→ 拒绝：与容器语义（组件可增删）及"移除/装载对称性"不符。
- ④ **立即装载**：已放置卡牌上 AddEffect 的新效果即时执行装载链（与放置驱动装载行为一致）；放置前 Add ＝静态组装（等待放置驱动）。该路径不必列为核心验收项，但**不得产生未定义行为（不得静默死效果）**。
  - 备选与拒绝：备选＝不承诺（放置后 Add 未定义）→ 拒绝："静默死效果"是隐性坑，与可测试性/可用性要求冲突。

**4a. 攻击流程最小行为与位置断言**
- 反制检查（Counter）/收尾（Finalize）：S4 作为**具名 band 扩展位**（存在、可注入）即可；默认处理器非必须（"考虑反制/护盾"在 S4 的体现＝扩展位成立）。
- **"伤害结算先于回血"＝验收强制项**（信号：事件流条目/子流次序，或状态观测——回血执行时伤害已生效）。
- 回血与 Finalize 的先后：由实现设计并在汇报说明（非强制验收项）。
- 备选与拒绝：备选＝"回血与 Finalize 先后"也作强制断言 → 拒绝：语义上未定（"攻击结算完成时"未指定相对 Finalize 的精确位置），强制会过度约束实现。

**4b. 伤害结算流程最小语义与观测面**
- 最小语义（实现设计，须满足）：护盾检查结算（读取承受方护盾值——来源＝数据组件；无护盾数据＝0，直伤）→ 伤害生效（扣减/记账）；细节由实现说明。
- "攻击/伤害分离"验收观测面（须覆盖"分离"与"次序"两要点，信号可选组合）：**分离**＝伤害结算流程可被独立触发（不经攻击流程亦可执行）**或** 事件流父/子流结构（攻击执行时伤害结算为其子流）；**次序**＝事件流条目次序**或**状态观测（护盾检查先于伤害生效）。

**4c. 施放流程最小形态与覆盖**
- 施放＝法术（主动效果）主触发器被调用；最小逻辑＝对目标调用伤害结算流程；**具名 band 扩展位非必须**（事件序列组织由实现自由；如声明 band 方案不禁止、无额外要求）。
- 验收③对"施放"的覆盖期望：**≥1 个施放用例**——主动效果施放 → 经伤害结算流程 → 目标受到伤害（表明复用同一伤害结算流程，与攻击链对照）。

### 父补充（对抗性审视）

- **留痕可观察性**：装载/注入/清理动作应提供事件流留痕（沿用 S3 留痕风格；粒度实现者定），至少支撑验收断言与阅读工具分析。
- **清理的安全与幂等**：重复清理安全（幂等）；清理中作者逻辑失败按轮 1 隔离原则处理（记录、不阻断其它效果）。
- **注入/撤销对称性**：每个效果的注入可被独立撤销、独立卸载（无"必须整体清理"的隐性前提）。
- 既有失效/异常机制（Stale、隔离）在流程执行中照常适用，本委托不新增额外失败模式要求。

## 戊、第 3 轮对齐：容器/数据组件 API 语义与更新载荷、销毁/移除入口（2026-10-03）

### 轮 3 问题（子 agent 原文）

**主问题 5：容器与数据组件 API 的语义（验收②的测试对象与边界）**
- 5a. AddData / GetData<T> 的键与重名策略：键＝类型吗？同一卡牌重复 Add 同类型数据组件如何处理（拒绝/覆盖）？一个卡牌持有多（不同）类型数据组件共存是否为期望能力？是否需要"同类型多实例（以名称区分）"（还是本期不需要）？
- 5b. GetData<T> 缺失行为：抛明确异常（可行动错误）还是返回 null/default？验收②"容器访问"期望覆盖的用例集是什么（正常存取、缺失、重复、移除？）——即哪些行为是必须测试锚定的？
- 5c. 范围与数据类约束：本期容器 API 范围是否即 AddData/GetData + AddEffect/Effects（不包含数据/效果的"替换"等其他操作）？"强类型数据类"是否有形态约束（任意类即可/需实现某接口/需继承）？GetData 返回实例引用、外部可直接修改其字段，是否为期望语义（引用共享）？

**主问题 6：三个更新的载荷构成与销毁/移除入口的定位语义**
- 6a. 载荷构成与多卡牌定位：card.placed 载荷＝卡牌引用/标识（已明）；effect.removed 与 card.destroyed 的载荷需携带什么（效果引用/卡牌引用/两者）以支撑"定位该效果/该卡牌"的清理？除 3b 多效果隔离专项外，是否要求多卡牌并存时的清理定位专项（如：两张卡各有效果，销毁其一不影响另一）？
- 6b. 销毁链入口：调用方组合两步（先 Destroy() 再发 card.destroyed）还是由卡牌/框架辅助一步完成（同一步内"杀＋发更新"）？"Destroy() 本身不触发卸载"（S3 约束）与"发更新驱动清理"的组合职责归谁？验收测试应以什么入口做销毁链路？
- 6c. 移除路径的边界：①放置前 Add 的效果被 RemoveEffect 时，应仅从 Effects 列表移除（无运行态清理动作）吗？②RemoveEffect 与直接发 effect.removed 更新两条路径是否都要有测试覆盖（"收敛于同一清理模板"的验证方式）？③对同一效果重复移除、或移除请求中含不存在的效果（部分命中）时，幂等语义如何（不抛错、只处理存在的）？

### 回复（本轮对齐结论）

**5a. 容器键与重名策略**
- **键＝类型**（`GetData<T>` 的泛型参数即键）：每卡牌每类型恰一份数据组件。
- **重复 Add 同类型＝拒绝**（明确错误，不静默覆盖）——静默覆盖丢数据、违背"可行动错误"风格；内容变更新＝取出实例改字段（引用共享，见 5c）。
- **多（不同）类型共存＝期望能力**（薄容器本义）。
- **同类型多实例（名称区分）＝本期不需要**（后置；如未来需要，属加性演进）。
- 备选与拒绝：备选＝允许按名称键注册多实例 → 拒绝：键模型复杂化、当前无场景诉求。

**5b. GetData<T> 缺失行为与验收用例集**
- 缺失 → **明确异常**（可行动错误；异常类型实现者定，测试以类型为锚、不锁消息——沿用 S1 口径）；不返回 null/default（防 null 蔓延）。
- （可选加性面：TryGetData 类试探读面——非必须，不进验收。）
- 验收②"容器访问"必测锚定集：**正常存取**（Add→Get 返回同一实例；多类型共存各自可取）＋**缺失**（未添加类型 GetData 抛明确异常）＋**重复**（重复 Add 同类型被拒绝）。数据组件的"移除/替换"非本期范围，不列验收。
- 备选与拒绝：备选＝缺失返回 null/default → 拒绝：null 蔓延、错误晚现（远离调用点才爆炸）。

**5c. 容器范围与数据类约束**
- 本期容器 API 范围＝**AddData / GetData<T> + AddEffect / Effects**（＋已单列的 RemoveEffect）；数据/效果的"替换"等其他操作**非本期**。
- "强类型数据类"＝**任意类即可**（无接口/继承约束；实例由外部构造后 Add）。
- **引用共享＝期望语义**：GetData 返回实例引用，外部可直接修改字段（容器不做隔离/拷贝）；沿用单线程语义、无额外保护。
- 备选与拒绝：备选＝数据类需实现标记接口/基类 → 拒绝：无实际收益、限制开放性（薄容器保持最小）。

**6a. 载荷构成与多卡牌定位**
- `effect.removed` 载荷：**卡牌（所属）＋ 效果**的引用/标识（两者）——支撑"定位效果、并从容器面移除"。具体键名与载体（对象引用/Ref/标识）由实现者定并在汇报说明。
- `card.destroyed` 载荷：**卡牌引用/标识**（清理该卡全部效果）。
- **多卡牌隔离＝列入验收**（边界用例：两卡各有效果，销毁其一不影响另一的装载面与生效）——与 3b（多效果隔离）属不同维度、分别覆盖。

**6b. 销毁链入口与职责**
- **规范入口＝一步式销毁辅助**（同一步内"杀（Destroy 语义）＋发 card.destroyed"；形态实现者定——卡牌侧或引擎侧）；**低层两步**（手动发更新）亦合法、行为等价。
- 职责划分：**"杀＋发更新"的编排**归辅助入口；**清理响应**归装载链模板（对 card.destroyed）；`Destroy()` 自身仍"只杀不管卸载"（S3 约束不变）。
- 验收：销毁链路以**一步式入口**为主做测试（两步等价用例可选）。
- 备选与拒绝：备选＝仅两步组合、不提供一步式 → 拒绝：漏发更新将导致效果泄漏（隐性坑）；一步式成本低、减少误用面。

**6c. 移除路径边界（三问）**
- ① 是：放置前（未装载）效果的移除＝**仅容器面移除**；清理模板对"未装载效果"须幂等（无操作成功）。
- ② 是：**两条路径各自至少 1 用例**（`RemoveEffect` 路径、`effect.removed` 直接驱动路径）——两路分别达到相同清理结果即"收敛"验证。
- ③ 幂等语义：重复移除＝幂等（不抛错）；移除不存在的效果＝幂等（不抛错）；如提供批量形态：部分命中＝处理存在项、忽略不存在项、不抛错（对齐 UnmountOwner 幂等风格）。

### 父补充（对抗性审视）

- **null 防御**：容器 API 的 null 参数（数据实例、效果）防御拒绝（对齐 S1"入口 null 防御"风格）。
- **Effects 读面**：`Effects` 为只读枚举面（外部增删应经 Add/Remove API；绕过行为不作承诺）。
- 其余既有口径（幂等、异常隔离、留痕）沿用，本委托不新增额外失败模式要求。

## 己、第 4 轮对齐：Effect 钩子契约（主动效果、撤销责任与作者上下文）（2026-10-03）

### 轮 4 问题（子 agent 原文）

**主问题 7：主动（法术）效果的钩子与清理语义**
- 7a. 主动效果是否也执行 OnMount/OnUnmount？轮 1 说"放置/加入时不做装载动作"——是"连钩子也不执行（纯列表进出）"，还是"不挂总线但钩子照常执行（钩子作为效果作者的通用初始化/清理扩展点）"？主动效果经 RemoveEffect 移除时，清理链的行为是什么（仅列表移除、无卸载与钩子动作？）？

### 回复（本轮对齐结论）

**7a. 主动效果不执行钩子（纯列表进出）**
- 钩子（OnMount/OnUnmount）隶属**装载/卸载语境**（既定：装载＝挂载主触发器→OnMount；卸载＝OnUnmount→总线卸载）。主动效果**无装载/卸载**（不挂总线、无更新接线）→ **不执行 OnMount/OnUnmount**。
- 主动效果生命周期＝**列表进出**：AddEffect 进入 Effects 列表；RemoveEffect/Destroy 时＝**仅列表移除**（无卸载动作、无钩子）；清理模板对"未装载效果"的幂等语义同样适用（6c①）。
- 备选与拒绝：备选＝钩子通用化（主动效果也执行，作为通用初始化/清理扩展点）→ 拒绝：当前无场景诉求（主动效果无装载面可清理）；"钩子＝装载语境"语义更纯粹；未来如需通用生命周期钩子，属加性演进。
- 备注：对已移除效果的施放/其他操作＝未作承诺（不列验收；防误用由调用方负责）。

**7b. 主动/被动效果行为对照（行为契约汇总）**

| 动作 | 被动效果 | 主动效果 |
|---|---|---|
| 加入卡牌（AddEffect） | 进入 Effects 列表（放置前＝静态组装） | 同左（**共通**） |
| 放置时（card.placed 驱动） | 装载＝挂载主触发器→OnMount（注入） | 无装载动作（等待施放） |
| 移除（RemoveEffect / effect.removed） | 卸载＝OnUnmount→总线卸载；列表移除 | 仅列表移除 |
| 销毁（card.destroyed） | 同"移除"（对该卡全部效果） | 同"移除" |
| 施放 | 不适用 | 调用主触发器（施放→伤害结算） |
| 钩子（OnMount/OnUnmount） | 执行（装载/卸载语境） | 不执行（本期） |
| 更新接线（hooks） | 主触发器 hooks 覆盖放置/移除类 | 无 |
| 列表进出 | **共通** | **共通** |

- 注：未装载的被动效果（放置前移除）＝与主动效果相同（仅列表移除＋幂等模板，6c① 既定）；重复放置不重复装载/不重复 OnMount（轮 1 幂等既定）。
- "实现自由"范围：装载/卸载链的内部编排方式（轮 1 已述）；除本表与各轮条目外无额外约束——自选部分在汇报说明。

**8a. 撤销责任＝框架自动（作者不手写撤销）**
- 目标契约：**框架按装载期登记自动撤销**——效果的注入应经装载语境（框架辅助/登记）完成，卸载时框架自动撤销全部登记项；**作者 OnUnmount 只写"专属清理"**（如清除引用），不手写撤销逻辑。
- 依据：用户既定"注册/注销属模板代码，待（最小）工具化"＋ Effect 基类方案（框架负责模板骨架）。
- 实现形态（登记方式、注入辅助 API 形态）由实现者设计并汇报。
- 备选与拒绝：备选＝作者全责（OnUnmount 中手动调用撤销能力）→ 拒绝：易漏（与"模板代码工具化"初衷矛盾）、撤销完整性无法由框架保证。

**8b. 作者上下文边界与验收④断言集**
- 需求级（须满足）：作者在钩子中可获取——**宿主卡牌（含数据组件访问）**、**注入目标（相应流程触发器）的获取路径**（构造传入/组装期配置/查询皆可）；具体形态（构造参数/基类属性/钩子参数）为设计自由，在汇报说明。
- 验收④断言集（必覆盖）：①**调用与否与次数**——被动效果：装载时 OnMount 恰一次、卸载时 OnUnmount 恰一次；主动效果：不调用；②**次序**——挂载先行、OnMount 后随；OnUnmount 先行、总线卸载后随（与轮 1 既定一致）；③**失败隔离**——钩子抛出→记录、不阻断其它效果（轮 1 父补充的实测证据）；④**上下文可获得**——以测试效果实现证明（钩子内可访问宿主卡牌/数据）。
- 备选与拒绝：备选＝框架强制统一上下文注入形态 → 拒绝：无必要过度约束（保留设计自由、以汇报为准）。

**8c. 钩子重入语义（多次成对发生）**

- 备选与拒绝：备选＝同一实例仅允许一次装载生命周期（复装须新实例）→ 拒绝：与轮 2 3c③"可重新 Add 重新装载"既定冲突、无必要限制。
