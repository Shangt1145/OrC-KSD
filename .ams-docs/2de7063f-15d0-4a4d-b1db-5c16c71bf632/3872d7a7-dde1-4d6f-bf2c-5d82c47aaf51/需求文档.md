# 2A 结构层 — 需求阐明记录

> 委托：游戏环境第二批「2A 结构层」（卡牌基类骨架／数据组件／hooks／槽位模型／标注机制）。
> 本文档记录需求阐明与对齐过程（功能职责、约束、验收标准、已解决的歧义）；**实现计划与技术设计由实现者在实现阶段自行制定**，本文档不作规定。

## 一、功能职责（本批范围）

1. **卡牌基类骨架**：`CardBase` 抽象基类 ＋ `UnitCard`/`CommandCard`/`CounterCard`；基类为**对局开始卡牌加载逻辑的模板**（模板方法步骤＋子类重写点预留）；**触发器声明位**：单位/指令＝预打出触发器＋打出触发器，反制＝使用反制的触发器（唯一）；持久化重建留空位（不实现）。
2. **数据组件全集**：指挥点花费（单列）；对战（行动花费/攻击力/防御力＝初始值）；单位（所在位置/是否被摧毁/单位类型枚举列表/三实时值）；指挥（可移动/可攻击）；词条（登记列表）；反制激活状态。
3. **hooks**：6 项常量与载荷键＋发射入口（`card.load`/`card.hand.add`/`card.died`/`unit.joined`/`unit.deployed`/`unit.position.changed`）。
4. **战线槽位模型**：三线统一槽位化（容量 4/5/4）；空槽位＝邻位动态计算（重叠去重）；总部初始占位；`Battlefield` 受控变更。
5. **底层/外部触发器标注与注册机制**（游戏层、轻量、靠自觉；重心＝底层触发器不漏发更新）。

## 二、已解决的歧义（逐轮记录）

### 轮 1（2026-10-03）：卡牌基类骨架的批内范围与「对局开始卡牌加载」

**子的问题原文（摘要）**：现状＝第一批初始化仅在「起手装载/回合抽牌」时经 `CardLibrary.Instantiate` 实例化；卡组＝id 名单（CONTEXT 冻结术语）；测试断言「初始化更新序列＝恰好 3 条、起手装载静默」。问：①2A 是否要求把「对局开始卡牌加载」接入 `Match.Initialize`（含卡组是否需整体实例化、冲突是否构成受控变更）？若不接入，2A 的加载模板以什么为验收、请给 2A 完成时可观测状态（card.load 是否出现于更新流）；②「与既有 CardDefinition/Card/CardLibrary 衔接形态由实现者定型」的边界：是否允许修改既有文件？三类卡在实例化通道上是否必须本批打通，还是允许衔接后置？附带：触发器声明位与持久化空位的可观测验收。

**回复（裁定）**：

- **R1 加载接入＝要求接入（2A 验收含）**：
  - R1.1 初始化时对**双方卡组全部卡牌**逐张执行加载（经卡牌基类加载模板），并**逐张广播 `card.load`**（载荷 {Card, Player}）。
  - R1.2 与第一批冻结面的关系＝**受控变更（允许）**：卡组（id 名单）的运行时表示、「初始化更新序列＝恰好 3 条」契约均可调整；要求：①「旧→新」前后对照在汇报列出；②加载后既有对外行为不回归（起手装载先手 4/后手 5、回合抽牌链路、卡组计数语义等）；③涉及术语的变更在汇报注明（供同步文档）。
  - R1.3 顺序与静默：**加载先于起手装载**；起手装载**维持静默**（不发任何更新）；加载与 `turn.start.*` 三连的相对顺序：轮 1 暂定实现决策——**轮 2 细化收紧为固定链（洗牌→加载→起手装载→三连），见轮 2 R7.5**。
  - R1.4 失败模式：加载过程失败（未注册 id、加载模板异常等）＝**初始化 fail-fast**（不进入进行态、明确上抛），与第一批「不足起手运行时抛错」同精神。
- **R2 衔接边界**：
  - R2.1 **允许修改 Orc.Game 内既有文件**（受控变更：最小化＋前后对照＋兼容或迁移说明）；红线：不得触碰 `src/Orc`、`src/Orc.Lua`、`tests/Orc.Tests`、`tests/Orc.Lua.Tests`。
  - R2.2 三类卡与实例化通道的衔接**本批最小打通**（不得整体后置）：①定义层可区分三类；②卡牌库实例化产出对应基类实例（三类之一）；③加载模板在加载路径被调用（占位/空实现可）；④对外公共面兼容或附迁移说明。完整行为（打出链等）留 2B。
  - R2.3「定型」边界：三类卡与既有 `Card`/`CardDefinition` 的层次与装配形态＝实现决策（须汇报）；但须满足 R2.2 与 R3 的可观测项。
- **R3 触发器声明位（可观测验收）**：
  - R3.1 三类卡实例上存在**可读的触发器对象（对象在位、非空）**：单位＝预打出＋打出；指令＝预打出＋打出；反制＝使用反制的触发器（单个）；名称/类型可断言。
  - R3.2「装配点就绪」＝触发器具备可用的注册/装配入口（可向其注册事件）；**链内容不要求**（2B 填入）。
  - R3.3 可观测：测试可读取并断言对象存在；对声明位触发器执行一次**事件装配**调用成功（占位事件）。〔术语澄清（轮 6）：此「注册」＝事件装配入口（触发器自身注册面），与轮 5 的「注册表登记」为不同概念〕
- **R4 持久化空位**：
  - R4.1 要求**显式预留**：「重建/装配」步骤为可重写的扩展点、**默认空实现**且不破坏流程；无任何重建逻辑。
  - R4.2 可观测：扩展点存在（可重写）；默认路径下加载全流程跑通。
- **R5 补充（审视新增）**：
  - R5.1 `card.hand.add` 边界：语义＝对局开始**之后**任意来源进手牌（含抽牌）；**起手装载体不发 `card.hand.add`**（维持静默约定）。
  - R5.2 加载失败模式＝R1.4（fail-fast）。
  - R5.3 非功能：本批无外部输入面（无安全面）；无特殊性能指标（初始化一次性、规模小）；受控变更管理保障可维护性。

**备选方案与拒绝原因**：
- 备选 A1「2A 仅做机制、不接入初始化」——**拒绝**：E10 已定「初始化时对卡组逐张加载」（用户确认）；不接入则 2A 无真实加载行为可验收，与基类模板定位脱节。
- 备选 A2「加载对象＝仅起手牌」——**拒绝**：加载语义为「整副卡牌装配就绪」；card.load 载荷含 Player 指向全体卡组；仅起手会与「起手静默」语义纠缠（静默 vs 发 load 无一致依据）。
- 备选 A3「维持卡组纯名单、加载延后到抽牌时」——**拒绝**：与 E10「初始化时」冲突；且造成起手装载的牌永不触发加载（漏洞）。
- 备选 B1「既有文件完全不动、仅新增类」——**拒绝**：实例化通道打通必然触及卡牌库/定义层；完全不动无法达成产出一致性、留双重结构债。
- 备选 B2「衔接整体后置（仅独立装配/测试）」——**拒绝**：2A 定位＝结构层（体系就位）；骨架不接通道则悬空、2B 返工；「最小打通」为必要且可验收。
- 备选 C1「触发器仅虚属性/预留方法（不实例化对象）」——**拒绝**：委托原文「对象在位」为明示验收；仅占位无法支撑 2B 直接接链。
- 备选 D1「持久化空位不做显式预留」——**拒绝**：委托将「子类重写点预留」列为验收；无显式空位不可验收、总装易返工。

### 轮 3（2026-10-03）：数据组件全集与既有 CardStatsData 的关系

**回复（裁定）**：

- **R9 拆分形态与受控变更**：
  - R9.1 **拆分实施**（需求明文）：【指挥点花费（部署费）】单列组件 ＋【对战（行动费/攻/防）】组件；**同一数据不得双真源**（不允许四合一与拆分组件并存重复承载）。
  - R9.2 原 `CardStatsData` 去留形态（移除并替换实例化挂载／改造为两组件等）＝**实现决策（须汇报）**；须附「旧→新」对照（含其现有注释「不拆分」语义的反转说明）。
  - R9.3 本批实例化路径挂载＝【指挥点花费】＋【对战】两个组件（替代原四合一）；单位/指挥/词条/反制组件＝**类定义就绪＋测试内构造挂载可测**；实际挂载时机（单位化/效果阶段）**不在本批接线**。
  - R9.4 术语确认 ✓：指挥点花费＝部署费（打出消耗）；行动费＝移动/攻击消耗（对战组件内）——与 KARDS 基线一致。
- **R10 组件字段契约与实时值**：
  - R10.1 三实时值＝行动费/攻击力/防御力**可变量**；**对战组件＝只读语义基准（初始值记录，运行期不改）**；单位数据三实时值＝运行值（挂载时复制自对战组件值；供效果/词条修改）。
  - R10.2「数值 API」本批边界＝**组件层公共可读写属性（基础读写）**；单位/卡牌层方法（修改攻击/受伤/伤害处理/死亡）**不在本批**（战斗批次）。

  - R10.4 单位类型＝**普通枚举 `UnitType` 列表**（Infantry/Tank/Artillery/Fighter/Bomber；非 [Flags]）；**允许 0 个/多个**（不设非空校验）。

- **R11 受控变更补充（CardStatsData 相关）**：`CardLibraryTests` 中 `GetData<CardStatsData>` 及四值断言＝迁移至拆分组件（归入 R8 授权；「旧→新」对照汇报）；`CardDefinition`（定义层）存储形态＝实现决策（可保持四值记录）。

**备选方案与拒绝原因**：
- 备选 F1「四合一保留＋拆分组件并存」——**拒绝**：同一数值双真源/重叠，清账成本后移。
- 备选 F2「不拆分（沿用四合一）」——**拒绝**：与需求明文冲突（「指挥点花费单独放一个数据组件」「对战＝三数值」）。

- 备选 F4「单位类型用 [Flags]」——**拒绝**：需求为「枚举列表」；列表承载扩展更直接、避免位枚举语义约束。

### 轮 5（2026-10-03）：底层/外部触发器标注与注册机制

**子的问题原文（摘要）**：
- Q1：「标注」与「注册」是两个独立动作还是同一登记动作的两面？本批是否要求每个触发器可携带/关联一个分层分类？分类承载形态（注册参数/对象属性/声明式标注）＝实现决策还是需求有取向？注册表登记信息面（至少）＝本体＋分类？是否含名称/来源/归属？注册与「挂载/运行」是否完全解耦（只记账、不影响运行）？注册表归属与生命周期（对局级？）与可注册方（公共 API）？
- Q2：查询最小验收集（按分层枚举/全量/按名称）？「不做强拦截」的边界（未注册照常运行？不强制底层注册？无运行期检查？重复注册拒绝还是幂等？null 入参？）；「重心＝不漏发」的支撑（清单审计 vs 仅分类记账、本批是否建审计）。
- 附带：与 R3 声明位的关系（声明位是否注册进注册表，还是本批仅测试演示、2C 起用于真实指挥触发器）？`card.died` 与引擎 `card.destroyed` 并存关系的注释标注（本批是否显式标注）？

**回复（裁定）**：

- **R15 标注与注册形态**：
  - R15.1 形态＝**同一登记动作的两面**：注册＝把触发器登记进游戏层注册表，**登记时携带分层分类（底层/外部）为必填**（「标注」＝该分类信息的登记内容，非独立动作）；本批要求注册的每个触发器携带一个分层分类。
  - R15.2 登记信息面（最小）＝**触发器对象本体＋分层分类**；名称/来源/归属不强制（可按需从触发器自身读取）；**注册与挂载/运行完全解耦**（注册表只记账，不影响运行、不参与挂载）。
  - R15.3 承载形态（注册参数/对象属性/声明式标注）＝**实现决策（须汇报）**；取向：轻量（与「靠自觉」原则一致，不引入重机制）。
  - R15.4 归属与生命周期＝**对局级**（每对局一份，与对局生命周期一致；持有形态实现定型汇报）；注册＝**公共 API**（游戏层公开，供框架与后续批次使用）。
- **R16 查询、边界与防漏发**：
  - R16.1 查询最小验收集＝**按分层枚举**（全部底层／全部外部）；全量枚举可选；按名称查找不要求。
  - R16.2 边界（「不做强拦截」的明确含义）：①未注册触发器**照常运行**（注册表不参与运行）；②**不强制**「底层必须注册」（靠自觉）；③**无**「是否真发更新」的运行期检查；④**不拦截**外部触发器发更新（技术可行但不拦）；⑤重复注册同一触发器对象＝**明确拒绝**；⑥null 入参＝**明确拒绝**；⑦本批**不提供移除**（注册后不可变；随对局销毁回收）。
  - R16.3 防漏发支撑（本批）＝机制提供**「底层触发器清单」查询**（即 R16.1 按分层枚举），供后续批次/审计核对；**本批不建审计行为**（无自动核对、无运行期验证；约束＝自觉＋后续审计）。
- **R17 附带裁定**：
  - R17.1 与声明位的关系：**声明位触发器本批不注册**——注册机制本批以测试触发器演示；真实注册自 **2C**（指挥触发器）启用。
  - R17.2 `card.died` 注释＝**须显式标注**与引擎内置 `card.destroyed` 的并存关系（游戏层死亡 vs 引擎销毁；本批零调用点）——避免近似名误用（维护性要求）。

**备选方案与拒绝原因**：
- 备选 H1「声明式特性（Attribute）标注」——**拒绝**：与「轻量/靠自觉」原则不符；分类为注册时信息，无需类级静态标注。
- 备选 H2「注册表含运行期拦截（强制校验）」——**拒绝**：已定落实形态 a＋主要靠自觉（用户决议），不做强拦截。
- 备选 H3「全局注册表（跨对局）」——**拒绝**：多对局相互串扰；对局级与触发器生命周期一致。
