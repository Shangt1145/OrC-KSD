# 2C 指挥与词条（需求阐明记录）

> 委托：游戏环境第二批 2C（指挥与词条·最终阶段）；级别＝类/功能流程级。
> 本记录随 grill 逐轮增长：每轮记录提问原文、裁决回复、备选方案与拒绝原因。

## 一、功能概览（基准）

2C 在 2A/2B 之上交付：
1. **指挥系统**：内置指挥触发器（注册为底层触发器）；单位拖拽 → targeter（空槽〔移动〕/敌方单位·总部〔攻击〕；其他禁入）→ 单位移动触发器（仅推进：支援线→前线；扣行动费）/ 单位攻击触发器（扣行动费）；指挥组件两 bool 先读判定 → 执行（嵌套触发器）→ 只在外层收尾更新。
2. **KARDS 规则矩阵**：坦克可攻击+移动、其他二选一；空军/炮兵任意阵线、步兵/坦克仅相邻；烟幕不可被攻击（置黑）；守护（相邻单位获被守护、仅能被炮/轰攻击、守护者不可被守护、由 unit.position.changed 维护）。
3. **攻击结算**：基础互伤 → HP≤0 死亡（card.died＋清理）＋ HQ 掉血（胜负后置）；「造成攻击伤害」触发器（伏击挂载点）；反击豁免体系最小化。
4. **对战词条**：＝逻辑组件、加载时挂效果；被动（奋战/烟幕）/主动（闪击/伏击）；四词条实现。
5. **更新接线**：unit.position.changed / card.died ＋ 行动费用扣费。

## 二、第 1 轮：行动状态（CanMove/CanAttack）生命周期与「只在外层更新」

### 2.1 提问原文（摘要）

**主问题 1（两 bool 置位/清除全量规则）**
(a) 置 true 时机全集：除闪击外，普通单位何时获得可行动状态？是否含「回合开始恢复」（接哪一步、作用于哪方单位）？若本批不做，是否后置并改为手动驱动？
(b) 行动后清除规则（与坦克双动/二选一精确对应）：移动/攻击后各清哪些 bool、是否互相清理、独立清位？奋战的首次/二次判定与 bool 更新的先后？
(c) 闪击写入点与「扣费后」矛盾：委托写「部署触发器末尾（扣费后）」，但 2B 链中执行到部署触发器末尾时尚未扣费——时序以哪侧为准？

**主问题 2（「只在外层更新」精确边界）**
(a) 「外层」所指层级与更新相对嵌套执行的位置要求？
(b) 禁止写路径与合法写入点清单？闪击是否为明确例外？硬约束还是设计口径？
(c) 读取面：公开可读即可，还是需要聚合判定能力？

### 2.2 裁决回复

**1(a) 置 true 时机全集**：
- ① 闪击：部署链收尾（扣费后）置 true；
- ② **回合恢复（本批包含、非后置）**：`turn.start` 处理阶段对当前行动方在场单位（HQ 除外）重置两 bool＝true；接线至回合开始处理段；验收须覆盖「跨回合恢复后可再次行动」；
- ③ 常态初值：部署/加入时 false/false（＝部署当回合不可行动）。

**1(b) 行动后清除（精确规则）**：
- 移动执行后：CanMove=false；**非坦克**同时 CanAttack=false（二选一）；坦克仅清 CanMove；
- 攻击执行后：CanAttack=false（奋战情形见下）；**非坦克**同时 CanMove=false；坦克仅清 CanAttack；
- 「二选一」＝非坦克执行任一动作后，另一个 bool 同被清；「坦克双动」＝两动作独立清位、互不影响；
- **奋战**：词条自行记账「本轮已攻次数」；外层收尾读取记账决定 CanAttack（首次攻击后保持可攻、二次后置 false）；**先执行（含记账）→ 后更新**；「本轮已攻次数」随回合恢复一并清零（词条侧）；
- 补充：清位条件＝**动作成功执行（成功返回）**；执行被取消/失败**不消耗**。

**1(c) 闪击时序矛盾裁决**：
- **以「扣费后」为准**（用户 Q13-b 决议）；语义＝「部署完成（含付费）后单位立即具备可行动状态」；
- 「部署触发器末尾」为近似表述，**修正**为：闪击注入/执行的落点位于**扣费完成之后、打出链返回之前**（如外层收尾段末尾或等价位置）；实现形式自选并汇报；
- 拒绝「扣费前注入＋仅语义保证」：与用户明确选择冲突、引入不可观测时序假设。

**2(a) 「外层」定义**：＝指挥流程外层（读判定 → 分派 → **嵌套执行返回后** → 收尾段统一更新）；更新严格要求位于移动/攻击触发器返回后的收尾段。

**2(b) 禁止写路径与法定写入点**：
- 禁止：移动触发器、攻击触发器、词条效果（含伏击）等内层一律不写两 bool；
- 法定写入点（全集）：① 指挥流程外层收尾；② 部署链收尾（闪击，扣费后）；③ 回合恢复（turn.start 处理）；
- 硬度：**硬约束**——以**可观测测试断言**保证（内层不写、外层写）；不要求运行时写保护机制（实现可自加防护，非要求）。

**2(c) 读取面**：
- 必须：两 bool 公开可读（供规则模块/测试）；
- 动作合法性聚合判定（bool＋规则矩阵＋费用）：至少须**可通过公开路径独立调用**（供 UI 预览与测试）；具体形式由实现自定。

### 2.3 备选方案与拒绝原因

| 点 | 备选 | 拒绝原因 |
|---|---|---|
| 1(a) | 回合恢复后置、验收以手动置位驱动 | 违背 KARDS「每回合」语义，无法覆盖跨回合可玩性 |
| 1(b) | 动作发起即消耗（失败也清位） | 健壮性差、与「验证先行」设计不符 |
| 1(b) | 奋战计数入指挥组件 | 违背词条自记账约定（E4-a） |
| 1(c) | 扣费前注入＋语义保证 | 与用户决议冲突（见 1(c)） |
| 2(b) | 运行时写保护机制 | 过度设计、无需求依据（约定＋断言足够） |

## 四、第 2 轮：攻击范围矩阵与守护/烟幕筛选语义

### 4.1 提问原文（摘要）

**主问题 1（步兵/坦克「仅相邻」的精确目标集合与 HQ 攻击条件）**
(a) 「仅相邻」是否含同阵线？请给出四类组合（支援线→敌支援线 / 支援线→前线 / 前线→敌支援线·HQ / 前线→前线）的允许·禁止清单。
(b) HQ 攻击资格（谁能打 HQ）；是否引入「敌方前线阻挡」规则（完整 KARDS 前线机制），还是仅以相邻性为唯一范围限制？
(c) HQ 攻击结算确认：伤害＝实时攻击力；HQ 不反击；胜负后置；血量写入口＝本批新增受控变更？

**主问题 2（守护与烟幕的筛选范围）**
(a) 烟幕：对一切攻击者生效（含炮/轰）还是仅筛除步/坦？自身移动/攻击是否受限？
(b) 守护「相邻」定义：同线槽位相邻？跨线计入？是否保护 HQ？
(c) 被守护/守护者筛选表现确认：被守护仅可被炮/轰、守护者自身不受影响、多守护不叠加？

### 4.2 裁决回复

**1(a) 范围矩阵（步/坦；「相邻」＝跨线且紧邻）**：

| 攻击者线 → 目标 | 判定 |
|---|---|
| 支援线 → 敌方**前线**单位 | **允许** |
| 支援线 → 敌方支援线单位 / 敌 HQ | **禁止**（不相邻） |
| 前线 → 敌方支援线单位 / 敌 HQ | **允许** |
| 前线 → 前线（同线敌方单位） | **不允许**（相邻＝跨线；按基线前线呈单方占据态；本批不实现占据机制，同线互攻不开） |
| 炮兵/空军（任意线） | 全组合允许（含 HQ、含同线） |

**1(b) HQ 攻击资格**：炮/轰任意线可攻；**步/坦仅前线可攻**（支援线不可）。**不引入「敌方前线阻挡」规则**——本批范围限制唯二＝①相邻性（步/坦）②目标归属正确；完整 KARDS 阻挡机制**后置**（后续如需另行对齐）。

**1(c) HQ 结算确认**：伤害＝攻击者**实时攻击力**；**HQ 不反击**（攻击者不受伤害）；胜负判定后置（本批只扣血、不判胜负）；**HQ 血量写入口＝本批新增受控变更**（2A 时为「纯数据、无修改入口」，现需扣血入口——受控变更、汇报标注）。

**2(a) 烟幕**：**对一切攻击者生效**（含炮/轰；烟幕单位不进任何攻击目标候选、置黑）；本批**只做被攻击面**——烟幕单位自身移动/攻击能力不受词条限制。

**2(b) 守护「相邻」**：以**同一线内槽位相邻**（左右邻位）为准；**跨线不计**；**保护计入 HQ**（HQ 相邻守护者时获「被守护」、仅能被炮/轰攻击）。

**2(c) 筛选表现确认**：被守护单位仅能被炮/轰攻击（步/坦视角＝筛除/置黑）；守护者自身不受「被守护」影响（可被任意合法攻击者攻击、可正常行动）；多守护者相邻**不叠加**（有其一即可）。
**补充（维护条件）**：被守护状态经「卡牌位置更新」触达——凡影响支援线占用布局的变动（移动、入场占位、离场/死亡清位）均须**等效触发维护**，防止被守护状态陈旧（至少覆盖 unit.position.changed 情境）。

### 4.3 备选方案与拒绝原因

| 点 | 备选 | 拒绝原因 |
|---|---|---|
| 1(a) | 允许前线同线互攻 | 与基线「前线单方占据」语义冲突；研究口径「前线→敌支援线与 HQ」未含同线 |
| 1(b) | 引入「敌方前线阻挡」规则 | 属完整 KARDS 前线机制、超出用户需求所列（相邻性）范围；本批简化并明确后置 |
| 2(a) | 烟幕仅对步/坦生效 | 无需求依据（用户未给例外）；「不可被攻击」按字面取最广 |
| 2(b) | 守护跨线计入 | 以槽位邻位（同线）为最明确、可测试的口径 |
| 2(b) | 守护不保护 HQ | 守护者战术职能（护脸）要求 HQ 计入；HQ 为支援线占位者、与「相邻单位」一致 |

## 五、第 3 轮：移动候选与范围口径、行动费用验证与扣费语义

### 5.1 提问原文（摘要）

**主问题 1（移动候选与范围口径）**
(a) 移动候选空槽口径：目标线（前线）的「邻位动态候选」？还是全部空槽？还是其他（如按移动单位当前槽位的投影）？
(b) 移动对象与方向：仅支援线单位可移动（前线单位无候选）？后撤/前线内横移均后置？「任意阵线」不作用于移动（对所有类型统一＝支援线→前线）？
(c) 成功可观测要素：①旧槽移除→放入目标空槽；②unit.position.changed 恰一次；③扣行动费；④外层清位——对吗？取消/失败＝零副作用？原支援线槽变为空槽？

**主问题 2（行动费用验证与扣费语义）**
(a) 费用口径：各扣 1 次实时行动费（UnitStateData.OperateCost）？坦克双动＝两次？从单位所有者扣除？
(b) 「走验证路径」精确语义：哪一环节拒绝（发起判定 vs 执行触发器内）？ValidationRejected 表意？零副作用＋留痕？
(c) 扣费时序：验证→执行→收尾扣费（成功后扣、恰一次）？失败/取消不扣？费用校验相对两 bool 判定的位置？

### 5.2 裁决回复

**1(a) 移动候选口径**：**前线目标＝任意空槽**（未被占的槽位均可作为移动目标；经 targeter 选择、产出槽位引用）——**不受邻位动态规则约束**（邻位规则为「支援线部署」专用）。澄清注记：2A 术语中「部署/移动候选位」的合并表述据此收窄——移动候选为独立口径（前线初始为空时亦必须可推进，避免邻位规则导致的推进死锁）。

**1(b) 对象与方向**：仅支援线单位可移动（前线单位无移动候选）；后撤与前线内横移**后置**（不实现）；「任意阵线」仅作用于攻击、不作用于移动——移动方向对所有单位类型统一＝支援线→前线。并确认：指挥仅限己方回合操作己方单位（行动方＝单位所有者＝当前回合方）。

**1(c) 成功可观测要素（确认）**：①从旧槽移除→放入目标空槽（**原槽变为空槽、参与邻位动态计算**）；②`unit.position.changed` **恰一次**（{Unit,Old,New}）；③扣行动费；④外层清位（第 1 轮已定）。取消/失败＝**零副作用**（不移动、不发更新、不扣费、不清位）。

**2(a) 费用口径**：每动作各扣 **1 次该单位的实时行动费**（UnitStateData 的 OperateCost 实时值）；坦克双动＝两次动作各扣一次；从**单位所有者（＝当前行动方）**的指挥点扣除。

**2(b) 验证路径（双层）**：①**发起判定**——费用不足＝**动作级**拒绝（该动作不可发起、整体置黑；非逐目标筛选）；②**执行前复验**（分派后、执行前兜底）。均以验证机制表意（ValidationRejected）；拒绝＝零副作用＋留痕。

**2(c) 扣费时序**：验证通过→执行（槽位变更/攻击结算）→**收尾扣费**（执行成功后扣、恰一次）；失败/取消不扣；费用校验与两 bool 判定为**并行聚合判定**（bool ∧ 规则矩阵 ∧ 费用，一次聚合、不分先后）。补充：执行中被隔离的异常视为已执行（照常收尾扣费）；仅「验证拒绝/取消」＝零副作用。

### 5.3 备选方案与拒绝原因

| 点 | 备选 | 拒绝原因 |
|---|---|---|
| 1(a) | 前线按「邻位动态」口径 | 前线初始为空时无被占位→无候选→推进死锁；邻位规则本为支援线部署语境 |
| 1(a) | 按移动单位当前槽位的投影计算 | 无需求依据；跨线投影语义不明确、不可测试 |
| 2(b) | 仅执行前单层验证 | 缺少快速反馈（UI 可用性）、与 2B「战前检查＋段前复验」双层精神不一致 |
| 2(c) | 执行前先扣费 | 与「成功即完整、失败即零副作用」不符（失败需退款、复杂化） |
| 2(c) | 费用先于 bool 单独校验 | 引入无意义的顺序耦合；聚合判定已覆盖 |

## 六、第 4 轮：攻击结算（互伤/死亡）与「造成攻击伤害」/伏击语义

### 6.1 提问原文（摘要）

**主问题 1（互伤的同时性与死亡清理口径）**
(a) 互伤同时性：同时结算（可同归于尽、以互扣前实时值为基准）还是固定顺序？同归于尽时两枚 card.died 是否均发射、顺序是否约定？
(b) 死亡清理的最小口径全集：①槽位释放；②IsDestroyed 置 true；③card.died 恰一次；④效果清理范围（词条/伏击挂载注销？）；⑤UnitStateData.Position 处置与实例去处；⑥是否发 unit.position.changed？
(c) 死亡触发的守护重算确认（且可观测）？

**主问题 2（「造成攻击伤害」触发器语义与伏击改写细节）**
(a) 伏击判定口径：目标侧含伏击？比较＝互扣前实时值？攻击者侧伏击不参与？不成立＝正常互伤？
(b) 改写结果：攻击者死亡是否走统一死亡流程（无 HP 逐步扣减）？被攻击者完全无伤？其他结算是否发生？
(c) 「造成攻击伤害」触发器归属：对局共享对象（伏击加载时挂载）还是瞬态构造？非伏击＝默认基础互伤？HQ 攻击是否走该流程？

### 6.2 裁决回复

**1(a) 互伤同时性**：**同时结算**——双方伤害以**互扣前的实时值**为基准、同时生效，可**同归于尽**；同归于尽时**两枚 card.died 均发射**，发射顺序约定为固定确定序：**被攻击者在前、攻击者在后**。补充：攻击执行前复验覆盖「目标引用有效性」（失效＝验证拒绝、零副作用）。

**1(b) 死亡清理最小口径（全集）**：①**槽位释放**（变空槽、参与后续邻位/移动候选计算）；② `IsDestroyed` 置 true（2A 字段启用）；③ `card.died` 发射（{Card}、**恰一次**）；④**已挂载效果（含词条效果）注销**（防残留幽灵效果）；⑤ `UnitStateData.Position` **置空**、实例**保留可查询**（不销毁、不进入任何区域）；⑥**不发 `unit.position.changed`**（该更新专属移动语义；死亡维护以等效方式内部触达，见 1(c)）。

**1(c) 死亡→被守护维护**：**确认**——守护者死亡清位后，相邻单位「被守护」须等效触达维护（与第 2 轮「离场/死亡清位均须等效触发维护」一致；**不以** position.changed 形式发射）；维护结果**可观测**（测试可断言被守护状态变化）。补充：死亡单位**不参与**后续指挥/目标筛选（尸体不可被指挥、不可被选为攻击者/目标）。

**2(a) 伏击判定口径**：触发条件＝**被攻击单位（目标侧）含伏击词条**（**攻击者侧伏击不参与**——伏击为防御方特性）；比较数值＝**双方互扣前的实时值**（目标实时攻击力 ＞ 攻击者实时防御力）；条件不成立＝**正常基础互伤**。

**2(b) 改写结果**：攻击者**死亡——走统一死亡流程**（card.died＋死亡清理＋守护重算；**无 HP 逐步扣减语义**，直接死亡结果）；被攻击者**完全不受伤**（防御力不变）；**其他结算不发生**（攻击者对目标的伤害被完全替代）。

**2(c) 「造成攻击伤害」触发器归属**：**与对局同生的内置共享流程触发器**（每次**单位 vs 单位**攻击结算**必经**其执行）；伏击效果＝（卡牌**加载时**）向该触发器**注册**其改写逻辑；非伏击路径＝默认基础互伤逻辑；**HQ 攻击不走该流程**（简化路径：直接扣 HQ 血；无互伤/伏击语义）。

### 6.3 备选方案与拒绝原因

| 点 | 备选 | 拒绝原因 |
|---|---|---|
| 1(a) | 固定顺序逐步结算（先目标后攻击者、先判死停算） | 与 KARDS 互伤语义不符；逐步结算改变「同归于尽」结果 |
| 1(b) | 死亡也发射 unit.position.changed | 混淆「移动」与「离场」语义、产生虚假移动事件；改用等效内部维护 |
| 1(b) | 死亡实例销毁/归还原区 | 失去查询面（IsDestroyed 不可读）、与卡牌生命周期不匹配（本批无归还逻辑） |

## 七、第 5 轮：指挥流程交互边界与守护相邻判定细节

### 7.1 提问原文（摘要）

**主问题 1（指挥流程的发起条件、候选与拒绝语义）**
(a) 发起条件与拒绝情形：前置＝己方回合＋己方在场（未死亡）单位；「两 bool 全 false」或「两动作候选均为空（费用不足/无合法目标）」——发起拒绝（不进入交互、零副作用，与 2B 预打出「候选为空＝拒绝」对齐），还是仍进入交互（全置黑）？「动作级拒绝·整体置黑」（第 3 轮）与「发起拒绝」的边界？

### 7.2 裁决回复

**1(a) 发起条件与拒绝语义（两层）**：
- 前置＝**己方回合＋己方在场未死亡单位**；
- **单动作不可用**（动作级）：bool＝false 或 费用不足 或 该动作无合法目标 → 该动作**整体不可用**（其候选**整类不进入**候选集——即第 3 轮「动作级拒绝·整体置黑」的精确语义：非逐目标筛选、是动作整体缺位）；
- **发起拒绝**（流程级）：两 bool 全 false 或 **两动作均不可用**（候选均空）→ **不进入交互、零副作用**（与 2B「候选为空＝拒绝」先例对齐）；
- 至少一动作可用 → 进入交互。

**1(b) 候选生成与合并**：**一次拖拽＝一次 targeter 请求**；候选＝**可用动作的候选并集**——移动候选（前线任意空槽；条件：CanMove∧费用足）＋攻击候选（合法敌方单位/敌方 HQ；条件：CanAttack∧费用足∧范围矩阵∧烟幕∧守护筛选后）；**候选面之外者＝后端筛除**（不入候选；前端将其余置黑——沿用既有 Targeter「后端只产出允许什么」口径）。

**1(c) 分派与取消**：选中空槽 → **单位移动触发器**；选中敌方单位/敌方 HQ → **单位攻击触发器**；**取消＝零副作用**（不发更新、不扣费、不清位、双方状态不变）；**无其他分派分支**；无效目标点击不构成确认（交互不产生终局）。

**2(a) 守护受益对象＝同方限定**：仅**守护者所属玩家**的相邻单位与**同方 HQ** 获得；敌方单位/敌方 HQ 不获（前线共享线上相邻的敌方单位亦不获）。

**2(b) 相邻判定**：＝**槽位索引差 1 的直接邻位**（物理邻位）；**中间隔空槽则不相邻**（如槽 0 有守护者、槽 1 空、槽 2 单位 → 槽 2 不获被守护）；**HQ 槽 0** 同规则（守护者在槽 1 → HQ 获保护；在槽 2（隔空）→ 否）。

**2(c) 读取面与叠加规则**：被守护为**可观测状态**（测试可断言「获得/失去」；读取形式自定）；确认：**守护者自身永不获被守护**（任何情形，含相邻另一守护者）；**多守护源不叠加**（仍为单一「被守护」、不区分来源数）；守护者移走/死亡后若仍有另一相邻守护者则**保留**（＝「存在至少一个相邻守护者」的**存在性判定**）。补充：被守护为维护型状态（由位置更新触达维护），维护须考虑**守护者存活状态**（死亡即不构成保护来源）。

### 7.3 备选方案与拒绝原因

| 点 | 备选 | 拒绝原因 |
|---|---|---|
| 1(a) | 候选均空仍进入交互（全置黑） | 与 2B「候选为空＝拒绝」先例不一致；空交互产生无意义请求 |
| 1(b) | 移动/攻击分次请求（两次 targeter） | 单次拖拽＝单一意图（移动到槽 vs 攻击目标），一次选择即可表达；分次增加交互成本、无需求依据 |
| 2(b) | 按「占用序列」跳过空槽计相邻 | 「槽位相邻」既定义务为物理邻位；跳空判定将令守护跨越空槽生效、语义不明且难测试 |
| 2(c) | 被守护按来源计数 | 无需求依据；存在性判定已覆盖语义 |

## 十二、第 10 轮：参与方死亡时收尾处理、更新与收尾段可观测顺序

### 12.1 提问原文（摘要）

**主问题 1（参与方死亡时「收尾扣费/清位/结局」的处理）**
场景：攻击结算中攻击者被伏击反杀（第 4 轮：走统一死亡流程），或普通互杀同归于尽（双方均死亡）。

(b) 结局分类：攻击者死亡的攻击是否仍为「成功」（非失败/非特殊结局）？
(c) 外层清位（两 bool 更新）对已死亡单位：跳过还是照写？观测是否有差别要求？
(d) 奋战第二次攻击：费用照扣、两次攻击各自独立完整结算？

(a) 发射（position.changed／card.died）与收尾段的相对位置是否有契约要求（更新属执行段、先发射后收尾，使监听者可见「bool 未更新、费未扣」——支撑「内层不写 bool」断言）？还是顺序无要求？

### 12.2 裁决回复

**1(a) 收尾扣费**：**照常执行**（恰一次；自**行动方玩家**扣除——攻击者单位死亡不影响玩家资源；**不因攻击者死亡豁免**）；「成功」口径＝攻击结算**完整完成**（包括以攻击者死亡告终的结算）。

**1(c) 外层清位（死亡单位）**：**照写（统一执行、不特判）**；观测**无差别要求**（死亡单位两 bool 无消费方〔不参与后续指挥/筛选〕；不要求跳过）。

**1(d) 奋战第二次攻击（确认）**：费用**照扣**（每次攻击动作各扣一次）；两次攻击**各自独立完整结算**（各自「执行→收尾」循环：互伤/死亡/记账/扣费/清位）。

**2(a) 发射与收尾的相对契约**：**确认并定型**——更新（position.changed／card.died）属**执行段**、发射**先于**收尾段（扣费＋两 bool 更新）；监听者在更新回调中可观测「**两 bool 尚未更新、行动费尚未扣**」的中间态（＝支撑「只在外层更新」的测试断言面）。

**2(b) 中间态**：**是**——「槽位已变更／清理已完成，但外层清位与扣费未发生」＝「只在外层更新」的**预期观测窗口**。

**2(c) 收尾扣费**：**无条件执行（不再失败）**——前置验证（发起判定／执行前复验）已保证费用充足；**不设二次失败路径**（理论上不应发生的不足情形，防御处理方式由实现自定）。

### 12.3 备选方案与拒绝原因

| 点 | 备选 | 拒绝原因 |
|---|---|---|
| 1(a) | 攻击者死亡＝失败/特殊结局 | 结算完整完成即成功（与「成功即完整、失败即零副作用」体系一致）；死亡为结果非失败 |
| 1(c) | 死亡单位跳过清位 | 引入特判分支、破坏收尾统一性；照写无副作用（无消费方） |
| 2(a) | 更新晚于收尾（或顺序无要求） | 失去「只在外层更新」的可观测窗口（监听者永远看到更新后状态、断言面塌缩）；与「信号先行」的既有精神不符 |

## 十五、第 13 轮：收尾确认（豁免体系/伏击适用面、类型清单缺省与重复语义）

### 15.1 提问原文（摘要）

**主问题 1（两个「实现者决定/自选」点位的拟案确认）**
(a) 反击豁免体系（授权「最小化实现或后置——实现者决定并汇报」）：拟全部后置——本批仅基础互伤（所有单位默认互伤、无任何类型豁免，如「轰炸机不反击」等特例均不实现），汇报标注后置——是否符合「最小化」口径？
(b) 伏击适用面：伏击改写触发不区分攻击者类型（步/坦/炮/战斗机/轰炸机攻击伏击者时一律按同一条件〔被攻击单位实时攻击力＞攻击者实时防御力〕判定改写）——确认？还是某些攻击者类型豁免？

**主问题 2（单位类型清单的缺省与重复项语义）**
(a) 缺省：未声明＝空列表（零类型，按「视同步兵」基线）？还是构造缺省填充 Infantry（零类型仅显式可达）？测试零类型以显式空列表构造？
(b) 重复项（如 [Tank, Tank]、[闪击, 闪击]）：幂等去重还是保留原样？或不作规定（实现防御、测试不构造）？另确认：类型/词条清单均为定义静态声明（不可运行时增删）、以定义为单一真源填充。

### 15.2 裁决回复

**1(a) 反击豁免体系**：**核准全部后置**——「最小化」的最简形态＝**零特例**（本批仅基础互伤：所有单位默认互伤、无任何类型豁免；特例均不实现、**汇报标注后置**）。零豁免下**伏击改写为唯一改写**（与第 9 轮「目标侧单命中」一致）。

**1(b) 伏击适用面**：**确认**——**不区分攻击者类型**（一律按同一条件判定改写；无类型豁免）；补充：伏击仅适用**单位 vs 单位**（HQ 攻击不走「造成攻击伤害」流程〔第 4 轮〕、伏击不适用）。

**2(a) 缺省语义**：**未声明＝空列表（零类型）**——数据层空列表、行为层按基线（「视同步兵」）；**不采用**「缺省填 Infantry」（隐性默认掩盖声明缺失；且与「0 个合法＋基线行为」体系重复）；测试零类型＝**显式空列表**构造。

**2(b) 重复项语义**：**fail-fast**——重复＝**定义声明的明确错误**（注册/加载期拒绝；**非**静默去重、**非**保留原样——与 hooks 声明先例一致）；验收建议覆盖「重复声明被拒」。另**确认**：类型/词条清单均为**定义静态声明（不可运行时增删）**；加载/单位化时以定义为**单一真源**填充。

### 15.3 备选方案与拒绝原因

| 点 | 备选 | 拒绝原因 |
|---|---|---|
| 1(a) | 实现最小豁免子集（如轰炸机单条） | 增加类型特例分支与测试面；「最小化」最简形态为零特例（全部后置不影响本批验收） |
| 2(a) | 缺省填 Infantry（零类型仅显式可达） | 隐性默认掩盖声明缺失（声明缺失≠步兵意图）；与「0 个合法＋基线行为」体系重复 |
