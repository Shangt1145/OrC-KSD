## 1. 功能职责（类/功能流程级）

本阶段交付 Orc 库的"核心运行时"层（`src/Orc/Core/`，命名空间 `Orc.Core`）：

- **Lifetime**：实体存活性令牌（IsAlive / Kill），线程安全。
- **Ref<T>**：安全引用（Name / IsAlive / Value）；访问失效引用抛 StaleReferenceException；仅内部创建（如 Entity）。
- **Entity**：实体基类（Name / Life / Ref）；Destroy() = Kill（总线卸载通知链路留 S3，不实现）。
- **Context（精简版）**：数据载体（Data：Dictionary<string, object?>）+ 最小访问 API；不含停止/中断/链标识语义（S2 对齐后再定）。
- **IContextView + 视图特性**：Bind(data, ctx) / Seal()；ContextViewAttribute（本阶段不带参数）、ReadAttribute、MutateAttribute、OptionalAttribute。
- **ContextViewBinder**：反射 + 元数据缓存；创建/绑定视图、必填校验（EnsureRequired）、属性代理（get/set）、权限矩阵。
- **Trigger（最小壳）**：仅承载"一个触发器只有一个 ContextView、ctx 全事件共享"约束；执行入口（绑定 ctx → 执行委托）；不实现事件列表/优先级/传参（S2 扩展），不得预埋与 S2 冲突的设计。
- **异常**：StaleReferenceException、PermissionDeniedException。

数据流（核心链路）：Context.Data 为唯一数据载体 → 触发器经 ContextView 访问数据 → Binder 负责创建视图实例并完成绑定/代理/校验。

### 第 1 轮（2026-10-03）：ContextView 体系与权限矩阵的运行语义

**子问题（要点原文）：**
（主问题）权限拒绝（及 [Optional] 缺省回退）的验收口径，是否要求"运行时实时拦截"——即每一次通过视图属性读写（如给 [Read] 属性赋值、访问未声明字段）都必须在访问发生的当下抛出对应异常，而不是仅在 Bind/Seal 时刻做批量校验；且该拦截能力必须由框架（Binder/视图代理）统一提供，视图作者无需手写转发代码？即：S1 是否以"视图属性访问是不可绕过的权限闸门"为硬性验收语义？
（a）"访问未声明字段"的准确定义？
（b）"视图 getter 访问失效 Ref 抛 StaleReferenceException"要求在哪一步抛？测试证据以哪种为准？
（c）视图作者的书写职责边界：是否要求"只声明属性+特性、无任何胶水代码"？若允许手写桥接，权限矩阵完备性如何验收？

**解答（结论）：**

1. **主问题：是。** S1 硬性语义 = "视图属性访问是不可绕过的权限闸门"：
   - 拦截在**每次属性访问的当下**实时执行（访问即判、即抛），不是 Bind/Seal 时刻批量校验；
   - 拦截能力由框架统一提供（Binder/视图代理），视图作者无需手写转发或校验代码——"声明即工作"；
   - 测试中"给 [Read] 属性赋值、访问未声明字段"等操作必须在访问当刻抛 PermissionDeniedException；
   - 绑定期仍保留"必填存在性校验"（EnsureRequired），与访问期权限拦截并存、不互相替代。
2. **a）"未声明字段"定义**：指视图声明中**没有有效访问特性**的属性被读写——属性无 [Read]/[Mutate]（含仅有 [Optional] 而缺主特性）时，任何读写都拒绝。不含"Data 键不存在"场景：那是必填缺失（绑定期报错）或 [Optional] 缺省回退（读 default）的范畴，不是权限拒绝。S1 视图不提供访问任意键的通用入口（如索引器）。
3. **b）失效 Ref 的抛出点**：按设计文档 §4.3.3 口径，**读取该 Ref 类型属性时即抛**（与设计文档生成代码"getter 内先查 IsAlive"一致），不要求"先拿到 Ref 再访问 .Value 才抛"。测试证据口径：①访问视图中失效 Ref 属性 → 当刻抛 StaleReferenceException；②直接访问 Ref.Value → 抛 StaleReferenceException（双层防线，二者各自有测试）。
4. **c）作者职责边界**：S1 要求"只声明属性 + 特性、无任何胶水代码"。若实现上存在手写桥接的可能，权限矩阵完备性验收口径为"**任何经由视图契约的属性访问都不得绕过矩阵**"；S1 不要求提供胶水扩展点。

**备选方案与拒绝原因：**
- 备选 1：Bind/Seal 时批量校验权限 → 拒绝：无法满足"每次访问当下抛出"的验收口径；设计文档生成代码在 getter 内校验，语义即访问时拦截。
- 备选 2：允许/要求视图作者手写转发与校验胶水 → 拒绝：与"框架统一提供拦截"矛盾，提高不完备风险；S1 目标为声明即工作。
- 备选 3（对 b）：仅在访问 Ref.Value 时校验 → 拒绝：偏离设计文档 getter 口径；放弃双防线会降低失效引用的早期发现能力。

**补充阐明（对抗性审视）：**
- **边界完整性**：权限矩阵只管"访问权限"；值语义（null、类型转换错误等）不属权限范畴，不要求矩阵特判。
- **并发**：S1 单线程假设；并发访问安全不在本阶段验收范围。
- **Seal**：S1 可最小实现；其实现在任何情况下**不得放松**权限矩阵（封印不导致授权）。
- **测试证据一致性**：权限与失效两个维度的测试都应体现"访问当刻抛出"的行为，而非以绑定期报错代替。

### 第 2 轮（2026-10-03）：Context 精简版的最小 API 与"共享而非拷贝"验收语义

**子问题（要点原文）：**
（主问题）"共享而非拷贝"的验收语义如何精确理解？
1) "同一触发器的多次执行"是否指：同一个 Context 实例（同一 Data 载体）被同一触发器连续执行多次，第一次执行中经视图的改写，在第二次执行中经视图可见；"两处"即这两次执行？
2) "共享而非拷贝"的边界：至少要求"Bind 时不得拷贝 Data"；Context 构造/接收外部数据时——不拷贝外部字典直接持有，还是允许（如设计文档 §4.2）创建时做一次拷贝、此后单一载体不再拷贝？
（a）Context 的公共形式：需要"接受数据字典的公共构造"入口吗？Data 对库外可见性（public/internal）？"最小访问 API"是否包含测试观察用途？
（b）是否完全不含其他元数据（Source/Parent/Results），还是保留一两项？
（c）多个 Context 实例是否可以共享同一 Data 字典？还是"一个 Context 独占一个载体"、共享性仅发生在"同一 Context 被多次使用"？

**解答（结论）：**

1. **主问题——验收④口径（含一处补强）**："同一触发器的多次执行" = **同一 Context 实例（同一 Data 载体）**被同一触发器连续执行多次；第一次经视图的改写，第二次经视图可见——"两处"即这两次执行，测试以此为准。为此，**触发器壳的执行入口需支持"接收既有 Context"的用法**（同一 Context 可被多次执行复用）。
   - "共享而非拷贝"的边界：**视图 Bind 与视图属性读写全程不得拷贝数据（直连载体）**；**Context 创建时允许——且本阶段采用——对传入的外部字典做一次拷贝**（对齐设计文档 §4.2），此后 Context 生命周期内保持单一载体、不再拷贝。
   - 测试④构造：同一 Context 实例两次执行 + 断言跨执行改写可见（可另加载体对象同一性断言）。
2. **a）公共形式**：保留"接受数据字典的公共构造"入口；**Data 本体保持 internal**（供绑定/代理直连）；对外提供**最小读取 API**（Get/TryGet 风格，形态由实现者定）供测试观察最终数据；测试无需 InternalsVisibleTo。公共写入 API 不在 S1 必需范围（数据预置经构造函数、改写经视图代理）。
3. **b）元数据**：**完全不含**（Source/Parent/Results/Event/Depth/停止/中断等一律留待 S2 对齐后定）；S1 的 Context = 纯数据载体。
4. **c）载体关系**：**一个 Context 独占一个 Data 载体**（由构造建立，此后不替换、不共享）；"共享性"验收仅限"同一 Context 被多次使用/多视图会话"场景；跨 Context 的载体共享不在本阶段范围（不设计、不测试）。

**备选方案与拒绝原因：**
- 备选 1（对 2）：任何情况下都不拷贝（构造亦直持外部字典）→ 拒绝：与设计文档 §4.2 不一致；载体所有权与外部字典纠缠，"产出式 ctx"语义不清。
- 备选 2（对 a）：Data 直接 public → 拒绝：削弱"最小 API"与封装（外部可随意篡改载体）；设计文档亦为 internal；以最小读 API 满足可测试性。
- 备选 3（对 c）：强制独占（以机制禁止跨 Context 共享）→ 不采用：构造拷贝后天然独占，无需额外机制；仅需约定该场景不在本阶段范围。

**补充阐明（对抗性审视）：**
- **数据源唯一性**：视图绑定的数据源必须唯一来自 Context 的载体——Binder/Bind 流程不得引入第二份数据源；绑定所用 data 即 Context 的 Data 载体本身。
- **Seal 与共享**：Seal 是视图会话级封印，**不影响 Data 载体的后续可访问性**（跨执行可见性不受首轮 Seal 影响）；封印不冻结数据。
- **空数据合法**：Context 可无初始数据（空载体）；构造传 null 数据视为空载体（对齐设计文档）。
- **并发**：沿用 S1 单线程假设（不在本阶段验收）。
- **与后续阶段关系（备注）**：S1 验收④为共享语义的近似验证（尚无事件体系）；S2 引入触发器事件后，将在"一个触发器多个事件共享同一 ctx"场景下复验。

### 第 3 轮（2026-10-03）：最小触发器壳"执行一次"的公共契约

**子问题（要点原文）：**
（主问题）为"执行一次"的公共契约定夺三点：
1) 输入形态：除"接收既有 Context"外，S1 是否还要求支持"不传 Context 时自动创建一个空载体 Context"的用法？还是一律显式传入 Context？
2) 执行委托的形态：委托接收什么（仅视图？视图 + Context？）；同步还是异步（Task 型）；有无返回值要求？（须符合"不得预埋与 S2 冲突的设计"）
3) 异常传播：执行委托运行期间抛出的异常（StaleReferenceException / PermissionDeniedException / 普通异常）——执行入口对外如何表现：传播还是隔离？四项验收测试的断言路径以哪种为准？
（a）委托是否需要 Context（视图即唯一数据通道，还是视图 + ctx）？
（b）执行入口的返回值：void / bool / 视图 / 委托返回值，还是无结果？
（c）重复调用时的状态语义：触发器是否维护任何跨调用状态（如已执行标记 Fired）？

**解答（结论）：**

1. **输入形态：一律显式传入 Context，S1 不提供"缺省创建"用法。** 理由：①S1 所有验收场景都以"显式提供的载体"为前提（共享验收需同一 Context 复用）；②"缺省创建何种 Context"的语义依赖 S2 元数据与激活模型（主动触发器缺省上下文、参数转接等），现在定会预埋约束；③需要空载体时可显式传入 `new Context()`，能力完备；入口签名以显式 Context 为必备参数。
2. **委托形态：`Func<TView, Task>`——接收视图（单参）、返回 Task、不接收取消令牌。** 理由：①异步基调已定（用户确认简化级别含 Task），Task 形态与 S2 同向、不构成结构性冲突；②S1 不引入超时/取消（属 S2 对齐项），故不带 CancellationToken；③同步逻辑以 `Task.CompletedTask` 表达（对齐设计文档口径）；④S2 如需扩展委托参数属加性变更，不会推翻执行模型。
3. **异常传播：S1 不实现隔离——异常原样向调用者传播。** 理由：①S1 无日志/链设施，"隔离并记录"缺乏观察通道；②"权限闸门/失效双防线"的验收依赖异常可见性；③隔离策略属未来执行机制层（S2 与"异步/超时/取消/异常隔离"一并对齐），S1 不预埋。执行入口**不得捕获、包装或吞掉**委托期间抛出的异常（Stale / PermissionDenied / 普通异常一律原样穿透）。
   - 测试断言路径：**两类都要**——①对视图/Ref 的直接访问断言（闸门与双防线本体）；②经执行入口调用、并在调用处捕获（传播路径验证）。
4. **a）委托只接收视图，不接收 Context**（视图即唯一数据通道；ctx 不经委托参数暴露，其暴露面（如需要）属 S2 触发器机制内部决策）。
5. **b）无返回值要求**：委托与执行入口均以 Task 完成表示"执行一次"结束，不返回结果数据；S1 不实现结果收集（Context.Results 不存在）。
6. **c）触发器完全无状态**：除不可变的"视图类型 + 执行委托"引用外，无任何跨调用状态（无 Fired / 计数器 / 缓存）；每次调用行为仅取决于输入（委托逻辑 + Context 当前数据）。

**备选方案与拒绝原因：**
- 备选 1（对 1）：支持"缺省创建空载体"→ 拒绝：S1 无此需求场景；缺省创建语义依赖 S2（触发模式、参数转接），易预埋约束。
- 备选 2（对 2）：同步 `Action<TView>` → 拒绝：与已确认的 Task 异步基调不同向，S2 升级将造成执行模型重构（结构性冲突）；设计文档亦为异步口径。
- 备选 3（对 2）：委托携带 CancellationToken → 拒绝：取消/超时属 S2 对齐项；S1 无取消场景，空壳传参即预埋。
- 备选 4（对 3）：异常隔离（吞掉/静默）→ 拒绝：S1 无日志设施，隔离将隐藏错误、且阻断验收断言；异常可见性正是本阶段验收所依赖。

**补充阐明（对抗性审视）：**
- **构造防御**：触发器构造必须提供视图类型与执行委托（非空），null 应被拒绝（防御性参数校验）。
- **分层清晰**：视图实例属"单次执行会话"（可 Seal）；数据载体（Data）属 Context（跨执行存续）——共享验收依赖此分层。
- **入口能力重申**：执行入口需支持接收既有 Context（第 2 轮结论）；绑定数据源唯一来自该 Context 的 Data 载体（不得引入第二份数据源）。
- **入口能力边界**：入口不负责创建 Context（显式传入）、不负责隔离异常（原样传播）、不负责结果返回（无）。
- **并发**：沿用 S1 单线程假设；并发调用安全不在本阶段验收范围。
- **与后续阶段关系（备注）**：S1 的"单段执行委托"是 S2"触发器内部多事件（handler）按优先级执行"的雏形；委托的最终参数形态（是否加入 ct/ctx）由 S2 对齐时决定，届时属加性/受控变更。

### 第 4 轮（2026-10-03）：视图实例的创建路径与"单次执行会话"契约

**子问题（要点原文）：**
（主问题）既然断言"直接对视图/Ref 访问"是验收路径之一，测试必须能拿到视图实例。S1 是否要求存在一条公共的视图创建/获取路径（例如 Binder 提供公共创建入口，供测试与将来复用）——即"由 Binder 创建视图实例并绑定"必须暴露为可测试、可复用的入口，而不是仅隐藏在触发器执行内部？请明示这条路径的归属与最小能力（创建者、是否需要显式传入 Data 与 Context）。
（a）视图实例生命周期：是否约定"每次执行会话新建一个视图实例"（跨执行不复用视图实例、每次 Bind 同一 Data 载体）？复用视图实例是否属未定义/被禁止？
（b）Seal 的调用者与时机：执行入口在委托结束后是否应自动 Seal（包括异常传播路径，封印不得被跳过）？Seal 之后同一视图实例的行为最低要求是什么（继续受权限矩阵约束；是否要求"再访问即拒绝/抛异常"，还是"未定义、不验收"）？Seal 是否要求可重复调用（幂等）？
（c）"一个触发器只有一个 ContextView、ctx 全事件共享"在 S1 的体现：是否要求用类型系统保证（如触发器泛型化为只允许一个视图类型），还是允许运行时持有单一视图类型引用、由测试证明即可？该约束的"测试证据"以什么为准？

**解答（结论）：**
（确认：子 agent 对第 1~3 轮结论的组合理解无误。）

1. **主问题：是——要求一条公共的视图创建/获取路径。** 归属：ContextViewBinder 的公共创建入口（供测试与将来复用）。最小能力：
   - 显式传入**视图类型 + Context**；Data 经 Context 唯一来源取得（不另行传入 data 形参——延续第 2 轮"数据源唯一性"裁定，杜绝第二数据源）；返回绑定完成的视图实例。
   - 该入口执行完整绑定契约（必填校验、代理装配、权限矩阵），保证"直接创建路径"与"触发器执行内部路径"行为一致——**同一入口原则**（触发器执行内部必须走同一入口，不得另起第二条创建路径）。
2. **a）视图实例生命周期**：**约定"每次执行会话新建视图实例"**（跨执行不复用实例；每次 Bind 同一 Data 载体）。理由：①"单次执行会话"与实例一一对应，Seal 语义无复用歧义；②避免复用带来的封印/状态残留风险；③性能非 S1 关切（实例池化等优化留后续，且须保持会话隔离语义等价）。实例复用不在本阶段支持与验收范围。
3. **b）Seal 的调用者与时机**：
   - 触发器执行入口在委托结束后**自动 Seal**，并以 finally 语义保证**异常传播路径同样执行 Seal（封印不得被跳过，同时不影响异常原样传播）**。
   - 通过 Binder 直接创建的实例：Seal 时机由创建方自行管理（测试可不 Seal 或自行 Seal 以验证行为）。
   - Seal 后行为最低要求：**不放松权限矩阵**（经实例的访问仍按原矩阵判定；失效引用校验照常）；"Seal 后新增访问是否被拒绝"属未定义、不作为验收项（留后续阶段细化）。
   - Seal **要求幂等**（重复调用安全、无副作用、不抛异常）。
4. **c）"一个触发器只有一个 ContextView"的保证**：**要求泛型化构造入口**——视图类型在触发器构造时以编译期类型参数固定（类型系统承载约束）；内部实现可持运行时类型引用。该约束的验收证据 = ①泛型构造固定唯一视图类型（编译期）；②行为层测试：同一触发器多次执行 → 共享同一 Data 载体（跨执行可见改写）且均经同一视图类型绑定。

**备选方案与拒绝原因：**
- 备选 1（对主问题）：创建入口仅库内可见（internal），测试经触发器执行间接断言 → 拒绝：阻断"直接访问断言"路径（第 3 轮已定两类断言都要）；复用性也受损。
- 备选 2（对 a）：实现可复用实例（设计文档"复用或新建均可"）→ 不采用：复用引入 Seal 后重用语义（解封/重置）等额外复杂度；S1 取最简且可测的一一对应形态。
- 备选 3（对 b）：Seal 后访问一律拒绝（抛异常）→ 拒绝：需引入额外异常语义、且无本阶段需求支撑；以"不放松矩阵"为最低要求即可。
- 备选 4（对 c）：非泛型壳（运行时单引用 + 测试证明）→ 不采用：类型系统是"单视图约束"的最直接载体，且与后续阶段（泛型工厂形态）同向。

**补充阐明（对抗性审视）：**
- **入口防御**：公共创建入口的 null 参数（视图类型 / Context）应被拒绝（防御性校验）。
- **分层重申**：视图实例属"单次执行会话"；Data 载体属 Context（跨执行存续）；创建路径与执行路径共用同一会话语义。
- **Seal 验收口径**：断言点为"幂等 + 不放松矩阵 + 异常路径不影响传播"；不要求对 Seal 内部状态做反射级断言。
- **与后续阶段关系（备注）**：每次新建实例是 S1 的取舍（后续可评估池化优化，但需保持会话隔离语义）；Seal 的强化语义（如"封印后写拒绝"）与实例复用策略均在后续阶段决策。

### 第 5 轮（2026-10-03）："可演进"的边界口径——冻结面、变更面与视图作者契约

**子问题（要点原文）：**

   - **方向冻结 + 受控变更点**：触发器泛型化构造形态（类型系统固定唯一视图类型）冻结；`Func<TView, Task>` 委托形态——"异步、以视图为核心参数、无结果"方向冻结，**参数集**为 S2 的受控变更点（允许加性扩展，不得推翻执行模型）。
4. **b）操作判据确认（补充精确化）**：是——两种同样可行时取"**最小 + 同向 + 可加**"：不添加未来可能被推翻的成员或语义；与已确认方向（用户模型/设计文档）同向；扩展不要求推翻既有面。"仅限签名不变前提下的加性空间"即为允许的扩展方式。**注意区分**：允许"未来加性扩展" ≠ "现在预埋"——不得为未来预留而预先添加未确认的成员或语义（预埋仍属违规）。

**备选方案与拒绝原因：**

**补充阐明（对抗性审视）：**

- **与后续阶段关系（备注）**：委托参数集的受控变更、ContextViewAttribute 参数面、Seal 强化语义等均已在 S2 对齐清单中；本轮的冻结面判定为后续阶段的变更边界。

### 第 6 轮（2026-10-03）：Lifetime / Ref / Entity 的交付契约（主层收尾）

**子问题（要点原文）：**
（主问题）
1) "Ref 仅由内部创建"的验收边界：S1 是否要求"程序集外部无法自行构造 Ref"（构造不公开），外部获取 Ref 的唯一途径是 Entity 等持有者暴露的 Ref 属性？测试是否以"经 Entity 获取 Ref"为路径来覆盖失效行为（Kill 后 IsAlive / Value / 视图 getter）？

**解答（结论）：**

2. **主问题②：T 的约束沿用设计文档 `where T : class`；S1 不引入非泛型引用抽象（判定为预埋违规）。** 说明：S1 的失效防线 = 视图属性 getter + Ref.Value 双层（均为访问期、实例级），无"批量预检（Preflight 式扫描）"场景——那是后续执行机制的组成部分（S2 对齐），届时如需（如统一识别扫描）再以加性方式引入（新增接口 + 实现），不推翻 Ref 既有形态。
3. **主问题③：Entity 契约定夺如下**：
   - Name：必须非 null（防御性拒绝；空/空白字符的处理由实现者自定）；
   - Life：公开只读（Lifetime 实例）；
   - Ref：公开只读，类型 `Ref<Entity>`（对齐设计文档）；
   - Destroy()：要求幂等（映射 Kill 的幂等性）；

5. **b）视图 getter 校验范围：全部确认**：①所有声明为 Ref 类型的属性读取时校验（含 [Optional] 且数据存在的情形）；②非 Ref 类型属性不做失效校验；③[Optional] 且数据缺省 = 返回 default、不触发校验。**补充**：校验仅针对读取路径（getter）；写入不校验旧值。
6. **c）Name 与异常口径**：Name 由创建者在构造时命名（Entity 场景 = 实体名），外部只读；**测试以异常类型断言为硬性口径**，不要求对异常携带的引用名/消息内容做断言（消息格式不锁定）；推荐异常消息包含足够诊断信息（如引用名）——"推荐"非验收项。异常本身不要求携带结构化字段（最小化，不预埋）。

**备选方案与拒绝原因：**
- 备选 1（对②）：S1 引入 IRef 式非泛型抽象 → 拒绝：无使用场景（预检属 S2），属预埋；未来引入为加性变更，风险低。
- 备选 2（对 a）：要求并发烟测（多任务 Kill 后一致性）→ 不采用：与 S1 单线程假设下的验收边界不符；测试成本与价值不匹配（不强求、不禁止）。
- 备选 3（对 c）：要求断言异常消息含引用名 → 拒绝：锁定消息格式，约束实现自由度且无必要；以类型断言为准。
- 备选 4（对①）：Ref 构造公开（测试可自造）→ 拒绝：破坏所有权/安全模型，违背委托约束与设计文档口径。

**补充阐明（对抗性审视）：**
- **一致性**：Entity.Ref 为 `Ref<Entity>`（基类视角）；后续继承者（卡牌/单位等）沿用实体基类的引用暴露模式（具体形态后续阶段定）。
- **可空性**：Ref<T> 的 T 非空引用语义由 `where T : class` 承载；Ref 实例自身引用不应为 null（创建时防御由实现者处理）。
- **与后续阶段关系（备注）**：Preflight 批量扫描、卸载通知链路（S3）、IRef 统一识别（如需）均在后续阶段决策；本轮的"外部不可构造 + 双层访问期校验"为 S1 验收口径。

### 第 7 轮（2026-10-03）：必填校验、[Optional]/写入语义与特性强制性（细节层）

**子问题（要点原文）：**
（主问题）
1) 必填校验的判定与报错形态：对"非 [Optional] 的 [Read]/[Mutate] 属性"，绑定期检查的是"Data 中不存在该键"还是"键存在但值为 null 也算缺失"？缺失时抛什么（复用现有两枚之一？新增专属？BCL 既有？）？该检查是否要求"在视图交到用户代码之前必然发生、访问期不替代、也不被访问期替代"？

（a）运行时类型不匹配（读/写）口径：未定义、不验收？（复核第 1 轮"值语义不属权限范畴"是否同样适用）
（b）视图属性类型支持范围：任意可存入 object 的类型？（S1 样例覆盖 int/string/Ref<T> 等即可）；"不支持的类型"是否无专门要求？
（c）异常体系复核：两枚异常的基类/是否 sealed/是否可序列化等硬性要求？"测试仅断言异常类型、不锁消息"口径是否同样适用于权限异常与绑定报错？

**解答（结论）：**
（确认：子的组合理解无误。）

1. **主问题①——必填校验**：
   - **判定**：**"键不存在"或"键存在但值为 null"均视为缺失**（缺失 = 无有效值）。分工说明：权限矩阵管"访问权限"；必填校验管"数据供给完整性"——二者互不替代（延续第 1 轮）。
   - **报错形态**：抛 **BCL 既有异常 `KeyNotFoundException`**；不新增第三枚专属异常（不扩张公共异常面；未来如需专属异常为加性引入）。
   - **时机与并存**：检查**在视图交到用户代码之前必然发生**（绑定完成前；失败即抛、不返回实例）；**与访问期拦截并存、互不替代**（不得以访问期懒校验替代绑定期检查，反之亦然）。
   - 读路径闭环：非 [Optional] 属性由必填校验保证"有值"（或绑定失败），因此不存在"读取时无值"的非 Optional 情形；[Optional] 缺省读取 = default（第 1 轮）。
2. **主问题②——写入语义**：**[Mutate] 为"可增改"**——写入时允许创建新键（更新或新增），不得因"键原本不存在"而拒绝或静默失败。理由：①权限矩阵只决定"能否写"，不附加"只可改写既有值"的额外值语义约束；②[Optional]+[Mutate] 组合下"从缺省到有值"的写入路径必须可用（否则该组合被废）；③写入后经共享载体的任意读取可见（呼应共享验收）。
3. **主问题③——特性强制性**：
   - **[ContextView] 为必须项**：未标注时创建**明确拒绝**（抛 BCL 参数类异常，如 `ArgumentException`）；不得静默放行。（理由：声明完整性；防漏标；对 S2 的绑定语义友好。）
   - **[Read]/[Mutate]/[Optional] 用错目标**（如标在类上）：由 `AttributeUsage` 的**编译期约束**承担（运行时无需检测；该类错误根本编译不通过，"未定义"不适用）。
4. **a）类型不匹配**：**复核确认**——运行时类型不匹配（读或写）属值语义，**未定义、不验收**；不要求矩阵/Binder 特判。实现者自加的防御（如类型预检）不违反本口径（不禁止、不验收）。
5. **b）属性类型支持范围**：**任意可存入 `object` 的类型皆可声明**（无黑名单、无特判）；S1 验收样例**至少覆盖** `int` / `string` / `Ref<T>`（可含 [Optional] 缺省场景）即算达标。
6. **c）异常体系**：两枚异常**继承 `System.Exception` 即可**；**不强制 sealed**（由实现者定）；**不要求可序列化**。**"测试仅断言异常类型、不锁定消息内容"的口径统一适用于全部 S1 异常**（含权限异常、绑定报错）。

**备选方案与拒绝原因：**
- 备选 1（对①报错形态）：复用 `StaleReferenceException`/`PermissionDeniedException` → 拒绝：语义不符（既非失效引用也非权限问题；第 1 轮已明确"Data 键缺失不属权限拒绝范畴"）。
- 备选 2（对①报错形态）：新增专属异常（如 MissingRequiredDataException）→ 不采用：扩张公共异常面且无本阶段需求；如未来需要可加性引入。
- 备选 3（对②）："只可改写既有值"（拒绝写入新键）→ 拒绝：附加了不必要的值语义限制；废弃 [Optional]+[Mutate] 的缺省→写值路径。
- 备选 4（对③）：[ContextView] 不强制（未标注允许）→ 拒绝：削弱声明完整性、放任作者漏标；对后续绑定语义不友好。
- 备选 5（对①判定）：null 视为合法值（仅查键存在性）→ 不采用：null 流入 Ref 属性/值类型属性会造成运行期噪声；"缺失=无有效值"口径更安全统一。

**补充阐明（对抗性审视）：**
- **绑定失败的原子性**：必填校验失败 = 绑定失败 = 不产出可用视图实例（调用方拿到的唯一结果是异常）——不存在"半可用实例"。

- **与后续阶段关系（备注）**：绑定失败在 S2 的异常隔离策略下的表现（吞掉/传播/跳过）属 S2 对齐内容；专属异常与更严格的数据校验（如类型预检）均可作加性演进。
