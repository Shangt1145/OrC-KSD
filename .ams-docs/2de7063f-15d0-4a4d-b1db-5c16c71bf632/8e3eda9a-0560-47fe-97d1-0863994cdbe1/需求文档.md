# S3 总线与更新 — 需求阐明记录

> 委托：S3『总线与更新』（Orc 库）· 对齐级别：类/功能流程级（GranularityLevel=class）。
> 用途：沉淀需求阐明——功能职责、约束、验收标准、已解决歧义；技术实现由实现者自主。

## 一、功能职责（本阶段）

1. **总线（Bus）**：按更新字符串分槽的订阅容器；负责被动触发器的挂载（Mount）、按所有者卸载（UnmountOwner）、更新广播（Emit）。只做广播，不做逻辑编排。
2. **更新类型**：字符串常量集（内置便利常量 + 允许任意自定义非空白字符串）+ 载荷字典；总线**不做更新类型注册/白名单**（开放集合）。
3. **更新入流**：Emit 时把更新作为条目（kind=update）写入事件流（发射者流/总流）。
4. **被动触发器挂载**：触发器在构造期声明 hook；Mount 时总线读 hook 列表注册订阅；同更新的多触发器按「挂载优先级 + 注册序」执行。
5. **引擎壳扩展**：LogicEngine 持总线 + 总事件流；多实例语义保持。

## 二、核心契约（本阶段已阐明）

### 2.1 触发器侧：hook / Kind / Owner（第 1 轮阐明）

- **hook 声明时机：仅构造期**（不提供运行期注册 hook 的 API；S4 不需要——效果装载＝对已构造触发器做 Mount、注入＝事件注册；未来如需再议）。
- **构造期一致性校验**：
  - `Kind=Active` 且 hooks 非空 → **拒绝**（矛盾声明：主动触发器不挂载；且会干扰"效果→主动/被动"分类）。
  - hooks 每项：空串 / 纯空白 → **拒绝**；同列表中重复项 → **拒绝**。
  - `Kind=Passive` 且 hooks 为空 → **允许构造**（可存在、不可挂载；保持 S2 中 Kind=Passive 可独立存在的语义）。
  - （错误类型实现者定，须在汇报中标注。）
- **Kind 语义**：保持 S2 不变（默认 Active、运行期可读）；S3 仅新增上述校验与"挂载条件"关联。
- **Owner**：触发器级声明、构造期给定、可选（object），默认 null；null=无所有者，**合法**。

### 2.2 总线侧：Mount / UnmountOwner / Emit

- **Mount(trigger) 拒绝集**（完整）：
  1. trigger 为 null → `ArgumentNullException`；
  2. Kind=Active → 拒绝；
  3. hooks 为空 → 拒绝；
  4. 该触发器已处于挂载状态 → 拒绝（防重复挂载导致双执行；卸载后状态复位、可再次挂载）。
- **挂载优先级**：触发器级声明（int；框架提供参考常量集，拟案 High=100 / Normal=0 / Low=-100，可调）；同一更新下排序＝挂载优先级 + 注册序兜底。
- **UnmountOwner(owner)**：
  - owner 为 null → 拒绝（`ArgumentNullException`；不把 null 特判为"无主"）。
  - 移除该 owner 跨**所有**更新字符串的全部挂载；卸载不打断在途 Emit 轮次（快照语义）。
  - 本阶段**仅此一种卸载途径**（无单触发器 Unmount）；owner=null 的被动触发器不可卸载＝**已知边界**（后续如需，另议）。
- **Emit(updateType, payload?)**：
  - updateType 为 null → 拒绝；空串/纯空白 → 拒绝；payload 为 null 视为空载荷。
  - 顺序 await 各订阅者（单线程）；执行期间注册/卸载变化不影响本轮（快照）。
  - **更新入流**：写入"发射时的当前执行者流"（在触发器执行中发射）；无执行帧（引擎边界）→ 写入引擎总流。
- **被动触发器的事件流挂载点**：被更新激活的执行流挂载到"发射时的当前执行者流"（无则总流）——沿用 S2 执行帧机制。

### 2.3 受控变更边界

- Trigger 构造签名：在现有 4 个可选参数（name / kind / bandType / events）**之后追加**可选参数（hooks / priority / owner）；**旧调用形态（省略或具名）保持完全可用**；不得改动既有参数的顺序、名称、类型。
- 旧行为保持：Kind 默认 Active、运行期可读（S2 语义）。若个别既有用例需调整，属受控变更并须在汇报中列出。

### 2.4 明确不做（防误扩展）

- 总线不做更新类型注册/白名单、不做订阅者并行、不打断在途轮次。
- 不禁止被动触发器被 `InvokeAsync` 直接调用（保持 S2 自由；语义上预期经总线激活）。

### 2.5 总线归属与引擎绑定（第 2 轮阐明）

- **一对一绑定**：每个 LogicEngine 实例恰持有一个总线（`engine.Bus` 只读、不可替换）；总线**不可脱离引擎**独立存在（测试场景＝创建引擎实例后经其获得总线）。总线经所属引擎触达总事件流（用于边界入流与顶层挂载）——该可达性是绑定关系的需求来源。
- **多实例互不相通**：多引擎实例之间总线完全独立（订阅表、广播、总流均不共享）；引擎 A 的广播与失败不影响引擎 B。
- **「已挂载」状态＝触发器实例级**：同一触发器实例同一时间只能挂在一个总线上（跨总线重复挂载拒绝；卸载后复位，可再挂）。
- **engine.Emit 便捷转发**：同时提供（与 Bus.Emit 完全一致、纯转发，含入流目标流判定）。
- **引擎壳形态**：保持 sealed / 多实例 / 无单例；RootStream 命名保持；Bus 为公开只读属性。
- **公开读面（最小）**：提供"查询某更新字符串的订阅者有序快照"（与执行序一致；未知更新返回空；用于调试与测试断言）；其余检视能力不做。

## 三、逐轮 Q&A 记录

### 第 1 轮 · 类/功能流程级 · 触发器侧契约（hook/Kind/Owner/受控变更）· 2026-10-03

**子的问题（原文）**：

> ■ 主问题（hook 声明形态与 Kind 一致性）：Requirements 第 2 条说"触发器直接声明其要挂载的更新字符串（构造参数或注册 API，取更简形态）；hook 列表非空即被动语义（与 TriggerKind 一致）"。请阐明这句话的准确语义与校验方向：
> (1) "hook 列表非空即被动语义"——当构造时 hook 非空但 Kind=Active 时，期望行为是哪一个：a) 构造期直接拒绝（参数非法，因为二者矛盾）？b) 允许构造但 Mount 时拒绝？c) hook 非空时框架自动认定/视作 Passive（即 Kind 由 hook 推断，与显式声明的 Kind 无强制一致关系）？
> (2) 反向：Kind=Passive 但 hook 为空是否允许"存在"（可构造、不可挂载，或等待运行期注册 hook）？还是也要求构造期拒绝？
> (3) Kind 仍保持"默认 Active、运行期可读"的 S2 语义不变，对吗？（即 S3 只增加"Passive+hook 才能挂载"的关联，不改变 Kind 自身含义。）
>
> ■ 子问题 a（Mount 拒绝条件完整边界）：Requirements 第 3 条"主动触发器（Kind=Active）挂载应被拒绝"。请阐明完整拒绝集：除 Kind=Active 外，Passive 但 hook 为空的触发器 Mount 也应被拒绝吗？hook 字符串本身的合法性校验范围（空串/空白拒绝；任意非空白自定义字符串一律合法、总线不做"更新类型注册"？）；Mount(null) 防御是否为预期。
>
> ■ 子问题 b（Owner 声明与卸载范围）：Requirements 第 8 条"触发器可声明 Owner（object，可选）"。请阐明：Owner 是声明在触发器级（与 hook 同位置，构造期给定）吗？owner 为 null 的触发器是否合法（合法则属于"无所有者"，UnmountOwner 无法命中它——本阶段是否存在除 UnmountOwner 外的卸载途径，例如单触发器 Unmount？还是明确只提供 UnmountOwner 一种、null-owner 触发器本阶段即只能不卸载？UnmountOwner(null) 的语义需要定义吗）。
>
> ■ 子问题 c（受控变更范围确认）：Requirements 第 10 条允许 Trigger 构造签名受控变更。请阐明可接受的最小破坏形态：在现有 4 个可选参数（name/kind/bandType/events）之后追加 hooks/priority/owner 这类可选参数、保持旧调用形态（具名参数或省略）完全可用，是否就是期望？以及 hook 声明是否明确"仅构造期"（不提供运行期注册 hook 的 API）——还是需要为 S4 效果预留运行期注册能力？

**阐明（决定）**（对应"二、核心契约"节）：

- (1) 选 **a：构造期拒绝**（Active + hooks 非空＝矛盾声明，fail-fast；并防止带 hooks 的 Active 干扰 S4 效果分类）。
- (2) **允许构造、不可挂载**（Passive + 空 hooks 可存在；Mount 时拒绝）。不做构造期拒绝。
- (3) 确认：**Kind 语义保持 S2 不变**；S3 只新增"构造期一致性校验"与"挂载条件"（Passive 且 hooks 非空）的关联。
- 子问题 a：Mount 完整拒绝集＝null / Kind=Active / hooks 空 / 已挂载（四类，见 2.2）；hook 字符串合法性在**构造期**校验（非空、非纯空白、不重复）；**任意非空白自定义字符串合法，总线不做注册/白名单**；`Mount(null)` 防御＝预期（`ArgumentNullException`）。
- 子问题 b：Owner＝**触发器级、构造期、可选**、默认 null；null-owner **合法**；本阶段**仅 UnmountOwner** 一种卸载途径；null-owner 触发器不可卸载＝已知边界；`UnmountOwner(null)` **拒绝**（`ArgumentNullException`）。
- 子问题 c：**是**——"末尾追加可选参数、旧调用完全可用"即期望的最小破坏形态；hook **仅构造期声明**，不提供运行期注册 API（S4 无此需求）。

**备选方案与拒绝原因**：

- (1) 备选 b（允许构造、Mount 才拒绝 Active+hooks）：拒绝——矛盾在构造期已知，延迟暴露增加排查成本；带 hooks 的 Active 会令 S4 效果分类产生歧义。
- (1) 备选 c（hook 非空自动视作 Passive）：拒绝——静默改写显式声明，无法区分"忘写 Kind"与"有意为之"，易埋坑。
- (2) 备选"双向严格"（Passive 空 hooks 也构造期拒绝）：拒绝——会破坏 S2 中 Kind=Passive 可独立存在的语义（兼容性），且该状态不构成矛盾。
- 子问题 b 备选"UnmountOwner(null) 视为卸载无主触发器"：拒绝——null 作特殊键语义歧义、易误用。
- 子问题 b 备选"增加单触发器 Unmount"：本阶段不加——保持 API 面最小；后续如需另议。

**对抗性补充（主动阐明）**：

- **重复 Mount 必须被拒绝**（防双执行；与"卸载后可重挂"配对）。
- **卸载不打断在途 Emit 轮次**（与注册快照语义一致）。
- Emit 的 updateType 空/纯空白拒绝；payload=null 视为空载荷。
- 不禁止被动触发器被 `InvokeAsync` 直接调用（保持 S2 行为）。
- **Emit 失败语义**（补充阐明）：订阅者执行中传播出的异常——取消类不捕获、原样穿透；其余（如绑定/契约失败）**记录进事件流（错误级）并继续后续订阅者**（广播容错：单个效果的故障不拖垮发射流程）。
- **Emit 与中断语义**（沿用 S2）：被更新激活的订阅者执行沿用执行帧/中断机制——发射链已中断时订阅者执行空转（正常返回空流）；订阅者可自身中断并沿链传播。
- **嵌套 Emit**：允许订阅者执行中再次 Emit（沿执行帧链自动成树）。
- **并发前提**：单线程（与全项目一致）；总线不引入锁语义。

### 第 2 轮 · 类/功能流程级 · 总线归属与引擎壳边界 · 2026-10-03

**子的问题（原文）**：

> ■ 主问题（总线归属与跨引擎语义）：Requirements 说 LogicEngine"持总线+总事件流"、"多实例（无单例）"。请阐明：
> (1) 总线是否**必须**绑定到一个引擎（即每个引擎实例恰好持有一个总线，总线经 engine.Bus 获取）？总线能否独立于引擎被构造/使用（例如测试里 new Bus()）？如果需要澄清"总线持有引擎引用"这件事在需求上的必要性：Emit 在"引擎边界（无当前执行帧）"要把更新条目写入引擎总流、被动触发器顶层执行需挂到引擎总流——这要求总线有一条通往某个具体引擎总流的通道。请给出这条通道的期望形态（总线与引擎是否一一对应、不可脱离引擎存在）。
> (2) 多引擎/多总线语义：两个引擎各自的总线是否完全互不相通？"已挂载"状态……是**触发器实例级**……还是**总线级**……？
>
> ■ 子问题 a（engine.Emit 转发入口）：取哪种：a) 仅 engine.Bus.Emit(...)；b) 同时提供 engine.Emit(updateType, payload?) 便捷转发；c) 其它。若取 b，它的行为是否与 Bus.Emit 完全一致（包括更新入流目标流判定）？
>
> ■ 子问题 b（引擎壳形态确认）：LogicEngine 现为 sealed class、仅持 RootStream（S2 冻结面）。本阶段扩展后：是否保持 sealed 与"多实例、无单例"？总流命名保持 RootStream？总线属性的公开名（如 Bus）与暴露形态（只读属性、不可替换）是否有要求？
>
> ■ 子问题 c（总线公开读面）：总线除 Mount/UnmountOwner/Emit 三个动作面外，是否需要公开**订阅查询读面**（如查询某更新字符串的订阅者列表/数量，供调试与测试断言）？还是保持动作面最小？

**阐明（决定）**（汇总见"2.5"节）：

- (1) **一对一绑定**：每引擎恰一总线（`engine.Bus` 只读、不可替换）；总线**不可脱离引擎**独立构造（测试经引擎实例获取）。总线经所属引擎触达总事件流——该"可达性"即所述通道；构造形态（引擎构造时创建/传引用或等效）由实现者自主。
- (2) **多引擎互不相通**；「已挂载」状态＝**触发器实例级**（同一实例不可同时挂多个总线；卸载后复位）。
- 子问题 a：**选 b**——同时提供 `engine.Emit` 便捷转发；与 `Bus.Emit` **完全一致**（含入流目标流判定；纯转发）。
- 子问题 b：保持 **sealed / 多实例 / 无单例**；RootStream 保持；**Bus 为公开只读属性（不可替换）**。
- 子问题 c：提供**最小公开读面**——查询某更新的订阅者有序快照（与执行序一致）；不提供更多检视面。

**备选方案与拒绝原因**：

- (1) 备选"总线可独立于引擎构造（如 new Bus()）"：拒绝——无主总线的 Emit 入流与顶层挂载语义悬空、易误用；测试可通过创建引擎实例获得总线，无独立构造必要。
- (2) 备选"「已挂载」状态＝总线级（同一实例可挂多个总线）"：拒绝——需 per-bus 状态管理（复杂）；同一触发器实例跨引擎世界共享语义混乱（执行时引擎归属不清）；实例级最简且安全。
- 子问题 a 备选"仅 engine.Bus.Emit"：拒绝——S5 对外「暴露 API」骨架已规划引擎级入口、调用顺滑；纯转发成本极低。
- 子问题 c 备选"保持动作面最小、不做查询"：拒绝——调试与测试断言直接受益（承袭可观测设计传统）；纯加性、低成本。

**对抗性补充（主动阐明）**：

- **Emit 无订阅者**：仍写入 update 条目（更新已发生，因果记录完整）；随后正常完成。
- **UnmountOwner 未命中**（该 owner 无任何挂载）：**幂等无操作**、不报错。
- **UnmountOwner 范围**重申：移除该 owner 的**全部触发器**的全部挂载（跨触发器、跨更新字符串）。
- **查询读面校验**：null/空白更新字符串按 Emit 同规则拒绝；未知更新返回空（开放集合，不报错）。
- **订阅者规模**：原型不设数量上限（与 S2 事件流一致）。
- **多引擎失败隔离**：引擎 A 的广播异常不影响引擎 B（多实例语义自然结果）。

## 四、验收关联

本阶段既有六项验收中，本轮阐明直接影响：
- ②多订阅者顺序（挂载优先级 + 注册序）；
- ④Mount/UnmountOwner 生效（含完整拒绝集；卸载后不再激活）；
- ⑤挂载校验（完整拒绝集；错误类型须在汇报中标注）。
