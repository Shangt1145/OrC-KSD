# S5 数据序列化、输出与测试集 — 需求阐明记录

> 记录 S5 委托的需求阐明与逐轮对齐结论。每轮＝【子的问题原文 → 对齐结论 → 备选方案与拒绝原因 → 边界与补充审查】。

## 1. 事件流 JSON 树形语义（第 1 轮）

### 1.1 子的问题（原文）

委托要求：『节点＝{ id, entries: [...], children: [...] }；条目＝{ kind, timestamp, level, source, message, keywords, data }（与现有 LogEntry / EventStream 读面对应）』。但现有 EventStream.Entries 的读面语义是「含本地写入与后代冒泡」——写入任一流的一条条目会以同一条目引用追加到其全部祖先流（含总流）。若按读面直接导出，同一逻辑条目会出现在「写入流→根」路径上每个节点的 entries 里（总流节点将包含全量条目，同时每个子节点又各自包含自己那份），JSON 体积与断言预期都会受影响。

**主问题**：树形 JSON 中节点的 entries 字段应表达哪种语义、以哪种作为验收「树形结构断言」的锚？
- 语义 A：忠实读面——节点 entries 含「本地＋后代冒泡」的全量条目，同一条目在父子节点重复出现属正常现象；
- 语义 B：本地条目——节点 entries 仅含该流自身写入的条目（子流条目只出现在子流节点上，树中同一条目仅出现一次）；
- 还是第三种（如导出时提供可选的去重/过滤语义，由实现者定义并说明）？

**子问题**：
① 从「任意流」导出时的范围：是否＝以该传入流为根（不含其祖先）的子树；总流（LogicEngine.RootStream）导出是否就是整棵树（等同把总流作为根）？
② 若选语义 A：同一条目在父子节点重复出现是否为验收接受的正常现象（树形断言不得对此做限制）？若选语义 B：允许在序列化层自行区分「本地 vs 冒泡」（例如借助差集或其他内部手段），还是必须新增读面能力（属受控变更需汇报）？
③ JSON 形式细节——字段命名风格、kind/level 枚举的 JSON 表示、timestamp 格式、导出入口的输出形态（返回 string / 写出到 TextWriter / 其他）——是否属实现自由（汇报说明即可），验收断言只锁「结构＋字段值内容」？

### 1.2 对齐结论

**主问题：取语义 B（本地条目）。**
- 树形 JSON 中每个节点的 `entries` 仅含**该流自身写入的条目**（本地条目）；后代条目只出现在其后代节点上；**同一逻辑条目在整棵树中恰出现一次**（位于其写入流的节点下）。
- **内存读面（`EventStream.Entries` 含冒泡）保持不变**——语义 B 仅约束 JSON 导出的呈现，不改动既有内存行为（受保护、S2 已锁定）。
- 理由：①语义 A 会让同一条目在「写入流→根」路径重复 N 次，且 JSON 无条目级 ID、消费者无法可靠去重——解析歧义＋体积膨胀；②"全量视图"可由树遍历自然获得（总流节点的聚合读面是内存便利视图，序列化层不必复刻）；③断言锚清晰稳定＝**结构（id/entries/children 层级）＋条目归属（条目出现在其写入流节点）**。

**子问题①（导出范围）：确认。**「从任意流导出」＝以传入流为根的**子树**（不含其祖先、含全部后代）；总流导出＝整棵树（同入口、同语义）；产出为根节点结构 `{ id, entries, children }`。

**子问题②（本地/冒泡区分途径）：优先新增只读能力。** 优先采用"本地条目"只读能力（写入时同步记录；**加性变更**，随汇报标注）；如实现者出于充分理由选用引用差集等内部手段作为备选，须保证近线性实例表现并在汇报说明；**验收只锁 JSON 输出语义（语义 B），不锁内部机制**。

**子问题③（形式细节）：确认属实现自由。** 字段命名风格、kind/level 的 JSON 表示、timestamp 格式、导出入口输出形态＝实现自由（随汇报说明）；验收断言只锁"**结构＋字段值内容**"。附注：事件流 JSON 的**最终格式定稿留待用户**（阅读工具的前置条件）；本阶段形式细节后续可微调，但**结构语义（树形＋本地条目）为准**。

### 1.3 备选方案与拒绝原因

- **语义 A（忠实读面、冒泡重复）**——拒绝：解析歧义（无条目级 ID 无法可靠去重）、体积膨胀（近 O(深度×条目数)）、与"树形即'该流自己的记录'"直觉相悖。若未来需要"全局时间序全量视图"，作为独立加性导出（后续），不混入树形 JSON。
- **第三种（可选去重/过滤语义）**——拒绝：可选分支模糊验收锚；原型取唯一定义（B），复杂导出模式留后续演进。
- **子问题②之"仅差集"途径**——不禁止但非优先：差集依赖冒泡实现细节、计算成本高；推荐新增本地读面。

### 1.4 边界与补充审查（对抗性审视）

- **空流/空树**：导出为合法 JSON（空 entries/children 数组），不得报错。
- **规模与深度**：导出复杂度近线性于条目总数；无隐性深度/规模上限（延续"不设封口/裁剪/上限"口径）。
- **不可序列化的 data 值**：确定性处理（降级表示或明确错误），由实现者定并在汇报说明。
- **职责边界**：本项仅涉"事件流 JSON 导出"的语义与验收锚；快照 JSON、三骨架、场景 1 的对齐见后续轮次。

## 2. 快照 JSON（第 2 轮）

### 2.1 子的问题（原文）

委托要求：『①单实体（从引用导出）——给定实体引用/卡牌 → { entityId?, components: { "<数据组件类型名>": { 属性... } } }（强类型数据组件反射序列化，原型级即可）；②全量——导出注册/在场卡牌列表的全量快照（组合 API）。API 形态自定并在汇报中说明。』

**主问题**：单实体快照的输入与 `entityId` 的来源/形态。
- "给定实体引用/卡牌"中的"引用"是否即 Ref/Lifetime 体系的安全引用（如 `Ref<Entity>` / `Card.Ref`）？入口需要同时支持「Ref 形态」与「卡牌对象」两种输入（"引用/卡牌"的斜杠是否＝两者皆应支持）？
- `entityId?` 的来源：现有 Entity 仅有 Name（无 Id 字段）。可选字段应取什么——实体名（Name，可能重名）、为实体新增标识（受控/加性变更）、导出时生成，还是由实现自定并汇报？"?"（可缺省）的缺省条件是什么？

**子问题**：
① 失效目标行为：给定已销毁实体或其失效引用（Ref.Value 会抛 Stale）时，导出行为应为——抛 StaleReferenceException、降级输出（如标记存活性）、还是由实现自定并汇报？原型级下验收是否要求锁定该行为？
② components 序列化口径："<数据组件类型名>"＝简单名还是含命名空间全名？反射范围＝公共可读属性即可（原型级）？复杂/引用型属性值（如指向别的卡牌/对象）的处理是否同事件流 data 的"确定性处理、实现者定并汇报"口径？
③ 全量快照的覆盖面与控制面：现有引擎未维护卡牌列表，S5 需为引擎新增"卡牌登记"（属加性扩展）吗？范围＝全部已创建卡牌（含未放置）还是仅已放置（IsPlaced）？销毁后的卡牌是移除、保留（标记）还是由实现自定并汇报？多引擎实例各自独立列表是否确认？"组合 API"（全量＝逐卡复用单实体结构）与输出形态（数组/以什么为键）是否属实现自由？

### 2.2 对齐结论

**主问题·输入：两者皆支持。** "引用"即安全引用体系（`Ref<Entity>` / `Card.Ref` 形态）；入口**同时支持**「安全引用形态」与「卡牌/实体对象形态」（对象形态内部经其引用解析）——"斜杠"含义＝两者皆应支持；具体 API 形态（双入口/统一入口）由实现者定、汇报。

**主问题·标识：语义＝实体标识符；首选新增加性标识，字段必输出。**
- `entityId` 的语义＝**实体标识符**（供外部关联/消费）。
- **首选**：为 Entity 新增**加性标识**（如 `Entity.Id`；形式＝Guid/引擎分配序号等，实现者定、汇报）——理由：快照面向外部关联消费，重名 Name 不满足"标识"语义；加性变更随汇报标注。
- **备选**：取用 `Name`（若实现者判断加标识成本过高）——须在汇报中记录"可能重名"的限制。
- **"?"的澄清**：`entityId` 不再是"可随意缺省"的字段——**标识应输出**；仅在实现者明确的降级场景下缺省（须汇报）。

**子问题①（失效目标）：降级输出，不抛；验收锁定。**
- 给定已销毁实体/失效引用时，导出**降级输出**（如呈现标记"已失效"；具体形态实现者定、汇报），**不得抛 StaleReferenceException**。
- 理由：与"引用失效可检测、消费方不崩溃"的引擎价值取向一致；快照＝呈现查询，不宜对时序竞态敏感；抛出语义保留给"逻辑执行访问失效引用"场景。
- **验收锁定**：失效输入必须产出可解析的降级结果（不得异常）；`null` 参数仍按库惯例抛参数类异常（编程误用，非运行时失效——不冲突）。
- 附注：全量导出路径若保证不含已销毁卡牌（见③），则正常路径不会遇到失效；两机制互补。

**子问题②（components 口径）：确认＋防环补充。**
- 类型名＝**简单名（Type.Name）**；同名冲突（不同命名空间同名）＝已知限制，汇报记录。
- 反射范围＝**公共可读实例属性**（原型级）。
- 复杂/引用型属性值：**同事件流 data 的"确定性处理、实现者定并汇报"口径**；补充：**不得递归导出引用目标**（如指向别的卡牌）——以防环；降级形态（如输出目标标识或跳过）实现者定、汇报。

**子问题③（全量快照）：确认＋登记表裁定。**
- **引擎新增"卡牌登记"**（加性扩展，汇报）：登记时机＝**卡牌创建即注册**；**范围＝全部已创建（注册）卡牌（含未放置）**；**销毁后移除**（一步式销毁路径明确；两步路径（仅杀未发更新）的移除时机由实现者保证一致，汇报）。
- **多引擎实例各自独立列表：确认**（与 LogicEngine 多实例语义一致）。
- "组合 API"＝**逐卡复用单实体结构**（确认）；**输出容器形态（数组等）＝实现自由**（汇报）。
- 空快照（无卡牌）＝**合法空集合**（不报错）。

### 2.3 备选方案与拒绝原因

- **输入仅支持 Ref 形态**——拒绝：委托文本"引用/卡牌"与 S5 拟案均表达两者皆应支持；对象形态是低成本便捷入口。
- **导出时生成 entityId**——拒绝：无稳定关联价值（每次不同）。
- **失效目标抛 Stale**——拒绝：与消费方容错价值取向冲突；快照是查询而非执行。
- **全量为"调用方自备列表"**——拒绝：字面要求"注册/在场卡牌列表"，需引擎侧登记支撑；委托方传列表仅为可选附加形态（不作要求）。
- **登记保留已销毁卡牌（标记）**——拒绝：快照＝当前状态呈现；死卡保留无消费价值，且与"移除干净"的既有清理哲学一致。

### 2.4 边界与补充审查（对抗性审视）

- **空快照/单卡无组件**：合法输出（空集合 / 空 components 对象），不报错。
- **属性 getter 异常/不可序列化值**：确定性处理（降级/跳过+可诊断），实现定、汇报（与事件流 data 口径一致）。
- **规模**：全量＝近线性于卡数×组件属性数；无隐性上限。
- **一致性**：快照与事件流 JSON 共用"确定性处理"原则；两者格式细节最终定稿均留用户。
- **职责边界**：本项仅涉"快照 JSON"；三骨架、场景 1 的对齐见后续轮次。

## 3. 三骨架接口（第 3 轮）

### 3.1 子的问题（原文）

委托要求：『① IEngineBridge（引擎→外部主动调用——宿主实现侧留接口与调用点）；② LogicEngine 公开 API（外部→引擎——梳理现有公开面[Emit/流程/DestroyCard 等]并结合注释、最小入口）；③ Subscribe 回调（外部注册、引擎在更新/关键事件时回调——最小实现或占位）。骨架要求：可编译、方向正确、可扩展；不得过度实现。』验收标准⑤：『三骨架接口存在且可编译、可扩展』。

**主问题**：三骨架的"最小接线"验收底线与测试要求。
- "仅接口定义＋占位/最小接线，不完善"——底线究竟是（a）接口/入口存在且编译通过即可（调用点可以只是占位注释/空转发），还是（b）要求接线真实贯通（如 Emit 时桥接口或回调被实际调用）并有自动化测试证明？
- 验收标准⑤只说"存在且可编译、可扩展"——是否意味着本项不要求行为测试（仅 API 存在性＋构建通过即可）？还是希望至少 1 个轻量冒烟断言（如 Subscribe 注册后某更新发生时可观察回调已触发）？

**子问题**：
① IEngineBridge 的方向与最小方法集："引擎→外部主动调用"——由宿主实现接口、引擎持引用并在关键时点调用；最小方法集（有哪些通知点位）由实现者定并汇报，还是父对方向有预期（例如"更新发生时/事件流产生时"通知宿主）？它与③ Subscribe 的定位差异是否为：桥＝宿主编译期实现接口（可强类型、多方法）；Subscribe＝外部运行期注册回调（可多注册、弱形态）？
② LogicEngine 公开 API 的"梳理"与"最小入口"：委托说"梳理现有公开面[Emit/流程/DestroyCard 等]并结合注释、最小入口"——这是指（a）对现有公开面补足说明性注释/组织即算完成，还是（b）要求新增某个"最小入口"方法/类型（如是，指什么方向）？"结合注释"的期望对象是 XML 文档注释、还是说明性组织（如公开面清单注释）？
③ Subscribe 回调的最小语义边界：注册面挂在引擎还是总线？订阅单位＝"更新"（Emit 时回调）还是更广的"关键事件"（如任意事件流写入/执行完成）？最小语义是否要求覆盖：多订阅者、取消注册、回调异常隔离？若最终选择"占位"形态，验收"方向正确、可扩展"应以什么为准？

### 3.2 对齐结论

**主问题裁定：底线＝"最小接线真实贯通"（非纯占位）＋轻量冒烟断言。**
- ①③ 要求**真实接线**：桥接口在至少一个关键时点被引擎实际调用；回调在更新发生时可被观察触发；并配 **1~3 条轻量冒烟断言**（验证接线方向真实成立，而非行为完备）。
- ② 以**梳理＋注释**为主（见下），无行为变更、无强制新增。
- 理由：纯"存在＋编译"无法排除"方向错误"（接口反向/永不被调用），"方向正确"不可验证；轻量冒烟成本极低、显著提升验收可信度；完备行为矩阵（重试/顺序/异步分发等）明确不做（守住"不得过度实现"）。

**子问题①（IEngineBridge）：**
- 方向确认：**宿主实现接口（编译期契约）；引擎侧持有（可空）引用；引擎在"更新广播（Emit）"这一关键时点真实调用**（最小点位）。
- 最小方法集：**至少一个"更新通知"方法**（签名形态实现者定、汇报）；允许增补但保持最小。
- 与③的定位差异：**确认**（桥＝编译期强类型接口；Subscribe＝运行期多注册弱形态）；同一更新路径的两种通道，各自独立测试。

**子问题②（LogicEngine 公开 API）：**
- 裁定：**（a）梳理＋注释为主**——对现有公开面（Emit/流程/DestroyCard/事件流/快照等）补 **XML 文档注释**并按用途组织；**不强制新增"最小入口"**；如梳理发现明显缺口且新增极简（纯转发/门面），允许加性、汇报。
- "结合注释"的期望对象＝**XML 文档注释**；说明性组织（如公开面清单注释）为辅。

**子问题③（Subscribe）：**
- 注册面：**引擎**（对外门面；内部转发/分发形态自由）。
- 订阅单位：**更新（Emit 时回调）**（最小）；更广范围留扩展。
- 最小语义（要求）：**多订阅者＋取消注册＋更新发生时回调＋回调异常不破坏更新广播主流程**；回调顺序与记录形态实现定、汇报。
- **不采纳"纯占位"形态**——按最小贯通形态实现。

### 3.3 备选方案与拒绝原因

- **纯占位（存在＋编译，空转发/注释）**——拒绝：与"方向正确"冲突；验收⑤"可扩展"缺最低可信证据；冒烟成本极低而收益高。
- **完备行为实现（重试/顺序优先级/异步分发/记录等）**——拒绝：违反"不得过度实现"；留后续演进。
- **桥的多点位（执行开始/结束/快照变化等）**——拒绝：超出最小；以"更新广播"单点位为准（可增补须最小）。
- **Subscribe 挂总线**——拒绝：总线是内部机制；对外注册应面向引擎（内部转发形态自由）。
- **Subscribe 纯占位**——拒绝：回调模式核心方向（注册→触发）无法验证。

### 3.4 边界与补充审查（对抗性审视）

- **桥未装配（null）**：引擎正常运转（跳过调用）——"都要"＝通道供给存在，不强制宿主必配。
- **桥方法异常**：不得破坏更新广播主流程（隔离处理）；记录形态实现定、汇报（与回调同口径）。

- **接口演进**：桥接口增补方法/回调形态调整须保持已接线方向可编译、可扩展（"可扩展"验收的一部分）。

## 4. 场景 1 端到端测试：火球/护盾/反制/中断（第 4 轮）

### 4.1 子的问题（原文）

委托要求：『火球＝主动效果（法术）施放 → 伤害结算流程（护盾减伤→扣血）；反制＝设计一个合理的「法术反制」编排（利用既有 Stop/Interrupt 机制；例：施放链在伤害发生前被反制→中断→伤害不发生/施放失败），测试覆盖正反两路径（被反制/未被反制）；与既有 AttackFlow/DamageFlow/ActiveEffect 机制一致（如需最小加性扩展，汇报说明）。』

**主问题**：反制编排的机制化程度与"施放失败"的验收观测面。
- "设计一个合理的『法术反制』编排"——反制检查位是否需要做成**可复用机制**（例如施放链上存在类似攻击流程 Counter 的扩展位/挂点，供未来不同反制效果接入）？还是场景 1 测试**内部自洽**即可（如测试内直接注册反制逻辑、或用一个专用反制效果类承担）？
- "被反制→中断→伤害不发生/施放失败"的硬性观测面是什么：(i) 仅要求"伤害不发生"（目标状态不变）；(ii) 要求施放链上出现中断留痕（如 interrupt 记录）；(iii) 还要求"施放失败"的额外可观察语义（如施放事件链剩余事件未执行、施放计数/状态不推进）？还是上述组合由实现者设计并汇报？

**子问题**：
① 反制者形态：反制的承担者是否应为"一个效果"（如反制卡上的被动效果，经既有装载/注入机制接线，体现 S4 框架价值）？还是允许测试直接编排（直接 Register/直接调用触发）即可？是否需要"条件反制"的最小演示（如仅对特定法术或特定目标响应）？
② 最小加性扩展的容许边界：若施放链需要为反制提供最小加性扩展（如施放触发器/反制检查位的公开或 band 化），确认允许并汇报；其边界是"只服务场景 1 自洽"还是需要达到"可复用扩展位"（供后续反制类效果复用的程度）？
③ 正反两路径与"中断"范围：两条路径（被反制/未被反制）是否都要求"端到端"级别断言（从施放入口→最终状态＋事件流结构）？"中断"是否就指反制引起的链中断（Interrupt），还是场景 1 还需额外覆盖 Stop（本级停止）或独立中断演示？护盾/HP 数值、法术命名、反制文案等语汇是否属实现自由？

### 4.2 对齐结论

**主问题A（机制化程度）裁定：取"可复用方向的最小扩展"——反制必须走"效果/触发器＋既有接线机制"的公共路径，施放链提供具名检查位（band 扩展位）。**
- 反制检查位＝**施放链的具名检查位（band 扩展位）**；反制效果经**既有机制**接入（首选：装载时注入/挂接，形态照 S4 既有模式）；
- **禁止**"仅测试内部自洽的 hack 路径"（如测试直接调用内部私有方法模拟反制）——必须走公共/既有机制，使未来同类反制效果可复用同一位点；
- **不要求**完备机制（多反制协调、优先级体系、注册/查询面等）——留后续演进。

**主问题B（验收观测面）裁定：(i)＋(ii)＋(iii) 组合。**
- (i) 伤害不发生（目标状态不变）；
- (ii) **中断留痕**：事件流中出现中断记录（证明打断发生在链中；形态实现定、须可断言）；
- (iii) **失败可查询**：施放结果/链路状态可查得"被反制"（可用既有 Interrupt 状态查询机制表达，不必新造 API）。
- 三项组合的具体观测形态由实现者设计并汇报。

**子问题①（反制者形态）：首选"效果"形态；完整装载链可选。**
- 反制＝**一个效果**（可反制卡上的被动效果），经 S4 既有装载/注入机制接线（体现框架价值）；
- 若完整链（卡牌创建→放置→装载→注入）使场景 1 测试过度臃肿，允许"最小等效装配"（仍须经效果/触发器机制、公共路径），汇报说明；
- "条件反制"（仅对特定法术/目标响应）：**不强制**——反制 handler 内部判断逻辑属实现自由（若加入，汇报）。

**子问题②（加性扩展边界）：允许，边界＝"可复用方向的最小扩展位"。**
- 允许为施放链提供最小加性扩展（施放流程/检查位 band 化等），汇报；
- 边界：扩展须落在**既有范式内**（具名 band＋注入/接线），使未来同类反制效果**可复用**；**不要求**建立额外完善体系（不做"仅测试自洽"、也不做"完备机制"）；
- 推荐形态：反制效果装载/注入施放链检查位（与"攻击时回血"同构）。

**子问题③（两路径与中断范围）：**
- 两路径均要求**端到端断言**：从施放入口 → 最终状态（HP/护盾值等）＋事件流关键结构（成功路径验完整链节点；反制路径验中断留痕与链结构）——断言粒度实现定（关键节点即可，不要求逐条目）；
- "中断"＝**反制引起的链中断（Interrupt）**；**不要求**额外覆盖 Stop 或独立中断演示（S2 已有机制级单测；如实现者轻量附带，非要求）；
- 护盾/HP 数值、法术命名、反制文案等语汇＝**实现自由**（汇报说明）。

### 4.3 备选方案与拒绝原因

- **"测试内部自洽/直接编排"（hack 路径）**——拒绝：方向错误（未来真实反制效果接不进来）；与"可演进奠基"原则冲突。
- **完备反制机制（多反制协调/优先级/注册面）**——拒绝：超出"不得过度实现"；留后续演进。
- **仅 (i) 伤害不发生**——拒绝：无法区分"链中断"与"压根没执行"；中断留痕与可查询状态是"反制/中断"场景的验收核心。
- **额外强制覆盖 Stop/独立中断演示**——拒绝：S2 已有机制级单测；场景 1 聚焦"反制引起的中断"端到端表现。
- **强制反制走完整卡牌放置链**——拒绝（降级为可选）：端到端价值在"机制接线"，完整链非验收必需；测试臃肿风险。

### 4.4 边界与补充审查（对抗性审视）

- **正路径补充**：施放成功时可顺带断言"护盾参与的减伤链"（护盾值变化）；若实现者纳入"条件反制未命中"分支，加分、非要求。
- **无残留**：中断路径下，除"未发生"外无其它可观察副作用残留（就现有可观察面：目标 HP、护盾值等不变；法术方无半完成状态）。
- **反制 handler 异常**：按既有异常隔离语义（S2）处理；场景 1 不强制覆盖该分支。
- **确定性**：测试确定性（不依赖时间/随机；语汇值实现自定但固定）。
- **职责边界**：本项仅涉场景 1；场景 3 已被 S4 生命周期测试覆盖（核对即可，如发现缺口汇报补测）；全量回归照原验收。

## 5. 反制的位点归属与装配形态（第 5 轮）

### 5.1 子的问题（原文）

第 4 轮已裁定：反制检查位＝『施放链的具名检查位（band 扩展位）』；反制效果经既有机制接入（『推荐形态：反制效果装载/注入施放链检查位（与「攻击时回血」同构）』）。而『攻击时回血』的注入目标是**引擎级共享**的 AttackFlow.Trigger——据此，『施放链检查位』的位点归属仍需明确。

**主问题**：『施放链』位点应落在哪一层？
- (a) **法术实例层**：每个法术（如火球）自身的施放链上设有具名检查位；反制效果针对**具体法术**注入（"这个法术的反制位"）；
- (b) **引擎层共享**：所有法术施放共享一个检查位载体（类比 AttackFlow 为引擎级共享触发器），反制效果不需要知道具体法术；
- (c) 其他/由实现者择定。
两种方向的"可复用"语义不同（未来同类反制效果接入的位点是"按法术"还是"按引擎"），也决定本轮最小加性扩展的公开面边界——请裁定方向；若皆可，请给出期望的优先方向与理由。

**子问题**：
① 检查位的提供者与验收锚：该位点由**框架层面统一提供**（如 ActiveEffect 基类统一提供检查位/band 支持），还是由**法术作者声明**（作者在施放链上自定位点，框架只给通用能力），抑或属实现自由？验收语句应表述为"反制效果能经既有接线机制接入可复用的施放检查位"，对吗？
② 反制者的装配形态与关联提供：反制效果是否应装配在**独立的反制卡牌**上并经放置/装载链（体现"反制者"单位概念与多卡交互），还是允许最小等效装配（第 4 轮已允"完整链可选"）？被反制法术（或引擎级载体）的引用由装配代码显式提供给反制效果（如构造传入）——这种关联提供方式是否可接受（属实现自由）？

### 5.2 对齐结论

**主问题裁定：取 (b) 引擎层共享**——施放流程（引擎级共享载体，与 AttackFlow/DamageFlow 同构）承载具名检查位；反制效果不需要知道具体法术，接入的是引擎级共享位点。
理由：
1. **同构性**：S4 已确立"引擎级共享流程"范式（AttackFlow/DamageFlow 均为引擎级共享触发器）；施放流程（SpellFlow 或等效形态）与之同构；
2. **自洽性**：与第 4 轮"与'攻击时回血'同构"的推荐一致（攻击时回血的注入目标亦为引擎级共享载体）；
3. **语义正确**：反制响应的是"施放流程"而非绑定某具体法术实例；"反制哪些法术/条件下是否反制"的判断属反制 handler 内部自由；
4. **可复用性**：未来同类反制效果接入同一引擎级位点，无需知道具体法术。
（(a) 法术实例层不作为裁定方向；"法术实例专属钩子"非本轮要求，留未来演进可选。）

**子问题①（提供者与验收锚）：框架层面统一提供；验收语句确认（加限定）。**
- 检查位由**框架层面统一提供**（引擎级共享施放流程统一承载检查位/band 支持）；法术作者无需（也不应）自定位点——法术（主动效果）经该共享流程施放；
- 验收语句确认（加限定）："反制效果能经既有接线机制接入**引擎级共享的施放检查位**"；
- 涉及的最小加性扩展（施放流程/检查位的引入）随汇报（第 4 轮已允）。

**子问题②（装配形态与关联提供）：维持第 4 轮口径；关联引用可接受、施放信息经执行上下文。**
- 装配：首选完整链（独立反制卡→放置→装载→注入共享检查位）；允许最小等效装配（仍走公共机制），汇报；
- 关联引用：装配代码在装载时提供"引擎级载体（共享施放流程）的引用/可达路径"（如构造传入/经装载上下文）——**可接受，属实现自由**；
- **补充限定**：具体施放信息（当前施放的法术/施法者/目标等）应在**执行时经检查位的既有数据通道**（流程 ctx/视图）获得——而非装配时预绑具体法术引用（后者属 (a) 模式，不采用）。

### 5.3 备选方案与拒绝原因

- **(a) 法术实例层**——不作为方向：与反制语义（对"施放流程"的响应）不符、需按法术逐一接线、可复用性差；"法术实例专属钩子"留未来可选演进（非本轮要求）。
- **检查位由法术作者声明**——不采用：与引擎级共享流程方向冲突；框架统一提供方能保证位点一致、可复用。
- **多反制者协调机制**——不要求：既有"中断即停"语义（S2）已覆盖顺次行为；多反制专项测试非本轮必需。

### 5.4 边界与补充审查（对抗性审视）

- **规范路径**：场景 1 的施放链路必须经过共享流程的检查位；其他直调路径不禁止（作者自由），但验收以规范路径为准。
- **检查位空位**：无反制者接入时施放正常继续（正路径天然覆盖）。
- **多反制者（补充）**：第一个反制成功（Interrupt）后，同层后续 handler 依既有"中断即停"语义停止；场景 1 不强制多反制专项测试（若轻量覆盖，加分）。
- **反制 handler 异常**：延续既有异常隔离语义（不强制场景内覆盖）。
- **施放信息通道**：见 5.2 补充限定（执行上下文提供，非装配预绑）。
- **职责边界**：本项仅涉反制的位点归属与装配形态；其余同前各轮（第 4 轮的观测面/两路径断言等维持）。
