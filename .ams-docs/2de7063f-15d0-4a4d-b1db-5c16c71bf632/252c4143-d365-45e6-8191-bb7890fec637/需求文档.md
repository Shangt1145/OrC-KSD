# S2 触发器与事件 —— 需求阐明记录

> 本记录用于 S2 委托（de50bf03）的 grill 对齐：记录需求阐明、约束、验收标准与已解决的歧义，逐轮增长。
> 级别：类/功能流程级（委托 GranularityLevel=class）。

## 一、功能职责概述

S2 在 S1（核心运行时）基础上交付触发器完整机制：触发器完整形态（事件列表、band 列表、主动/被动、重载触发入口）、事件（handler）执行与 band/优先级排序、嵌套触发、Stop/Interrupt、异常隔离、ContextView 转接（Translate）、事件流（EventStream）机制。（细则以委托 Requirements 与父层已归档规格为准。）

## 二、第 1 轮：触发方法重载（三形态）与 ContextView 转接（Translate）

### 2.1 子问题原文（摘要）

- **主问题 1**：三种触发形态各自的公共签名方向与职责边界——(a)"统一入口"指什么、完整参数形态（含取消令牌、是否参与转接）、是否同一方法名重载；(b)"具名重载"归属（泛型无法统一提供）与验收④口径；(c)"直接传字典（透传）"的字典类型、透传含义、拷贝边界。
- **主问题 2**：Translate 的契约归属与转接语义——(a) Translate 定义在哪、静态/实例、由谁在何时调用、ctx 由谁创建；(b)"引用可变/共享"的验收断言语义；(c)"值快照/值不可变"边界与"直接透传赋值"含义。

### 2.2 解答（对齐结论）

**触发入口三形态（同一 `InvokeAsync` 重载族，最终收敛于统一入口）**

① **统一入口（框架提供；规范收敛点）**
- 方向性签名：`InvokeAsync(<引擎引用> engine, IDictionary<string, object?> data, CancellationToken ct = default)` → `Task<EventStream>`（命名可微调）；
- 职责：以 data 创建本次执行的 ctx（沿用既有 Context 构造"入料拷贝一次"语义）；顺序执行事件链；返回事件流；
- 它接收"转接产物/就绪数据"，**本身不触发转接（不隐式调用 Translate）**。

② **具名重载（作者侧书写）**
- 框架无法为泛型 `Trigger<TView>` 统一提供具名参数重载（编译期不知参数集）——由作者/编排代码在具体触发器（或其子类）上自行书写（如 `InvokeAsync(engine, Ref<Entity> source, int amount, Ref<Entity> target, ct)`）；
- 职责：通过**手写转接**把具名参数写入数据字典，再汇入①。

③ **字典透传（统一入口的直接使用）**
- 调用方自备就绪字典直接调用①；字典内容不经任何转换/加工成为本次执行 ctx 的数据；"透传"＝零加工；存储沿用"入料拷贝一次"。

- 关系：三形态为**同一方法名（InvokeAsync）的重载族**；②③最终都收敛到①；参与转接的仅②路径（由作者代码执行）。
- S1 壳的 `RunAsync(Context)` 属 S2 受控变更点：其对外调用面由本形态取代（是否保留内部/兼容方法由实现自定）。
- **验收④口径修订**：由"三种触发入口经 View.Translate 转接"修订为——"**具名重载路径经视图手写转接汇入统一入口；字典透传路径零加工直入；两路径均可正常执行**"（框架层面只需保证统一入口接受转接产物）。

**Translate 契约（转接）**

- **归属与形态（S2 原型口径）**：转接＝**作者视图类上的手写静态方法**（书写约定；如 `public static void Translate(<引擎引用> engine, <该触发器参数…>, Dictionary<string, object?> data)` → void，结果写入 data）。框架**不建立强制接口/契约类型**（FilesToModify 中 ContextView.cs"如需：转接契约补充"按**不需要**处理；若实现中因示例书写需要最小辅助物料，限于示例/内部层并列入汇报）；框架**不隐式调用** Translate。
- **调用时机与链路**：具名重载（调用侧代码）→ 调用视图类静态 Translate（参数→data）→ 调用统一入口（以 data 创建 ctx）→ 绑定创建视图实例 → 执行事件链。转接**不得依赖视图实例状态**（视图实例由框架在绑定阶段创建，时序晚于转接）。
- **引用类参数**：以**同一 Ref 实例**入 data（`ReferenceEquals`）；"可变/共享"断言基准＝①入的是同一实例（不拷贝 Ref 包装、不拷贝目标对象）②视图 `[Mutate]` 属性可改写该键、改写后同一次执行内其他读取可见新值。（不约定"Ref 指向对象"内部状态的引擎语义。）
- **值类参数**：以**快照**入（值拷贝、双向独立：ctx 内改写不回写调用方原值；调用方原值后续变化不影响 ctx 内已入值）；"允许直接透传赋值"＝`data["Amount"] = amount;` 直接赋值即可，无包装 API。
- **澄清**："值不可变"仅指与调用方的解耦语义，**不禁止** ctx 内值被 `[Mutate]` 改写（如护盾减伤改写 Amount 属正常业务）。

**边界与失败模式补充（对抗性审视结果）**

- 转接时序：转接先于视图实例创建；Translate 不得访问被代理属性；
- Translate 抛出异常：发生在执行前，按调用方异常处理（框架不包装、不写事件流）；
- 参数与视图声明不一致：原型由作者责任承担（硬编码、不做编译期校验；工具化演进再收）；
- 数据键/null/必填/取消传播：沿用既有口径（权限矩阵、必填缺失含 null 抛 KeyNotFoundException、取消类异常上抛）；
- 性能：转接为一次性字典写入，无缓存/池化要求（原型）。

### 2.3 备选方案与拒绝原因

- **备选 A**：框架在 `Trigger<TView>` 上统一提供 `params object?[] args` 并由框架隐式调用 Translate → 拒绝：泛型无法表达具名参数集；位置参数语义脆弱；与"手写转接、作者侧负责"的已定口径冲突。
- **备选 B**：框架定义强制转接契约接口（ITranslator 等）→ 拒绝：原型阶段过度约束（已定"手写硬编码"）；声明式/生成器化属后续演进。
- **备选 C**：统一入口沿用 S1 显式 Context 入参 → 拒绝：与"转接产物→ctx 由入口创建"的边界不符；且该参数集本就是受控变更点。
- **备选 D**：字典透传路径亦强制先经 Translate → 拒绝：与"可以直接透传 ctx 字典"的既定要求冲突。
- **备选 E**：Translate 采用实例方法（需先造视图实例）→ 拒绝：转接发生在绑定之前，无自然实例；空实例方案破坏"视图每会话新建"语义。

## 三、第 2 轮：触发器完整形态（band 列表、构造/注册、Kind 与身份）

### 3.1 子问题原文（摘要）

- **主问题 1**：band 列表的确切含义、声明与数值契约——(a)"内部维护 band 列表"含义、数值来源（显式指定/自动编号）、默认项、default 可否改名/移除/改值、固定时机；(b) band 定义与事件注册的衔接（定义入口、注册形态、未声明处理、"注册 API"形态）；(c) 数值契约与校验义务（越界处理、重名/同值裁决）。
- **主问题 2**：事件注册边界、Kind 与身份标识——(a) 注册时机与封闭边界、默认优先级；(b) Kind 指定方式、取值面、默认值与 S2 行为差异；(c) 触发器名称字段、source 构成、事件名重复与用途边界。

### 3.2 解答（对齐结论）

**A. band 的定义与数值契约（问题 1a / 1c）**

- band 以 **C# 枚举类型**定义（成员名＝区段名、成员值＝数值）；作者可在枚举上**显式指定值**（如 `Prevent = 100`），未指定时按 C# 语义自动递增；**框架不额外编号**。
- 触发器持有的不是"可增删的列表"，而是**装配期声明的 band 方案**：①未声明 → 默认枚举（框架内置、仅含 `default = 0`）；②声明 → 专门枚举（作者定义，成员即区段）。方案一经装配即**固定、运行期只读**（枚举本身编译期固定，不存在运行期改名/增删/改值）。
- 数值契约与校验义务（**装配/注册期明确拒绝**，不留给作者兜底）：
  - band 值须为**自然数**且避免打包溢出（负值、超限拒绝；建议上限 1,000,000）；
  - band 内优先级须满足 0 ≤ 内优先级 < 1000，越界拒绝；
  - 重名/同名异值由 C# 枚举编译期语义排除；**同值不同名＝别名，视作同一区段**（排序键相同）；
  - 排序键＝band 值×1000＋内优先级＋注册序，**仅排列同一触发器内的事件**（与 S3 总线层"触发器间参考优先级"是两个层面，勿混用）。

**B. 二选一保护与注册衔接（问题 1b）**

- **默认枚举方案**：注册可省略 band（只给优先级 → 落 default）；注册显式携带默认枚举成员亦合法。
- **专门枚举方案**：注册**必须显式携带该专门枚举成员**；省略 band（回落 default）**报错**；传入默认枚举成员**明确拒绝**（防混用/技术债）；专门枚举**允许含 0 值成员**（0 不被 default 独占）。——即"二选一保护"（已定）。
- 注册指定 band 的形态＝**枚举成员引用**（强类型）：未声明成员＝编译期错误，**不存在运行期"即席登记"**。
- 注册入口：**触发器公共注册 API（构造后可调用）＋构造期初始事件集合（便捷形态）**并存；注册项＝｛事件名、handler、band 成员（依方案可省）、优先级（默认 0）｝。

**C. 注册边界与一致性（问题 2a）**

- 事件可**构造期传入**、也可**构造后经注册 API 追加**（S4"注入"即基于带 band 的注册，此为本阶段必须支持的运行期追加能力）。
- 原型**不设显式冻结 API**；"除事件注册外无跨调用可变状态"＝**注册表为唯一可变面**。
- 一致性：单线程原型；执行采用执行时点的稳定视图（快照或等效），**执行期间的注册变化不影响本次迭代**。

**D. Kind 与身份（问题 2b / 2c）**

- Kind：取值＝主动/被动；**默认主动**（被动需显式声明）；S2 阶段**仅标识、无行为差异**（被动挂载留 S3）；**运行期可读**（供 S4 效果分类）。
- 触发器名称：**新增可选名称**（构造声明）；用途＝事件流 source 与调试；未命名时 source 以事件名（或类型名）退化标识。
- 事件流 source 构成：优先"触发器名/事件名"；触发器未命名时至少含事件名。
- 事件名：**允许重复**；用途＝日志/事件流定位与调试；**不承担唯一键/查重职责**（不作注册键）。

**边界补充（对抗性审视结果）**

- band 方案与 Kind 是两个独立维度（band＝事件的区段定义；Kind＝触发器的激活类型）；
- "无 band 注册方法报错"与越界（负值/超限/内优先级越界）＝装配/注册期明确异常（防技术债于早期暴露）；
- 打包溢出防护＝上限校验（示例上限 1,000,000；取值×1000＋999 的安全范围）。

### 3.3 备选方案与拒绝原因

- **备选 A**：band 用"字符串名＋独立数值表"（运行期自由增删）→ 拒绝：已定 C# 枚举；自由增删破坏"防技术债"目标。
- **备选 B**：band 值由框架按声明顺序自动编号 → 拒绝：C# 枚举可显式指定值（在"值×1000"打包下预留空隙是刻意能力）。
- **备选 C**：专门枚举方案下省略 band 时宽容回落到 default → 拒绝：违反"二选一保护"。
- **备选 D**：触发器 Kind 无默认值（必填）→ 拒绝：主动为无害默认、减少样板；且 S2 阶段无行为差异。
- **备选 E**：事件名唯一性查重 → 拒绝：名称仅供定位；查重增加装配负担、无需求支撑。
- **备选 F**：band 运行期即席登记（未声明名自动创建）→ 拒绝：与枚举强类型冲突；未声明成员应编译期拒绝。

## 四、第 3 轮：触发器公共 API 面（band 方案的类型表达、注册 API、构造形态与 S1 迁移）

### 4.1 子问题原文（摘要）

- **主问题 1**：band 方案在触发器公共面上的表达形态——(a)"装配期声明"发生何处（单泛型 vs 第二泛型/等价机制）、专门枚举如何进入静态/构造面；(b)"二选一保护"在注册 API 上的成立方式（单一签名 vs 多重载；编译期还是运行期拒绝；默认枚举公共形态）；(c) 两方案 band 参数静态类型的统一容纳方式。
- **主问题 2**：构造形态与 S1 单委托构造的迁移——(a) 构造期初始事件集合形态与完整签名方向；(b) `Trigger<TView>(Func<TView, Task>)` 旧构造的处置与 S1 测试迁移确认。

### 4.2 解答（对齐结论）

**A. band 方案的类型表达（问题 1a）**

- 触发器**保持单泛型 `Trigger<TView>`**（不引入第二泛型参数；"一个触发器一个 ContextView"的泛型方向不变）。
- band 方案经**构造面显式声明**：未声明＝默认枚举；声明＝专门枚举（构造参数携带该枚举类型——如类型引用或等价形态，具体承载方式实现择定，须满足：默认可缺省、专门需显式）。
- **方案必须显式声明**：不得由注册行为（如首个带 band 的注册）隐式推断/升级（防隐式技术债；与"二选一保护"一致）。

**B. 注册 API 与二选一保护（问题 1b / 1c）**

- 注册 API＝**同一组公共方法（双重载）**，不设两套独立注册面：
  - 无 band 重载：名＋handler＋优先级（默认 0）；
  - 带 band 重载：名＋handler＋band 成员＋优先级（默认 0）。
- band 参数采用**可容纳任意枚举成员的形态**（方向：`Enum` 基类参数或等价的泛型约束参数 `where TBand : struct, Enum`；实现择一），运行期可读取成员值与所属枚举类型做一致性校验；不引入额外接口/类型约束体系。
- "二选一保护"由**注册/装配期运行校验**实现（不依赖编译期排除；"报错/拒绝"＝注册期明确异常，错误信息需可读、可行动）。判定矩阵：
  - 默认方案＋无 band 重载 → 通过（落 default）；
  - 默认方案＋带 band 重载（默认枚举成员）→ 通过；
  - 默认方案＋带 band 重载（他类枚举成员）→ **拒绝**（提示需声明专门枚举方案）；
  - 专门方案＋带 band 重载（本枚举成员）→ 通过；
  - 专门方案＋无 band 重载 → **报错**（省略 band 被拒绝）；
  - 专门方案＋带 band 重载（他类枚举成员）→ **拒绝**。
- 框架内置默认枚举的公共形态：框架公共类型（命名如 `DefaultBands`，成员 `default = 0`；成员命名需规避 C# 关键字，实际标识符实现固化并汇报）；专门枚举由作者自行声明。

**C. 构造形态（问题 2a）**

- 构造提供**初始化形态**（方向：名称〔可选〕、Kind〔默认主动〕、band 方案〔默认缺省〕、初始事件集合〔可选〕；具体承载形状——参数列表或选项对象——实现择定）。
- 初始事件集合＝**一组公共注册项**（元素类型方向：事件名、handler、band 成员〔依方案可省〕、优先级〔默认 0〕）；构造通道与注册 API 为**等价通道**（后者为追加通道，S4"注入"的基座）。
- 单事件便捷：以新形态表达（注册项默认值/便捷构造）；**不保留旧签名兼容层**。

**D. S1 构造与测试迁移（问题 2b）**

- S1 的 `Trigger<TView>(Func<TView, Task>)`（单参、无 ctx/ct）：**由新形态取代，不保留为兼容简写**（该参数集为已声明的 S2 受控变更点；旧签名与新事件签名不兼容，保留会引入语义模糊的适配层）。
- 测试迁移**确认**：
  - 改写既有测试以适配新 API，**保持其验收语义覆盖**（共享/绑定失败/防御）；
  - "共享"语义按 S2 形态重新表述——核心为"同一执行会话内视图与全部事件共用同一 ctx 载体（Bind 直连、不拷贝）"；若实现保留显式 ctx 入口，可同时保留"同一 ctx 多次执行改写可见"的原断言（实现择定）；
  - **S1 基线以迁移后全套测试全绿为准**；迁移范围限定于适配 Trigger 新形态及其联动，其他测试与 S1 冻结面不变。

**边界补充（对抗性审视结果）**

- 方案显式声明原则：不得由注册隐式推断（见 A）；
- 注册/校验失败须为**明确、可行动的异常**（防技术债：指出来源与修正路径）；
- 旧构造删除后的**遗留引用**（示例/测试）须全部迁移，形成"单一形态"的公共面；
- 非功能性：注册与校验为装配期一次性开销，无性能要求（原型）。

### 4.3 备选方案与拒绝原因

- **备选 A**：双泛型 `Trigger<TView, TBand>` 承载方案 → 拒绝：默认场景强制显式 `DefaultBands` 泛型参数（样板噪音）；且与"保持 Trigger<TView> 泛型方向"不符。
- **备选 B**：由注册推断方案（首个带 band 注册定方案）→ 拒绝：隐式升级、顺序敏感，违背"显式声明/防技术债"。
- **备选 C**：编译期排除（两套独立注册面/仅编译期拒绝）→ 拒绝：需双类型/双注册面，公共面膨胀；运行期明确拒绝已满足保护目标。
- **备选 D**：保留旧签名兼容层 → 拒绝：旧签名（无 ctx/ct）与新事件签名不兼容；兼容层造成语义模糊与技术债。
- **备选 E**：S1 测试不迁移（允许旧构造共存以供旧测试）→ 拒绝：与 D 同因；S1 受控变更点已声明，迁移是约定动作。

## 五、第 4 轮：执行语义（嵌套链与 ctx 关系）与 Stop/Interrupt 的传播与检查点

### 5.1 子问题原文（摘要）

- **主问题 1**：嵌套触发链上 ctx 的组织与"共享 ctx"的确切语义——(a) 子执行 ctx 与调用者 ctx 的关系（独立/共享/父子关联）；验收②"共享"的覆盖层级与"跨触发器共享"的条件；(b) 嵌套关系的判定方式（框架自动感知/调用方显式关联），及其对事件流挂载与 Interrupt 传播载体的意义；(c) 嵌套链数据流是否严格显式（是否有"以父 ctx 为基础"的继承语义）。
- **主问题 2**：Stop/Interrupt 的调用入口、状态载体与检查点——(a) 入口与状态查询面、传播执行者与传播范围（起点/祖先层/兄弟分支）；(b) 检查点唯一性与停止粒度（in-flight 事件、Stop 仅本级）；(c) 组合语义（子层参与、最外层返回形态、验收⑤断言基准）。

### 5.2 解答（对齐结论）

**A. 嵌套链上的 ctx 组织与"共享"语义（问题 1）**

- **子执行 ctx 与父执行 ctx＝各自独立的数据载体**：每次执行（无论顶层或嵌套）经统一入口以数据创建自己的 ctx（一次性执行上下文）；链上仅**逻辑关联**（用于流挂载、传播、状态查询），**不共享载体**。
- **"共享 ctx"的准确覆盖范围**：验收②的"共享"＝"**同一触发器内：视图与全部事件共用同一 ctx 载体（Bind 直连、不拷贝）**"；**不**要求"嵌套链上跨触发器共享载体"。
- **数据流模型**：严格**显式传递**（不继承）——跨触发器数据由调用方经子触发器的转接/字典传入；引用实例的共享只能源于显式传入同一实例；框架**不自动**把父 ctx（或其数据）传给子执行；**不存在**"子执行以父 ctx 为基础"的继承语义。
- **嵌套关系判定（框架自动）**：由统一入口**自动感知当前执行者**（执行栈/AsyncLocal 或等效机制；执行会话入/出栈），**不要求调用方显式关联**；同一判定机制同时服务：①子流自动挂载到当前执行者的流；②Interrupt 传播的链载体；③"无父执行者时顶层挂载到 LogicEngine 总流"（栈空＝顶层）。

**B. Stop/Interrupt 的入口、传播与检查点（问题 2）**

- **入口与状态面**：均为 Context 上的方法（`ctx.Stop()` / `ctx.Interrupt()`）；"最外层调用方可查状态"＝读取**根执行 ctx** 的 Stopped/Interrupted（经传播在链上各层可见/可查）。
- **传播机制与范围（方向性）**：Interrupt 由框架沿链传播——**起点＝Interrupt 所在执行层，影响范围＝所在层及其全部祖先层**（链上仍在进行的各层在各自下一检查点停止）。单线程顺序 await 语义下无并行兄弟分支：已完成执行不受追溯影响；**已中断状态下，链上不得再启动任何新执行单元的事件序列**（新发起的子执行不执行任何事件、正常返回，视作"剩余未执行"）。
- **检查点**：**事件边界＝唯一检查点**（每层在"每个事件执行之前"检查；in-flight 事件必跑完后才停；框架不在事件中途强制打断用户逻辑）。
- **粒度确认**：
  - Stop＝仅本级（当前触发器剩余事件停止；不影响父层；**已触发的子执行照常完成**）；
  - Interrupt＝链级（所在层及其祖先层均停止剩余事件；**各层含子层**——子执行在自身事件边界检查并停其剩余事件后正常返回）。
- **返回与异常**：Interrupt 后最外层 InvokeAsync **正常返回 EventStream**（剩余事件不再执行；**不外抛异常**）；中断行为应写入事件流（供追踪）。

**验收⑤断言基准**：三类断言组合——①执行到哪（可观测执行序列：in-flight 事件已完成、后续事件未启动）；②状态（相关层 ctx 的 Stopped/Interrupted 查询结果正确）；③剩余事件未执行（未执行事件的副作用/记录缺失）。核心为②③，①辅助验证"事件边界"语义。

**边界补充（对抗性审视结果）**

- 确定性：单线程、顺序 await 下传播无并发歧义；
- 已中断状态下新执行单元的空转行为（见 B 传播范围）；
- 状态查询一致性：各层查询面与其检查点使用同一状态源（避免"可查"与"停止判定"不一致）；
- 非功能：中断/停止行为可追踪（写入事件流）。

### 5.3 备选方案与拒绝原因

- **备选 A**：嵌套链共享同一 ctx 载体 → 拒绝：各执行的数据契约由各自视图定义（契约不同）；共享载体破坏明确数据边界（防隐式依赖）。
- **备选 B**：框架自动把父 ctx/数据传给子执行（隐式继承）→ 拒绝：隐式依赖再现；与"显式转接"模型冲突。
- **备选 C**：调用方必须显式关联链（手动传父流/链上下文）→ 拒绝：与已定"自动挂载"（1.a）冲突；模板代码泛滥。
- **备选 D**：Interrupt 以异常打断 in-flight 逻辑 → 拒绝：与"事件边界协作式停止"已定语义冲突；异常污染正常控制流。
- **备选 E**：Interrupt 仅影响本级（不传播）→ 拒绝：与"沿嵌套链传播、动作链取消"已定语义冲突。
- **备选 F**：已中断后允许启动新子执行并执行完 → 拒绝：与"链取消"目标不符；留下"死后继续"的不可控路径。

## 六、第 5 轮：事件流（EventStream）——挂载、冒泡、条目规范与读/写 API 边界

### 6.1 子问题原文（摘要）

- **主问题 1**：子流挂载与冒泡语义——(a) "当前执行者"的粒度与挂载时机（执行会话级/事件级；执行结束后流是否持久保留）；(b) 冒泡的准确语义（是否递归至根、kind 范围、条目身份与顺序、祖先流增长接受度）；(c) attach 条目写入哪条流与最小信息集合。
- **主问题 2**：条目规范、公共读面与写入 API"就绪"边界——(a) level 取值域与取级规则、timestamp 基准、keywords 协议是否 S2 固定、data 用途边界；(b) 公共读 API 最小面与"便于序列化"验收底线；(c) log/update 写 API 的就绪状态、框架自动写入范围（Stop/Interrupt 覆盖）、验收⑥测试路径。

### 6.2 解答（对齐结论）

**A. 子流挂载与冒泡语义（问题 1）**

- **挂载时机与粒度**：子执行进入执行会话时，其流**自动挂载到当时的执行栈顶（触发者）的流**下；"触发者"＝**执行会话级**（非事件级）——同一执行内多个事件先后触发的多个子流，**都挂到该执行的同一父流**下。
- **持久性**：子执行结束后其流**保留**在父流下（持久树结构）；执行结束后框架不再自动写入；**不设封口**（外部/测试写入不受限，封口机制属后续演进）。
- **冒泡语义**：写入任一流的一条条目**出现在其全部祖先流中（逐级递归至根，含引擎总流）**；**kind 全量参与**（log/attach/update）；条目在祖先流中**视为同一条目**（同一逻辑记录；实现可用同一引用或等价形式），顺序＝**写入时序**；**接受**由此带来的祖先流增长（原型无裁剪/上限要求）。
- **attach 条目**：写入**父流**（挂载发生所在流；经冒泡可达祖先/总流）；子流侧关系由公共读面的"父流引用"承载（不双写）。最小信息集合＝kind(attach)＋timestamp＋source（触发者执行会话上下文：触发器/事件名）＋data｛parentId, childId｝（**父/子流 ID 为必备**）。

**B. 条目规范、公共读面与写入 API"就绪"边界（问题 2）**

- **字段规范**：
  - level：取值域**固定四档**（Debug/Info/Warning/Error；承载形式实现择定）；框架自动记录按性质取级（异常类 → Error；停止/中断 → Warning/Info 方向；同类型取级一致）；
  - timestamp：统一 **UTC**；
  - keywords：S2 固定为"**扁平字符串列表，允许 `key:value` 形式**"的协议；具体 key 词表不由 S2 固定（由使用侧/S5 工具约定）；
  - data：结构化负载，**可省略/为空**；类型以 JSON 可表达为方向（为 S5 序列化预留；原型不强制全量校验）。
- **公共读 API 最小面**：唯一 ID、**父流引用**（顶层为 null/总流侧）、**条目可枚举**、**子流可枚举**（树导航需要；顺序＝挂载时序）。
- **"便于序列化"验收底线**：**公共可枚举＋字段完备＋父/子可导航**。
- **写入 API 就绪边界**：
  - log 与 update 类别的**公共写入面存在**且可被测试调用（update 的实际接线留 S3——已定）；
  - 框架**自动写入最小集**＝attach（挂载）、异常隔离记录、**Stop 与 Interrupt 记录（两者均写**；kind=log；取级方向：Interrupt 高于 Stop）；
  - 执行中 handler 的写入通道**不作强制要求**（实现自由，不得破坏嵌套判定与冒泡语义）；
  - 验收⑥"条目含关键词"的测试路径＝**经公共写 API 写入一条含 keywords 的 log 条目**即满足；框架自动条目按各自最小集校验。
- **失败模式补充**：异常路径下**已写入条目保留**（取消上抛不要求封口/补全记录）。

**边界补充（对抗性审视结果）**

- 冒泡终止条件＝根（引擎总流）；总流归属 LogicEngine（已定）；
- 单线程语义下挂载/冒泡/顺序无并发歧义；
- 规模：原型无条目上限/采样/裁剪要求；
- 一致性：冒泡为"同一条目在祖先流的可见性"，不得改写条目内容。

### 6.3 备选方案与拒绝原因

- **备选 A**：attach 条目写入子流（子流自记"被挂载"）→ 拒绝：挂载发生在父的执行会话上下文；子流侧关系由读面（父引用）承载，避免双写冗余。
- **备选 B**：冒泡仅限 log 类别（attach/update 不冒泡）→ 拒绝：总流需完整因果记录（含挂载与更新）；选择性冒泡破坏"经触发链收集全局日志"。
- **备选 C**：冒泡为独立深拷贝记录（与源头解耦）→ 拒绝：应视为同一逻辑条目（追踪/工具需要）；深拷贝增加复杂度且易漂移。
- **备选 D**：level 采用自由字符串（无固定域）→ 拒绝：工具过滤需要固定域。
- **备选 E**：公共读面不含子流枚举 → 拒绝：树导航（追踪工具）需要。
- **备选 F**：S2 不提供公共 log/update 写入面（等 S5 再补）→ 拒绝：验收⑥（条目含关键词）需在 S2 可测；写 API 是"就绪"要求的直接内容。
- **备选 G**：执行结束后流封口禁写 → 拒绝：原型不设封口（测试/工具可补记；封口机制属后续演进）。

## 七、第 6 轮：LogicEngine 最小壳与"引擎引用"的角色（含链标识边界确认）

### 7.1 子问题原文（摘要）

- **主问题 1**："引擎引用"的公共角色与执行期可达路径——(a) 类型与语义（统一入口/Translate 首参是否同一概念；链上是否恒定）；(b) 引擎引用是否进入 ctx 数据（自动/作者经 Translate）；handler 内嵌套触发的推荐路径（ctx 取用/闭包捕获）；(c) 顶层挂载目标是否即"本次传入引擎的总流"（不依赖全局单例）。
- **主问题 2**：LogicEngine 最小壳的公共面、顶层挂载语义与链标识边界——(a) 公共成员最小集与实例化约定；触发器与引擎的关系；(b) 顶层挂载形态与总流树导航；(c) 是否严格止于"总流＋顶层挂载"；链标识（ChainId/Depth）是否落地。

### 7.2 解答（对齐结论）

**A. "引擎引用"的角色与可达路径（问题 1）**

- **类型与语义**：引擎引用＝**LogicEngine 实例**；统一入口与 Translate 首参为**同一概念**（同一类型的同一实际实例引用）。
- **链上恒定**：期望同一执行链使用**同一引擎实例**；框架**不强制校验**异例——行为定义：链中挂载**不受**引擎引用影响（恒随触发者流）；仅**顶层挂载**随"本次执行传入的引擎"（其总流）。引擎引用为必填（null 防御拒绝）。
- **执行期可达路径**：
  - 框架**不自动**把引擎引用注入 ctx 数据（**不占用/不保留键名**）；
  - 是否把引擎引用（或引擎域内共享对象）放入数据＝**作者手写 Translate 的自由**（显式数据契约；视图未声明则不可访问）；
  - handler（签名 `Task(TView, Context, CancellationToken)`，无引擎参数）内"嵌套触发"的推荐路径：**闭包捕获**（最自然）或**经 ctx 数据取用**（作者在 Translate 中放入时）——**两者皆合法**；
  - "转接的引擎引用"服务两个用途：①转接期获取引擎域内容（供数据产出）；②**顶层挂载目标**（见 B）。
- **不设全局单例**：一切经由"调用时显式传入的引擎引用"，顶层挂载目标＝该引用的总流。

**B. LogicEngine 最小壳公共面与顶层挂载（问题 2a / 2b）**

- **公共成员最小集**：**总事件流（读访问）**；顶层挂载＝框架内部自动机制（**不要求公共 API**）。
- **实例化约定**：**允许多个实例（每实例独立总流）**；**不要求单例/默认实例**；无全局单例依赖（可测试性、多域灵活性）。
- **触发器与引擎的关系**：**仅为"调用时显式传入"**——触发器**不持有**引擎引用（构造不注入）。
- **顶层挂载形式**：无父执行者时，框架**自动**把该执行流挂到"本次执行传入引擎的总流"——**调用方无需手动挂载**；先后多次顶层执行各自成流、共同挂于总流之下（兄弟顶层流）。
- **树导航**：总流为根，经子流枚举可导航完整树（任意深度）；与第 5 轮读面一致。

**C. 边界纪律与链标识（问题 2c）**

- **严格止于"总流＋顶层挂载"**：总线/Mount/Emit/UnmountOwner 等**不预埋、不出现**（S3 范围）。
- **链标识判定：不需要**——ChainId/Depth 之类**不落地**（既不作 Context 成员、也不作事件流条目字段）；链的可视表达由**事件流树结构**承担（流 ID 唯一＋父子可导航，等义且无重复真相源）。

**边界补充（对抗性审视结果）**

- 异引擎混链的行为已定义（链中不受影响、顶层随传入引擎）；原型不强制同链同引擎；
- 无引擎生命周期/清理要求（与"无裁剪"一致）；
- 引擎引用 null 防御（统一入口/Translate）；
- 元审视：子问基于的假设（引擎引用＝统一入口/Translate 首参）与已定一致，无修正。

### 7.3 备选方案与拒绝原因

- **备选 A**：框架自动把引擎引用注入 ctx 数据（固定键名）→ 拒绝：隐式依赖再现；与"显式数据契约/未声明访问拒绝"冲突；键名占用污染作者空间。
- **备选 B**：触发器持有引擎引用（构造注入）→ 拒绝：触发器应无环境依赖（调用时显式传入）；持有固化耦合、妨碍测试与复用。
- **备选 C**：单例/默认引擎实例 → 拒绝：可测试性与多实例灵活性；全局单例引入隐式状态。
- **备选 D**：顶层挂载需调用方手动 → 拒绝：与"自动感知"一致性；模板代码。
- **备选 E**：Context 增加 ChainId/Depth 字段 → 拒绝：与事件流树重复（冗余真相源）；树结构已完整承担链可视。
- **备选 F**：S2 预埋总线/Mount/Emit 空壳 → 拒绝：边界纪律（S3 范围）；预埋产生未定义行为面。

## 八、第 7 轮：异常隔离——类别判定、记录义务与取消传播（含绑定阶段失败归属）

### 8.1 子问题原文（摘要）

- **主问题 1**：异常类别判定与隔离/上抛边界——(a) "业务异常/越权/失效"的判定口径与取消类判定；(b) 绑定阶段失败的归属（隔离 vs 原样传播）与 Translate 异常的分线；(c) 取消类的穿透语义（跨层上抛、流与条目、最外层拿不到 EventStream）。
- **主问题 2**：异常隔离的记录义务与取消令牌检查义务——(a) 记录条目的硬性字段（source/message/keywords/data）；(b) 写入时机、流归属、条数与"继续"边界；(c) ct 检查义务与验收⑦认定路径。

### 8.2 解答（对齐结论）

**A. 类别判定与隔离/上抛边界（问题 1）**

- **判定口径**：隔离捕获范围＝**除取消类外的全部异常**（业务异常为任意 `Exception` 的一般情形；`PermissionDeniedException`〔越权〕、`StaleReferenceException`〔失效〕为**例举**而非穷举）；取消类判定以 **`is OperationCanceledException`（含派生，如 `TaskCanceledException`）** 为准。
- **绑定阶段失败（执行前）**：必填缺失（`KeyNotFoundException`）、声明非法（`ArgumentException`）、未标 `[ContextView]` 等 → **原样传播到调用方**（不隔离、不写隔离记录、不继续）；S1 "绑定失败跳过执行并传播"用例语义**保持**（仅随 API 适配迁移）；视图 Seal 在异常路径**不跳过**（S1 语义延续）。
- **Translate 异常**（执行前，调用侧）：按调用方异常处理（不包装、不写流——第 1 轮已定）；与绑定失败**同属"不进入隔离路径"**，但为两条独立线（Translate 在调用侧、绑定在执行启动时）。
- **取消类穿透**：任一层抛 OCE → 该层终止剩余事件、OCE 穿透其 InvokeAsync；途经的每一层**同样不隔离、继续上抛**，直至最外层调用方；期间**已写入条目保留**；最外层以 OCE 结束（**拿不到 EventStream**）。——确认。

**B. 记录义务、流归属与 ct 检查（问题 2）**

- **隔离记录硬性字段**：kind=log、level=Error、source（当前触发器/事件名）、message（异常可读摘要）、**keywords 含异常类型名**（如 `exception:{TypeName}`）；data（结构化详情）＝**实现自由**（建议含摘要；异常对象原文不强制）。
- **写入与计数**：写入**当前执行自己的流**（经冒泡祖先可见）；每次隔离**至少一条**（额外记录不禁止、不强制）。
- **继续语义**：当前层**剩余事件继续**；父层不受影响（嵌套子执行的隔离不向父上抛，子正常返回流）；**隔离不提供回滚**（已发生的 ctx 改写保留）；记录写入不得反向影响主流程（记录失败不升级为链失败）。
- **ct 检查义务**：框架**不要求主动检查 ct**（S2 已定"可暂不启用超时/取消机制"）；ct 的**透传义务成立**（统一入口 → 事件 handler 签名参数）；"取消类异常上抛"承诺＝用户代码（或其调用的子操作）抛出的 OCE 不被隔离、穿透上抛。**验收⑦认定路径＝主动 throw OCE（或等价）即可**，不要求 CTS.Cancel 场景。

**边界补充（对抗性审视结果）**

- 隔离≠回滚（控制流语义，不涉数据撤回）；
- 记录失败不反噬主流程；
- 绑定失败与 Translate 异常的分线定义（两条独立线、同属"非隔离路径"）；
- Seal 语义延续（S1 异常路径不跳过）；
- 元审视：子问基于的假设与已定一致，无修正。

### 8.3 备选方案与拒绝原因

- **备选 A**：绑定失败也被隔离（记录+跳过+返回流）→ 拒绝：契约/配置错误应早期可见（防技术债）；与 S1"原样传播"及既有测试语义冲突。
- **备选 B**：隔离范围含取消类（一律捕获）→ 拒绝：与"取消向上传播"已定冲突；吞取消破坏终止语义。
- **备选 C**：框架在事件边界主动检查 ct 并以 OCE 终止 → 拒绝：S2 明确"可暂不启用"；主动检查改变行为契约（超出本阶段范围）。
- **备选 D**：隔离记录强制携带异常对象原文 → 拒绝：序列化负担与引用泄漏风险；结构化摘要足够（实现自由）。
- **备选 E**：隔离＝回滚 ctx 改写 → 拒绝：原型无回滚机制（超范围）；隔离仅指"跳过/继续"控制流。
- **备选 F**：绑定失败写一条"隔离记录"→ 拒绝：绑定失败不属隔离路径（执行未开始）；不伪造记录类别。

## 九、第 8 轮：方法级边界语义收口与工程红线继承确认

### 9.1 子问题原文（摘要）

- **主问题 1**：方法级边界语义收口——(a) 顶层流父引用的取值与形态（与读面、attach 断言的统一口径）；(b) 空转执行是否产流/挂载、"剩余未执行"断言基准与"不启动新执行"的边界分层；(c) 多事件执行下视图实例与 Seal 的对应语义。
- **主问题 2**：工程红线继承与交付口径——(a) S1 工程红线的延续/变化；(b) S1 既有测试文件的修改边界；(c) 验收③"造成伤害"示例的断言基准。

### 9.2 解答（对齐结论）

**A. 边界语义收口（问题 1）**

- **顶层流父引用最终口径（统一第 5/6 轮两处表述）**：顶层流自动挂载到总流后，其**父流引用＝总流对象**；**总流为根**（无父）。读面形态＝**两者**：父流引用（流对象）＋每流唯一 ID 属性；attach 断言路径＝"attach 条目 data 必备 parentId/childId（值从流对象的 ID 属性读取）"。（第 5 轮"顶层为 null/总流侧"的表述以本轮为准。）
- **空转执行**：已中断状态下新发起的子执行**仍为执行会话**——产出**空流**、自动挂载到触发者流下（遵守挂载统一规则，含 attach 记录）、**不执行任何事件、不进行视图绑定**、正常返回空流。验收⑤"剩余未执行"断言以**执行序列缺失（含副作用缺失）**为准（不依赖空流形态做认定）。
- **"不启动新执行单元"的边界分层**：①**后续事件**——不被触达（事件边界检查点拦截，事件根本不开始）；②**in-flight 事件代码内**已发出的调用——**被调用但空转**（可观察）。两层面均"不执行事件"。
- **视图实例与 Seal（多事件执行）**：**一次执行（整条事件链）＝一个视图实例**（与 ctx 同构），全部事件共用；执行结束（含异常/隔离/取消路径）**Seal 一次**（幂等；异常路径不跳过——S1 语义延续）。**不是**每事件新建视图。

**B. 工程红线继承与交付口径（问题 2）**

- **工程红线（全部延续，无变化）**：不引入 InternalsVisibleTo（测试经公共面断言）；不产出 README/独立说明文档（说明归汇报）；不删除任何文件；不执行 git 提交；不使用 Source Generator。
- **S1 既有测试文件修改边界**：**允许**在同文件内重组/重写内容以适配新形态与新语义（**文件保留、不删除**；验收语义覆盖保持——第 3 轮已定）。
- **验收③基准确认**："同一主动触发器内两事件（护盾检查→伤害生效）按 band/优先级排序执行、ctx 数据随执行演进"为核心即可；具体场景形态与是否与其他验收项串联由实现组织。

**边界补充（对抗性审视结果）**

- 空转的挂载与记录遵守统一规则（不另设"静默"通道）；空转不绑定视图（无绑定失败路径）；
- 顶层口径统一后，历史轮次中的"null"表述不再单独解释；
- 元审视：子问假设（总流为事件流类型、可作根）与已定一致，无修正。

### 9.3 备选方案与拒绝原因

- **备选 A**：顶层流父引用为 null（总流经子流枚举关联）→ 拒绝：导航闭包需要"非根流皆有父"；统一为"父＝总流"最简。
- **备选 B**：空转不产流不挂载 → 拒绝：统一路径与追踪完整性（调用痕迹可观察）；产流成本低。
- **备选 C**：每事件新建视图实例（共享 ctx）→ 拒绝：与"一个触发器一个 ContextView/视图与全部事件共用"冲突；视图会话＝执行会话。
- **备选 D**：放开某条工程红线（如允许 InternalsVisibleTo）→ 拒绝：无必要，延续 S1 口径。
- **备选 E**：S1 测试文件只能新建不能改写 → 拒绝：适配新 API 需同文件重组；文件保留＋验收语义不变已足够。

## 十、第 9 轮：Trigger<TView> 开放性定夺与终极复查

### 10.1 子问题原文（摘要）

- **主问题 1**：Trigger<TView> 的继承/封闭开放性——(a) 最终定夺（保持 sealed / 开放继承）及受控变更说明；(b) 若 sealed，具名重载的认可书写形态；(c) 若开放，继承者的书写契约方向。
- **主问题 2**：终极复查——(a) 各轮结论的矛盾/表述不一排查与统一（含指定两案例）；(b) Requirements 与验收 7 项漏项核对；(c) 验收证据数量与形态底线、实现择定项处置约定。

### 10.2 解答（对齐结论）

**A. Trigger<TView> 继承开放性（问题 1）**

- **定夺：开放继承**（取消 `sealed`）——作为 S4"继承＝额外注入 handler 途径"的基座；属 S2 **受控变更**范围（Trigger 壳形态的一部分，与"参数集受控变更点"同源）。
- **继承者契约（方向）**：
  - 执行与流产出**不得绕过公共执行入口**（统一入口路径为唯一执行面）；
  - 注册/校验**仍走公共注册面**（不得旁路）；
  - **不引入新的跨调用可变状态面**（注册表为唯一可变面；子类只应增加不可变配置/行为）；
  - 泛型约束不破坏（一个触发器一个 ContextView；TView 恒定）。
- **默认路线重申**：效果组装默认**实例化**；开放继承仅服务"额外注入"路线；具名重载载体自由度不变（子类/包装类/调用侧代码任选；验收④证据以任一形态呈现均可）。(b) 情形（若 sealed 的形态约束）因定夺为开放继承而**不适用**。

**B. 终极复查（问题 2）**

- **（a）表述统一（本轮修正，共 2 处）**：
  1. **source 构成统一**：所有框架写入条目的 source 统一按"触发器名/事件名"构成；触发器未命名时退化为事件名（或类型名）；**attach 条目的 source 亦为此构成**（其 data 另含 parentId/childId）。（合并第 2 轮 D 段与第 5 轮 attach 表述）
  2. **执行面统一**：对外公共执行面**唯一＝统一入口**（InvokeAsync 重载族）；旧 `RunAsync` 的对外调用面已被取代（**不保留为对外形态**）；实现内部的等价路径属内部细节、不构成公共面（单一形态公共面原则；与第 3 轮测试迁移口径一致）。
  - 其余逐项核对：**未发现新的矛盾**。
- **（b）Requirements 与验收 7 项漏项核对**：**无其他补充**。（两点易误认为漏项者已在相关轮次注明：①"更新写入事件流"在 S2 仅要求写入 API 就绪、实际接线在 S3；②空转执行不以流形态为断言对象、以执行序列缺失为准。）
- **（c）验收证据底线（确认）**：沿用 S1 口径——测试方法命名/数量/文件组织由实现自定；"测试方法→验收点映射清单可完整指认"即达标；**无硬性数量要求**。**实现择定项处置约定（确认）**：API 命名、默认值等"实现择定"项——**最小化＋汇报记录**；如遇与已定口径冲突的问题，**暂停并反馈**（不得自行放宽）。

### 10.3 备选方案与拒绝原因

- **备选 A**：保持 sealed（继承路线由包装类承载）→ 拒绝：与 S4 已定"继承＝额外注入途径"（用户亲定）冲突；包装类承载"继承"语义失真。
- **备选 B**：开放继承且无契约约束 → 拒绝：可能绕过公共执行面/注册面，破坏"注册表唯一可变面"与单一公共面。
- **备选 C**：source 两套规则（事件条目/attach 各表）→ 拒绝：统一为同一构成规则更简（attach 无特殊化必要）。
- **备选 D**：保留 RunAsync 为对外兼容面 → 拒绝：与"单一形态公共面"及测试迁移口径冲突。
- **备选 E**：对测试证据设定硬性数量要求 → 拒绝：无必要；S1 口径（映射可指认）已足够。
- **备选 F**：实现细节授权项可自行放宽口径 → 拒绝：须最小化＋汇报；口径冲突应暂停反馈。
