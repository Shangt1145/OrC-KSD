# 需求 — 触发器引擎原型

为 Godot C# 游戏提供后端逻辑引擎（ECS 组件式风格）的"原型"：按设计文档规定的简化级别落地核心框架，作为后续迭代地基。本需求定义其定位、范围与完成标准，作为敲定开发阶段划分的依据。（对齐中，随 grill 逐轮沉淀。）

## Scope
- Includes:
  - 触发器引擎核心机制（设计文档全量核心）：生命周期引用（Ref/Lifetime）、上下文（Context）、声明式视图（ContextView）、触发器（Trigger）、总线（TriggerBus）、优先级、异步/超时/中断、日志。
  - 用户骨架（2026-10-03 第 1~8 轮澄清）：
    - **卡牌**：组件的容器。
    - **数据组件**：游戏内强类型类 + 类主导的外部 JSON 序列化/反序列化，可产出序列化快照。
    - **逻辑组件＝效果**（术语合并）：挂在卡牌上的逻辑封装；组成＝主触发器＋附带的逻辑引用。主触发器为主动 → **主动效果**（法术/一次性效果等）；为被动 → **被动效果**（可能与场上单位绑定）。
      - 挂载：把其被动触发器挂载到总线；挂载逻辑同时 hook"效果移除"并注册专属移除逻辑（如清除引用等）。
      - 示例"攻击时回血"（被动效果）：主触发器 hook"卡牌部署更新"→ 单位初始化后注入回血 handler 到攻击触发器对应位置；hook"效果移除"→ 取消注册、清理。
      - 注册/注销属模板代码，需工具化。
    - **逻辑引擎**：①维护总线驱动逻辑；②产出事件流并从引用提供快照，供 UI 端消费。
    - **总线**：只负责广播更新（如"卡牌数据更新"），是中间层，不做逻辑编排。
    - **触发器**：逻辑的起点（主动/被动）；**内部注册多个事件、按优先级顺序触发**；一个触发器只有一个 ContextView，产出的 ctx 被全部事件共用（解决"引用隐式依赖"，用户称"关键设计"）。
    - **事件**：原子逻辑 = handler；可改写 ctx 数据；事件内可触发其他触发器。
    - **ContextView（=转接器）**：触发器唯一数据契约；接收引擎引用与额外参数，产出 ctx。主动触发器触发函数可重载（支持传入额外参数），其 ContextView 负责转接。
    - **Hook**：时机点；触发器内部维护 hook 列表；被动触发器借此挂载在总线上。
    - **更新**：总线广播的消息，如"卡牌部署更新""卡牌销毁""卡牌数据更新""效果移除"。
    - **编排演进**：原型阶段用硬编码编排（C#）；后续开发 csx/gds 脚本接口 + 继承模式。效果 = 继承通用触发器（如攻击触发器，含反制/护盾等标准编排）+ 注入自己的 handler。
  - 执行结构示例（用户给出）："造成伤害"主动触发器被激活 → 内部事件 [护盾检查和结算（优先级高）→ 伤害生效] 按序执行 → ctx（ContextView 定义"伤害数字"字段）被改写 → 触发更新（如"卡牌数据更新"）。
  - 输出/交互契约（第 7~8 轮）：
    - 程序只产出事件流 + 数据快照，供外界消费（原始需求）。
    - 四种接口形式都要：①通过 C# 桥接主动调用外部 API；②暴露 API 供外部调用；③回调模式；④产出各种 JSON。
    - **原型阶段仅完善 JSON 模式，其余三种只做骨架。**
    - **JSON 模式覆盖范围（第 8 轮确认）：a. 事件流输出 + b. 数据快照输出**（数据组件载入、日志 JSON 不在本次完善范围）。
  - 原型验证载体（第 8 轮确认）：**测试集承载全部演示场景**——场景 1（火球/护盾/反制/中断）、场景 2（攻击时回血）、场景 3（部署/移除链路）。
- Excludes: （待对齐——设计文档非目标：游戏规则本身/网络同步/UI；脚本化编排与完整工具化属后续演进）

## Constraints
- 语言/平台：C# (.NET 8+)；面向 Godot C# 游戏（引擎为后端类库）。
- 架构风格：ECS（组件式；用户称"Unity 的 ECS 架构"，具体所指待澄清）。
- 原型简化级别（设计文档 MVP 级）：反射视图 / 单线程 / Task。
- 输出纯净性：只产出事件流与数据快照，无 UI/渲染耦合。
- 原型阶段编排方式：硬编码（C#）；脚本化（csx/gds）+ 继承模式为后续演进。
