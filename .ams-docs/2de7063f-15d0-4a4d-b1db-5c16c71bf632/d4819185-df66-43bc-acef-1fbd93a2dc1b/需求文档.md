# 游戏环境第一批（对局骨架）— 需求阐明记录

> 委托目标：在 Orc 引擎之上新增 Orc.Game（对局骨架：集合类/基础数据组件/卡牌库/战场/玩家/对局 Match 与管理器/回合体系/通用更新）。本记录通过 grill 逐轮沉淀需求阐明（功能职责、约束、验收标准、已解决歧义）。
> 轮次：第 1 轮——对局装配与初始化流程（2026-10-03）。

## 一、对局装配与初始化流程（第 1 轮）

### 子的问题（原文）

> 【主层·对局装配与初始化流程】委托写道："对局 Match：持有 LogicEngine 实例、双玩家、回合数、当前行动方、状态（准备/进行）、战场、随机源（种子可传、可复现）；初始化＝生成并初始化管理器群（回合/玩家/战场/资源/卡牌库）；初始化完成后为先手发起回合开始序列（见下），并完成起手牌装载（先手 4 / 后手 5，静默、不发更新）。"我对"一个对局从被创建到进入'进行'状态"的完整接线还无法确定，请阐明：
>
> 1）对局创建的输入与装配责任：创建一场对局时，玩家与双方卡组名单由谁提供（作为 Match 的创建参数传入？还是先创建玩家、由外部装填卡组后再交给 Match？）；卡牌库注册（id→定义的代码注册）发生在对局创建的哪个时点、由哪个对象暴露注册入口？先手玩家如何确定（固定为先建的一方？创建参数指定？还是由随机源决定？）
>
> 2）初始化的触发形态与"准备/进行"语义：初始化是随 Match 构造自动完成的，还是有独立的初始化调用？"准备/进行"两个状态各自对应什么时点（创建后未初始化=准备？初始化完成=进行？），以及本批是否会存在其他状态。
>
> 3）初始化内的两件事的先后与时序：起手牌装载（先手 4 / 后手 5，静默）与"为先手发起回合开始序列"的先后顺序是什么；初始化时发出的更新序列是否就是先手回合的 turn.start.before → turn.start → turn.start.after 三条（第 1 回合不抽牌、故无 card.drawn）？

### 父的解答

**1）输入与装配责任**

- **装配模式＝调用方提供数据、Match 负责装配**。玩家由 Match 初始化时统一创建（资源初始值、卡组＝传入名单、手牌空、HQ 20 血）。
- **创建输入（Match 创建参数）**：①双方卡组名单（CardList）×2；②卡牌定义集（批量，用于注册卡牌库）；③可选随机种子（可复现）；④可选先手指定（默认第一位玩家）。
- **卡牌库**：属对局内管理器，由初始化生成；**注册入口在卡牌库实例上**（`Register(id, definition)`）；初始化时以上述定义集**批量注册**；运行期增量注册本批不强制（也不禁止）。
- **先手**：**创建参数显式指定，默认第一位玩家**（测试需可控、可复现）。
- **引擎**：创建时**内部新建 LogicEngine 并公开**（外部经 `match.Engine` 访问总线/总流以订阅更新）。

**2）初始化形态与状态**

- **两步式：创建 → 显式 `Initialize()`**（初始化完成置为"进行"）。
- **状态语义**：准备＝已创建、未初始化（数据已装配；无管理器、无玩家、无更新）；进行＝初始化完成、回合可推进。**本批仅此两态**（"结束"态随胜负批次引入）。
- **失败模式**：重复 `Initialize()` **抛错**（明确拒绝、非幂等）；初始化中异常**直接传播**、对局保持"准备"态（不承诺回滚；失败可重建对局）；创建参数为 null 等无效输入 → 参数校验异常。
- **状态门禁**：回合推进（EndTurn 等）**仅在"进行"态允许**；"准备"态调用应抛错（与重复初始化处理口径一致）。

**3）初始化内时序**

- **先后顺序：起手牌装载（静默）→ 先手回合开始序列**（装载属"准备"收尾；回合序列属"第 1 回合进入"）。
- **初始化期更新序列＝恰好 3 条**：`turn.start.before` → `turn.start` → `turn.start.after`（先手第 1 回合：槽＝1、点数＝1、不抽牌 → 无 `card.drawn`）。
- **更新入流**：初始化期无执行帧 → 3 条更新写入引擎**总事件流**（与既有"边界 Emit→总流"语义一致）。
- **顺序保证**：三条更新按序（顺序 await）完结后 `Initialize()` 才返回；其后由外部调用推进（EndTurn）。
- 边界：卡组不足起手张数时，按既有的"抽取空集合行为"约定处理（实现者定义并汇报）。

### 备选方案与拒绝原因（汇总）

1. 外部预建玩家再交 Match——装配责任分散、半初始化风险 → 拒；
2. 构造即完成全部初始化——外部无法先挂订阅（初始化期更新不可断言）、"准备"态不可测 → 拒；
3. 先手由随机源决定——测试不可控 → 拒（留后续批扩展）；
4. 外部传入 LogicEngine——装配面扩大、本批无需求 → 拒；
5. 重复 Initialize 幂等——语义模糊（调用方意图可能是错误）→ 拒，采用抛错。

## 需求要点汇总（滚动）

- **对局（Match）职责**：承载双玩家/回合序/战场/管理器群（回合/玩家/战场/资源/卡牌库）；对外暴露引擎与总线访问；统一负责装配与初始化；状态机仅"准备→进行"。
- **初始化流程步骤**：生成管理器群 → 注册卡牌定义（批量）→ 创建玩家（含 HQ）→ 双方卡组洗牌 → 起手装载（静默，先手 4 / 后手 5）→ 先手回合开始序列（3 条更新入总流）→ 置"进行"。
- **数据流**：创建参数（卡组名单×2、定义集、[种子]、[先手]）→ 初始化装配 → 更新经总线 Emit（初始化期入总流）。
- **失败模式**：无效创建参数 → 校验异常；重复初始化 / 准备态推进 → 抛错；初始化异常传播不吞。
- **玩家容器与抽牌**（第 2 轮）：卡组（名单）＋ 手牌（引用集）＋ 资源/HQ；抽牌链路＝卡组（名单）取首张并移除 → 经卡牌库实例化 → 入手牌；洗牌＝初始化内自动（装载前、传对局随机源）；`card.drawn` 载荷＝{ 玩家, 卡牌实例 }。
- **管理器群**（第 3 轮）：领域单一真源＋Match 协调转发（回合数/当前方→回合管理器；玩家→玩家管理器；战场→战场管理器；结算→资源管理器；定义/实例化→卡牌库）；`match.EndTurn()` 无参、门禁；五管理器公开；准备态访问抛错；无共同基类；资源初始＝槽 0/点数 0（统一 +1）。
- **回合循环精确序列**（第 4 轮）：回合开始处理＝结算→抽牌，执行于 `turn.start` 与 `turn.start.after` 之间（`card.drawn` 在此间发出）；回合结束处理＝`turn.end` 后清零点数；`Initialize`/`EndTurn` 返回即全部结算与更新完结；场景断言全集＝初始化 3 条＋第一循环 6 条（共 9 条）；抽牌例外＝仅先手第 1 回合不抽。
- **HQ 与战场三线**（第 5 轮）：HQ＝玩家纯数据（20 血、可读、无修改入口、不落位；"占支援线一格"＝设计预留）；战线固定归属＋按玩家查询支援线、前线中立共享；初始化后三线空集；容量 4/5/4 可读（位置实现者定、校验后置）。
- **可配置性与可复现**（第 6 轮）：指挥点上限＝创建期可选配置（默认 12、正整数校验；封顶验证推荐小上限路径）；战线容量/手牌上限＝可读（不可配置）、起手张数＝固定值；可复现＝同种子＋同参数逐位一致（洗牌/起手/抽牌）、纳入测试、实际种子可读。
- **集合类 API 面**（第 7 轮）：装填（单/批量）＋读面（可枚举/Count）为要求；边界收口——Insert 越界抛错、CardSet 保持顺序且拒绝重复实例、Instantiate 纯转换（空→空集/未注册抛错/重复→独立实例、保序）、空集 Draw 抛错；元素＝string id / Orc Card；命名与签名实现者定型并汇报。
- **卡牌库与基础数据组件**（第 8 轮）：定义＝名称＋四数值（id 由注册键）；重复注册拒绝、null 校验、数值域校验后置；基础数据组件＝单类四整数、走 AddData、纯数据；实例化＝Card＋组件装配（名称取自定义）；查询读面＝存在性（不抛）/取得（未注册抛错）/枚举（可选）。
- **更新常量与发射 API**（第 9 轮）：单一常量类承载 8 条（turn 五连＋card.played/drawn/stat.changed；字面值原样、均新定义、字面值冻结）；发射统一走总线 Emit（不强制发射助手）；card.played 载荷后置、stat.changed 无载荷为硬约定；played/stat.changed 零调用点（存在性验证）。
- **测试与构建验证口径**（第 10 轮）：验收对象＝OrcEngine.sln（显式、全解决方案、三测试项目均跑；slnx 保持不动）；回归＝既有用例数不减少（156/157 下限）且全绿；锚点每项 ≥1 测试、边界清单 5 条逐条覆盖；0 警告＝努力目标。
- **玩家对象与结构自由度**（第 11 轮）：玩家＝普通对局数据类（不强制 Entity）、读面直接可读；命名/密封性/文件组织实现者定；空名单创建期拒绝、不足起手走运行时抛错、先手非法与空白 id 创建期拒绝。

## 二、卡组形态与抽牌流程（第 2 轮）

### 子的问题（原文）

> 【主层·卡组形态与抽牌流程】第 1 轮已确认：创建参数含双方卡组名单（CardList）×2；初始化步骤为"生成管理器群 → 注册卡牌定义 → 创建玩家（含 HQ）→ 起手装载（静默）→ 先手回合开始序列"。但我对"名单→实例→抽牌"的数据流转还有歧义：委托规定"玩家：卡组（CardList）＋手牌（CardSet）"，且集合类中"CardList.Instantiate（cardLibrary）→ CardSet（名单到引用集的实例化）"、"两者均提供 Shuffle / Insert / Draw（取首张并移除）"。请阐明：
>
> 1）玩家"卡组"字段的最终形态：创建时传入的 id 名单（CardList）在初始化中是否被实例化为卡牌实例集（CardSet）？若是，实例集是否就是实际抽牌用的"牌库"——它挂在玩家的哪个位置（如玩家的牌库字段），还是名单本身保留、另有实例集；玩家最终同时持有哪些容器（名单 / 实例牌库 / 手牌）？
>
> 2）洗牌的对象与时点：洗牌作用于 id 名单还是卡牌实例集？在初始化的哪个环节执行、由谁触发（初始化内自动洗，还是由调用方显式调用）？"对局级随机源"如何抵达集合的洗牌操作（洗牌方法接收对局随机源作为输入吗）？
>
> 3）抽牌源与落点：起手装载（先手 4 / 后手 5）与回合抽牌（抽 1）分别从哪个容器抽（取首张并移除）、抽出的卡落入玩家手牌（CardSet）；"先手第 1 回合不抽"在初始化序列中即表现为"无抽牌动作、无 card.drawn"（已在第 1 轮确认）；请顺带确认：后手的第一次回合（全局回合 2）照常抽 1。

### 父的解答

**1）玩家"卡组"字段形态＝名单（不做全量实例化）**

- 玩家"卡组"字段＝CardList（名单），与"卡组是卡牌名单"既定表述一致；初始化中**不做全量实例化**、**不引入额外的"牌库"字段**。
- 名单即"剩余可抽的牌"：抽牌时从名单**取首张并移除**（消耗名单）；抽出的 id **逐张实例化**（经卡牌库）后落入容器。
- 玩家最终持有的容器：**卡组（CardList）＋ 手牌（CardSet）＋ 资源/HQ**（无"实例牌库"层）。
- CardList.Instantiate（名单→引用集）保留为**通用能力**（含测试覆盖），非本批主流程路径。

**2）洗牌：对象＝名单；时点＝初始化内自动；随机源传入**

- 洗牌对象＝卡组（名单）——打乱剩余牌的 id 序列。（引用集等亦可洗：通用能力。）
- 时点与触发：**初始化流程内自动执行**（双方卡组；位于"创建玩家"之后、"起手装载"之前）；无需调用方显式触发。
- 随机源抵达：**洗牌方法接收对局随机源作为输入**（Shuffle(random)）；初始化流程把对局随机源传给双方卡组；集合类自身不持有随机源。

**3）抽牌：源＝卡组（名单）；落点＝手牌（CardSet）**

- 起手装载与回合抽牌同一链路：**卡组（名单）取首张并移除 → 经卡牌库实例化 → 加入玩家手牌**。
- 起手装载：先手 4、后手 5；静默（不发更新）。
- 回合抽牌：抽 1，发 card.drawn；先手第 1 回合不抽（无动作、无更新）——**确认：后手第一次回合（全局回合 2）照常抽 1**。
- 顺带明确（父）：card.drawn 载荷＝{ 玩家, 卡牌实例 }。
- 边界：卡组为空按既有"Draw 空集合"约定（实现者定义并汇报）；名单含未注册 id → 实例化抛明确错误（配置错误不吞）；手牌上限本批仅字段存在、不做超限裁决（弃置后置）。

### 备选方案与拒绝原因

1. 初始化全量实例化（名单→牌库实例集；玩家持"牌库＋手牌"）——与"卡组是卡牌名单"既定表述冲突、多一层容器、本批无收益 → 拒；
2. 洗牌由调用方显式触发——开局洗牌为对局标准动作，初始化内自动更不易错（且第 1 轮已承诺初始化全流程） → 拒；
3. 集合类构造注入随机源——随机源属对局级，集合保持"方法传参"更清晰 → 拒（采用方法传参）。

### 第 2 轮新增确认需求点

- 玩家容器＝卡组（名单）＋手牌（引用集）；抽牌链路＝名单移除→实例化→入手牌；
- 洗牌＝初始化内自动（装载前、双方、传随机源）；
- card.drawn 载荷＝{ 玩家, 卡牌实例 }；空卡组 / 未注册 id / 手牌超限 边界口径如上。

## 三、管理器群职责与使用面（第 3 轮）

### 子的问题（原文）

> 【主层·管理器群职责与使用面】委托写道："对局 Match 与管理器群（回合/玩家/战场/资源/卡牌库）"、"初始化＝生成并初始化管理器群（回合 / 玩家 / 战场 / 资源 / 卡牌库）"，以及"回合体系（核心）：结束回合 API＝EndTurn（当前方）"。第 1 轮已确认 Match 外露引擎（match.Engine）与状态门禁（进行态才可推进回合），但管理器群的职责边界与使用面仍未阐明。请阐明：
>
> 1）五个管理器各自的职责边界：回合管理器 / 玩家管理器 / 战场管理器 / 资源管理器 / 卡牌库（管理器）分别负责什么，彼此如何分工——例如：回合数与当前行动方归哪个对象管理；指挥点结算（槽+1、点数=槽值）由谁执行；双玩家对象与战场三线由谁持有、谁负责创建；"生成并初始化管理器群"中每个管理器的初始化动作是什么？
>
> 2）使用面归属与访问路径：EndTurn 由谁暴露（Match 直接暴露还是经回合管理器）、"当前方"在调用形态中如何体现（无参自动取当前方？）；测试与调用方访问双玩家、战场三线、回合数、当前行动方、对局状态时，经 Match 的直接属性还是经管理器逐层获取；五个管理器本身是否需要对外可访问（如测试断言"5 管理器就绪"时的访问方式）。
>
> 3）命名与结构自由度：管理器类名、属性名、文件组织是否定型自由（实现者定型并汇报），还是需遵循既有命名惯例（如 XxxManager 后缀）；管理器是否都具备可辨识的公共类型形态（如共同的基类/接口）——还是各自独立类即可。

### 父的解答

**1）职责划分＝领域单一真源＋协调编排**

总原则：**每个领域一个管理器（单一真源），Match 为聚合根与协调者**（不复制状态；转发属性不得缓存）。

| 管理器 | 领域真源 | 职责（本批） | 初始化动作 |
|---|---|---|---|
| 回合管理器 | 回合数、当前行动方 | 回合推进编排（EndTurn：发 turn.end.before/end → 切换当前方、回合数+1 → turn.start.before/start/after）；turn.start 内**调用**资源结算与抽牌 | 置回合数＝1、当前行动方＝先手；发起先手回合开始序列 |
| 玩家管理器 | 双玩家对象 | 创建玩家；提供玩家访问；**抽牌操作**（卡组取首张 → 经卡牌库实例化 → 入手牌） | 创建双玩家（资源初始：槽＝0、点数＝0；卡组＝传入名单；手牌空；HQ 20） |
| 战场管理器 | 战场（三线 CardSet） | 创建/提供三线访问（容量配置 4/5/4） | 创建三条空战线 |
| 资源管理器 | （无独立状态；规则服务） | 指挥点结算（对玩家：槽+1 至上限 12 → 点数＝槽值）；回合结束不保留处理 | 载入配置（上限 12 等） |
| 卡牌库 | id→定义注册表 | 注册/查询/实例化（id→Card） | 批量注册创建参数中的卡牌定义集 |

- **指挥点结算的执行者＝资源管理器**（由回合管理器在 turn.start 内调用）；**抽牌的执行者＝玩家管理器**（同被回合管理器调用）。
- **口径澄清（重要）**：玩家资源初始值＝**槽 0、点数 0**；第 1 回合结算执行"槽+1"后即 1、点数＝1——即"第 1 回合＝1 点"由"统一 +1 结算"达成，**无特例分支**；上限 12 一致。
- **初始化全程（管理器视角）**：生成管理器群 → 卡牌库注册 → 玩家管理器创建双玩家 → 双方卡组洗牌（由流程调用，传随机源）→ 起手装载（经玩家管理器抽牌，静默）→ 回合管理器发起先手回合开始序列 → 置"进行"。

**2）使用面归属与访问路径**

- **EndTurn**：主路径＝**`match.EndTurn()`**（Match 便捷入口，转发回合管理器同语义方法）；**无参、自动取当前行动方**；门禁：仅"进行"态可调用（准备态抛错）。
- **便捷转发读面（Match 上）**：`Players`（→玩家管理器）、`CurrentPlayer` 与 `TurnNumber`（→回合管理器）、`Battlefield`（→战场管理器）、`State`（Match 自身）；**转发只读、不得复制状态**。
- **管理器访问**：五个管理器**对外公开**（如 `match.TurnManager` / `match.PlayerManager` / `match.BattlefieldManager` / `match.ResourceManager` / `match.CardLibrary`）——测试断言"5 管理器就绪"经此；细粒度操作（如后续批的战斗能力）走管理器通道。
- **准备态行为**：管理器尚未生成，准备态访问管理器（含转发属性）**抛错**（与状态门禁口径一致）。
- 备选（拒）：EndTurn 仅经管理器（主路径不顺手）；仅经 Match、管理器不公开（测试与后续扩展不便）。

**3）命名与结构自由度**

- 类名/属性名/文件组织：**实现者定型并在汇报中列出**（建议沿用既有风格；"XxxManager"后缀可选、非强制）。
- 管理器**无需共同基类/接口**：各自独立类即可（本批无多态使用场景）；"管理器"为概念称谓。
- 命名自由度上限：对外可见的 **Match 便捷属性与控制流语义**（EndTurn 无参、状态门禁、转发只读）须符合本记录；其余自由。

### 备选方案与拒绝原因

1. 状态放 Match、管理器仅作服务——职责表述绕（管理器操作他处数据）、易生双份真源 → 拒（采用"管理器单一真源＋Match 转发"）；
2. 共同基类/IManager 接口——本批无使用场景、过度抽象 → 拒；
3. EndTurn 提供"指定玩家"重载——无需求、易误用（回合语义天然只作用于当前方） → 拒；
4. 管理器在创建期生成、初始化仅配置——与既定"初始化＝生成并初始化管理器群"表述不符 → 拒。

### 第 3 轮新增确认需求点

- 单一真源＋协调：回合数/当前方→回合管理器；玩家→玩家管理器；战场→战场管理器；资源结算→资源管理器；定义/实例化→卡牌库；
- 结算与抽牌的执行者：资源管理器 / 玩家管理器（回合管理器在 turn.start 内调用）；
- 资源初始口径：槽 0/点数 0 + 统一 +1；第 1 回合＝1、无特例；
- 使用面：match.EndTurn()（无参、门禁）；便捷转发只读；五管理器公开；准备态访问抛错；
- 命名/结构：实现者定型（汇报列出）；无共同基类。

## 四、回合循环与更新序列的精确期望（第 4 轮）

### 子的问题（原文）

> 【主层·回合循环与更新序列的精确期望】委托写道："发 turn.end.before → 发 turn.end（结束处理）→ 切换当前方、回合数+1 → 发 turn.start.before → 发 turn.start（内含：指挥点结算＋抽牌）→ 发 turn.start.after"，且验收锚点②要求"回合循环：5 个 turn 系列更新按序广播（可订阅断言）"、锚点⑤要求"骨架场景端到端（初始化→回合 1 开始→结束→回合 2→更新序列与资源数值断言）"。第 3 轮已确认 turn.start 内由回合管理器调用资源结算与抽牌，但更新到达订阅者的精确序列仍是验收断言的空白，请阐明：
>
> 1）一次 EndTurn 的完整广播序列期望：从"回合 1 先手结束、进入回合 2 后手"这一回合循环为例，订阅者应观察到的确切更新顺序是什么？特别是 card.drawn（回合 2 后手抽 1）相对 5 条 turn 系列更新的位置——是 turn.start.before → turn.start → card.drawn → turn.start.after 这样的插入位置，还是只要 5 条 turn.* 的相对顺序正确、card.drawn 位置不作硬性约定？
>
> 2）结算与更新的先后观测语义："turn.start（内含：指挥点结算＋抽牌）"应如何理解——指挥点结算（槽+1、点数=槽值）与抽牌动作发生在 turn.start 更新广播之前、之后、还是广播处理链中的某个位置；资源数值断言在 Initialize()/EndTurn() 返回后观测是否即已就绪（即 API 返回时全部结算与更新已完结）。
>
> 3）骨架场景的序列断言范围：锚点⑤"更新序列断言"期望覆盖哪些更新（是完整全集——初始化 3 条 + 第一循环 5 条 + card.drawn，还是仅 turn.* 系列）；订阅断言所用的订阅渠道是否为对局公开的引擎/总线（第 1 轮已确认 match.Engine 公开）。

### 父的解答（对"内含"的精确化——"信号先行、处理随后"模型）

**总模型**：turn 系列更新＝"阶段信号"；**回合开始处理**（结算→抽牌）与**回合结束处理**（点数清零）＝"信号之间的静默动作段"（其中仅抽牌产生更新 card.drawn）。

**1）一次 EndTurn 的完整观测序列**（以"回合 1 先手结束 → 回合 2 后手"为例）

```
turn.end.before        （回合结束前）
turn.end               （回合结束信号）
[回合结束处理：结束方点数清零（槽保留）——静默]
切换当前方、回合数+1   （静默）
turn.start.before      （新回合开始前：尚未结算、未抽牌）
turn.start             （回合开始信号）
[回合开始处理：资源结算（槽+1 至上限 → 点数＝槽值；静默）→ 抽牌（后手第 1 次回合照抽 1）]
card.drawn             （当回合需抽牌时发出；无需抽牌时此条不存在）
turn.start.after       （回合开始处理完成后）
```

- **card.drawn 的位置有硬性约定**：位于 `turn.start` 之后、`turn.start.after` 之前（插入式）；资源结算为静默动作（无独立更新），其效果经资源数值观测。
- 回合循环的 turn 系列固定 5 条（end.before → end → start.before → start → start.after）；card.drawn 视"该方当回合是否需抽牌"出现。

**2）结算与更新的先后观测语义**

- "turn.start（内含：指挥点结算＋抽牌）"的准确含义＝**结算与抽牌在 `turn.start` 与 `turn.start.after` 两条更新之间执行**（先结算、后抽牌；均先于 after 通知）。
- **API 返回时序**：`Initialize()` 与 `EndTurn()` 返回时，**全部结算与更新（含顺序 await 的广播链）均已完结**——资源数值断言在返回后观测即为就绪终值（无需等待/轮询）。
- 补明确（父）：**回合结束处理＝将结束方"当前点数"清零**（槽保留）；"不保留"由此在回合结束点上可观测地达成。
- 补明确（父）："先手第 1 回合不抽"为唯一抽牌例外；**自回合 3（先手第二次回合）起，双方每回合均抽 1**。

**3）骨架场景的序列断言范围**

- 断言覆盖**完整全集**（共 9 条可观测更新）：
  - 初始化＝3 条：`turn.start.before` → `turn.start` → `turn.start.after`（先手第 1 回合：无 card.drawn）；
  - 第一循环＝6 条：`turn.end.before` → `turn.end` → `turn.start.before` → `turn.start` → `card.drawn` → `turn.start.after`（后手第 1 次回合照抽 1）。
- 订阅渠道＝**对局公开的引擎/总线**（`match.Engine`；测试在 `Initialize()` 前挂订阅——两步式设计已保证可行）。
- 资源数值断言点：API 返回后观测（如初始化后：先手槽＝1、点数＝1；循环后：后手槽＝1、点数＝1，先手点数已清零；手牌数同步）。

### 备选方案与拒绝原因

1. card.drawn 位置不作硬性约定（仅保 turn 系列相对序）——验收断言需精确序列，模糊约定会导致实现分歧 → 拒（采用插入式硬性约定）；
2. 结算发生在 turn.start 之前（start＝"处理完成后"信号）——与 after 语义重复、before/start/after 三连信号模型不成立 → 拒；
3. 结算/抽牌发射独立更新（如 credits.changed）——本批无需求、扩大更新面 → 拒（保持静默动作，需要时后续批扩展）；
4. 回合结束不清零、依赖下回合重设——非当前方点数读数不明确（"不保留"在结束点不可观测） → 拒（采用 turn.end 后清零）。

### 第 4 轮新增确认需求点

- 处理序模型：信号先行、处理随后；开始处理（结算→抽牌）在 start 与 after 之间；结束处理（点数清零）在 turn.end 之后；
- card.drawn 精确位置：`turn.start` 之后、`turn.start.after` 之前（当回合需抽牌时）；
- API 返回即全部完结（无异步残留）；
- 场景断言全集＝初始化 3 条＋第一循环 6 条（共 9 条），经 `match.Engine` 总线订阅；
- 抽牌例外规则收口：仅"先手第 1 回合"不抽，其余照抽。

## 六、可配置性与可复现性（第 6 轮）

### 子的问题（原文）

> 【方法级·可配置性与可复现性】委托中多处出现"配置/可配置/可复现"表述："指挥点结算＝槽+1（至上限 12，可配置）"、"随机源（种子可传、可复现）"；同时"容量配置字段＝4/5/4"、"手牌上限 9（仅字段存在）"。请阐明这些数字项与随机性的验收口径：
>
> 1）指挥点上限"可配置"的落地程度：配置入口是什么形态（创建对局时的可选参数？资源管理器上的配置项？还是仅语义标注、默认 12 固定）；锚点③"含上限行为"的验证手段期望——是允许通过配置较小上限快速验证上限封顶行为，还是期望以默认 12 通过多轮回合循环验证（或两者皆可，实现者择定并汇报）？
>
> 2）其余数字项的配置性质：起手张数（4/5）、手牌上限（9）、战线容量（4/5/4）——哪些要求对外可配置/可读字段，哪些按固定值实现即可；"手牌上限本批仅字段存在"中的"字段"是否要求对外可读。
>
> 3）随机种子"可复现"的确切语义与验收期望：同一种子创建的两个对局，其初始化洗牌结果（及随后的起手/抽牌结果）是否必须逐位一致；"可复现"是否要求纳入测试覆盖（属锚点④边界内），还是只需在传入种子时行为确定的承诺、测试覆盖可选；对局是否需对外可读本次种子以支撑复现。

### 父的解答

**1）指挥点上限：创建期可选配置（默认 12）；封顶验证推荐"小上限"路径**

- 配置入口＝**对局创建的可选参数**（对局级"规则/开局配置"，至少含"指挥点上限"，默认 12；形态（配置对象/具名参数）由实现者定并汇报）；初始化时注入资源管理器，结算按其封顶。
- 校验：上限须为正整数（≥1）；非法配置 → 参数校验异常（抛错）。
- 锚点③"含上限行为"验证：**两者皆可、实现者择定并汇报**；**推荐"配置较小上限（如 2~3）→ 多回合推进 → 断言封顶"**（快、确定，同时覆盖配置入口本身）；默认 12 的语义不变。

**2）其余数字项：可读/固定分档**

| 数字项 | 本批性质 |
|---|---|
| 指挥点上限（12） | **可配置**（创建参数，默认 12） |
| 战线容量（4/5/4） | **可读字段**（不可配置；位置实现者定——第 5 轮已定） |
| 手牌上限（9） | **可读字段**（不可配置；仅数据、不触发行为） |
| 起手张数（4/5） | **固定值实现即可**（无需配置/读面；测试以常量断言） |

- "手牌上限字段"＝**要求对外可读**；不做超限裁决（前轮已定，重申）。

**3）可复现：强语义（逐位一致）＋ 要求测试覆盖 ＋ 种子可读**

- **强语义**：相同种子＋相同创建参数（卡组名单/先手/配置）→ 两个对局的**洗牌序列、起手装载、后续抽牌序列逐位一致**——此为"可复现"的验收定义。
- **要求纳入测试**：至少 1 条复现用例（同种子 → 逐位一致；可选补充"异种子 → 序列不同"）；归属锚点④/⑤范围，具体用例位置实现者择定并汇报。
- **种子可读**：对局对外可读**本次实际使用的种子**（传入则＝传入值；未传入则＝实际生成值，支撑事后复现）；类型由实现者定并汇报。

### 备选方案与拒绝原因

**1）装填与构建能力：要求具备**

**3）元素类型与命名：确认＋实现者定型**

- CardList 元素＝**字符串 id**（与卡牌库注册键一致）；CardSet 元素＝**引擎卡牌实例（Orc Card）**。
- 方法命名与签名形态（如 Draw 返回形态：CardList→string、CardSet→Card）＝**实现者定型并汇报**（沿用"实现者定并汇报"原则）。

### 备选方案与拒绝原因

1. 无常规装填 API（仅 Insert/Draw）——测试与场景构建困难 → 拒（要求装填＋读面）；

- 锚点④"含边界"＝**逐条覆盖以下最低边界清单**（允许增补）：
  1. 空集 Draw 抛错——CardList 与 CardSet 各覆盖（或参数化）；
  2. Insert 越界抛错（至少一例；推荐负索引与超量两端各一）；
  3. CardSet 同一实例重复添加拒绝；
  4. Instantiate 三情形：空→空集、未注册→抛错、重复 id→独立实例（并体现保序）；
  5. 同种子复现：两次对局逐位一致（第 6 轮要求）。
- "尽量 0 警告"＝**努力目标、非硬验收门槛**（硬门槛＝0 错误）；产生的警告须在汇报中说明，不留未解释警告。

### 备选方案与拒绝原因

1. 仅跑新增项目、既有项目轻检——不足以防回归 → 拒（三项目全跑）；
2. 依赖根默认解析/使用 slnx——slnx 为空占位、默认解析有歧义 → 拒（显式 OrcEngine.sln）；
3. 为 Orc.Game.Tests 设预设用例数——过度约束、用例数为设计自由 → 拒（无预设数量、覆盖为准）；
4. "0 警告"作为硬门槛——过度刚性 → 拒（努力目标＋须解释）。

### 第 10 轮新增确认需求点

- 验收构建/测试对象＝OrcEngine.sln（显式）；全解决方案、三测试项目均执行；slnx 保持不动；
- 回归＝既有用例数不减少（156/157 下限）且全绿；新增无预设数量、覆盖为准；
- 锚点每项 ≥1 条测试（硬性）；边界最低清单 5 条逐条覆盖；0 警告为努力目标。

## 十一、玩家对象形态与结构自由度（第 11 轮）

### 子的问题（原文）

> 【类级收尾·玩家对象形态与结构自由度】多轮问答已确定各对象的职责与使用面（Match 便捷属性、五管理器公开、集合/卡牌库/常量类的 API 面与边界），但其"结构自由度边界"还有两处值得收口，请阐明：
>
> 1）玩家对象的形态：玩家是否作为引擎域实体承载（既有引擎 Entity 类注释预示"卡牌、单位、玩家等后续均继承此类"）——本批玩家应继承引擎实体惯例，还是普通对局数据类即可（实现者定型并汇报）；无论哪种，玩家的公开读面是否要求直接可读——资源（点数 point / 槽 slot）、卡组（名单）、手牌（引用集）、HQ 血量，供测试断言与展示。
>
> 2）结构自由度的最终边界确认：除已明确的对外契约——Match 便捷属性与控制流语义（EndTurn 无参/状态门禁/转发只读）、管理器公开与单一真源分工、集合类/卡牌库/常量类的既定 API 面与边界——之外，各类的命名、密封性（sealed 与否）、文件组织是否均为实现者定型并在汇报中列出即可。
>
> 3）创建参数的默认与边界收口：种子未传=自动生成且事后可读；先手未指定=第一位玩家；指挥点上限未传=默认 12；卡组名单传空的集合（空名单）是否允许创建（随后初始化时因空集抽取行为抛错），还是创建期即校验拒绝——请给出空名单的口径；此外是否还有需要在创建期显式校验/默认的参数。

### 父的解答

**1）玩家对象形态：普通对局数据类；读面直接可读**

- 本批玩家＝**普通对局数据类**（实现者定型并汇报）；**不要求继承引擎 Entity**——本批无引用/生命周期需求（玩家不失效、不销毁、不被效果引用）；引擎 Entity 的"玩家等后续继承"为长期方向，实体化（引用语义）**留后续批次评估**。
- 玩家**公开读面要求直接可读**：资源（点数/槽）、卡组（名单）、手牌（引用集）、HQ 血量——供测试断言与展示。

**2）结构自由度最终边界：确认**

- 除已定对外契约（Match 便捷属性与控制流语义＝EndTurn 无参/状态门禁/转发只读；管理器公开与单一真源分工；集合类/卡牌库/常量类既定 API 面与边界）之外——**各类命名、密封性（sealed 与否）、文件组织＝实现者定型并在汇报中列出即可**。
- 总原则（重申）：对外可见行为须符合本记录；内部结构与命名自由。

**3）创建参数默认与校验收口**

- 默认：种子未传＝自动生成且事后可读；先手未指定＝第一位玩家；指挥点上限未传＝默认 12（均重申）。
- **空名单口径**：**任一方的卡组名单为空 → 创建期拒绝**（参数校验异常；fail-fast、错误信息明确，不产生半成品对局）。
- **不足起手（非空但 < 所需）**：**不创建期拦截**——允许创建；初始化抽到空集时按"空集 Draw 抛错"契约抛出（该路径同时作为"初始化失败→保持准备态"契约的测试触发）。
- 补充校验/默认（收口）：
  - 先手指定非法（越界/非双玩家之一）→ 创建期校验异常；
  - 名单含 null/空白 id → 创建期拒绝（格式错误 fail-fast）；名单中的"未注册 id"不在创建期校验（初始化实例化时抛错——既有契约）；
  - 定义集为空 → 允许（空库；第 8 轮既定）；
  - 其他参数无额外校验要求。

### 备选方案与拒绝原因

1. 玩家继承引擎 Entity——本批无引用/生命周期需求、增加包袱 → 拒（本批）；长期方向记录；
2. 玩家读面仅经管理器逐层获取——断言与展示需便捷 → 拒（直接可读）；
3. 空名单允许创建（初始化时抛错）——错误延迟、信息不直接；"初始化失败"测试价值由"不足起手"路径保留 → 拒（创建期拒绝）；
4. 不足起手亦创建期拦截——消灭"初始化失败"契约的天然测试触发 → 不采纳（保留运行时路径）。

### 第 11 轮新增确认需求点

- 玩家＝普通对局数据类（不强制 Entity）；读面直接可读（资源/卡组/手牌/HQ）；
- 结构自由度：命名/密封性/文件组织实现者定（汇报列出）；
- 默认与校验：种子/先手/上限默认重申；空名单创建期拒绝；不足起手走运行时抛错；先手非法与空白 id 创建期拒绝。
