# A3 运行时装载修复 — 需求阐明记录

> 委托：第 2 批 W3-A3（CodeImplementation；grill 层级＝类/功能流程级）。
> 职责范围＝《实现文档（第 2 批）》S3：①补 `card.placed` 发射；②移除框架 IsPlaced 显式门控（未上场语义下放效果·三策略）；③装载路径统一（托管登记入通用装载路径、复装重建）；④补 `effect.removed` 发射；⑤效果级授予路径。

## 一、功能职责与流程约束（本委托需求基线）

- **装载动机统一**：被动效果经三条装载入口驱动——加载时点装载（先于 `card.load` 广播）／放置驱动装载（`card.placed` 处理器；幂等）／Add 即时装载（本单变更：**不再要求已放置**）。
- **"仅在场生效"的未上场语义＝效果侧责任**（三策略：延迟自挂载／内部状态门控／直挂靠触发时机）；框架不替效果门控（"靠卡牌自觉"）；未按策略处理的效果其未上场误触发由效果自身承担。
- **复装（移除后再添加）＝装载路径统一重建**（托管登记随通用装载路径；二次卸载仍自动撤销该效果施加的修饰/光环）。
- **既有防御语义保留**：重复 Add 拒绝、移除幂等、装载失败＝记录＋回滚隔离（不阻断其它效果与宿主）、独立构造（缺对局上下文）＝跳过装载、不抛错。
- **非功能**：更新同步语义（P2）；幂等（重复驱动无副作用）；测试覆盖不减少。

## 二、已解决的歧义（Q&A 逐轮记录）

### Q&A-1（2026-10-04）："移除框架 IsPlaced 显式门控"的准确语义与既有测试口径

**子的问题原文**（摘要）：

1. A3 后"未放置卡的 AddEffect 被动效果"是否立即执行装载链（挂主触发器＋OnMount）——即装载不再以放置状态为前提、由效果按三策略自行处理"未上场"语义？还是"移除门控"指别的（例如：不再由 AddEffect 隐式装载、装载一律经显式装载驱动）？请给出"移除门控"后 AddEffect 行为的准确读法。
2. 行为变更触及既有测试断言：①「放置前＝静态组装、放置驱动装载」与②「未装载移除＝仅容器面移除」（`tests/Orc.Tests/EffectLifecycleTests.cs`）；③「手动装配效果在装载前静态组装、经加载链装载」（`tests/Orc.Game.Tests/EffectSystemTests.cs`）。"不破坏既有测试"应理解为"测试随语义受控适配并逐条记录"（沿用本仓已有先例），还是这些断言必须原样通过？若必须原样通过，如何与"移除门控"相容？
3. `IsPlaced` 状态本身是否保留（作为策略 1/2 效果可查询的"已放置"判断原语——删除门控逻辑 ≠ 删除状态可用性）？既有装载链口径是否维持：加载时点装载（先于 card.load 广播）＋放置驱动装载（幂等）＋放置后 Add 即时装载（S4"不得静默死效果"）——A3 仅是在"即时装载"条件上去掉 IsPlaced 一项？

**解答**：

**1. 门控移除的准确读法——"被动效果 AddEffect 即装载"：**

- `Card.AddEffect` 的即时装载判定：从 `IsPlaced && Kind==Passive` 改为 `Kind==Passive`（**仅移除 IsPlaced 一项**）；任何时点添加的被动效果**立即执行装载链（挂主触发器 → OnMount）**——"装载不再以放置状态为前提"成立。
- "由效果按三策略自行处理未上场语义"成立：三策略是**效果侧（作者）对"未上场"的自行处理方式**，非框架提供的开关；框架职责＝装载统一执行＋提供原语（本单补 `card.placed` 发射；`IsPlaced` 状态保留；总线订阅既有）。
  - 策略 1（延迟）：效果在装载流程内自注册"等待包装"，上场（`card.placed`）时再挂实际逻辑；
  - 策略 2：装载即挂载，效果内部按状态门控是否生效；
  - 策略 3：直接装载注册、无门控（触发时机自然保证，如部署/亡计）。
- 备选读法（"不再自动装载、装载一律经显式驱动"）→ **拒绝**：与裁定原文"就直接加载时注册、不要显式的 IsPlaced 门控"相悖，且会破坏既有三入口幂等口径。

**2. 测试口径裁定——受控适配＋逐条记录（非"原样通过"）：**

- "不破坏既有测试"的准确含义：不得留下失败用例、不得静默弱化/删除覆盖；允许按新语义**受控更新断言并逐条记录**（本仓先例：S2 迁移"保持验收语义覆盖，基线＝迁移后全套测试全绿"；A1"内部结构断言受控随改＋逐条记录、覆盖不减少"）。
- "必须原样通过"→ **拒绝**：与有意语义变更矛盾（若"放置前＝不装载"必须保留，门控就无法移除）；不接受"删断言/降覆盖"式破坏。

  - ②「未装载移除＝仅容器面移除」→ **幂等防御语义保留**、构造手段受控调整（旧构造"未放置卡 Add 后移除"在新语义下不再产生"未装载"态；改用如"装载失败回滚后的效果"等路径构造未装载态）；
  - ③「手动装配在装载前静态组装、经加载链装载」→ 断言更新：**手动装配即装载**；加载链装载步骤改写为"幂等/已装载跳过"覆盖；
  - 补充确认：`Standalone_Construction_Skips_Effect_Load`（独立构造跳过装载）的防御语义保留；若"Add 即装载 × 独立构造（无对局上下文）"组合出现新问题，按"防御跳过、不抛错"既有口径处置并记录。

**3. IsPlaced 保留与口径确认：**

- `IsPlaced` 状态**保留**（删除门控逻辑 ≠ 删除状态；作为查询原语供效果使用）。
- 装载三入口口径**维持**：加载时点装载（先于 card.load 广播）／放置驱动装载（幂等）／Add 即时装载（仅去 IsPlaced 一项）。
- A3 范围不止"去 IsPlaced 一项"：另含 ③装载路径统一（托管登记入通用装载路径、复装重建）／④`effect.removed` 发射／⑤效果级授予路径——验收按 S3 全量执行。

### Q&A-2（2026-10-04）：`card.placed` 发射路径、时点与载荷契约

**子的问题原文**（摘要）：

1. **发射路径与时点**：部署（单位打出链内的部署链）与加入（加入链）两条路径均应发射。其相对既有链节的时点要求是什么——倾向「单位化成功之后、部署完成信号（unit.deployed / unit.joined）之前」发射（承「初始化就绪先、效果注入后」的语义）；请确认或纠正。另明确：加载时点（LoadAsync，先于 card.load 广播）不发射 card.placed——对吗（否则对局载入会把卡组/手牌的全部卡误标为「已放置」）？
2. **重复与失败语义**：同一卡重复部署/加入时每次都要发射吗（由放置处理器幂等吸收，发射本身不做「仅一次」限制）？部署/加入链失败或被中止（如单位化未完成）时明确不发射——对吗？「每次成功的部署/加入恰发射一次」是否即发射频次契约？
3. **载荷与可见性契约**：载荷键以既有夹具/CardEventView 对齐为准（Card 键携带卡牌对象引用）；是否需要额外携带 Position 或 Player 等键？**card.placed 到达策略 1 效果订阅者时，「已放置」标记（IsPlaced）是否须已置位**——策略 1 的上场判定应依据「收到该卡的 card.placed 事件」本身，还是框架须保障「订阅者观察到时 IsPlaced 已为 true」？

**解答**：

**1. 发射路径与时点——确认（倾向正确）：**

- 部署链与加入链**均发射**；时点＝**单位化（组件挂载＋槽位占用）成功完成之后、完成信号（unit.deployed / unit.joined）之前**：
  `单位化 await 完成 → ctx.Interrupted 防御（中断则不发射）→ 【card.placed 发射】→ unit.deployed / unit.joined`。
- 依据：策略 1 效果挂载时需完整就绪状态（组件/槽位已成立）；完成信号观察者须看到「效果注入后」状态（承「初始化就绪先、效果注入后」语义）。
- **加载时点（LoadAsync，先于 card.load 广播）不发射——确认**：放置＝「上场」语义；否则装载期会把卡组/手牌全部卡误标「已放置」。加载时点装载（`MountPassiveEffects`）与 card.placed 无关（三入口之一，不受影响）。

**2. 重复与失败语义——确认：**

- 频次契约＝**「每次成功完成的部署/加入恰发射一次」**；发射点位于既有中断防御（单位化未完成 return）之后——**失败/中止不发射**。
- 重复部署/加入：既有守卫（仅空槽、未单位化的卡可单位化）使重复驱动在单位化处中止（不达发射点）——正常流无重复发射；**发射本身不做「仅一次」限制**（未来同类路径仍按「每次成功驱动恰发射一次、放置处理器幂等吸收」处理）。

**3. 载荷与可见性契约：**

- 载荷＝**对齐既有夹具/CardEventView：`{ PayloadKeys.Card: 卡牌对象引用 }`**；**不额外追加 Position/Player**（消费方可从卡牌读取就绪后的单位数据；对齐最小原则，未来按加性演进）。
- **IsPlaced 可见性**：策略 1 的「上场」判定**以收到该卡的 card.placed 事件本身为准**；框架**不承诺**「订阅者观察时 IsPlaced 已置位」（置位由放置处理器在同一事件传播中完成，订阅者间先后依挂载/注册序、不作保证）。
  - 依据：事件即「上场时机原语」；置位与兜底装载＝处理器职责、响应上场＝效果职责——解耦。
  - 备选（框架保障「置位先于其他订阅者」的两阶段派发）→ **拒绝**：引入派发顺序契约与实现耦合，收益不抵复杂度。
  - 策略 1 编写指引：收到 card.placed → 查就绪数据（单位/位置）→ 挂载实际逻辑；**不读 IsPlaced 作上场判定**。

**架构审视补充（本点）：**

- 边界：未来新增「上场类」路径（回场/移动等）＝按同语义接入（就绪后、完成信号前；中断不发射）。
- 非功能：发射为同步顺序（P2）；处理器侧幂等（既有，`wasPlaced` 检查＋幂等装载）。
- 失败模式：发射链异常语义＝沿用引擎 Emit/总线既有口径（实现者确认并记录）。

### Q&A-3（2026-10-04）：装载路径统一（托管登记）与验收①复装闭环

**子的问题原文**（摘要）：

1. **覆盖范围与自动化契约**：是否要求「任何被动效果的**装载成功**（无论入口：加载时点装载 / 放置驱动装载 / Add 即时装载 / 词条内嵌效果）都**自动**完成托管登记，调用方不再手动登记」？复装时自动**重建**登记——对吗？为达成「内核通用装载路径自动完成游戏层托管登记」，允许在内核（src/Orc）**加性**提供「装载后自动动作」一类的扩展点（游戏层在装配时注册托管动作）吗？还是要求不改内核装载链、仅在游戏层收口？（分层边界约束，请给出倾向。）
2. **幂等与失败口径**：①已装载（重复驱动幂等跳过）时不重复登记；②装载失败的既有隔离语义维持（记录＋回滚为未生效＋不登记＋失败残留清理）；③「托管登记」动作自身异常的处理口径——随装载失败回滚？还是隔离记录？
3. **验收①闭环的确切含义**：「授予→装载→移除→复装」中的「授予/复装」是否即由效果级授予路径（需求点⑤）承担？闭环断言＝「复装后**二次卸载**仍自动撤销该效果施加的修饰器/光环」；是否要求多入口覆盖（如加载链装载的效果经移除→复装同样重建）？以及「修饰器与光环**两者都**须覆盖」——对吗？

**解答**：

**1. 覆盖范围与自动化契约——确认 + 分层倾向：**

- **任何被动效果的装载成功**（无论入口：加载时点装载 / 放置驱动装载 / Add 即时装载 / 词条内嵌效果）都**自动**完成托管登记；**调用方不再手动登记**（加载链⑤与词条内嵌的现手动登记点随之移除/收口）。
- **复装自动重建登记——对**（与 `Effect.AddUnmountCleanup` 既有契约「执行后清空——重新装载需重新登记」衔接：把「重新登记」从调用方义务改为装载路径自动化）。
- **分层边界倾向：允许内核（src/Orc）加性提供「装载后自动动作」扩展点**（形态由实现者设计并申报；如装载管线钩子），游戏层在装配期注册「托管动作」；内核不感知游戏层语义。
  - 理由：Add 即时装载走内核路径（`Card.AddEffect → CardLoadout.MountEffect`），游戏层无法无侵入拦截全部装载入口；把「装载后自动动作」作为内核通用原语、托管动作留在游戏层＝分层正确（通用机制进内核、KARDS 语义留游戏层）。
  - 备选「仅在游戏层收口」→ **拒绝**：无法覆盖内核路径与未来新入口（漏网入口类缺口再发）。
  - 备选「内核装载链硬编码游戏层托管动作」→ **拒绝**：内核反向依赖游戏层语义。
  - 补充：扩展点**可缺省**（未注册时装载照常）；自动动作在**装载成功后**（`ExecuteMount` 成功）触发——与 `AddUnmountCleanup` 既有「登记约定＝装载完成后进行」一致。
  - 形态注记：既有 `RegisterManagedCleanup`（单源入口）可作为托管动作的实现内核保留；变化的是调用点（从各路径手动 → 通用装载路径自动）。

**2. 幂等与失败口径——确认 + 裁定：**

- ① 已装载（重复驱动幂等跳过）**不重复登记**——对（装载链执行一次 → 自动动作恰一次；重复驱动不触发装载即无重复）。
- ② 装载失败的既有隔离语义**维持**：记录＋回滚为未生效＋**不登记**＋失败残留清理（幂等兜底）。装载回滚不触发已登记动作（既有契约不变）。
- ③ **「托管登记（自动动作）」自身异常＝归入装载失败口径**：记录＋回滚为未生效＋不登记残留（不阻断其他效果与宿主）——「装载成功」的定义包含「自动动作完成」；**不采用「隔离记录、装载仍成功」**（备选拒绝原因：登记缺失 → 卸载时托管撤销缺失，复现同类缺口）。
  - 实现顺序（先自动动作后置成功 / 失败时走卸载对账）由实现者设计并记录。

**3. 验收①闭环——确认：**

- 「授予/复装」**由效果级授予路径（需求点⑤）承担**（或测试内按同一路径形态等价操作）；复装＝移除后再次添加同一实例（`Effect` 骨架已允许多次成对装载/卸载）。
- **多入口覆盖＝验收要求**（证明「登记与入口无关」）：至少覆盖**加载链装载**与 **Add 即时装载**两入口的「移除→复装→二次卸载」；**词条内嵌效果**为应测（若其装载同样收口）。
- **修饰器与光环两者都须覆盖——对**（`RunManagedCleanup` 含：光环注销＋修饰器按来源撤销＋受益侧重跑）；断言「复装后二次卸载仍自动撤销（修饰器＋光环）」；可一例双覆或分列，覆盖不减少。

**架构审视补充（本点）：**

- 边界：自动动作「可缺省」；注册归属＝游戏层装配期；内核不感知语义。
- 失败模式：多轮复装循环稳定（每次装载→登记、每次卸载→清理；建议断言含一轮完整闭环，多轮由实现者酌增）。
- 非功能：P2 同步顺序；登记后进先出（既有）。

### Q&A-4（2026-10-04）：`effect.removed` 发射点——触发点外延、顺序与幂等

**子的问题原文**（摘要）：

1. **触发点外延**：发射点＝`Card.RemoveEffect`（容器规范移除入口）执行时——对吗？其它「移除类」路径（卡牌销毁/死亡清理的批量卸载、词条移除引发内嵌效果卸载、词条授予失败回滚中的移除）是否也要发 effect.removed——即「移除路径」的准确外延是什么？（还是仅「显式单效果移除」一类发更新，销毁类维持只发 card.destroyed？）

**解答**：

**1. 触发点外延——「成功事务的实际移除恰一条信号」＋发/不发清单：**

- **发**：
  - ① 显式移除（`Card.RemoveEffect`；含复装前置移除）；
  - ② 死亡/销毁清理链上的逐效果移除（经 `RemoveEffect`——死亡链既有调用点）；
  - ③ 词条（成功）撤销引发的内嵌效果卸载（经规范入口）；

- **不发**：
  - ① 装载失败/授予失败等**未成功事务的回滚**路径（「无痕」——回滚中的卸载不得借 `RemoveEffect` 的发射行为误发；实现需为回滚提供静默清理路径，设计并记录）；
  - ② `effect.removed` 更新处理器的自身清理（**源头即信号**——无论驱动来自 `RemoveEffect`〔已发〕还是外部 `RemoveViaUpdate`〔源头条目即信号〕——防重复/自循环）。

**2. 顺序与通道——「先清理（落定）后发射」＋引擎总线：**

- **先清理（落定）后发射（对外通知）**——与「先落定后发射」的既有原则一致；发射在清理模板完成（容器移除＋卸载链）之后；**发射失败不影响清理**（已落定）。

- 备选「发射即驱动清理（清理仅由更新处理器完成）」→ **拒绝**：与「清理模板直接调用」的既有收敛语义相悖（双路径汇入模板、而非更新单源）；引入清理时机/失败路径不确定性。

**3. 幂等与载荷——确认：**

- ①「无操作＝不发射」；重复 `RemoveEffect`（第二次起无操作）不重复发射；**「每次实际移除恰发射一次」**（移除→复装→再移除＝两次实际移除＝两条信号）。备选「每次都发、接收侧幂等」→ **拒绝**（信号语义污染）。
- ② 载荷＝`{PayloadKeys.Card, PayloadKeys.Effect}`——**对**（S4 既有口径「effect.removed 含卡牌+效果」；对齐夹具 `RemoveViaUpdate` 与 CardEventView）；不追加其他键。

**架构审视补充（本点）：**

- 边界：发/不发清单如上（含回滚静默路径的实现要求与记录义务）；「卡销毁分支发射」为新增可观察行为——相关测试断言按需受控适配/新增（覆盖不减）。
- 失败模式：发射链异常＝沿用引擎总线既有语义；防循环＝「源头即信号」＋「命中才发」双规则。
- 非功能：P2 同步顺序；单源（规范入口）。
