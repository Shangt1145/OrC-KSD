# K0·B12 烧牌统一 — 需求阐明记录

> 判定器收编（A+B）· K0（B 档第 12 项）：把两处 HandLimit 烧牌实现（PlayerManager.DrawCard 满手路径、MatchCardService.PlaceToHandAsync 满手路径）统一为共享烧牌单元。本记录为需求阐明（功能职责/约束/验收标准/已解决歧义）；实现计划与技术细节由实现阶段自行制定。

## 一、功能职责

1. **统一烧牌单元**：两处满手烧牌路径收敛为同一共享单元——满手判定（IsAtLimit）＋烧牌动作（销毁＋card.discarded 发射）单一实现。
2. **两路语义差异参数化保留**：
   - DrawCard 路径＝"算被抽到"：发 card.drawn → 销毁 → card.discarded；
   - PlaceToHand 路径＝"未经手牌"：销毁 → card.discarded（不发 card.drawn / card.hand.add）。
3. **消除双重实现**：销毁＋card.discarded 的重复实现合并（原两处各自实现不再保留）。

## 二、约束

1. **行为零变化**：两路信号组合、顺序、载荷与现状完全一致；HandLimit＝9 不变（常量值与两处判定用法均保持现状，不做配置面改造）。
2. **最小改动**：仅两处调用点接入共享单元；共享单元的存放与命名由实现定型并申报。
3. **不做项**（本单边界）：判定器注册面引入、JudicatorNames 新增、GameHooks/GameHooksJson 判定器清单同步、moding/可改写专项、任何配置面改造。
4. **起手装载**：LoadOpeningHand 链路不受裁决、不接入共享单元——行为与现状完全一致。
5. **编辑域隔离**：在途包文件零触碰（『换牌/认输』全套、S-C 六文件、Prefab/Script/DynamicEffect）；GameHooksJson.cs 按第 1 轮裁决**严格禁编**（接受锚点暂态失真，申报待同步项）。
6. 构建（-t:Rebuild）0 警告；全量回归（四套件）不破坏。

## 三、验收标准（本单口径）

- [ ] ① 烧牌两路统一为共享单元（参数化语义；销毁＋discarded 单一实现）；
- [ ] ② 行为零变化：既有测试全绿＋两路语义差异显式断言（DrawCard：drawn→discarded；PlaceToHand：discarded 且无 drawn/hand.add）；
- [ ] ③ 构建 0 警告 0 错误（-t:Rebuild）；
- [ ] ④ 全量回归不破坏（以工作区实际全绿为准）；
- [ ] ⑤ 实现记录落盘（含受控适配/待同步项申报）。

> 边界注记：本单为"最小共享单元"，**无 moding/可改写专项验收**——"行为零变化＋moding 可改写专项"为收编全链（K1-K4）通用口径，不适用本单。

## 四、对齐记录

### 第 1 轮 · 主问题 1：K0 交付边界——"共享烧牌单元"的形态深度

**问题（整理）**：① K0 是否仅为"两处烧牌统一为共享代码单元"——不引入判定器注册、不新增 JudicatorNames、不同步 GameHooks/GameHooksJson 判定器清单、不含 moding/可改写专项验收场景；判定器化/配置化（若属链后续单）留给 K1-K4？验收②"两路语义差异显式断言"是否以纯行为断言为准（无 moding 场景）？② "HandLimit＝9 不变"是否＝本次不做任何配置面改造（常量值与两处判定用法均保持现状）？③ "起手装载不受裁决语义不变"是否＝LoadOpeningHand 链路（静默抽牌）不接入共享单元、行为与现状完全一致？④ 若本单确为"最小共享单元"，是否对共享单元形态（含后续可替换性）不设额外要求——以最小改动、行为零变化为准，将来需要 moding/配置时由后续单再受控改造？

**解答**：
- ① **是**。K0＝最小共享单元统一（纯重构）；**不含**判定器注册面/Names/GameHooks 同步/mod ing 专项验收。验收②＝**纯行为断言**（两路信号组合显式覆盖，无 moding 场景）。澄清：方案文档中"行为零变化＋moding 可改写专项"为**全链 K1-K4 通用口径**，不适用 K0——K0 以本记录"三、验收标准"为准。判定器化/配置化不在本单。
- ② **是**。不做任何配置面改造（HandLimit＝9 常量值与两处判定用法保持现状）。
- ③ **是**。LoadOpeningHand 链路不接入共享单元、行为完全一致（"起手不受裁决"语义不变）。
- ④ **是**。对共享单元形态（含后续可替换性）不设额外要求；以最小改动、行为零变化为准；将来需要 moding/配置时由后续单受控改造。

**备选方案与拒绝原因**：
- (i) 顺带判定器化（含 Names/清单同步）——**拒绝**：超出本单交付边界；B12 收编目标＝消除双重实现；扩大风险面。
- (ii) 为共享单元预设可替换接口/扩展点——**拒绝**：超前设计，违反最小改动与行为零变化原则。

### 第 1 轮 · 主问题 2：GameHooksJson 信号元数据锚点冲突——编辑域裁决

**问题（整理）**：GameHooksJson.cs 的 SignalMetadata"权威描述表"含受影响精确锚点——CardDrawn：["Managers/PlayerManager.cs:156·DrawCard（烧牌）","Managers/PlayerManager.cs:162·DrawCard（常规）"]；CardHandAdd：["Match/MatchCardService.cs:220·PlaceToHandAsync","Managers/PlayerManager.cs:163·DrawCard"]；CardDiscarded：["Match/MatchCardService.cs:215·PlaceToHandAsync（烧牌）","Managers/PlayerManager.cs:255·DestroyAndEmitDiscardedAsync"]。本次统一必然致行号漂移、发射点描述转移；GameHooksTests 为结构化断言（不校验行号，漂移不破坏测试），但权威元数据将失真。① 裁决：(a) 严格禁编、接受过期并申报待同步 / (b) 豁免本次、最小加性行级更新 / (c) 其他？② 若 (a)，申报落点；若 (b)，范围限定？

**解答**：
- ① 裁决 **(a) 严格禁编**：不得编辑 GameHooksJson.cs（属在途 Prefab 包；隔离声明为硬约束）。接受锚点**暂态失真**——失真为注释级元数据，不破坏 GameHooksTests 结构化断言、不影响信号契约与功能。
- ② 申报落点＝**受控适配/待同步项清单**（实现记录落文档区）＋汇报；须注明：受影响条目（CardDrawn / CardHandAdd / CardDiscarded）、受影响锚点描述、失真原因（本次统一致行号/发射点描述转移）、**建议同步时机＝Prefab 包冻结后由受控维护统一同步**（届时若隔离解除；同步不并入本单）。

**备选方案与拒绝原因**：
- (b) 最小加性行级更新——**拒绝**：触碰在途包文件（并发写覆盖风险）；元数据准确性收益远低于隔离红线风险；延迟同步至变更稳定后成本更低、一致性更好。
- (c) 先同步元数据再做统一——**拒绝**：无法在不触碰在途包的前提下完成；本单不宜承担跨包元数据同步职责。

### 第 2 轮 · 主问题 3：统一范围与"销毁＋card.discarded 单一实现"的完整边界

**问题（整理）**：现状三个消费点——①DrawCard 满手路径（经私有助手 DestroyAndEmitDiscardedAsync＝销毁＋discarded）；②DiscardCardAsync 弃置路径（同一私有助手）；③PlaceToHandAsync 满手路径（内联销毁＋discarded）。两处"各自实现"＝私有助手 vs 内联实现。委托"仅两处调用点接入"与验收①"原两处各自实现不再保留"对第三消费点存在解释空间。① "单一实现"是否要求全库仅存一份（旧私有助手删除/并入；弃置路径也转复用、行为不变）？还是允许弃置路径保持现状（保留第二入口）？② 弃置路径复用是否超界？"两处"精确含义？③ 旧私有助手最终形态是否要求申报（删除/迁移/转发壳）？

**解答**：
- ① **要求全库该组合仅存一份实现**。共享单元承载唯一的"销毁＋card.discarded"原语；旧私有助手**作为独立实现不予保留**（其逻辑并入共享单元）；**弃置路径 DiscardCardAsync 同步转为复用共享单元原语**（行为不变；由既有 G7 弃置测试与全量回归共同锁定）——此为"实现迁移的必然结果"，非"第三处新接入"；不接反而留下第二份实现/第二入口，与验收①矛盾。如盘查发现其它"销毁＋discarded"同组合消费点：一并纳入复用（行为不变）并申报，确保"单一实现"无残留。
- ② **不超界**。"两处"精确含义＝"两个烧牌调用点（DrawCard / PlaceToHand 的业务接入面）"；**不排除**其它既有调用方复用同一原语——前提即"不产生第二份实现"；弃置路径属"原消费方随实现迁移继续复用"，属合理且必要范围。须在实现记录中**申报**（弃置路径接续方式＋旧助手去向）。
- ③ **要求申报**。确认："原两处各自实现不再保留"指向**删除双实现**（私有助手与内联实现均不作为独立实现留存）。最终形态推荐**删除**（最干净）；如因最小 diff 等理由保留为**纯转发壳**（零独立逻辑、仅委托共享单元），亦可接受——须申报并以"无第二份实现"检验。

**备选方案与拒绝原因**：
- (i) 弃置路径保持现状（旧助手原样保留）——**拒绝**：与验收①"单一实现"矛盾（留下两份实现/双入口）；弃置路径复用零额外成本且行为不变。
- (ii) 旧助手保留为独立实现（与共享单元平行）——**拒绝**：同上（双实现）；且将导致未来维护分叉。

### 第 2 轮 · 主问题 4：测试增量与验证口径

**问题（整理）**：验收②＝"既有测试全绿＋两路语义差异显式断言"；既有测试已分别覆盖两路（G7DiscardScenarioTests⑥ 与 CardServiceTests），FilesToModify 列有 tests 暗示应有变更。① 测试增量最小要求：(a) 新增专门对照用例 / (b) 既有文件补强 / (c) 两者皆可、以显式断言为准——是否有倾向？② 允许修改既有测试文件（Orc.Game.Tests；不得删除文件）？③ 若基线存在非本单引起的失败/警告，验收④按"无新增失败＋申报在途包袱"还是"必须全绿"判定？

**解答**：
- ① **实质标准＝"两路差异被显式断言"**（对照标准：同一满手条件下分别走两路，显式断言 drawn 有/无差异＋其余信号一致）。默认预期：**至少新增或补强出"并排对照"断言**——"分别覆盖"≠"显式差异对照"。放置方式 (a)/(b) 皆可，**倾向独立对照用例**（统一改造的专属回归锚）；若置于既有文件，须为**加性**（不扰动既有断言语义）。
- ② **允许**修改既有测试文件（加性、不得删除文件、既有断言语义不降级）；套件＝Orc.Game.Tests。
- ③ 判定＝"**无本单新增失败**＋在途包袱逐条申报"：以**改造前基线对比**为准（实现者先取证改造前状态留档）；在途包引起的失败/警告按"在途包袱"申报（不归本单、须记录）。**若工作区因在途改动导致构建/评测不可用（无法取得对照基线）：中止并申报阻塞**，不得在破损基线上强行改造。

**备选方案与拒绝原因**：
- (i) "必须全绿、否则等待"——**拒绝**：在途包不受本单控制，等待不可执行；"无新增失败＋申报"可控且可审计。
- (ii) 零测试变更（既有覆盖已足够）——**拒绝**：既有为"分别覆盖"，非"显式差异对照"；统一改造需专属对照锚。

## 五、已解决的歧义（摘要）

1. K0 交付边界＝最小共享单元（纯重构、行为零变化、最小改动）；不含判定器化/配置化/mod ing。
2. 验收②＝纯行为断言（两路信号组合显式覆盖；无 moding 场景）。
3. GameHooksJson 锚点失真处置＝严格禁编＋申报待同步项（Prefab 冻结后受控同步）。
4. LoadOpeningHand 不接入共享单元；HandLimit＝9 与两处判定用法保持现状。
5. 单一实现范围＝全库唯一：旧私有助手不作为独立实现保留（推荐删除、纯转发壳可接受，须申报）；弃置路径随迁复用同一原语（行为不变）；无第二实现/入口（发现其它同组合消费点一并纳入并申报）。
6. 测试口径＝两路差异**并排对照**显式断言（独立用例优先；既有文件加性亦可；不得删除文件）。
7. 验证口径＝"无本单新增失败"＋在途包袱申报（改造前基线取证对比；不可构建时中止申报阻塞）。
