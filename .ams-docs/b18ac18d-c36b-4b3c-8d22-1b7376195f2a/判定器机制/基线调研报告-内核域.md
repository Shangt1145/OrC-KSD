# 基线调研报告 — 判定器 · 内核域

> 来源：CodeAnalysis 委托 9acfe81f（子 Agent 84455173#2），2026-10-04。报告经子 Agent 汇报承载、由功能面管理者誊录落盘。
> 用途：为「判定器机制」设计提供内核侧现状基线（参照物：X4 handler moding；通道现状：handler 引用服务方式；先例：字符串键注册表、服务注入模式）。

## 〇、结论速览

1. **X4 handler moding（逻辑替换）已在内核完全落地**——锚＝注册句柄（TriggerRegistration）、执行时动态解析「最后未注销 moding 项」（栈语义、最后者胜、注销回退）、纯替换（无 next/proceed）、快照一致、幂等宽容、句柄即权限、机制静默无读面；全部事件 handler 注册项（构造期装配项＋流程内置处理器＋装载链处理器＋效果触发器＋游戏层检查触发器）均可寻址（InitialRegistrations 供给）。
2. **内核 handler 形态**＝`Func<TView, Context, CancellationToken, Task>`；handler 引用服务通道现状＝闭包捕获／执行时数据／「卡→玩家→服务」ResolveFor 静态解析；**无服务定位器、无按字符串名解析服务/函数的现成通道**（按名解析面需新增）。
3. **字符串键注册表先例集中在游戏层**：CardEffectRegistry（effectId→工厂、cardId→声明清单，ordinal、注册即配置 fail-fast、装载时解析）、KeywordRegistry（进程级全局）、CardLibrary（id→定义）；内核事件名/hooks 为开放字符串集合、非唯一键。
4. **服务注入范式**＝装配期一次性注入（ConfigureXxx＋重复注入拒绝）＋延迟读取提供器 lambda＋可选注入 null 降级；引擎级服务随 LogicEngine 构造、对局级随 Match.Initialize 装配。
5. **关键差距提示**：X4 moding 作用域＝单注册项；「moding 后全局生效」内核无先例（属新增能力面，但语义要素可完整复用——需在判定器层设统一解析点）。

## 二、内核 handler/触发器体系

1. handler 抽象形态：`Func<TView, Context, CancellationToken, Task>`（无接口/基类；delegate 即 handler；moding 与 handler 同参同返回）。
2. 注册与调用路径：`Trigger.InvokeAsync` 统一入口 L290（data 字典→Context 拷贝一次→Validate L273〔每次固定调用、空转后绑定前、可覆写、只读无副作用、输入 IReadOnlyList<Ref<Entity>>〕→ContextViewBinder.Create→RunEventsAsync L403〔SortKey＝band×1000＋优先级＋注册序兜底〕→事件链）；嵌套执行帧 ExecutionFrame L662+（AsyncLocal 栈；Stop/Interrupt 检查点；子流自动挂载；异常隔离/契约兜底）；触发入口三形态（统一入口/具名重载/字典透传；框架不隐式 Translate）。
3. 参数约定：TView＝[ContextView] 类、属性 [Read]/[Mutate]/[Optional]、访问器须 virtual（src/Orc/Core/ViewMeta.cs 构建期校验）；Context＝数据载体＋TryGet/Get＋Stop/Interrupt（src/Orc/Core/Context.cs 55 行）；Ref<Entity>＝安全引用（src/Orc/Core/Ref.cs 52 行，失效抛 StaleReferenceException）；载荷键 PayloadKeys（CardLifecycle.cs L13-45：Card/Effect/Source/Target/Amount/Order）。
4. 总线与被动触发器：hooks（字符串、构造期声明、开放集合）→Bus.Mount（src/Orc/Core/Bus.cs L31）/UnmountOwner L85/Emit L133（先写 update 条目→外部通道→订阅者快照，挂载优先级升序→注册序）；更新字符串 ordinal、大小写敏感、无注册/白名单。
5. **handler 引用通道现状（判定器将被 handler 引用的关键事实）**：
   - ①闭包捕获（delegate 构造时捕获服务引用——流程类捕获 _engine、效果工厂 Func<CardBase,Effect> 捕获服务）；
   - ②执行时数据（Context data/视图属性——只承载数据、不携带服务）；
   - ③静态解析「卡→玩家→服务」（ResolveFor，见四）；
   - ④**无服务定位器、无按字符串名解析 handler/服务的内核通道**；
   - ⑤判定型扩展点先例＝Trigger.Validate（只读、每次调用、覆写；DelegateCheckTrigger 委托化实例：src/Orc.Game/Commanding/CommandManager.cs L1498-1514），X4 明确 moding 不覆盖 Validate——判定器若走 Validate 路线与 handler 侧互补而非同一。

## 五、对判定器提案的基线关联结论

- a) 「handler 按字符串名/ID 引用判定器」：内核无现成通道；可用先例＝字符串键注册表（游戏层）＋闭包/视图数据/ResolveFor。若判定器为「由游戏规则预定义的独立无状态服务」，可参照 CardEffectRegistry 形态（装配期注册＋装载/调用时解析），**按名解析面需新增**。
- b) 「注入 delegate moding、语义与 handler moding 一致」：X4 全部语义要素可直接复用；但 X4 锚＝触发器注册项，判定器换锚为「判定器函数条目」时需自带等价句柄产物（对照 TriggerRegistration/TriggerModingRegistration 形态与幂等口径）。
- c) 「moding 后全局生效」：现状 moding 为逐条目作用域；全局生效＝解析点从触发器执行循环（L418）搬到判定器调用内部（所有 handler 每次调用时解析同一栈）——内核无先例，属新增能力面。
- d) 「对局加载时加载」：先例＝Match 装配链注入（调用方构造→创建参数→Initialize 注入→延迟读取解决装配顺序→装载期/运行期取用）；判定器可挂靠同一范式。
- e) 完整性核对：内核全部构造期装配点（流程内置/装载链/效果/游戏层检查触发器）均已可寻址；若判定器成为 handler 引用对象，建议同步规划其自身「可寻址性」，延续 X4「不得存在无法被 moding 的注册项」精神。
