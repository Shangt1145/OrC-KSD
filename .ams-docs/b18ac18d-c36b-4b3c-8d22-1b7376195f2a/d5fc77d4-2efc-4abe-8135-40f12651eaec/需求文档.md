# 弃置动作与 card.discarded 信号——需求阐明（S8）

> 委托：W2-G7 手牌操作与弃置（第 2 批·S8）。本文档记录 grill 对齐中的需求阐明（功能职责／约束／验收口径）；技术实现细节由实现者自行制定。
> 范围修正（D16）：KARDS 官方无弃牌堆/墓地语义；弃置＝「从手牌移除＋销毁（接线引擎既有销毁机制）＋card.discarded 信号」。

## 一、弃置动作的承载形态与三路径收敛

### 1.1 动作面与组合方式（子问①）
**子问**：是否需要生产侧存在一个「弃置动作面」（对外可调用的受控动作）？三路径（选择弃/随机弃/指定弃）是否＝经既有面组合调用该弃置动作，还是要求为「随机弃」「指定弃」提供生产侧专属封装入口？

**阐明**：
- 需要存在**一个**生产侧受控「弃置动作」（职责：从手牌移除＋销毁＋信号）；
- 三路径＝**组合式**调用该动作，**不提供**「随机弃」「指定弃」的专属封装：
  - 选择弃＝手牌选择交互终局产出卡引用 → 调用弃置动作；
  - 随机弃＝随机服务取样 → 调用弃置动作；
  - 指定弃＝顺序原子面定位（如"最左"） → 调用弃置动作。

**备选与拒绝**：备选＝为「随机弃/指定弃」提供生产侧专属封装入口。拒绝原因：与既定「组合式」哲学冲突（纯原语＋调用方组合——同"随机分配"/随机形态之裁定）；专属封装固化组合语义、增加面数，且与验收场景（三路径＝三种组合）不一致。

### 1.2 「选择并弃掉手牌」整合链路的验收含义（子问②）
**子问**：验收含义＝测试内驱动手牌选择流程（槽位交互）至终局、再调用弃置动作的两步组合即可，还是要求生产侧存在「选择→弃置」的整合入口/流程？

**阐明**：验收含义＝**两步组合**（测试内驱动手牌选择至终局 → 调用弃置动作）；**不要求**生产侧整合入口/流程。
约束：组合**无跨步原子性承诺**——链路一致性由调用方（效果）在同一执行序列内保证；框架不引入「选择→弃置」事务机制。

**备选与拒绝**：备选＝生产侧整合入口。拒绝原因：整合入口将"选择＋动作"固化、违背要素解耦；"组合即链路"与既定哲学一致。

### 1.3 边界与拒绝语义（子问③）
**子问**：弃置他方手牌的应答；弃置"不在该玩家手牌中"的卡的应答（明确拒绝还是幂等）；对同一卡重复弃置的应答；归属校验口径。

**阐明**：
- 归属口径＝**「卡当前所在手牌」**（不设"仅己方"限制）；他方手牌中卡的弃置（如"随机弃对手 1 张牌"类）经调用方组合合法可达；
- 前提校验失败（卡不在任何手牌中／不在所声明玩家手牌中）＝**明确拒绝**（可区分成功/拒绝；不静默、不幂等）；
- 对同一卡重复弃置＝第二次因前提失败而拒绝（不幂等放行）；
- 拒绝的形态（异常/结果对象）由实现者自定。

**备选与拒绝**：备选＝幂等（重复弃置静默通过）。拒绝原因：与受控动作的强契约哲学不一致；静默会掩盖双重弃置类缺陷。

## 二、card.discarded 信号契约

### 2.1 载荷形态（子问①）
**子问**：「载荷风格对齐现有信号」的具体形态——应含哪些键、键的形态与顺序以哪个为对齐基准（现状 card.drawn＝{Player, Card}、card.hand.add＝{Card, Player}、card.died＝{Card} 不统一）？

**阐明**：载荷＝**{Card, Player}**（被弃卡在前、玩家在后）——对齐"卡的动作事件"族（card.played＝{Card, Player}、card.hand.add＝{Card, Player}、card.load＝{Card, Player}）；Player 语义＝该卡被弃置时所归属的玩家。既有信号不回改。

**备选与拒绝**：备选＝以 card.drawn 的 {Player, Card} 为准。拒绝原因：该形态（玩家在前）属少数派；新增信号对齐"卡在前"多数派。

### 2.2 原因/路径是否入载荷（子问②）
**子问**：是否需要携带「原因/路径」（选择/随机/指定）或其它区分弃置来源的方式？（烧牌归下一轮单独问。）

**阐明**：**不携带**——信号只报事实（"某卡被弃置"）；路径为调用方语义、观察者毋须区分；未来如出现区分需求再行扩展（本批不预置）。
烧牌（HandLimit 超限弃置）的信号归属留待 HandLimit 轮裁决。

### 2.3 次序语义与验收深度（子问③）
**子问**：「移除＋销毁＋信号」的次序语义；验收「移除＋销毁验证」的观测深度（不可再用＋信号断言即可，还是要求资源清理可观测）？

**阐明**：
- 次序＝**移除 → 销毁（含资源清理）→ 发射 card.discarded**（动作完成后发信号、观察者所见即终态；与死亡链「清理先于信号」同哲学）；
- 验收深度三层：① 卡离手（不可再使用）；② 信号**恰一次**、载荷正确；③ 销毁接线佐证（最小用例观测"引擎既有销毁机制被调用/生效"）；**如既有机制不含清理面，实现须申报、不得静默**（不扩 Scope 自建清理）。

**补充（失败模式）**：实现须保证「移除＋销毁」不产生未定义的半态（离手未销毁）；如机制上存在可失败点，须定义可观测行为并申报（不静默）。

**备选与拒绝**：备选＝信号先于销毁（可观察"销毁前状态"）。拒绝原因：与既有链「清理先于信号」一致性优先；弃置语义无"销毁前观察"需求。

## 三、与既有离手路径的边界（触及确认）
**子问**：弃置需与既有「离手」路径（打出链 Hand.Remove）区分——请确认弃置为独立动作面、不改造既有离手路径。

**阐明**：**确认**。弃置＝独立动作面；既有打出链离手路径**不改造、不销毁**（打出≠弃置）。弃置动作不得被既有离手路径复用（保持"打出离手不销毁"现状语义）。

## 四、HandLimit 烧牌（裁决点、动作语义与信号流）

### 4.1 裁决点与适用范围（子问一）
**子问**：HandLimit 裁决装配于哪个环节——仅「回合抽牌链路」，还是「抽取核心链路」（起手装载同受裁决）？其余"进手牌"路径（未来生成→手牌等）本批是否不涉？若起手同受裁决，其「静默」约定与弃置信号如何协调？

**阐明**：
- **裁决点**＝装配于**回合抽牌链路**（对局进行中的抽取 → 进手牌前判定）；
- **起手装载不受裁决**——维持现状（数量 4/5 ＜ 上限 9、当前不可达超限场景；保持"静默、不发任何更新"约定）；**若未来配置变更致可达超限场景，另行评估（不在本批）**；
- **其余"进手牌"路径**（未来生成→手牌等）本批不涉——其与 HandLimit 的关系留后续批次对齐（边界披露）。

**备选与拒绝**：备选＝「抽取核心链路」统一裁决（起手亦走判定）。拒绝原因：起手数量固定（4/5）低于上限、裁决不可触发；统一裁决会引入"起手万一触发则要发信号"与"起手静默"的约定纠缠——收窄裁决点＝最小变更、无歧义。

### 4.2 烧牌的动作语义（子问二·①）
**子问**：新抽的牌「先加入手牌、再作为弃置出手牌」（手牌短暂第 10 张）？还是「抽牌时判定满则不经手牌、直接弃掉」（手牌全程保持 9）？请按 KARDS 烧牌语义裁定。

**阐明**：**直烧口径**——抽牌时判定满 → **不经手牌、直接处置**（"移除"由抽取步骤自然完成〔从卡组取出即已移除〕；处置＝销毁）；**手牌全程保持 9（无瞬时第 10 张）**。
- KARDS 烧牌语义：被烧的牌不进入手牌（玩家不可见、不占手牌位）；
- 与「弃置动作」的关系：**烧牌不经弃置动作**（弃置动作前提＝卡在所在手牌——烧牌不满足亦不适用；二者**共享"销毁"原语与 `card.discarded` 信号**）。

**备选与拒绝**：备选＝两段式（先加手牌→弃置动作）。拒绝原因：① 与 KARDS 语义不符（被烧牌未进过手牌）；② 制造可观察的瞬时超限（`card.hand.add` 信号处理器可观测到第 10 张），破坏"手牌 ≤9"不变量；③ 稀释「弃置」语义（把从未在手牌的卡先塞进手牌再弃）。

### 4.3 信号流（子问二·②）
**子问**：烧牌时是否发射 card.drawn？card.hand.add？card.discarded（复用、同 {Card, Player} 载荷），还是静默/另立？

**阐明**：
- **发 `card.drawn`**（恰一次；"抽牌动作信号"——烧牌必经抽取、语义适用；沿用既有载荷 {Player, Card}、不回改）；
- **不发 `card.hand.add`**（语义＝"进手牌"——烧牌未进手牌）；
- **发 `card.discarded`**（恰一次；复用同一信号与第 1 轮确认的 {Card, Player} 载荷；销毁先于信号）；
- **不另立信号**（烧牌＝"弃置的自动路径〔超限触发〕"、与选择/随机/指定路径并列——与"不携原因/路径"的简洁取向一致；未来若出现必须区分"烧"与"弃"的场景，再评估扩展、本批不预置）。

**语义裁定（触及项）**：烧掉的牌**算"被抽到"**（drawn 发）、**不算"进过手牌"**（hand.add 不发）；`card.hand.add` 与 `card.drawn` 的既有语义均**无需修改**（各自适用）。

**备选与拒绝**：① 备选＝独立信号（如 card.burned）。拒绝原因：过度细分（烧牌属弃置的自动路径；观察者按"处置销毁"统一处理即可）。② 备选＝静默。拒绝原因：不可观测（"当牌被烧时"类表达无法承载，违背表达力目标）。

### 4.4 验收⑥断言口径（子问二·③）
**子问**：手牌终态张数、卡组计数、被烧卡销毁可观测性、信号序列的分段断言——期望观测？

**阐明**（前置于：手牌 9、卡组 N，触发一次回合抽牌）：
- **手牌**：终态＝9（不变）、**全程＝9**（含 drawn 信号观测点读取——不出现 10）；
- **卡组**：计数＝N−1（抽取发生）；
- **被烧卡**：不可再抽到/使用；销毁接线佐证（同 2.3 三层口径①③）；
- **信号序列（分段断言）**：`card.drawn` 恰一次 → `card.discarded` 恰一次（drawn 先于 discarded）；`card.hand.add` **零次**。

**补充（失败模式）**：失败语义沿用 2.3 补充（不留未定义半态）。

## 五、手牌顺序原子面（CardSet 操作集语义与边界）

### 5.1 四个操作的精确语义（子问一）
**子问**：「移至最左/最右/指定位置」的目标位置语义与三种情形应答；「按索引移除」的索引语义、越界应答、返回值；「Peek」的语义与用途（查什么、是否只读、与索引器读面关系、验收断言）。

**阐明**：

**① 移至最左/最右/指定位置**
- 目标对象＝手牌中的某张卡（调用方提供卡引用）；
- 「指定位置」语义＝**0 基索引、且＝移动完成后该卡所在位置**（等价表述："移至第 N 位"；有效范围 0..Count−1，以移动后的序列为准）；返回值形态由实现者自定；
- 三种情形的应答：
  - 目标卡不在手牌中 → **明确拒绝**（前提校验失败）；
  - 目标位置越界（负数或 ≥Count） → **明确拒绝**；
  - 目标位置恰为当前位置（自移） → **无操作、视为成功**（结果＝集合不变；合法请求、无需调用方特判）。

**② 按索引移除**
- 0 基索引；越界 → **明确拒绝**；
- **返回被移除的卡引用**（供调用方承接后续处置）。

**③ Peek**
- 语义＝**按索引的只读读取**（0 基；"最左"＝索引 0、"最右"＝Count−1）；**不移除、不改动**；越界 → **明确拒绝**；
- 用途＝为"定位→组合"提供明确读点（如"弃掉最左"＝Peek(0)＋弃置动作）；
- 与既有索引器读面的关系＝**能力导向**：委托要求的是"存在明确的只读读取路径"；若既有索引器读面已满足（读实例、越界行为有定义），实现者可将 Peek 实现为索引器的显式封装/便捷方法（**不强制重复建设**）；
- 验收断言＝读取后集合（成员＋顺序）不变＋返回引用正确＋越界可区分。

**备选与拒绝**：
- 自移"明确拒绝"：拒绝——自移是合法请求（结果＝原样），拒绝将迫使调用方特判"当前位置"；"无操作成功"更友好且结果可断言。
- Peek"独立于索引器重建"：拒绝——能力导向（避免重复建设）；以"只读、越界可区分、集合不变"为要求项。

### 5.2 操作性质与组合边界（子问二）
**子问**：顺序操作是否为纯容器操作（无副作用＋原子）？「弃掉最左」组合的接口边界（定位＋弃置动作；「按索引移除」不得与销毁混用）？范围确认（CardSet 限定、空/单牌边界）。

**阐明**：

**① 纯容器操作（确认）**：
- 顺序操作＝**纯容器操作**——除成员/顺序变化外**无任何副作用**（不发射信号、不销毁卡、不触发更新）；
- **原子性**：单次操作要么成功、要么集合不变（无部分应用）。

**② 「弃掉最左」类组合的接口边界（确认）**：
- 组合＝「**定位（读/Peek 最左）** ＋ **弃置动作**」（弃置动作内部完成移除＋销毁＋信号）；
- 顺序原子面的「按索引移除」＝**纯容器操作**、**不得与销毁混用**；"先按索引移除再弃置"将因弃置前提校验失败而被拒绝——**该失败为预期行为**（不得以"移除＋弃置"拆分串联规避）；
- 「按索引移除」的用途边界＝**"取出（不销毁）供其他处置"的通用容器能力**；与销毁型动作（弃置）**解耦**——凡销毁型处置一律"定位 → 对应动作"直达。

**③ 范围确认**：
- 本原子面**限定手牌容器（CardSet）**；卡组容器（CardList）**无对称面要求**（基线与委托均指手牌；"回迁原子化"属另一要求、不受此限）；
- **空牌/单牌边界**：要求覆盖并测试——空手牌（任何目标卡"不在手牌中"＝拒绝；越界读取/移除＝拒绝）；单牌（自移＝无操作成功）。

**备选与拒绝**：
- "按索引移除与弃置串联"：拒绝——与弃置前提（卡在所在手牌）冲突、破坏"定位→动作"的组合模型；且移除后卡无归属、弃置的归属口径失效。
- 卡组对称面：拒绝（本委托范围限定；如未来需要另行对齐）。

## 六、回迁原子化（手牌→卡组）与洗入类衔接

### 6.1 回迁原子面的形态、输入面与边界（子问一）
**子问**：① 落点与职责划分（卡组容器层单操作 vs 跨集合受控动作；不变量谁保证）？② 输入面最小要求（仅凭手牌卡引用是否即可）？③ 位置参数（卡组顶/指定位置；索引语义与方向；是否还要求尾部）？④ 边界与拒绝（不在手牌/重复归属/越界；是否发信号）？

**阐明**：

**① 落点与职责（跨集合受控动作）**：
- 「回迁」＝**跨集合受控动作**（单一操作）：**手牌移出＋装入卡组**一体完成（含位置参数）；
- 同时要求其基础件：**卡组容器级原子面**（"新增条目＋装配实例"封装的单操作）——由回迁动作组合调用（原委托明示；两层均属要求）；
- **不变量由回迁动作保证**：同一实例——移出手牌后被装入卡组、不丢失不重复（成功即完整迁移）。

**② 输入面最小要求**：
- **仅凭「手牌中的卡引用」即可完成回迁**（条目 id 等素材由实现自行解析；调用方不额外提供）；
- 依据用例："将所有手牌洗入卡组"（调用方只有手牌卡引用集）。

**③ 位置参数**：
- 位置形态＝**卡组顶**（索引 0）与**指定位置**（0 基、**索引 0＝下次抽取取件端**、有效范围 0..N〔N＝装入前集合大小；含尾部〕）；
- "尾部/其它位置"＝指定位置的特例（p＝N），不另设形态。

**④ 边界与拒绝**：
- 卡不在所声明玩家手牌中 → **明确拒绝**；
- 卡组侧已含同一实例（重复归属） → **明确拒绝**（"实例唯一归属"不变量；对齐既有"重复装配拒绝"）；
- 目标位置越界 → **明确拒绝**；
- **信号**：回迁动作**不发信号**（放回卡组静默＋手牌移出静默——现状延续）；未来如出现"当牌进入卡组时"类表达需求再统一评估（本批不预置）。

**备选与拒绝**：
