# csx 动态效果能力（批 4）— 需求阐明记录

> 委托：CodeImplementation `961333a6`（端到端创作卡牌工具链·批 4）｜级别：类/功能流程级（class）
> 设计依据：设计定稿 §决策 2（T0 运行期通道）；《需求-grill计划》Q8（用户裁定：abc 全要、面向 csx）；《需求文档》R6

## 一、功能职责（本批）

1. **受控挂载/卸载（面向 csx）**：把内核已有的「从快照/已注册预制体实例化动态效果 → 挂到卡（Add 即装载）→ 按凭据/引用卸载」暴露为 EffectRuntime 受控方法；语义沿用统一装载链（幂等/回滚/托管/信号）。
2. **运行时从模板/DSL 生成并挂载**：DSL → 编译 → 快照 → 实例化 → 挂载（编译驱动接入门面）。
3. **配套测试**：csx 视角端到端（含「临时获得某能力」）、失败路径、托管/信号。

## 二、需求阐明（逐轮 Q&A）

### 第 1 轮（2026-10-08）：受控挂/卸的核心语义

**子的问题（原文）**

> 我对委托的理解：EffectRuntime 新增受控方法，把内核已有的「从快照/已注册预制体实例化动态效果→挂到卡（Add 即装载）→按句柄卸载」暴露给 csx；委托把「句柄形态」与「卡上已有者的指认形态」的裁决权留给 grill 对齐。
>
> 主问题 1：DetachEffectAsync 的「卸载覆盖面」与句柄语义。
> 委托原文：「DetachEffectAsync(target, 句柄)（卸载——覆盖两类『已有效果』：本门面挂载返回者、卡上已有者；后者形态由 grill 定）；返回『句柄＋结果』（句柄形态由 grill 定，候选＝不透明 handle）」。请阐明：
> a) 「卡上已有者」（非本门面挂载、如装载期/词条内嵌/他人挂载的效果）的期望指认方式是什么？请给出典型使用场景（为什么 csx 创作者需要卸载不是自己挂的效果——是为了撤销装载期效果、还是为了让「临时获得某能力」在更广范围内对称）？
> b) 句柄除「传入 Detach」外，是否还需要任何读面能力（如校验句柄有效、列出本门面已挂句柄、按卡查询）？句柄只需要「持有并回传」即可，还是要求可序列化/跨会话保持？
> c) 同一卡上由同一 prefabId/同一 DSL 多次挂载时：应允许多个实例并存（各持独立句柄、可分别卸载），还是应拒绝「重复挂载」？「复装」（先 Detach 再重新 Attach 同一来源）的期望语义是否为「重新装载、新句柄、效果行为恢复」？
>
> 主问题 2：挂载目标域与「跨卡归属」失败的预期行为。
> 委托 N4 列出失败路径含「跨卡归属」；请阐明：
> a) target 的可达域期望：任意 Card（单位/指令/反制/HQ 均可），还是限某些卡类型（如仅单位，非单位＝降级拒绝）？「临时获得某能力」的目标主要是什么？
> b) 「跨卡归属」具体指哪个场景的校验失败（如：用卡 B 作 target 卸载挂在卡 A 上的句柄；或企图把已属于卡 A 的效果实例挂到卡 B），以及期望的外部表现（结构化失败不抛错／异常／幂等无操作）？
> c) 卡被销毁后（或对局已结束），对该卡上句柄调用 Detach 的期望行为（失效＝失败结果，还是按「目标已不构成有效宿主」幂等无操作）？

**术语裁定**：统一使用「**挂载凭据**」（下称「凭据」）指代"Attach 返回的不透明引用"；**不采用「句柄」表述**——该词在 orc-engine 领域为 `Ref` 的 _Avoid_ 词，易混淆。

**答复与决策**

**1a 卸载覆盖面：两类都支持**
- **本门面挂载者** → 经 Attach 返回的**挂载凭据**指认；
- **卡上已有者**（装载期效果／词条内嵌／他人挂载）→ 经**效果引用**指认：csx 可经公开读面 `Card.Effects`（既有只读列表）取得实例引用；**门面不自建"按名/按 id 查询"面**（避免平行寻址体系）。
- 典型场景：①「沉默/驱散」类机制——移除目标卡上的既有效果（含装载期效果）；②「临时获得某能力」的对称撤销——任何来源挂上的效果（只要在卡的效果列表内）都可被卸载；③机制性「效果失效/替换」。
- 备选与拒绝：仅覆盖本门面挂载者——拒绝（"卡上已有者"卸载属常见卡牌机制需求；引用指认无实现障碍）；自建按名/按 id 寻址——拒绝（与列表读面重复、平行体系）。

**1b 凭据读面：最小面**
- **仅需「持有并回传」**（用于 Detach）；**不需要**：可序列化、跨会话保持、枚举/查询面、独立有效性校验面（有效性由 Detach 的**结果类别**承载，见 2b/2c）。
- 备选与拒绝：可序列化凭据——拒绝（对局内对象、弱持续性、无场景）；枚举/查询面——拒绝（csx 自行持有已挂凭据即可）。

**1c 重复挂载与复装：允许多次挂载；复装＝新实例新凭据**
- 同一来源（同 prefabId／同 DSL）在**同一卡上多次挂载**＝多个独立实例并存，各持独立凭据、可分别卸载（与内核"不同实例可并存"语义一致）；**不做按来源去重拒绝**。
- **复装**（Detach 后重新 Attach 同一来源）＝新实例＋新凭据、效果行为恢复（对齐"Add 即装载／复装自动重建托管"既有语义）；**旧凭据失效**（对旧凭据 Detach＝结果类别"未命中/已失效"）。
- 备选与拒绝：拒绝重复挂载——拒绝（限制合理玩法；需引入"按来源查重"额外语义）；复装复用旧凭据——拒绝（凭据对应单次挂载）。

**2a 挂载目标域：任意 Card**
- target＝**任意 Card**（单位/指令/反制/HQ 均可）——与内核 `Card.AddEffect` 域一致；「临时获得某能力」主目标＝单位，但机制不设卡类型限制（HQ 与各类卡均有 AddEffect 面）。
- 备选与拒绝：限单位/非单位降级拒绝——拒绝（不必要限制、与内核域不一致）。

**2b 「跨卡归属」＝用卡 B 作 target 操作挂在卡 A 上的效果/凭据；期望＝结构化结果（不抛）**
- 语义层失败**返回结构化结果（不抛错）**，类别可区分：**成功卸载／未命中（不存在或已清理）／跨卡归属（非本卡效果）／其它失败**；参数层错误（null 等）沿用既有风格（抛）。
- 说明：Attach 面**不接收既有实例**（每次挂载新建独立实例），故"把已属于卡 A 的实例挂到卡 B"在 Attach 面不成立；该场景仅在卸载指认面出现并被校验（"非本卡"类别）。
- 备选与拒绝：静默无操作（内核清理模板的 false 语义）——拒绝（csx 面向需可诊断；且"未命中"与"跨卡"应分类）；抛异常——拒绝（可恢复语义、批量操作不应中断）。

**2c 卡销毁/终局后的 Detach：未命中/失效类别（幂等无害）**
- 卡已销毁（效果已被清理链移除）→ Detach＝结构化结果"未命中/已失效"（幂等无害、不抛）；对局结束后 → 延续"终局门禁"先例（随机服务/对局卡牌服务「进行」态门禁），按"失效结果"处理，不得抛出未定义异常。
- 备选与拒绝：抛异常——拒绝（csx 可恢复语义）；静默成功——拒绝（掩盖误用）。

**架构审视补充（对抗性审视，纳入需求）**
- 失败模式：批量/连续操作下**单条失败不阻断其余**（对齐装载链隔离精神）。
- 非功能性：不新增线程/异步语义（沿用 P2 同步/顺序）；不新增持久化面。
- 边界：凭据与效果引用均可能指向"已失效对象"——统一按"未命中"类别处理（不静默腐坏、不抛）。
- 元审视：子问题覆盖核心歧义；无错误假设。（命名层面已统一"挂载凭据"。）

### 第 2 轮（2026-10-08）：失败路径与结果语义

**子的问题（原文）**

> 【第 2 轮·主层（class 级）：失败路径与结果语义】
> 上轮已定：跨卡归属/未命中走结构化结果类别（不抛）；参数层 null 抛；批内单条失败不阻断。本轮补齐 Attach 侧（挂载入口）失败语义与结果体系。
>
> 主问题 1：Attach 系列（AttachPrefabAsync / AttachSnapshotAsync / CompileAttachAsync）失败的期望语义与类别粒度。
> 委托 N1/N2b 原文：「失败＝隔离＋回滚」「编译失败＝失败分类与隔离（不阻断）」。请阐明：
> a) 失败类别粒度：是否需要**可区分的结构化类别**（如：来源未找到〔未注册 prefabId／模板缺失〕／数据无效〔快照 JSON 反序列化失败／DSL 解析失败〕／实例化失败／编译失败），供 csx 创作者修正数据？还是「失败＋原因说明」单类即可？（这决定失败测试的断言形态。）
> b) 边界场景：「实例化成功、但装载（挂载）失败」时（内核装载链语义＝记录＋回滚为未生效、不阻断容器）——门面应返回「失败」（不给出凭据）还是「成功」？（我倾向失败＋回滚语义，请裁定。）对应地，「成功」的判据是否为「实例化且装载成功、凭据有效」？
> c) 「隔离」的硬验收检查点请确认：失败＝对卡零残留（效果列表无新增）、信号零发射、宿主与其它效果不受影响、后续操作不受阻、不抛业务异常（仅参数层 null 抛）。
>
> 主问题 2：结果记录的统一性与信息量。
> a) 上轮定的卸载面类别集（成功／未命中／跨卡归属／其它失败）是否为**贯穿挂/卸/编译的统一结果体系**（Attach 面复用同一套，如「成功挂载／来源未命中／其它失败〔含编译失败细分〕」），还是各面独立类别族？
> b) 「未命中」在 Attach 面的映射期望：未注册 prefabId／模板缺失算「未命中」还是「其它失败」？请给出你期望的类别映射（可一句话级）。
> c) 结果的信息量：成功结果除凭据外是否要求携带诊断信息（效果名／来源标识／快照）；失败结果是否要求携带上下文（目标卡／来源标识／原因），还是保持最小面（凭据＋类别＋原因）？

**答复与决策**

**1a 失败类别粒度：可区分结构化类别（最低五类）**
- 采用**可区分的结构化类别**（附原因文本），类别字面稳定、测试锁定（对齐批 3 预检器"类别稳定契约"先例）。最低覆盖集（贯穿 Attach 三门面）：
  1. **来源未命中**（未注册 prefabId／模板或 op 资产缺失）；
  2. **数据无效**（快照 JSON 反序列化失败／DSL 解析失败）；
  3. **编译失败**（DSL→快照渲染/编译层失败）；
  4. **实例化失败**（视图类型/处理器解析等——内核实例化失败分类映射）；
  5. **装载失败**（挂载/OnMount/装载完成动作失败——已回滚）。
- 理由：csx 创作者需按类别修正数据（补注册／改 JSON／改 DSL）；消费端可分类统计与断言。
- 备选与拒绝：单类"失败＋原因"——拒绝（不可编程分流、弱断言）；更细分类（如模板缺失 vs op 缺失独立类）——不做硬性要求（实现可细分，五类为最低集）。

**1b 「实例化成功、装载失败」＝失败（不给凭据）；成功判据＝实例化＋装载成功＋凭据有效**
- 裁定：**失败＋完整回滚**（认可子倾向并收紧）。装载失败（OnMount／装载完成动作抛）→ 门面返回失败、不发放凭据；并执行**完整回滚**：从卡效果列表**移除**该效果（静默清理：**不发射 effect.removed**）＋残留清理（修饰器/光环等托管物）。
- 收紧说明（与内核"留列表"语义的差异）：内核 `Card.AddEffect` 装载失败时"回滚为未生效、不阻断容器添加"（效果留列表，可供兜底重试）；但受控门面**必须零残留**——若留列表，该效果可能被**放置驱动的幂等兜底**在后续"静默复活"（创作者判定为失败、实际后来生效），与受控契约不一致。失败后如需重试＝**重新 Attach**（新实例）。
- 「成功」判据＝实例化成功＋装载成功＋**凭据有效**（凭据对应"已生效的挂载"）。

**1c 隔离硬验收检查点：确认（按 1b 收紧口径）**
- 失败＝对卡**零残留**（效果列表无新增——含完整回滚）；
- **信号零发射**（静默回滚：不发射 effect.removed、不发射其它）；
- 宿主与其它效果不受影响；后续操作不受阻；
- **不抛业务异常**（仅参数层 null/空白照抛）。
- 参数层与语义层边界：**null/空白参数＝抛**；合法但不可解析的来源（未注册 id 等）＝结构化结果（不抛）。

**2a 统一结果体系：单一结果结构＋统一类别族（贯穿挂/卸/编译挂载）**
- 裁定：**统一**——单一结果结构（成功：凭据＋（建议）诊断；失败：类别＋原因），类别为**单一枚举族**（Attach 五类＋卸载面：未命中〔已失效〕／跨卡归属）。三门面与 Detach 共用。
- 备选与拒绝：各面独立类别族——拒绝（平行体系、消费端分叉、断言分散）。

**2b 「未命中」类别映射（一句话级）**
- AttachPrefab：未注册 prefabId → **来源未命中**；
- AttachSnapshot：JSON 无效 → **数据无效**；
- CompileAttach：DSL 解析失败 → **数据无效**；模板/op 资产缺失 → **来源未命中**；渲染/编译失败 → **编译失败**；
- 三面共有：实例化失败 → **实例化失败**；装载失败 → **装载失败**；
- Detach：凭据/引用不存在或已清理 → **未命中（已失效）**；效果不在目标卡 → **跨卡归属**。

**2c 结果信息量**
- 成功：**凭据（必需）**；效果名/来源标识＝附加诊断（实现择定；若提供则测试锁定）。
- 失败：**类别＋原因文本（必需）**；来源标识/目标卡引用＝可用时附上（诊断辅助）。
- 备选与拒绝：成功面强载完整诊断——拒绝（信息冗余、实现面绑定）；失败面仅类别无原因——拒绝（不可诊断）。

**信号口径（补充确认）**
- 挂载成功：不新增专用信号（可经装载留痕/审查链观察）；
- 卸载成功：恰一次 effect.removed（既有语义）；
- 失败回滚：零发射（见 1c）。

**架构审视补充（对抗性审视，纳入需求）**
- 失败模式：连续/批量调用单条失败不阻断（承接第 1 轮）；回滚路径幂等、不产生二次副作用。
- 边界：**防"未授权复活"**（1b）为硬防线。
- 非功能性：类别字面与原因文本可稳定测试；无新增线程/持久化。
- 元审视：子问题梳理到位；1b 由子"倾向失败＋回滚"收紧为"完整回滚（列表移除）"——理由见 1b。

### 第 3 轮（2026-10-08）：N2b 运行时编译面（资产、缓存、产物身份）

**子的问题（原文）**

> 【第 3 轮·主层（class 级）：N2b 运行时编译面（资产、缓存、产物身份）】
> 前两轮已定：受控挂/卸、凭据、失败五类＋未命中/跨卡、统一结果体系、零残留回滚。本轮专攻委托 N2b：「CompileAttachAsync（名称待定）——DSL（DslJson）→ EffectCompiler（模板/ops 资产加载）→ 快照 → 实例化＋挂载；含模板/ops 资产路径与编译缓存策略（首次编译成本；对齐 csx 编译缓存先例）；编译失败＝失败分类与隔离（不阻断）」。
>
> 主问题 1：模板/ops 资产的来源与就绪时点。
> 背景：既有机制中模板资产（`*.tpl.json`）与 op 模板（`*.csx.tpl`）经各自 Loader 从目录加载、有默认目录约定（程序集输出目录下 EffectParsing/Templates）。请阐明运行时编译面的期望：
> a) 资产来源：沿用「默认目录约定」由门面惰性加载，还是要求可显式指定/装配期注入（如对局初始化时传入资产集合）？两者可兼（默认＋覆盖）是否为期望？
> b) 资产就绪与失败：资产缺失/目录不存在/单文件坏时，「来源未命中」失败结果是否即期望？资产加载是一次性（缓存）还是每次编译重新加载？测试（临时目录/内嵌数据）是否需要支持「直接注入内存资产」或「指定目录」的入口？
> c) 编译产物的「效果身份」：DSL 编译需给出 effectId（快照 root.id，用于审查链/效果名检索）。对 csx 创作者，这个身份由谁确定——调用时指定／模板内声明／自动生成？创作者可观察面（效果名）有何期望？
>
> 主问题 2：编译缓存策略的形态与作用域。
> 委托要求「对齐 csx 编译缓存先例」（csx 侧缓存＝按源码哈希复用编译结果、编译一次）。请阐明：
> a) 缓存的硬性要求与粒度：`DSL→快照`的编译结果是否必须缓存（同 DSL 重复编译不重做）？缓存键的依据（DSL 文本＋模板/ops 资产指纹？）有无期望？「有则更好」还是「必须且测试锁定」？
> b) 缓存作用域与对局隔离：进程级共享（跨对局复用、成本摊薄）还是对局级（对局结束即失效）？对「对局间数据串扰」的期望（测试隔离：不同测试/不同资产目录不得互相污染）？
> c) 缓存对「行为可观察性」的期望：缓存命中与否是否会改变可观察行为（应当无差别？）；缓存容量/失效（资产变更、创建新效果实例）有无要求，还是保持最小（进程内、无淘汰、不保证失效）？

**答复与决策**

**1a 资产来源：默认目录约定＋可显式覆盖（两者兼）**
- **默认**：沿用既有目录约定（程序集输出目录 `EffectParsing/Templates`——模板 `*.tpl.json` 与 ops `*.csx.tpl`），随程序集分发（对齐既有复制规则）——csx 创作者开箱即用；
- **可覆盖**：提供显式入口（指定目录或**直接注入内存资产集合**）——测试自含（临时目录/内嵌数据不依赖程序集目录）与工具链（自定义资产集）必需；
- 惰性加载：首次需要编译时加载并缓存（见 2）。
- 备选与拒绝：仅默认目录——拒绝（测试/工具链无法自含、无法隔离）；仅显式——拒绝（丢失开箱即用）。

**1b 资产失败语义：按子集继续；相关请求按类别失败**
- 资产缺失/目录不存在/单文件坏：**单文件失败隔离（可用子集继续）**；受影响的具体编译请求返回失败类别——**模板/op 缺失 → 「来源未命中」**；资产内容问题 → 按「编译失败/数据无效」归类（承接第 2 轮类别体系）；
- 资产加载为**一次性**（惰性、加载后进程内缓存）；测试入口需支持「内存资产注入/指定目录」（见 1a）。
- 备选与拒绝：资产加载失败整体拒绝服务——拒绝（不必要；子集可用性更优）；每次编译重新加载——拒绝（重复 IO、无意义）。

**1c 效果身份（effectId）：调用时指定为主；缺省自动生成**
- **调用时指定**（门面方法的 identity 参数；用于快照 root.id／效果名／审查链检索）；**缺省＝自动生成**（便捷路径，不依赖唯一性语义——同名不同实例允许）；
- **模板内声明身份不作为主路径**（模板为跨作者共享资产，身份属调用场景）；创作者可观察面＝挂载效果名（＝指定身份/缺省自动）；
- **不新增「按名检索已挂效果」面**（凭据已承载指认；避免平行寻址——承接第 1 轮）。
- 备选与拒绝：模板内声明——拒绝（共享资产叠身份、跨实例冲突）；必填——拒绝（DX 负担）；按名检索面——拒绝（平行寻址）。

**2a 缓存：必须提供（进程内）；键＝DSL 文本＋资产指纹**
- **提供编译缓存**（同 DSL＋同资产→不重复全量编译）；**键依据＝DSL 文本＋资产指纹**（模板/op 等资产的内容签名）；
- 测试锁定形态：**行为等价**（同输入产出等值快照）＋**资产变更必反映**（资产内容变化后编译产出反映新资产——即指纹使缓存分键/失效）；
- 不要求暴露缓存统计/命中面。
- 备选与拒绝：无缓存——拒绝（重复成本）；暴露统计面——拒绝（非需求、增加 API 面）。

**2b 作用域：进程级共享；隔离由键保证**
- **进程级共享**（跨对局复用、成本摊薄）；编译产物为**纯数据**（无对局态）→ 无对局间串扰；不同资产集/不同 DSL＝不同键 → 测试隔离天然成立（不同测试与资产目录不互相污染）。
- 备选与拒绝：对局级缓存——拒绝（摊薄差且无收益）；要求每对局清空——拒绝（无必要）。

**2c 行为可观察性与容量：命中与否行为无差别；最小化**
- **硬性**：缓存命中与否**可观察行为无差别**（同 DSL＋同资产→等值快照；各次挂载实例彼此独立）；资产变更必须生效（见 2a）；
- **容量/失效＝最小**：进程内、不强制淘汰（可实现简单容量上限，仍须行为无差别）；不做跨进程持久化；不要求缓存清理 API。
- 备选与拒绝：持久化缓存——拒绝（无场景、复杂度）；强制淘汰策略——拒绝（非需求）。

**补充（对抗性审视，纳入需求）**
- 边界：**空白/空 DSL＝参数层抛**；语法/结构非法 DSL＝「数据无效」；部分资产缺失＝仅相关请求失败（见 1b）。
- 安全边界：DSL 编译产物中的 csx 文本（经 op 填槽生成）与「直接书写的 csx」处于**同一沙箱/权限域**（装载求值走既有求值器）——不引入新权限面；沙箱边界承 N3 评估。
- 非功能性：不新增线程/持久化；资产加载 IO 一次（惰性）；无外部依赖。
- 权衡：不引入「DSL 版本/迁移」面（schema 版本策略沿用严格相等现状）；不引入「编译预览/导出」面（超出本批）。
- 元审视：子问题覆盖三大面（资产/身份/缓存）；裁定均给出可测试形态。

### 第 4 轮（2026-10-08）：主动形态覆盖边界与 N3 策略（受控约定、评估产物）

**子的问题（原文）**

> 【第 4 轮·主层（class 级）：主动形态覆盖边界与 N3 策略（受控约定、评估产物）】

**1b Attach 遇主动形态：接受、不区分（与内核"列表进出"语义一致）；边界须文档化**

**2a 「文档化约定」落点：XML 文档注释（必需）；不强制独立文档**

- 备选与拒绝：独立文档为硬性——拒绝（重复、易漂移）。

**2b 评估产物：文字说明为必需；量化实测为建议（非硬性）**
- **必需**：汇报文字说明——风险机理（嵌套 csx 在既有沙箱内执行、无新增权限面；递归＝csx 挂链可自触发的既有属性；放大＝动态挂载数量无门面级上限）＋现状依据＋本批处置结论（文档化、不做门面级限制）；
- **建议**（非硬性）：若能低成本构造嵌套样例（csx 挂含 csx 的快照）实测，鼓励提供一条证据；不为测而测。
- 备选与拒绝：量化实测硬性——拒绝（成本/收益不匹配）。

**2c csx 可见性：凭据/结果类型必须 public、可被 csx 持有与传递；本批「只增不收窄」**
- **是**：凭据与结果类型＝public、可被 csx 引用（变量持有、闭包、经既有数据面带存跨事件传递）——否则功能不可用；不要求序列化（第 1 轮已定）；
- **「public 面收口留后续」边界＝本批不收窄既有 public 面、只做加性新增**；收口评估留后续批次。
- 备选与拒绝：凭据 internal——拒绝（csx 无法持有=不可用）；本批收窄——拒绝（跨批影响面大）。

**补充（对抗性审视，纳入需求）**
- 边界：主动形态卸载同样成立（列表移除）；主动形态失败类别同被动（实例化失败等——无装载步）。
