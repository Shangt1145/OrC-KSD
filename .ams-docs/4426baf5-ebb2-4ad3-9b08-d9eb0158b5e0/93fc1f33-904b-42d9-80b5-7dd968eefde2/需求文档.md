1. **示例卡包**（`samples/card-pack-demo/`）：可跑的分发数据——卡目录（≥2 个）＋效果库目录（1 个）＋中文 README；展示"json→游戏内卡牌"全链与多形态分发。

## 二、需求阐明（逐轮 Q&A）

### 第 1 轮（2026-10-08）：结构与组成裁定

**子的问题（要点）**

- （a）共享引用与"预检双零"的结构性矛盾：同一卡目录内多卡共享同一效果 id 会被读面软隔离（Warning）并被预检照实汇入 → 破坏双零；跨目录布置可维持双零。请裁定：示例包是否需要演示"多卡共享效果库效果"？若需要，是否采用多卡目录（跨目录）结构？若不需要，是否接受"一卡一效果、id 互不重复"的简单形态？
- （b）"定向取卡/动态能力"示例的必须性（委托原文标"建议/可选"）：硬性还是可选？若纳入，是否要求演示测试行为断言（如卡组-1、手牌+1）并计入验收？
- （c）数量与目录配置：卡 3-5 张的落点（建议 4 张？）；库 `*.prefab.json` 下限（≥1？）；"1 卡目录＋1 库目录"还是允许多目录？
- 子问题 1：形态覆盖边界（"等"字圈定）——除内联 csx、库引用外，还要覆盖字符串态内联、assemblyKey 形态吗？
- 子问题 2：自包含性口径——是否要求"完全自包含、不依赖宿主 C# 行为注册"（效果库优先 csx、测试无需注册 C# handler）？
- 子问题 3：是否需要在示例中显式演示"效果库注册先于卡加载"的时序要求（README/测试体现）？

**答复与决策**

1. **（a）需要演示共享；采用跨卡目录结构维持双零（硬性）。**
   - 理由：共享效果库效果是"效果库"机制的核心用途，示例包若不演示共享则展示不完整；"同卡目录内重复声明同一效果 id＝读面软隔离（防重复注册、隔离该条）＋预检照实汇入"是既有设计边界（批 3 已裁定），示例包不应制造警告面。
   - 结论：**≥2 个卡目录**；"共享"演示＝**跨目录**两张卡引用同一库效果 id；预检维持 Error/Warning 双零。
   - 教育化要求：README 须注明该边界——"同一卡目录内重复声明同一效果 id 会触发读面软隔离（警告）；共享效果请跨卡目录布置"。
   - 备选与拒绝：单一卡目录内共享——拒绝（破坏双零）；完全避开共享的"一卡一专属效果"简单形态——拒绝作为唯一形态（展示不完整）；实现者额外补"专属效果卡"作补充＝允许（不冲突）。
2. **（b）"定向取卡"示例＝硬性（含行为断言，计入验收）。**
   - 理由：它是本工具链（批 6）核心能力的演示，为用户关注场景的完整落地样例；演示价值高、成本可控（批 6 有先例可参照）。
   - 结论：**纳入为硬性**；演示测试须含行为断言（触发后卡组-1／手牌+1）；实现形态＝csx（经受控面 `FetchFromDeckAsync(self)`）——与批 6 先例同构。
   - 其余动态能力（动态挂载/AttachSnapshot 等）＝可选加分项（不作硬性）。
3. **（c）数量与配置（锁定验收面）**：卡总数 **4-5 张**（≥4）；卡目录 **≥2 个**（跨目录共享结构所需）；效果库目录 **1 个**（含 ≥1 条被跨目录共享的 csx 效果）。
   - 建议分布（实现者可微调、不改变硬性面）：基础单位卡（无效果）×1、内联 csx 效果卡×1、"定向取卡"csx 卡×1、库共享引用卡×2（跨目录各一、引用同一库效果）。
4. **（子问题 1）形态覆盖边界**：
   - **硬性**：①基础单位（无效果）；②内联 csx 效果（对象态）；③效果库引用（csx 形态）。
   - **可选**：字符串态内联（若含，README 注明"兼容读取形态、推荐对象态"）。
   - **明确排除**：卡面文本（分发包为 json 层）；C# 类型（非数据面）。
5. **（子问题 2）自包含性＝硬性**：示例包全部效果为 **csx 形态**（内联与库均为 csx）；演示测试**零 C# 行为注册**（不注册 handler）；不依赖 outputs。理由："纯数据分发即可跑"正是示例包宣传点；assemblyKey 形态需宿主 C# 配合，不作为示例包内容。
6. **（子问题 3）注册顺序＝硬性（文档化）**：README 必须含完整使用步骤＝**预检 → 装载 → 注册 → 初始化 → 使用**（体现"效果库/声明注册先于卡加载"的引用就绪前提与三段管道）；演示测试按同序组织并带步骤注释（它同时是用法示例）。

**委托方补充（对抗性审视增补，纳入验收面）**

- **失败模式**：示例目录缺失＝演示测试可辨识跳过（对齐 `OfficialCardDataSmokeTests` 先例）；README 描述"成功的样子"（预检双零、测试通过）。
- **数据版本**：示例数据用当前格式版本（卡 `schemaVersion=1`／效果快照 v2）。
- **语言与可读性**：README 中文；演示测试分步骤注释（既是验证也是用法示例）。
- **多视角**：以"创作者/工具链用户"视角检查示例的实用性（结构清晰、可直接复制为模板）。
- **元审视**：子问题合理（尤其（a）的结构性矛盾发现敏锐）；无错误假设。

### 第 4 轮（2026-10-08）：演示语义选型与确定性口径

**子的问题（要点）**

- （1）演示行为语义的选型偏好：跨目录共享的库效果（两卡各自打出＋断言）——对演示的行为类型是否有偏好/禁忌（如倾向"部署/加入类时机、结果可直接观察"）？内联 csx 卡、基础单位卡的行为/数值档位是否有要求（其理解：基础卡＝可真实打出＋数值就绪；内联卡＝效果行为可断言；档位由实现者裁量）？
- （2）"定向取卡"演示场景的完整度：是否需"触发条件发生后从卡组抽取"的完整叙事（确实经由触发/事件驱动取卡），还是允许简化到"效果装载后由一次事件/动作驱动取卡"？触发条件形态是否有偏好（如既有对局信号），还是实现者裁量？
- （3）确定性与稳定性：是否需要"重复运行结果一致"（固定种子、不依赖时间/随机序、测试顺序无关、csx 编译结果稳定）？是否有超先例的额外要求？
- 子问题 1：文案与命名风格——示例卡 `name`（中文名）与效果 `stableKey` 的可读性要求？"demo." 前缀适用对象（卡 id／效果 id／两者）与目录命名偏好？
- 子问题 2："可玩样例数据"口径确认（本批"可玩"＝演示测试内真实对局驱动〔打出＋效果生效＋取卡〕，不要求多回合完整可玩循环）？
- 子问题 3：定向取卡效果的承载形态（内联 csx／库中另一条效果）偏好？库内可否含多条效果？两条共享卡之外是否允许其它卡也引用库？

**答复与决策**

1. **（1）演示行为语义＝"可断言原则"＋推荐清单（锁定）**：
   - **原则（硬性）**：演示行为须**确定性可断言**——以世界状态/可观察结果为证；**不得依赖随机性（除非种子可控且断言稳健）或不稳定时序**。
   - **共享卡行为（推荐）**：倾向"部署/加入类时机、结果可直接观察"的行为（如抽牌/数值变更）；实现者可在可断言原则下裁量，不锁死具体行为类型。
   - **内联 csx 卡/基础单位卡档位＝实现者裁量（确认其理解）**：基础卡＝可真实打出＋数值就绪；内联卡＝效果行为可断言；费用/数值的具体档位以"可打出、可行动作链完整"为准。
2. **（2）定向取卡演示完整度（锁定）**：
   - **须经真实对局事件/信号触发驱动取卡（硬性）**——**不得绕过触发条件直接调 API**（"（触发条件）后"是演示语义的灵魂）。
   - 不要求超出"触发→抽取→断言"的额外叙事编排（多回合循环等）。
   - 触发形态＝**推荐既有对局信号（部署/加入类）**；实现者在"可断言、贴近真实场景"前提下裁量。
3. **（3）确定性底线（硬性、显式化）**：固定随机种子（沿 `CommandTestKit` 先例）、不依赖时间/全局状态、测试顺序无关（无全局注册面变更/无跨测试状态）、可重复运行结果一致；csx 编译结果稳定（既有求值器确定性与缓存先例）——**无超既有先例的额外要求**。
4. **（子问题 1）文案与命名**：`name`＝通顺中文、体现卡功能（轻要求）；效果 `stableKey`＝具描述性（轻要求）；"demo." 前缀＝**推荐覆盖卡 id 与效果 id（一致族）**、须在 README 说明；目录命名＝实现者裁量（建议语义清晰）。
5. **（子问题 2）"可玩"口径＝确认**：本批"可玩"＝演示测试内真实对局驱动（真实对局对象＋真实动作链：打出/触发/取卡＋行为断言）；**不要求**"多回合完整可玩循环"（超出示例卡包范围）。
6. **（子问题 3）承载与库弹性（锁定）**：定向取卡效果＝**推荐内联 csx**（专属行为、随卡携带）；允许实现者择库形态（若择，库内相应增条）。**库内可含多条效果（≥1 条被共享为硬性下限）**；**允许其它卡引用库**（须遵守跨目录共享边界、维持双零）。

**委托方补充（对抗性审视增补，纳入验收面）**

- **失败模式**：演示行为若含随机/时序敏感要素（如随机目标）——须种子可控且断言稳健，否则不进入演示（本裁定原则的显化）。
- **多视角**：创作者可读性（`name`/`stableKey` 描述性）与"照抄即可用"的一致性。
- **元审视**：子问题合理、无错误假设；（2）的两种表述理解正确（"完整叙事"与"事件驱动"非对立——本裁定＝事件驱动为硬性、叙事深度不追加）。

## 三、验收标准（滚动累积）

- [ ] 结构：卡 4-5 张（≥4）；≥2 个卡目录；1 个效果库目录；跨目录共享（≥1 条库效果被跨目录两卡引用）。
- [ ] 预检双零（Errors/Warnings）——含共享引用面。
- [ ] 演示测试：预检 → 装载 → 注册 → 初始化 → 打出 → 行为断言；含定向取卡断言（卡组-1／手牌+1）；零 C# handler 注册；目录缺失可辨识跳过。
- [ ] README：五段步骤（预检 → 装载 → 注册 → 初始化 → 使用）＋共享边界说明（同目录重复声明软隔离）＋成功判据描述；中文。
- [ ] 形态：基础单位／内联 csx（对象态）／库引用（csx）＝硬性；字符串态＝可选。
- [ ] 仅新增（`samples/card-pack-demo/` ＋ tests 新文件）；既有测试零回归（基线 1400/1400）；构建 0 警告 0 错误。
- [ ] 打出/演示覆盖（锁定）：内联 csx 卡×1、共享库卡×2（**各自**真实打出＋行为断言）、基础单位卡×1（打出成功＋数值就绪）；定向取卡卡×1＝真实抽取链路＋断言（卡组-1／手牌+1；不要求其再被打出）。
- [ ] 预检统计面断言：输入面目录数（2 卡目录＋1 库目录）、成功卡数、成功快照数、问题计数（Errors=Warnings=0）。
- [ ] 测试组织：按场景拆分（推荐 3-6 条）＋步骤注释；文件名体现演示语义（不锁定）；不设新增条数硬指标。
- [ ] 跳过口径：任一必需目录缺失＝整组测试跳过（早退+注释为底线、与先例对齐；输出提示＝可选增强）。
- [ ] 运行时长轻量（秒级、无 outputs 依赖）。
- [ ] README 章节（锁定）：包结构总览（目录树＋用途）／五段步骤（关键 API 调用片段·签名级）／共享边界／成功判据／"复制为模板"指引（轻量）／延伸阅读（一句带过）；术语与 CONTEXT 一致、引用与演示测试实际一致（防漂移）。
- [ ] 数据规范：六组件"应用面完备"（`factionCost`＋`tagData` 必填；单位卡含 `typeCategory`＋`battleStats`；`keywords`/`effects` 按需、不写空组件）；命名契约＋前缀（推荐 `demo.` 风格·README 说明）＋不与官方/既有 id 冲突；JSON 文本 LF／UTF-8 无 BOM／2 空格缩进（硬性）。
