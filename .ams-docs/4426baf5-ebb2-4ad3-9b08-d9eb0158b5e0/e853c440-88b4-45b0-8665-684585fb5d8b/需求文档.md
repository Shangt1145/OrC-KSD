# 效果离线编译驱动（批 5·N2a）— 需求阐明记录

> 委托：CodeImplementation `b2488094`（端到端创作卡牌工具链·批 5·N2a）｜级别：类/功能流程级（class）
> 设计依据：需求-grill计划 Q8/N2a（用户裁定 P3）；设计定稿 §6.2 薄弱点③；批 2 实现记录（PrefabWriter 落盘风格）；批 4 实现记录（EffectCompilationAssets 先例）。
> 本文件随 grill 对齐逐轮增长；记录需求阐明（功能职责、约束、验收标准、已解决歧义）。

## 一、功能职责（本批）

1. **离线编译驱动**（工具链/生产级调用面，非运行期）：卡面文本/DSL → 解析（EffectParser）→ 编译（EffectCompiler）→ 快照；可选落盘 `*.prefab.json`（**效果级产出**）。
2. **单条入口**：文本 ＋ 身份基名 → 效果级快照集合（JSON 文本/内存对象）。
3. **目录级批量**：文本目录 → 效果文件目录；单条失败隔离、报告式返回；批内重复＝首见写＋重复失败。
4. **留痕报告**：Unresolved／needsCsx／占位条件不静默丢弃（入报告）；失败分层（解析/编译/IO/身份）。

## 二、需求阐明（逐轮 Q&A）

### 第 1 轮（2026-10-08）：单条入口粒度/身份派生/批量输入输出契约

**子的提问（原文）**

> **主问题 1：单条入口的产物粒度与「一卡多效果」的适配口径**
> - 当一份卡面文本解析出**多个**效果而调用方只给一个 effectId 时，单条入口的产物应当是「单个快照」「快照集合」还是「按失败分层拒绝」？请给出判定口径（含：多效果时是否要求调用方逐个指定身份／由驱动派生带序号的稳定身份／是否属于显式失败类别之一）。
> - 若驱动需要为「无显式身份的产出」派生身份或派生文件名（以便落到 `<id>.prefab.json`），派生规则要不要定为**确定性**的（同输入同身份、跨运行稳定）？派生身份与调用方显式给出的身份若撞车（同批重复/跨批重名），驱动应如何留痕（沿用批 2「首见写＋重复进失败」是否就是本驱动口径）？
>
> **主问题 2：目录级批量的输入契约与输入→产出对应关系**
> - 「文本目录」的输入契约请定形：文件模式（是否只认约定扩展名）、编码与换行契约（是否需要与落盘文本契约同款的 UTF-8／LF 规范化口径）、以及**一个文本文件＝一卡（可含多效果）还是一效果**的判定；目录不存在、空目录、单文件读失败分别属于哪一层失败（整体性失败 vs 单条隔离）。
> - 输出侧「文本目录 → 效果文件目录」的对应关系请定形：一个输入文件允许产出**多个**输出文件吗？报告是否需要携带「源文件名 → 产出文件（可多个）」的可追溯字段（Requirements 1 要求「不静默丢弃、入报告」，我需要知道追溯粒度是文件名级还是效果级）。

**答复与决策**

**主问题 1（产物粒度与身份）**：

1. **产出粒度＝效果级**：一份文本解析出 N 个效果（N≥0）→ 逐一编译、各产出一个快照；**N=0＝空成功**（0 产出；无效果卡为合法输入，**不得**视为失败）。
2. **身份规则＝基名＋声明序序号**（确定性派生）：
   - 调用方给出的 `effectId`＝**身份基名**（必给）；
   - N=1 → 产物 id＝`{基名}`（直观、与既有先例一致）；
   - N≥2 → 按**声明序**派生 `{基名}.{n}`（n 自 1 起）；
   - **确定性要求**：同输入同身份、跨运行稳定；第 n 个身份只取决于基名与序号（不依赖其它效果的内容/数量）。
3. **撞车留痕**：
   - 单条入口（纯内存返回）：同一文本内不会撞（序号唯一）；与外部环境重名不属该上下文（调用方责任）。
   - 目录级批量：输出标识＝快照 `root.id`；**批内重复＝首见写＋重复进失败**（逐字沿用批 2 `PrefabWriter` 口径）；跨批重名＝跨运行覆盖（沿用批 2 口径）。
4. **备选与拒绝**：①「多效果＝拒绝（要求调用方拆分文本/逐个指定身份）」——拒绝：一卡多效果是领域常态（一卡可多效果），拒绝会强迫调用方做文本切分，且与「不静默丢弃」精神冲突；②「随机/哈希派生身份」——拒绝：不可读、不可预测、与协作语义冲突；③「同 id 产出多个文件」——不可能（撞车）。补充：若实现者提供「无基名」便捷形态，须仍以确定性为底线（本裁定按「必给基名」执行）。

**主问题 2（批量输入输出契约）**：

1. **输入契约**：
   - **文件模式＝只认约定扩展名 `*.txt`**（只扫顶层；非约定文件跳过、不报错——对齐「只认约定模式」惯例与读取宽容）。扫描文件序需确定（建议 Ordinal 文件名序）。
   - **编码/换行＝读取宽容**：UTF-8（容忍 BOM）、CRLF/LF 均接受（解析前规范化）；**写出侧＝既有落盘文本契约**（UTF-8 无 BOM、LF、2 空格缩进——走批 2 落盘出口，不另立契约）。
   - **一文件＝一卡**（可含多效果）——领域语义（一卡面文本）；多效果经效果数组承载。
   - **失败分层**：目录不存在＝**整体性失败（抛出）**（调用方错误；防「静默空产出被误读为全部成功」——对齐批 3「全空输入＝抛」精神）；空目录（存在、无匹配文件）＝**空成功**（0 产出＋空报告）；单文件读失败（IO/权限）＝**单条隔离**；单效果编译失败＝该效果进失败明细（隔离）；Unresolved 记录＝**留痕不失败**（入报告）。
2. **输出对应**：
   - **一输入文件允许多输出文件**（一卡多效果 → N 个 `{派生id}.prefab.json`）。
   - **追溯粒度＝效果级**：报告携带「源文件名 → 产出文件列表（可多个）＋逐效果状态（成功〔身份/文件〕、失败〔序号或身份/原因〕）」，并含汇总（输入数/效果数/成功/失败）。
   - 命名/冲突：`<root.id>.prefab.json`、非法 id 拒绝、批内重复首见写＋失败（批 2 口径）。

**架构审视补充（对抗性视角）**：

- **边界**：空文本/0 效果＝空成功（同主问题 1）；同一文本含两个相同效果＝两条产出一视同仁（序号不同）；不设驱动级时限（沿用解析器既有行为）。
- **失败模式**：部分失败继续、报告式全收集（不早退）；失败分类字面稳定（测试锁定）。
- **非功能性**：**确定性**（同输入 → 同身份/同文件字节/同报告序）；无全局可变状态（或明确生命周期）。
- **权衡记录**：「任意文件 vs 约定扩展名」→ 约定；「目录缺失：抛 vs 空结果」→ 抛（防假阴性）；「Unresolved：失败 vs 留痕」→ 留痕。
- **元审视**：子的提问合理——原始「文本＋effectId → 快照/JSON」措辞与「效果数组」存在歧义，本轮明确为「效果级产出＋基名序号派生」。

### 第 2 轮（2026-10-08）：留痕报告形态与编译失败分类契约

**子的提问（原文）**

> 【主层·功能流程级｜需求点 B：失败分层与「不静默丢弃」的报告口径】背景核实（只读代码）：①未解析记录＝`ParseResult.Unresolved`（`UnresolvedRecord`：原文起/长/原文/原因，**文本级、不归任何效果**）；②`needsCsx`／`csx` 留痕＝解析产物 DSL 里的 op（`DslOp.Op` 取值为 `needsCsx`／`csx`，带 `Script`＝原文），**效果级、嵌在 fills 里**；③占位条件＝`DslCondition` 的一种（`raw`＝渲染为 `if (false /* TODO */)`），同样**效果级**。Requirements 1 只写了「Unresolved／needsCsx／占位条件——不静默丢弃、入报告」，但报告形态未定形：
>
> **主问题 1：留痕三类的报告形态、「成功」判定与档位标注**
> - 覆盖范围与最小必需字段请定形：三类留痕是否都必须**逐条**入报告？是否需要**分列三类**（而不是合成一个笼统「警告」清单）？每条至少要能回答「哪来的（源文件／效果身份／槽位或条件位置）＋原文或原因」到什么程度——是否需要携带「命中该留痕的那个产出文件」（把留痕关联到具体 `<派生id>.prefab.json`）？
> - 报告结构是否需要**同时承载文本级（Unresolved）与效果级（needsCsx／占位条件）**两种归属层级？Unresolved 无法归属到效果，这一点是否要在口径上明说（即允许「文本级留痕 + 0 产出」这种组合，且仍是成功档）？
> - 档位判定：带留痕的条目是否仍算「成功」（照常产出＋落盘），只是被标注？是否要求在条目／汇总上给出「语义完整（无占位条件、无 needsCsx/csx 留痕）」的档位标注与计数（对齐 CONTEXT 既有『直接可跑』口径）？
>
> **主问题 2：编译失败分类的粒度与字面稳定性**
> - Requirements 1 要求「编译失败分类」，但未定形粒度：是否需要驱动层给出**结构化、字面稳定（可被测试锁定）**的失败类别枚举？至少应覆盖哪些类别——是否要求把「模板/op 资产缺失（来源未命中）」与「DSL 内容问题（槽位未填／槽位越界／op 参数非法／modings 缺 csx 等）」分成不同类别（沿用批 4 的 SourceMissing 与 CompileFailed 双分法），再叠加身份非法／序列化失败／IO 这类工程类别？
> - 「不吞不降级」的具体口径：既有层（解析器/编译器）的错误消息是否必须**原样保留**在失败明细里（作为可读原因字段），还是允许驱动层改写为自有措辞？同批中「解析失败・留痕」与「编译失败」是否必须在报告里可区分（不同类别字面），以免把「留痕」误当作「失败」或反之？

**答复与决策**

**主问题 1（留痕报告形态/成功判定/档位）**：

1. **三类逐条入报告、分列三类**（不得合并为笼统「警告」清单）：
   - `Unresolved`（文本级）／`needsCsx|csx 留痕`（效果级）／`占位条件`（效果级）——分列（独立清单或稳定类别标识）；**类别字面稳定、测试锁定**（对齐批 3/批 4 类别稳定契约先例）。
   - 理由：三类语义不同（解析不了 vs 逃生舱 vs 暂不可求值）、消费方式不同（分别对应 CONTEXT 不同口径）、合并丢语义。
2. **最小必需字段（逐条）**：
   - **类别** ＋ **原文或原因**（原文优先——「不吞」；有原文者必须携带原文）；
   - 归属锚点（按可得性）：**源文件名**（必）；效果级留痕＝**效果身份（派生 id）或声明序序号**（必）；**槽位名/条件位置**（best effort）；
   - **产出文件关联**：效果级留痕**需要**携带「命中该留痕的产出文件（`<派生id>.prefab.json`）」；文本级 Unresolved 关联到「源文件」级（无产出文件时允许缺省——见下条）。
3. **双归属层级同时承载**：报告结构同时承载文本级与效果级留痕；**明确允许「文本级留痕＋0 产出」组合且属成功档**（例：整段文本未解析出效果／纯词条文本——0 产出不视为失败）。
4. **档位判定**：
   - **带留痕的条目仍算成功**（照常产出＋落盘），留痕＝标注而非失败；
   - **要求「语义完整」档位标注与计数**（条目级＋汇总级）：口径＝CONTEXT 既有「语义完整覆盖率」——**无占位条件、无 needsCsx/csx 留痕**；
   - Unresolved **单独分列并计入汇总**（不并入「语义完整」定义——不改动 CONTEXT 既有口径）；消费方可自行组合判断。
5. **备选与拒绝**：①三类合为单一「警告」清单——拒：语义/消费方式不同，破坏可测试性与分流能力；②未解析导致整条失败——拒：部分解析是常态设计（显式失败＋诊断、不产占位），「不静默」由报告承载而非失败；③留痕不关联产出文件——拒：违背「可定位/可追溯」要求；④带留痕拒绝产出——拒：占位条件效果仍是**可编译产物**（结构可用），档位标注已足够（产出照常）。

**主问题 2（编译失败分类粒度与字面稳定）**：

1. **要求结构化、字面稳定（测试锁定）的失败类别**（对齐批 3/批 4 先例）。
2. **最小类别集（语义覆盖，至少）**——字面由实现定形并测试锁定；**建议沿用批 4 既有字面**：
   - `SourceMissing`（来源未命中：模板/op 资产缺失）；
   - `CompileFailed`（DSL 内容问题：槽位未填／槽位越界／op 参数非法／modings 缺 csx 等——渲染/编译层失败）——**与 SourceMissing 分列**（消费方处置不同：补资产 vs 修文本）；
   - `InvalidIdentity`（身份非法：显式/派生 id 空白或非法字符——落盘侧防路径穿越用批 2 口径）；
   - `IoFailed`（IO 类：输入读取失败／输出写入失败——合并或分列由实现者定，但**须有类别**）；
   - （可选防御）`SerializeFailed`——序列化失败（防御性分支；若实现保留须列类别与测试）。
3. **「不吞不降级」口径**：
   - 既有层（解析器/编译器）错误消息**原样保留**：失败条目的「原因」字段必须**完整包含**既有例外消息原文（允许驱动层加前缀/定位上下文，但**不得删改或替换**原文）；
   - **「留痕」与「失败」必须可区分**：分属不同区段/不同类别字面（测试锁定）——不得把留痕误标为失败、或反之；两概念可并存（同一效果可既成功又带留痕，也可失败）。
4. **备选与拒绝**：①单一失败类别不细分——拒：消费方无法分流（补资产/修文本/修身份/查磁盘）；②允许驱动改写既有消息——拒：损失诊断信息、违反「不吞」；③留痕与失败合用同一类别族——拒：档位语义混淆（成功带标注 vs 失败）。

**架构审视补充（对抗性视角）**：

- **边界**：部分解析（如 3 段效果中 1 段 Unresolved）→ 产出＝解析成功部分，Unresolved 单列；同一效果同时带 needsCsx 与占位条件 → 两类留痕**各自独立**记录（不互斥）；文本级留痕在批量中的归属＝源文件（单条入口＝调用上下文）。
- **失败模式**：批量中单文件「全部效果失败」＝该文件相关条目进失败区，其余文件继续（隔离）；汇总计数覆盖各留痕类与失败类。
- **非功能性**：报告**确定性**（留痕/失败条目顺序：源文件序 → 效果声明序 → 条内出现序）；类别字面稳定（测试锁定）。
- **多视角**：CI 消费（类别＋计数＋语义完整档位）；创作诊断（原文＋定位锚点＋产出文件关联）。
- **元审视**：子的核实（①②③）与库内实况一致；两问均为报告契约层面的必要细化——本轮定形后，报告「留痕区（三类）／失败区（类别集）／成功区（含语义完整标注）」三段结构即完整。

### 第 3 轮（2026-10-08）：驱动定位·出口形态·资产来源·调用者

**子的提问（原文）**

> 【主层·功能流程级｜需求点 C：驱动定位·出口形态·资产来源·调用者】委托 Requirements 2 写了「入口形态：单条（文本＋effectId → 快照/JSON 文本）＋目录级批量（文本目录 → 效果文件目录）……模板/ops 资产加载复用批 4 EffectCompilationAssets 先例（可复用则复用；可见性调整由 grill 定）」；Requirements 3 写了「驱动定位＝工具链/生产面（非运行期）：不启动对局；纯数据转换＋落盘（落盘为可选出口）」。三处仍有关键歧义：
>
> **主问题 1：出口形态、「可选落盘」的可达性与落盘行为契约**

**架构审视补充（对抗性视角）**：

- **职责边界**：单条（纯返回）／批量（落盘＋报告＋dry-run）／落盘（单一真源 `PrefabWriter`）／资产（单一来源三形态）——职责清晰无重叠。
