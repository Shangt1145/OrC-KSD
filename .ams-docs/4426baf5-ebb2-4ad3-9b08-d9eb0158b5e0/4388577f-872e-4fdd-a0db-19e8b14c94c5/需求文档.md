# 卡组定向取卡（批 6）— 需求阐明记录

> 委托：CodeImplementation `9d7b58f5`（端到端创作卡牌工具链·批 6·Q7）｜级别：类/功能流程级（class）
> 设计依据：需求-grill计划 Q7（用户裁定：列入待补清单）；Q7 核查结论（PlayerManager／CardList／EffectRuntime）
> 本文件随 grill 对齐逐轮增长；记录需求阐明（功能职责、约束、验收标准、已解决歧义）。

## 一、功能职责（本批）

1. **卡组定向取卡**：为游戏层补上「从卡组定向取出指定卡实例并移动到目标区域（手牌）」的受控动作——补齐 Q7 核查确认的能力缺口（现状：抽牌仅取卡组顶；`AddToHandAsync` 为按名新建；卡组容器无按实例移除；回迁动作仅「手牌→卡组」单向）。
2. 三层落点（实现细节由实现者定）：`CardList` 按实例移除基础件 → `PlayerManager` 移动受控动作 → `EffectRuntime` csx 受控面（主场景：效果触发时「从卡组抽取自己」）。
3. 范围边界：目标区域**锁定手牌**；其余区域（阵线/卡组顶等）不在本批；不新增信号（见第 1 轮裁定）。

## 二、需求阐明（逐轮 Q&A）

### 第 1 轮（2026-10-08）：动作语义与信号口径

**子的问题（要点）**

- 主问题：定向取卡（卡组→手牌）正常路径（未满手）下的对外信号口径——(i) 是否「算被抽到」（发 `card.drawn`）？(ii) 是否发 `card.hand.add`？(iii) 是否引入新专属信号，还是「不新增、只复用既有口径」？
- 附 1：语义定位＝「抽取」（同抽牌链路类、取件位置改为指定实例）还是「跨集合迁移」（同回迁类、方向相反）？
- 附 2：载荷是否＝`{ 玩家, 卡牌实例 }`？
- 附 3：信号选择依据＝「动作语义」还是「来源/时机」——效果触发的定向取卡是否与回合抽卡发出完全相同的信号？

**答复与决策**

**主问题：语义定位＝「抽取」——发 `card.drawn` → `card.hand.add`（对齐抽牌链路）；不新增专属信号。**

1. **(i) 发 `card.drawn`**——该动作「算被抽到」。依据：动作本质＝「从卡组取出实例」的获取（与回合抽卡同族；仅取件位置从卡组顶改为指定实例）；「抽到」监听面（`drawn_basic` 等既有监听模板、历史计数）应统一覆盖；起手装载的静默先例属**动作语义不同**（装载≠抽到），不构成对本动作的先例。
2. **(ii) 发 `card.hand.add`**——既有语义＝「任意来源进手牌（含抽牌）；与 card.drawn 并存、粒度不同」（更新常量类定义原文）；本动作「进手牌」必发。
3. **(iii) 不新增信号**——更新常量类字面值＝对外订阅契约（冻结）；「抽取」语义已有 drawn＋hand.add 完整表达；拒绝 `deck.fetch` 类第三方信号（碎片化、消费方须多头监听）。
4. **顺序与载荷**：`card.drawn` 先、`card.hand.add` 后；载荷均＝`{ 玩家, 卡牌实例 }`。

**附 1：语义定位＝「抽取」**（非「跨集合迁移」）。
- 取件位置＝指定实例（相对抽牌的"卡组顶"）；其余口径（信号、裁决、载荷）与抽牌链路完全一致。
- 备选与拒绝：「迁移」定位（对齐回迁动作的静默口径）——拒绝：①回迁（手牌→卡组）为"归还"语义、静默合理；本动作为"获取"语义，静默将造成"游玩中获取卡牌但零对外信号"的可观察性缺口；②与委托及用户场景措辞（"抽取此牌"）不符。

**附 2：载荷＝`{ 玩家, 卡牌实例 }`**（对齐 `card.drawn`／`card.hand.add` 既有载荷）。

**附 3：依据＝「动作语义」**（非来源/时机）——效果触发下的定向取卡与回合抽卡发出**完全相同**的信号（同一 drawn→hand.add 序列）；来源（回合流程 vs 效果触发）不改变信号。现网依据：效果触发的抽牌（`EffectRuntime.DrawAsync` → `PlayerManager.DrawCard`）即发同一信号——"来源不影响信号"已有先例。

**架构审视补充（纳入需求）**

- **满手边界（爆牌裁决·对齐 DrawCard 路径）**：满手（≥ HandLimit〔9〕）＝**爆牌裁决**——「计为被抽到」：`card.drawn` 恰一次 → 销毁 → `card.burned` 恰一次；`card.hand.add` 零次；卡自卡组移除。
  - 对照既有口径：爆牌（K0 统一）有两条路径——**DrawCard 路径＝计为被抽到（发 drawn）**；PlaceToHand 路径＝未经手牌（不发 drawn/hand.add）。本动作＝「从卡组取件」⇒ 对齐 **DrawCard 路径**（非 PlaceToHand 路径）。
  - 备选与拒绝：「满手＝业务失败、卡留卡组、零信号」——拒绝（引入第三种满手口径；静默不可观察）；「对齐 PlaceToHand 路径（不发 drawn）」——拒绝（本动作非"生成放置"、是取件；不"计为被抽到"将使其与抽牌语义割裂）。
- **失败路径零信号**：卡不在卡组（含已取出）／已销毁／非本局引用等＝失败（不执行、零发射、卡留原处）；失败分类沿用常规分层（见第 2 轮细化）。
- **信号恰一次**：正常＝drawn 恰一次、hand.add 恰一次；爆牌＝drawn 恰一次、burned 恰一次（hand.add 零次）；失败＝零发射。
- **范围锁定**：目标区域本批仅手牌；「卡组→其它区域」不在本批（如未来需要另议）。

### 第 2 轮（2026-10-08）：失败分层与边界裁定

**子的问题（要点）**

- 主问题：逐项裁定边界情形的归类（调用方错误＝异常，还是业务失败＝结果对象），并指出未列出的情形：①卡不在所声明玩家卡组中（含从未在过／已取出）；②重复调用（第二次取出）；③卡已销毁；④卡非本局（未加载／独立构造／定义未注册于本对局）；⑤门禁边界（准备态／初始化加载期／终局后）；⑥空参数／null。
- 附 a：业务失败的真实情形还有哪些？「卡不在卡组／重复调用」这类运行时状态是否需在异常之外另有可编程处置落点（结果对象）？
- 附 b：结果对象形态——两层（PlayerManager 动作与 csx 受控面）是否同一对象？是否需要三态＋失败原因类别化？爆牌是否＝成功语义？
- 附 c：原子性确认——失败＝零变更；爆牌＝变更已发生（完成）。
- 注：附加术语建议——动作正式名确认。

**答复与决策**

**总原则（本动作失败分层总裁定）**：**异常面仅限参数层**（null／空白参数等编程契约错误——全库一致 fail-fast）；**其余一切语义层结局统一以结果对象返回**（三态：完成／爆牌／失败 ＋ 失败类别化）。

- 依据：本动作定位＝面向效果（csx）的运行时动作（与批 4「csx 动态效果」同族）——批 4 先例已确立「引用类无效一律结果化」，且其验收曾将「已销毁卡引用未结果化」判为缺陷（修复方向＝结构化失败）；本动作主调用者之一是 csx handler——抛异常会走隔离链记录、且无编程处置落点。
- 备选与拒绝：机械套用 `MatchCardService`「调用方错误＝异常」清单——拒绝（那是面向引擎内部调用者的生成／放置面，与本动作调用域不符；将造成同族动作两层风格割裂）。

**逐项归类（裁定）**：

1. 卡不在所声明玩家卡组中（含从未在过、已被取出）＝**失败·`NotInDeck`**（运行时状态；零副作用；可编程处置）。
2. 重复调用（同一卡第二次取出）＝同 1（此时不在卡组）→ **失败·`NotInDeck`**；口径：失败路径**幂等零副作用**（动作本身非幂等）。
3. 卡已销毁＝**失败·`CardDestroyed`（已失效）**（对齐批 4「已销毁→结果化」先例）。
4. 卡非本局（未加载／独立构造／定义未注册）＝**失败·`InvalidTarget`**（结果化——对齐批 4；拒绝「异常」备选：效果域需要统一的结构化消费面）。
5. 门禁边界（准备态／初始化加载未完成／终局后）＝**失败·`Unavailable`**（对齐批 4 服务不可用／门禁先例）；零副作用、不抛。
6. 空参数／null＝**异常**（参数层——全库一致）。

**附 a（业务失败情形与非成功结局）**：业务失败（结果对象）真实情形＝上表 1–5；除满手（＝爆牌裁决、完成语义）外，全部非成功结局均由结果对象承载（失败类别化）；异常不承载运行时状态。
- 备选与拒绝：「运行时状态全部异常化」——拒绝（csx 主场景不可编程处置、抛异常入隔离链）。

**附 b（结果对象形态）**：**统一结果对象、两层同型**（单一新类型，游戏层定义；`PlayerManager` 动作与 `EffectRuntime` csx 面返回同一类型）——**三态可判别 ＋ 失败原因类别化**（类别字面稳定、测试锁定）；**爆牌＝完成语义**（对齐 `CardPlaceResult.Burned`「裁决完成——非失败」口径）。「三态＋类别」结构为**需求级硬性**；类别字面由实现者定形、实现中锁定并汇报。

**附 c（原子性）**：**确认**——①失败＝零变更（卡留卡组、手牌不变、零信号）；②爆牌＝卡已自卡组移除并销毁（变更已发生、完成语义；drawn→burned、hand.add 零次）；③完成＝移除＋进手牌＋drawn→hand.add。

**架构审视补充（纳入需求）**

- **跨玩家**：若签名含「玩家」参数而卡归属≠玩家＝**失败·`InvalidTarget`**（或实现采用「从卡推导玩家」形态规避——实现者定）。
- **卡组实例未装配**（本局异常态、正常流程不可达）＝失败·`InvalidTarget`／`Unavailable`（登记边界，实现者择一并测试）。
- **并发**：单线程语义（不引入并发处理口径——与引擎一致）。
- **非功能性**：类别字面稳定（供断言）；信号序列与「恰一次」测试锁定；失败路径零副作用（可重复调用）。
- **动作正式名（术语裁定）**：**「定向取卡」**（英文：Deck Fetch）；操作名建议 `FetchFromDeckAsync`（两层同名）——以 CONTEXT 登记为准。

### 第 3 轮（2026-10-08）：调用面能力范围与归属口径

**子的问题（要点）**

- 主 1：定向取卡的「卡组归属口径」——是否对称采用弃置/回迁的「卡当前所在手牌」口径（只校验「卡确实在所声明玩家的卡组中」，不设「仅己方／仅宿主所属」限制）；第 2 轮「跨玩家＝InvalidTarget」仅指「声明玩家≠卡归属玩家」的参数自洽校验？
- 主 2：csx 受控面能力范围——(i) 仅「宿主卡抽取自己」还是开放「抽取任意指定实例」？(ii) 是否引入一次多张（count）？(iii) 若仅「自己」，则「取出其它实例」是否仅经 PlayerManager 层、不对 csx 开放？
- 附 a：入位语义——尾部追加（对齐先例）还是指定位置参数（对齐回迁）？
- 附 b：csx 面对「对手卡组」的开放度——同主 1，还是收窄为「仅宿主卡自己所属卡组」？
- 附 c：效果生命周期边界（Q7 遗留项）——本批是否明确「不处理效果被抽出后的失效／卸载约定」，仅提供取卡能力本身？

**答复与决策**

**主 1（归属口径）：对称采用「卡当前所在卡组」口径。**
- 校验＝「卡确实在所声明玩家的卡组中」（实例存在性）；**不额外限制「仅己方卡组／仅宿主所属卡组」**（他方卡组经调用方组合合法可达——对称弃置/回迁的「卡当前所在手牌」口径）。
- 第 2 轮「跨玩家＝`InvalidTarget`」**仅指参数自洽校验**（所声明玩家 ≠ 卡的归属玩家）；非「禁止操作他方卡组」。
- 备选与拒绝：「仅己方／仅宿主所属」收窄——拒绝（与弃置/回迁口径不对称；无需求支撑；约束属调用方策略层）。

**主 2（csx 受控面能力范围）：(i) 开放「抽取任意指定实例」；(ii) 本批单张；(iii) 不适用（两层能力对等）。**
1. **(i) 开放任意指定实例**（参数＝卡引用；不限定「宿主/己方」）。依据：①门面既有多数以「任意卡引用」为目标（`KillAsync`／`DamageAsync`／`AttachPrefabAsync` 等），本动作开放同类引用不引入新权限面；②实现更自然（收窄「仅自己」反需额外判定）；③主场景仍为「宿主卡自取」，但能力边界与门面风格一致。
   - 备选与拒绝：「仅宿主卡（无目标参数）」——拒绝（额外限制、与门面风格不一致、未来必被要求扩展）。
2. **(ii) 单张**（本批明确；不引入 count）。依据：需求场景为单张；多张会拖入部分成功/原子性/裁决细节、无需求支撑；可加性扩展留未来（连续调用＝N 次单张、非原子——调用方组合）。
3. **(iii) 不适用**——因 (i) 已开放任意实例，两层能力对等（无「仅 PlayerManager 可用」区隔）。

**附 a（入位语义）：尾部追加**（对齐既有一切「抽牌/生成到手牌」先例：`DrawCard` 加入手牌、`MatchCardService` 放置「手牌（尾部追加）」）。**不引入「指定位置」参数**（回迁能力不迁移；无需求交叉）。
- 备选与拒绝：「指定位置」——拒绝（本动作「抽取」语义与回迁「放回」不同；无场景）。

**附 b（csx 面对「对手卡组」开放度）：与主 1 对称——允许**（引用可达即可操作；不额外收窄「仅宿主自身卡组」）。依据：门面既有方法不设「仅己方」限制；弱沙箱（非安全边界）下收窄无防护意义；两层同口径（第 2 轮「两层同型」精神）。**平衡/授权类约束属调用方（效果编写与卡牌规则）层**，非本动作职责。

**附 c（效果生命周期边界，Q7 遗留项）：确认——本批不处理**（维持 Q7「自描述时机扩展暂缓」裁定）：不引入「效果随区域变化自动卸载／失效」机制；被取出卡上已装载的效果**继续有效**（存续由效果自持策略或宿主生命周期决定）；本批仅提供取卡能力本身。

**架构审视补充（纳入需求）**

- **被取出卡的效果存续**：牌库期已装载的效果随卡移动继续存活（不自动卸载）——与附 c 一致；「仅卡组期有效」类需求由效果自持（既定三策略）承载。
- **多张语义**：明确单张后，「取 N 张」＝调用方连续组合（每次独立结果、非原子）——登记。
- **并发**：单线程语义（第 2 轮已登记，重申）。
- **非功能性**：入位序与信号序确定性（尾部追加、drawn→hand.add）；失败路径零副作用（第 2 轮已定）；可测试性（断言「手牌尾部位置」「卡组计数-1」）。
- **元审视**：子的问题基于合理对照（弃置/回迁先例）——采纳。
- **术语补充**：本动作归属口径＝「卡当前所在卡组」；能力范围＝「任意指定实例·单张」——与第 1/2 轮条目共同构成该动作的调用面口径。

### 第 4 轮（2026-10-08）：CardList「按实例移除条目」基础件的边界与失败形态

**子的问题（要点）**

- 主问题：(i) 实例不存在于卡组＝明确失败（异常，对齐容器风格）还是幂等无操作（返回 false）？(ii) 成功返回形态——void 还是返回条目信息（id／索引）？(iii)「未装载实例的条目」语义确认 ＋「移除即释放唯一归属」（实例此后可再装入；不变量＝任何时刻至多归属一处）。
- 附 a：null 实例参数＝异常（全库参数层一致）？
- 附 b：原子性——失败＝集合不变（校验先于变更）、成功＝单一条目稳定删除（其余条目相对顺序不变）？
- 附 c：是否需配套新读面（按实例检索位置等），还是保持最小面（仅新增移除操作）？

**答复与决策**

**本基础件为容器域组件（与第 2 轮「效果动作域」分层不同域）——裁定：遵循 CardList 既有容器风格（明确失败＋原子＋参数层异常）。**

1. **(i) 明确失败（异常）**——实例不存在（引用不匹配任何已装配实例的条目，含未装载条目不可匹配）／重复移除（已不在）皆抛。依据：CardList 既有操作全部为「明确失败（异常）＋校验通过才变更（原子）」（空集合 Draw 抛、重复装配抛、重复归属抛、越界抛；「明确失败优于静默」）；容器无幂等先例。
   - **分层说明（与第 2 轮的关系）**：第 2 轮「异常仅参数层、其余结果化」＝**效果动作层**裁定；本基础件＝**容器域**——动作层在调用基础件前**先做前置校验**（`ContainsInstance`），将「不在卡组」转为结构化结果（`NotInDeck`）；基础件异常**不透传为动作层失败结论**（异常＝编程契约违反的硬失败）。
   - 备选与拒绝：幂等无操作（返回 false）——拒绝（与容器风格不符；职责重叠——静默会让动作层难以区分「原本就不在」与程序性错误）。
2. **(ii) 成功返回＝`void`（最简）**。参数即实例、结果无需回传；如需卡 id，调用方可经既有卡库反查（回迁动作先例）。
   - 备选与拒绝：返回 id／索引——拒绝（无消费场景；扩 API 面）。
3. **(iii) 语义确认**：匹配基准＝**引用相等**（对齐 `ContainsInstance` 先例）；「按实例移除」只匹配已装配实例的条目（未装载条目无实例可比、不在本操作语义内）；**移除即释放卡组侧归属**——实例此后可再次被装入（如回迁等路径）；设计不变量＝**「任何时刻至多归属一处」**（本基础件负责卡组侧脱出，跨集合唯一性由动作层组合保证）。

**附 a**：**确认**——null 实例参数＝异常（全库参数层一致）。

**附 b**：**确认**——原子性：校验先于变更（失败＝集合不变）；成功＝**单一条目稳定删除**（其余条目相对顺序保持，计数-1）。

**附 c**：**保持最小面**（仅新增移除操作；不加新读面）。`ContainsInstance`（存在性）已足够支撑动作层前置校验；「按实例检索位置／索引」无消费场景。
- 备选与拒绝：新增 `IndexOfInstance`——拒绝（无场景、扩面）。
