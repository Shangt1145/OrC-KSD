# 需求阐明 — S1 老兵机制（组件替换式升级／信号／数据映射／读取面）

> 委托：S1（CodeImplementation；grill 层级＝类/功能流程级）；"老兵与隐蔽（模板效果补全）"三单串行的第 1 单。
> 职责范围＝老兵机制：老兵专属触发器＋升级执行（全清口径）＋`unit.upgraded` 信号＋数据映射（`BecomesVeteran:`/`VeteranOf:`）＋老兵读取面。
> 不在本单：解析层（`EffectParsing/**`——S3）、目标与判定器域（`Targeting/**`、`Judicators/**`——S2）。
> 功能面文档（只读参考）：`.ams-docs/890b145c-1a6c-4a06-b05c-9285932d81dc/老兵与隐蔽机制/实现文档.md`（S1 节）、`需求文档.md`。

## 一、功能职责与流程约束（本委托需求基线）

- **升级执行（全清口径）**：清损伤＋修饰器全清（含永久型）＋词条集全清（含运行时授予）→ 按"老兵版本"换成新数据组件（战斗数值；攻/行动费的运行值同步受控刷新）＋授予老兵版本词条集；全部数值处置**合并为一次重算**（一次、不重复；详见 Q&A-2）。
- **老兵专属触发器**：升级动作的唯一标准发动入口（卡侧具名主动触发器）；由卡牌的老兵触发效果（自托管自己的主/被动效果）触发；升级完成广播 `unit.upgraded`（先落定后发射、恰一次）。
- **数据映射**：`BecomesVeteran:<老兵卡id>` 转正式承载为**升级链信息（静态端口）**；`VeteranOf:<基础卡id>` 转正式承载为**"老兵"标记**（随升级"换成新的"落地；详见 Q&A-2）；脱离"未实现留痕"归类。
- **老兵读取面**：升级后"老兵"可被筛选（"老兵单位""若是老兵"）；权威依据＝"老兵"标记（V4 断言以此为基准）。
- **非功能约束**：构建 0 警告；全量测试绿；P1/P2；不删除文件；编辑范围限本单；遇规格歧义按 grill 提问（不自行发明语义）。

## 二、已解决的歧义（Q&A 逐轮记录）

### Q&A-1（2026-10-06）：S1/S3 边界、专属触发器契约、V1-V5 触发源与验收深度

**子的问题原文（摘要）**：

- 主问题：S1 中"老兵专属触发器"在需求上的对外契约是什么，以及 V1-V5 的触发源由谁承载？
- 1：S1 交付的"专属触发器"是否是升级动作的唯一对外触发入口？名字是否需本单定稿（成为对 S3 可见的契约）？效果触发它的接入方式在需求上是否已定？
- 2：V1-V5"机制级全链"是否允许且期望测试侧用机制代码/现有效果系统手工构造等价触发源（不依赖 S3）？还是要求 S1 内置某类"老兵触发条件"的通用支撑？"在场回合数"可否沿用既有读取面而不新建机制？
- 3：V2"升级时效果执行"验收需打通到什么深度——只要证明"监听 `unit.upgraded` 的监听方可执行效果"即可，还是"升级时效果"的机制支撑也属本单？

**解答**：

**0）边界定调**：S1＝机制层交付（专属触发器＋升级执行＋信号＋数据映射＋读取面）；卡面文本的解析与条件表达（"在场上的第三回合开始时"等）属 S3。V1-V5 在 S1 以"机制级全链"验收——触发源由测试/效果层以机制代码**经公共面手工构造**，不依赖 S3。

**1）专属触发器契约**：
- "老兵专属触发器"＝升级动作对效果层的**唯一标准发动入口**（触发它＝发动升级：全清换新＋广播 `unit.upgraded`）。升级内部服务/门户为实现内部支撑，不作为效果层直接调用契约——避免双路径分歧，保证"经触发器"架构（既定裁定）。
- **标识名本单定稿**并申报（对 S3 可见的跨单契约；对齐既有具名主动触发器命名先例）。
- 效果的触发接入（装载时注入 handler／激活时调用等）：需求只约定"由卡牌的老兵触发效果触发、效果自托管"；具体接入形态由实现阶段制定；歧义处按 grill 申报。

**2）机制级全链与触发源**：
- **允许且要求**测试/效果层以机制代码（经公共面）构造等价触发源——如监听既有信号（回合开始/造成伤害/战斗存活等）＋条件成立时发动专属触发器；**不要求** S1 内置"老兵触发条件"通用支撑（该表达属效果层/S3）。
- "在场回合数"**沿用既有读取面**（`UnitCard.TurnsInPlay`，已具备：入场即 1、回合推进递增）；**不新建机制**。
- 构造须经公共面（效果/触发器体系）——不得绕过专属触发器直调内部服务，以免"经触发器发动"未被验证。

**3）V2 深度**：证明"监听 `unit.upgraded` 的监听方（经公共面构造）可执行一个效果（如将指定卡加入手牌）"——**到这一步即可**；不新增"升级时效果"专门机制（"升为老兵时，X"＝监听 `unit.upgraded` 的普通效果；文本表达在 S3）。若验证中发现通用效果系统缺"监听信号→执行效果"能力，按 grill 申报、不自行扩机制。

**备选与拒绝**：

- 备选 A：S1 内置"老兵触发条件"通用支撑（自动读在场回合数等触发）→ **拒绝**：条件表达属效果层（S3）职责；内置与解析层重复、扩大本单；既有读取面已够测试构造。
- 备选 B：效果层直接调用升级服务方法（不经触发器）→ **拒绝**：与"经触发器发动"裁定不符；须唯一标准入口以免双路径分歧。
- 备选 C：V2 仅验证"信号被发出"（不含监听方执行效果）→ **拒绝**：验收要求"升级＋升级时效果执行"，须证明监听方可执行效果。
- 备选 D：为测试开专用后门（直调内部）→ **拒绝**：须验证"经专属触发器可发动"这一外部行为。

### Q&A-2（2026-10-06）：全清口径的结果面——老兵标记与词条集、重复发动、升级期间信号语义

**子的问题原文（摘要）**：

- 主问题 1："老兵"读取面的承载与"授予老兵版本词条集"的关系：①标记由升级执行无条件统一授予，还是由老兵版本数据携带、随"换成新的"一起落地？②升级前已带该标记（异常/重复发动）："词条集全清"会先清掉它再按升级流程重授吗？③读取面判定"是否老兵"的权威依据：老兵标记／`VeteranOf` 类数据映射／两者之一即可？V4 验收应以哪一读面断言（或两者都须成立）？
- 主问题 2：重复发动"升为老兵"（已是老兵形态再次触发）的语义：可否由实现者自定并申报？若选"幂等无操作"，是否＝零副作用、零信号（`unit.upgraded` 零发射），且与"升级完成广播恰一次"断言相容？
- 主问题 3：升级执行期间的信号语义与观察者一致性：①是否要求对外零中间发射（只在全部结果落定后发一次 `unit.upgraded`）？②攻/防/行动费变化是否经既有数值更新管线发 `card.stat.changed`（有变更恰一次），还是以 `unit.upgraded` 为准、不发？（测试断言口径）③"单次重算"是否为硬性验收点？

**解答**：

**1）"老兵"标记的落地路径与权威读面**：
- ①**由老兵版本内容携带、随"换成新的"一体化落地**：`VeteranOf:<基础卡id>` 转正式承载为"老兵"标记（实例数据/词条层；与隐蔽同族方案；标记承载形态与载荷语义由实现者在申报中定）——**不**在换新之外另设无条件授予。语义＝"当前形态内容（老兵版本）本身声明其为老兵"（单一真源）。
- ②**全清先行**：升级执行以"全清→换新"为序；升级前若已带标记（异常场景）会被清除，随后由老兵版本内容落地；**结果保证＝标记存在且唯一**（无重复残留）。
- ③**权威依据＝"老兵"标记**；V4 断言以其为唯一基准。`VeteranOf:` 的正式承载与该读面为**同一承载体**（避免双真源）；`BecomesVeteran:` 转正式承载为**升级链信息（静态端口）**——供升级执行查找老兵版本定义，**不作**"是否老兵"判据。
- 行为断言：升级前（基础形态）false；升级后 true。

**2）重复发动语义**：
- **裁定＝幂等无操作**（已是老兵形态→无操作）：零副作用、零信号（`unit.upgraded` 零发射）、不中断触发链。理由：重复触发来自正常规则组合（多条件先后达成），"拒绝（异常）"会把正常组合变成异常路径、有中断风险；幂等同时天然断开"升级→监听→再升级"的重入环。
- **与"恰一次"相容（确认）**：每次**真实形态切换**`unit.upgraded` 恰一次；重复发动无形态变化→零发射。"恰一次"断言口径＝"每次真实升级"。
- 实现者若发现更优语义（如携带"未升级"结果标识的幂等返回），在汇报申报。

**3）升级执行期间的信号语义（裁定）**：
- ①**对外零中间发射**：升级执行（清空→换新→词条替换）期间不发任何信号、中间态不可观察；全部结果落定后统一发射。顺序＝**先数值结果（`card.stat.changed`，如有变更）、后机制宣告（`unit.upgraded`）**——监听升级者所见即终态（形态＋数值均就绪）。
- ②**数值变化经既有数值更新管线发出**：攻/防/行动费变化走通用数据改变管线，`card.stat.changed` **有变更恰一次、无变更零发射**（载荷含变化字段，按管线既有语义自然产出）；`unit.upgraded` 独立发出（恰一次）——两者并存、粒度不同（对齐"card.drawn 与 card.hand.add 并存"先例）。**测试断言**：升级后观察者应见 `card.stat.changed`（有变更恰一次）＋`unit.upgraded`（恰一次）。
- ③**"单次重算"为硬性验收口径**：升级的全部数值处置（清修饰／换基准／刷新实时值）合并为**一次重算、一次集中触发**——不得分步触发多轮；测试以 `card.stat.changed` 恰一次（有变更时）断言（实现 API 形态由实现者定）。

**备选与拒绝**：

- 备选 A（主 1①）：升级执行无条件统一授予标记（不依赖数据）→ **拒绝**：与"换成新的"一体化流程重复、引入第二授予源；数据携带为单一真源。
- 备选 B（主 2）：重复发动＝拒绝（异常）→ **拒绝**：正常规则组合会成为异常路径；幂等零中断更安全。
- 备选 C（主 3②）：升级不发 `card.stat.changed`、仅以 `unit.upgraded` 为准 → **拒绝**：数值观察面断裂、与"任意数值变更走管线"既有原则冲突。
- 备选 D（主 3③）：分步重算（清修饰/换基准各触发一轮）→ **拒绝**：违反"一次处理、一次集中触发"（P1 精神）、产生多次数值信号。

### Q&A-3（2026-10-06）：升级发动/执行失败的语义——拒绝形态、回滚目标、失败路径信号

**子的问题原文（摘要）**：

- 主问题 1："拒绝"的统一对外形态与判定口径：①对外形态＝异常上抛／返回失败结果／静默无操作？调用方（效果层/测试）如何区分三类结果（拒绝／幂等无操作／成功升级）？②"已离场/不在场"的判定口径（未单位化？已死亡/已毁？槽位已不在战场？）；③"无老兵版本"的判定口径（未声明 `BecomesVeteran:`／声明了但卡库查不到——两者是否都归拒绝）？
- 主问题 2：执行段失败的回滚目标与"无半态"验收：①回滚目标＝恢复升级前完整原状 vs 尽力恢复以实况计？②"无半态"是否指定必测失败场景与断言内容？③是否要求"预检先行"（全部前置条件先于任何副作用校验；执行段内失败＝异常路径）？
- 主问题 3：失败路径的信号与状态观测：①拒绝/回滚路径是否保证零信号（未落定＝不发射）？②失败后单位保持可正常操作是否为验收点？

**解答**：

**1）"拒绝"的形态与三态可判定性**：
- **三态语义**（锁定）：**成功升级**（形态切换＋信号恰一次）／**幂等无操作**（已是老兵；零副作用、零信号）／**拒绝**（零副作用、零信号）。三态**必须可程序化区分**（供测试断言与调用方分流）——承载形态（结果对象／返回枚举等）由实现者设计并申报（对齐既有"失败原因携带输出""结果对象"惯例）。
- **不得以异常表达三态**：异常仅保留两类——①契约类错误（对象类型/参数违反公开契约等，按既有 fail-fast 惯例）；②执行段意外（见 2）。效果层常规路径（延迟触发、链式触发）下"不在场／无老兵版本"一律＝**结果面拒绝**（对齐 `SuppressRules`/`InhibitRules` 服务先例"拒绝而非部分执行、零副作用"；死亡/离场竞态常见，异常会中断效果链）。
- "不在场"判定口径：**"在场且存活"谓词不满足即拒绝**——未单位化（未入场）、已死亡/已毁、已不在场（不属于战场）均归此类（以既有"存活/放置"读面组合判定；具体读面由实现者选用）。注：本口径与 UnitCard 数值门户"未单位化＝装配错误"先例的差异**以本文为准**——升级调用方为数据驱动效果、按防御式处理。
- "无老兵版本"判定口径：①基础形态未声明 `BecomesVeteran:`；②声明了但运行时查不到对应老兵定义——**两者均归"拒绝"**（可细分原因类别）；**可选增强**：加载/装配期一致性校验（由实现者视成本申报）。
- **边界（重要）**：老兵版本词条集含"未实现词条项"（如 `shock` 等未映射标识）**不构成**升级失败因由——未映射项按既有"留痕"口径承载、不阻止升级。

**2）执行段失败的回滚目标与"无半态"验收**：
- **回滚目标＝恢复升级前完整原状**（损伤/修饰/词条/数值全还原；对齐 S9"失败的转换不得损坏原实例状态"硬约束）——**不采用**"尽力恢复、以实况计"。
- **预检先行＝是（硬性）**：全部前置条件（在场存活、老兵版本可解析、待授词条集可构造等）在产生任何副作用前校验完毕；可预检失败＝拒绝（零副作用）。执行段内失败（不可预检的意外）＝**回滚＋异常上抛**（对齐词条授予装载链 fail-fast 先例）。
- "无半态"验收（必测）：①预检拒绝场景——原状完整、零信号；②执行段失败场景（可构造）——回滚至原状、零信号、单位保持可正常操作、**可再次发动**。执行段失败须有可测构造方式（实现者提供，可在测试装配层构造）。

**3）失败路径的信号与状态观测**：
- **零信号保证**：拒绝/回滚路径不出现 `card.stat.changed` / `unit.upgraded`——"未落定＝不发射"（"先落定后发射"的必然推论）。
- **失败后单位保持可正常操作**＝**验收点**（原状完整性的行为侧面；含"可再次发动升级"）。

**备选与拒绝**：

- 备选 A（主 1①）：拒绝＝异常上抛 → **拒绝**：效果层常规路径下死亡/离场竞态常见、异常中断效果链；与 `SuppressRules`"拒绝＝零副作用结果"服务先例不符。
- 备选 B（主 1①）：静默无操作（三态不区分）→ **拒绝**：三态不可判定、失败专项断言无法成立。
- 备选 C（主 2①）：尽力恢复、以实况计 → **拒绝**：不可预测中间态、违背"无半态"目标；原子恢复更可断言。
- 备选 D（主 2③）：不做预检、直接执行按失败回滚 → **拒绝**：可预检失败应先零副作用拒绝；执行段只应承载"意外"。

**补充（对抗性审视）**：

- 失败可诊断性：拒绝原因须**类别化可读**（供测试与诊断分流）。
- 幂等/拒绝的测试断言写法（兜底口径）：成功＝信号恰一次＋形态变化断言；幂等/拒绝＝零信号＋原状不变断言；"拒绝 vs 幂等"若结果载体不可得，可以"调用前状态预读（是否已老兵）"确立场景语义。

### Q&A-4（2026-10-06）：`unit.upgraded` 载荷与跨卡监听判定；数据映射端口/校验；老兵标记的内容语义

**子的问题原文（摘要）**：

### Q&A-5（2026-10-06）：升级"换成新的"的范围边界（定义/类型/其它卡面信息）＋状态交互与损伤语义

- 泛化口径：**除本次明确清空/替换者（损伤、修饰、词条集、战斗数值基准）外，单位全部运行时数据保持原样**。

**备选与拒绝**：

- 备选 B（主 2①）：机制层内建状态阻断（被压制/被抑制不得升级）→ **拒绝**：属效果层职责；无卡池需求依据；机制层不应发明规则。

### Q&A-7（2026-10-06 收尾）：定稿申报的对外契约边界；工程检查与测试覆盖口径

**子的问题原文（摘要）**：

- 主问题 1：S1 定稿申报的对外契约中，是否存在委托方既定的命名/形态约束？①"老兵专属触发器"标识名：是否已有期望命名或必须复用/避免的词汇（如对齐"部署触发器"风格），还是完全由实现者按既有先例定稿、在汇报中申报（S3 以该名对接）？②"老兵"标记标识（若走词条体系）、单位级"是否老兵"读口命名、"升级发动结果"三态承载形态——是否全部由实现者设计并申报（无额外偏好/禁止项）？③申报清单是否有特定呈现要求，还是随汇报以"申报项清单"形式列出即可？
- 主问题 2：工程检查与测试覆盖口径：①"全量测试绿"的检查范围＝解决方案全部测试工程（Orc.Tests／Orc.Game.Tests／Orc.Script.Tests 等）？"构建 0 警告"是否沿用既有"非 sample 面 0 警告；samples 在途锁定按在途包袱申报"口径（Kb 先例）？②新增测试的组织是否有要求（按"自证对应验收点"组织、命名/数量不限）？③"升级→监听方再尝试发动（重入环）"是否作为必测边界项（幂等零信号）纳入清空/边界专项？清空专项是否必须包含信号断言＋状态断言？

**解答**：

**1）定稿申报的对外契约**：
- 命名总体原则：**定稿即冻结**（对外契约、S3 依赖——对齐"信号名/判定器名一经引用即冻结"先例）；风格对齐同族先例；不得与既有标识冲突。
- "老兵专属触发器"标识名：**由实现者按既有具名触发器命名先例定稿**（风格＝中文＋"触发器"尾缀，对齐"部署触发器""部署词条触发器"等）；**推荐候选"老兵触发器"**（查证无冲突即可采用）；避免项：与既有名重名、直接使用"专属触发器"作为字面（那是文档称法、非正式名）。定稿后申报（S3 以该名对接）。
- 其余标识（"老兵"标记标识〔若走词条体系〕——推荐候选字面"老兵"（与术语一致）、单位级"是否老兵"读口命名、三态承载形态、映射端口形态）：**全部由实现者设计并申报**——无额外偏好/禁止项；须满足：①定稿即冻结；②对齐同族先例命名与卡面词汇域（词条标记情形）；③不冲突。
- 申报清单呈现：随汇报以"**申报项清单**"形式列出即可（对齐既有汇报惯例）、无需特定模板；涉及 S3 对接的项（触发器名等）**标注"对 S3 契约"**字样。

**2）工程检查与测试覆盖口径**：
- ①"全量测试绿"＝**解决方案全部测试套件**（Orc.Tests／Orc.Game.Tests／Orc.Script.Tests／Orc.Lua.Tests——以解决方案实际为准；对齐"四套件全绿"先例）。"构建 0 警告"＝**沿用既有口径**（非 sample 面 0 警告；samples 若有在途锁定情形按在途包袱申报——Kb 先例）。
- ②新增测试组织：按"**自证对应验收点**"组织（对齐既有先例"组织/数量/命名＝实现自由，须自证对应验收点"）；覆盖＝V1-V5＋清空专项＋失败专项（预检拒绝＋执行段失败回滚）＋数据映射专项（自含数据——硬要求）＋读取面；命名与数量不限。
- ③**重入环＝必测边界项**：升级→监听方再尝试发动→幂等零信号（零副作用、零信号、无形态变化）——纳入清空/边界专项。
- **清空专项＝信号断言＋状态断言齐备（是）**：
  - 信号：`card.stat.changed` 恰一次（有变更时）、`unit.upgraded` 恰一次、失败/幂等路径零信号；
  - 状态：损伤归零、修饰全清（含永久型）、词条全清（含运行时授予）、数值＝新基准满值、范围外字段不变（Q&A-5）、标记 true 且唯一。

**补充（对抗性审视）——验收断言矩阵**（防覆盖遗漏）：

| 路径 | 信号 | 状态 | 其它 |
|---|---|---|---|
| 成功升级 | `card.stat.changed` 恰一次（有变更）＋`unit.upgraded` 恰一次 | 清空四项＋数值＝新基准满值＋标记 true 且唯一 | 范围外字段不变；可继续正常操作 |
| 幂等/重入 | 零 | 零变化 | 不中断触发链 |
| 拒绝（不在场/无老兵版本） | 零 | 原状不变 | 可再发动；拒绝原因类别可读 |
| 执行段失败 | 零 | 回滚至原状 | 可再发动；异常上抛（可辨识） |

## 三、边界与失败模式（对抗性审视补充）

- **失败模式**：升级发动时单位已死亡/已离场/无老兵版本→拒绝、零副作用、不产生半态；重复发动（已是老兵形态）→**幂等无操作**（零副作用、零信号、不中断触发链；见 Q&A-2）。
- **原子性**：升级执行（清空→换新→词条替换）失败回滚；观察者不得看到半升级中间态（先落定后发射）。
- **可测试性**：V1-V5 均可经公共面在测试中复现（含确定性；沿用固定种子等既有手段）；信号断言集＝升级前 false/升级后 true、`card.stat.changed` 恰一次（有变更时）、`unit.upgraded` 恰一次、幂等路径零信号。
