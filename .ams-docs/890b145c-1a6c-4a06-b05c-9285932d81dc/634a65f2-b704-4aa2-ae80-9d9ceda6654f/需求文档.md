# 守护词条化 — 需求阐明记录

> 委托：词条效果化·守护（guard）词条化（CodeImplementation；grill 层级＝类/功能流程级）。
> 职责范围＝守护成为词条：词条注册与数据映射（同单落地）＋维护链读点双通道改造＋升级维护驱动扩展（`unit.upgraded` 订阅）＋打标入对战词条池；含守护专项与相关断言更新。

## 一、功能职责与流程约束（本委托需求基线）

- **注册与映射同单落地**：`KeywordIds.Guard`（＝『守护』）注册＋打标（`isBattleKeyword`）；`CardAttributeMap` 增 `guard→守护` 映射——**同单落地**（词条声明含未注册标识＝定义期 fail-fast，否则全卡库加载失败）。
- **维护链读点双通道**：`IsGuardianAt`（CommandManager.cs:813-824）与 `MaintainGuardForLine` 的守护者自身跳过（:781-783）改读 `IsGuard || 词条`——`IsGuard` 通道**并行保留**；判定/保护/豁免规则零变化。
- **升级维护驱动扩展**：维护订阅增加 `GameUpdates.UnitUpgraded`（升级获得/失去守护后重算）。
- **打标**：guard 入对战词条池（wiki『属于对战词条』）；本单全集计数 5→6（shock 后续单 6→7）。
- **测试**：守护专项＋`BattleKeywordTests` 全集更新＋`CardDataBodyTests` 映射断言适配（shock 留痕保持）＋`OfficialCardDataSmokeTests` 注释同步。
- **非功能**：构建 0 警告；四套件全绿；P1/P2；不删除文件；跨批禁区（老兵/隐蔽、词条效果化批 1-3 产物）零触碰；编辑范围限本单。

## 二、已解决的歧义（Q&A 逐轮记录）

### Q&A-1（2026-10-07）：词条化语义边界与判定读取面

**子的问题原文（摘要）**：
- 问题 1：(a) guard 词条生效后的守护行为是否与 IsGuard 通道**完全等价**（词条只是『守护者』第二来源，判定/保护/豁免零变化）？(b)『语义差异显式申报（前线适用/HQ 覆盖为现状扩展项）』的准确含义与申报要求？(c) 官方 guard 卡加载后获得守护行为＝『官方数据经词条生效』预期影响面？是否连同 (b) 申报？（子核实：官方 guard 卡 124 张〔9 老兵＋115 其它〕；升级链『基础无→老兵有 guard』7 条、『失去 guard』0 条。）
- 问题 2：(a)『读点改 IsGuard||词条』的读取面＝**单位实例现势词条面**（反映加载/授予-移除-复装/升级变化，非静态声明）——对吗？（子观察：词条授予/移除链不存在『词条变更』类更新信号。）(b)『查询面/资格链零改动』＝代码零改动、因读维护产物而自动随动——对吗？(c) 双通道统一用于**全部**守护者判定点（相邻守护者判定＋自身跳过）？自身跳过语义保持（含相邻另一守护者）？

**解答**：

**1(a) 等价性＝是，完全等价。** guard 词条生效后，词条只是『守护者』的**第二个来源**（守护者谓词＝`IsGuard || 词条`）；判定规则/保护规则/豁免规则零变化、零修正——含三线＋HQ 维护、相邻＝同线索引差 1、同方限定、死亡不计、守护者自身跳过（含相邻另一守护者）、多源存在性、被守护效果（步/坦攻击者不可攻、炮/轰可通过）等全部点。
- 备选：以词条全量替代 IsGuard 通道 → **拒绝**（既有测试适配面大、无收益；既定裁定为并行保留）。

**1(b) 『前线适用』『HQ 覆盖』的准确含义与申报要求（对象＝现状行为）。**
- **前线适用**＝现状维护链对**前线**亦执行守护维护（`MaintainGuardState` 逐线＝A 支援线＋**前线**＋B 支援线，CommandManager.cs:764-766）——前线单位亦可获被守护、前线的守护者亦为保护来源。
- **HQ 覆盖**＝守护的保护范围**覆盖 HQ**（`MaintainHqGuard`，:798-811：HQ 相邻槽有己方守护者时 HQ 获被守护；HQ 判定链分支含『守护』环节，:720-721）。
- **申报要求＝是**：本单保持现状行为**不改**；交付记录的差异/申报节须将两点**显式声明为『相对官方的现状扩展项』**（供后续官方对齐评审；不得作为本单修正对象）。
- 备选：本单按『官方语义』修正这两点 → **拒绝**（无官方明文细据、超出本单范围、破坏既有行为与测试）。

**1(c) 官方数据影响面＝是，预期影响面；连同 (b) 申报。** 官方 124 张 guard 卡（以子核实为准；委托文本『≥65』为样本下限）加载后获得守护行为——即『官方数据经词条生效』；属预期（任务目标）。交付时连同 (b) 一并在申报节列明（含升级链样本：获得 7 条、失去 0 条）。

**2(a) 读取面＝单位实例的现势词条面——是。** 判定读现势（词条读取面，反映加载期装载/运行期授予-移除-复装/升级后词条集变化），非卡定义静态声明。
- **随动驱动口径（重要）**：『随动』的验收含义＝**词条授予/移除/复装动作完成后，守护维护须被驱动重算一次**（与既有四类更新、升级驱动同模式：动作完成即重算）；**不接受**『等到下一次其它维护事件』的弱语义。
- 实现途径：现状『词条授予/移除链无词条变更类更新信号』——须以**最小加性扩展**补驱动（如在词条链完成点接入维护重算；具体由实现者裁量设计并申报；涉机制面的扩展按既批『最小加性＋申报』口径）。
- 备选：弱语义（等下个维护事件再随动）→ **拒绝**（验收③④随动不成立、与升级驱动口径不一致）。

**2(b) 查询面/资格链零改动＋自动随动——是。** 查询面（`IsUnitGuarded`/`IsHqGuarded`，:732-752）与战斗合法性资格链读**维护产物**（被守护缓存集合）；词条化只改『维护时的守护者判定来源』、产物语义不变 → 这些面代码零改动、因维护重算自动随动。

**2(c) 双通道统一于全部守护者判定点——是；自身跳过语义保持——是。** 『相邻守护者判定』（`IsGuardianAt`）与『守护者自身跳过』（`MaintainGuardForLine` 内）两处统一双通道；『守护者自身永不获被守护』语义保持（含相邻另一守护者、含词条来源）。

**架构审视补充**：
- 边界完整性：升级『失去 guard』官方 0 条，但运行期移除场景仍须专项覆盖（验收③④已含）。
- 失败模式：注册与映射同单＋全卡库加载 fail-fast；『注册先于使用』契约由既有体系保证。
- 非功能：全量重算语义不变（无新增复杂度）；维护同步语义（P2）保持；词条变更驱动加性扩展不得引入异步。
- 多视角：官方对局行为变化面（124 张）＝申报覆盖；对既有 IsGuard 卡与测试＝零影响（双通道）。

### Q&A-2（2026-10-07）：升级边界与专项测试形态

**子的问题原文（摘要）**：
- 子核实：官方升级链共 44 条（『基础无 guard→老兵有 guard』7 条；『失去 guard』0 条）；`BattleKeywordTests.BattleKeyword_GrantAll_Composition` 含两处『5』硬断言（`CountBattleKeywords`/`HasAtLeastBattleKeywords`）。
- 问题 1：(a) `UnitUpgraded` 触发重算＝同模式一次**全量重算**（`MaintainGuardState` 全量、逐线清空重建）？(b) 验收③『升级失去 guard→维护撤销』：以升级路径**黑盒断言**覆盖（自造样本），还是以**运行期移除**等效覆盖即可（升级专项只覆盖『获得』方向）？(c) 官方样本（190th/216th）测试角色：引用官方数据（依赖 outputs/kards-cards、缺则跳过）还是仅作交付申报核实记录、专项用自含样本？
- 问题 2：(a) 专项数据体路径样本＝『自含数据体 JSON→加载路径→行为断言』（不依赖 outputs）硬要求？(b) 官方数据影响（124 张/7-0）＝需断言落测试，还是『注释同步＋交付申报』即可？(c) `BattleKeywordTests` 两处『5』硬断言＝属『全集更新 5→6』统一更新（同文件全部口径一致）？

**解答**：

**1(a) ＝是（同模式全量重算）。** `UnitUpgraded` 驱动与既有四类更新一样**调用唯一的全量重算**（`MaintainGuardState`：清空重建、逐线维护）——升级驱动只新增『何时调用』，不引入增量重算、不改重算语义。
- 备选：增量重算（仅更新受影响单位）→ **拒绝**（无先例、无收益、破坏全量重算简单性；P1/P2 无此需要）。

**1(b) ＝以升级路径黑盒断言覆盖『失去』（自造升级样本）。** 自造『基础有 guard→老兵无 guard』的 BecomesVeteran 链样本（自含数据体），断言升级后维护撤销（原相邻者不再被守护）；与『获得』方向（升级获得 guard→相邻即被守护）成对覆盖。『运行期移除』的撤销断言**不能替代**——那是词条移除链（另一路径），两路径均须各自覆盖（Q&A-1 已定）。
- 备选：仅运行期移除等效覆盖（升级专项只做『获得』方向）→ **拒绝**（升级路径的『失去』无黑盒验证、驱动语义不完整）。

**1(c) ＝官方样本仅作交付申报中的核实记录；专项测试采用自含样本。** 190th/216th 等官方引用为申报记录（链计数 7/0、44 条总链）；测试不依赖 outputs/kards-cards（无环境依赖、无跳过分支）。
- 备选：测试引用官方数据（缺目录则跳过）→ **拒绝**（环境依赖、非先例、测试脆弱）。

**2(a) ＝是（自含数据体硬要求）。** 按先例（老兵/隐蔽/批 1-3 专项模式）：自含数据体 JSON→加载路径→行为断言；不依赖 outputs/kards-cards。

**2(b) ＝注释同步＋交付申报记录即可；不新增官方卡断言。** 官方映射的断言面由 `CardDataBodyTests` 映射断言适配承担；全卡库加载路径由 `OfficialCardDataSmokeTests` 既有覆盖保障（加载失败即红）；最小变更原则。
- 备选：新增 Smoke 官方卡断言（如对某 guard 卡断言词条含 Guard）→ **拒绝**（与必改清单不符、重复覆盖、无必要）。

**2(c) ＝是（5→6 全口径统一）。** `BattleKeywordTests` 内全部『5』口径统一更新为『6』（两处硬断言＋GrantAll 构成场景＋同文件其余口径；须全文件排查一致）。
- 备选：部分更新 → **拒绝**（口径不一致）。

**架构审视补充**：
- 边界完整性：升级全量重算自然覆盖『守护者身份经升级变化』的全部子情形（获得/失去/无变化）。
- 失败模式：自造升级样本的链配置错误＝定义期/加载期 fail-fast（老兵机制既有）；无新增失败模式。
- 非功能：升级事件频率低、全量重算成本不变（与既有四类更新同）；P2 同步语义保持。
- 元审视：子核实数据（44 链/7-0）较 Q&A-1 更全，采纳为记录；问题精准，无需纠正。

### Q&A-3（2026-10-07）：非功能口径与编辑边界

**子的问题原文（摘要）**：
- 问题 1：(a)『P1/P2』的确切含义（对应什么要求/属性？）、在验收中如何体现？(b)『四套件』＝4 个测试项目（Orc.Tests/Orc.Lua.Tests/Orc.Game.Tests/Orc.Script.Tests）？『构建 0 警告』范围＝全解决方案（含 samples）？『四套件全绿』＝代码冻结后全量复跑＋交付记录测试计数（批 3 复跑计数义务适用本单）？
- 问题 2：(a) 跨批次文件（KeywordSystem/KeywordRegistry/CommandManager/CardAttributeMap）编辑边界＝仅限本单直接触及区域、其余零触碰？注释同步允许清单（KeywordRegistry 枚数描述与『守护/冲击』句、KeywordIds 头注释与清单、CardAttributeMap 头注释、Smoke、BattleKeywordTests）？(b) 清单外既有测试『直接所致』翻红＝逐条等效性论证＋必要适配＋完整申报（沿批 3）？非直接所致＝停手申报？(c) 词条变更驱动扩展的防御语义：无对局上下文下授予/移除 Guard 不得抛错（沿用『可缺省＝防御跳过、功能不可用、操作不失败』先例）？

**解答**：

**1(a) P1/P2＝项目既有实现原则（CONTEXT 权威定义）**：
- **P1＝禁止无条件数据更新**（改变才传播、收敛）。本单体现：守护维护重算只在**驱动**（四类更新/升级/词条变更）时执行；词条变更驱动扩展须为『变更驱动』（有实际授予/移除才触发），**不得**无条件常驻/轮询/无变更重算。维护重算内部『清空重建』＝按实际状态计算产物，无『无条件传播』问题。
- **P2＝更新不允许异步**（同步/顺序语义、防竞态）。本单体现：维护重算在动作完成点**同步**完成；驱动扩展与订阅不得引入异步/悬挂；升级驱动与四类更新同语义（同步调用全量重算）。
- 验收体现：实现申报中『驱动扩展设计含 P1/P2 自证』＋全量测试（既有同步语义断言面）＋无新增异步面。

**1(b) 范围与复跑口径（据解决方案文件核实）**：
- 『四套件』＝**4 个测试项目**（`Orc.Tests` / `Orc.Lua.Tests` / `Orc.Game.Tests` / `Orc.Script.Tests`）——确认。
- 『构建 0 警告』范围＝**全解决方案 `OrcEngine.sln`**——据 sln 核实包含：源码 4 项目（Orc/Orc.Lua/Orc.Game/Orc.Script）＋测试 4 项目＋**samples（Orc.Game.Sample）**（含 samples）。
- 『四套件全绿』＝**是**：代码冻结后 `dotnet build OrcEngine.sln --no-incremental`＋`dotnet test OrcEngine.sln` 全量复跑；交付记录**测试计数（四套件各自与总数）**——批 3 复跑计数义务**适用本单**。

**2(a) ＝是（仅限本单直接触及区域），注释允许清单确认（含补充）**：
- 区域原则：仅限 Guard 标识与注册新增、维护链读点与订阅改造、**直接相关注释同步**；其余区域（含老兵/隐蔽/词条效果化批 1-3 功能、Targeter 等）零触碰；必须波及区域外＝停手申报。
- 注释同步允许清单（确认＋补充）：①`KeywordRegistry`：生产内建枚数描述（十七⇒十八）与『「守护」「冲击」…不在本批实现范围』句（守护部分）；②`KeywordIds`：头注释与清单（Guard 加入）；③`CardAttributeMap`：头注释（『guard/shock…』句剔除 guard）；④`CommandManager`：**维护链段直接相关注释**（守护者判定/HQ 表述等，随读点改造同步）；⑤`OfficialCardDataSmokeTests` 注释；⑥`BattleKeywordTests` 注释。
- 说明：与其它批次已登记的重叠注释项（如支援线遗留清单中的 CommandManager 维护段表述）属**直接相关区域可同步项**——同步并在申报中注明即可；备选（严格回避重叠项）→ **拒绝**（同段注释不同步将造成文档不一致）。

**2(b) ＝是（沿批 3 翻红口径）**：直接所致＝逐条**等效性论证**＋必要适配＋**完整申报**；非直接所致＝**停手申报**（不得顺手修改掩盖）。

**2(c) ＝是（防御语义沿用既有先例）**：无对局上下文（独立构造）下授予/移除 Guard＝**防御跳过、功能不可用、加载/操作不失败**（沿用词条装载上下文『可缺省』与批 1/2 模式『独立构造不注册/不订阅』先例）；词条变更驱动扩展在无上下文时**不得抛错**；既有装载/操作链失败回滚语义保持。

**架构审视补充**：
- 非功能：性能（全量重算成本不变、变更驱动不引入高频触发）；可维护性（注释同步清单化、边界申报制）。
- 失败模式：无上下文降级（不失败、功能不可用）；驱动扩展如涉装配期/运行期注册面，语义沿既有（最小加性＋申报）。
- 权衡记录：注释同步『直接相关区域』与『他批登记清单』重叠处理＝可同步＋注明（替代『严格回避』被拒：造成同段注释不一致）。
- 元审视：P1/P2 与『四套件』为项目既有术语（CONTEXT）与既批口径（委托简写）；问题合理，本单沿用不改。
