# Requirements Grill Plan — 消费式 UI 的事件流输出改造

> 本轮 grill 聚焦：**统一引用的定位**（Nexum 已查清：它只是传输层，不提供实体级引用/寻址，实体 ID 须应用层自带），并顺带暴露**稳定 ID 跨计算机一致性**这一前提。

## 未决问题

### Q20: 对局拓扑（引擎跑在哪、谁权威）In Progress
- 待定：**t1** 服务端权威跑引擎、客户端仅消费/渲染 / **t2** 每个 Godot 端各跑一份引擎并确定性同步 / **t3** 混合（服务端权威＋客户端预测）。
- 影响：决定 ID 分配、引用解析方式、段是否跨机器传输；t1 下客户端可能**没有本地实体**（收到的是 id 形态，需靠配套快照建"id→表现对象"表）。

### Q12: 稳定 ID 键空间与快照对齐 Pending
- 与 Q19/Q20 耦合：ID 键空间＝Guid / 对局内序号 / 复合；是否需"ID → 实体当前状态"配套快照与对齐点。

### Q6: 多次段消费的排队/背压 Pending
- 待定：UI 未播完又来新段 → 排队/合并/丢弃；缓冲上限；与"引擎不等 UI"（R4）配套。

### Q8: "段"是否携带元信息（段号/序号/时间戳/动作标识/版本）Pending
- 待定：决定 UI 能否排序、对齐快照、检测漏段。

### Q11: 消费粒度与回放能力 Pending
- 待定：仅顺序播放 / 需暂停·快进·回溯·重放。

### Q13: 漏段/断线补齐容忍（联网场景）Pending
- 待定：联网下丢段/重连是否需要补齐/重同步；与 Q12 对齐点耦合。

### Q14: 表现编排元数据 Pending
- 待定：引擎侧是否输出时长/分组/串并行，还是纯逻辑事件由 UI 排练。

### Q15: 多消费者形态 Pending
- 待定：单客户端 / 多订阅者 / 旁观 / 回放服务（联网下多端消费）。

### Q16: 改造边界（加性 vs 受控变更）Pending
- 待定：仅 Output 层加性扩展，还是可动内核既有语义（流封口/裁剪、`Ref<T>` 语义、Emit 通知顺序）。

### Q20: 对局拓扑（引擎跑在哪、谁权威）Pending
- 待定：服务端权威跑引擎、客户端仅渲染 / 每个 Godot 端各跑一份引擎并同步；决定 ID 分配与引用解析方式。

## 已决问题

### Q1: 「事件流」消费对象定型 Completed
- 决策：**b** —— UI 消费 `EventStream`（因果记录树），不实时更新，以"一段事件流"（批）形态接收；UI 收到后异步播放。

### Q2: 批边界判定依据 Completed
- 决策：**a** —— 逻辑边界：一次外部动作调用返回即切一段；不引入时间阈值/计时器。

### Q3: "一段事件流"的载体形态与内容范围 Completed
- 决策：**b** —— 自包含"段"对象；子决策 **s2**：段起点＝本段**第一个条目**（不限 kind）。

### Q4: 交付给 UI 是快照/拷贝还是引用 Completed（同进程前提）
- 结论：**引用即安全**（LogEntry 不可变＋执行流静止）；跨计算机场景改由统一引用承载。

### Q5: UI 注册与段交付形态 Completed
- 决策：**a** —— 新增独立"段订阅"注册口；子决策 **Q5a**：接收**所有段**，过滤由 UI 自持。

### Q7: 动作边界的界定与段产出驱动 Completed
- 决策：**a** —— 引擎提供"动作作用域"原语，游戏层动作入口统一包载，引擎在结束点自动产出段。
- 子决策 **Q7a**：动作口径＝对局级操作入口；`Initialize` 计一次大动作；底层 `Emit`/`DestroyCard` 不算。
- 子决策 **Q7b**：外层作用域优先，内层合并为外层单段。

### Q10: 部署与进程拓扑 Completed
- 决策：**a** —— 同进程同语言（**Godot C#**）；但为**联网游戏**，另需跨计算机引用（→ 统一引用，Q17）。

### Q18: Nexum 方案澄清 Completed
- Nexum（`aizuon/nexum`，MIT，.NET 10，受 ProudNet 启发）＝**传输层＋消息路由库**：TCP／可靠·不可靠 UDP、NAT 打洞、P2P 组、MTU 发现、自适应分片、Zlib、AES/RC4＋RSA 密钥交换、服务器时间同步、RMI（`ushort` RMI ID）＋Roslyn 源生成序列化。
- **不提供**：实体级网络对象 ID／状态同步／快照／预测回滚／对象引用与生命周期／Godot 集成。**实体标识须应用层自带**（如 DTO 字段 `PlayerId`）。
- ⚠️ 版本落差：Nexum 目标 **.NET 10**，Godot 4 的 C# 为 .NET 8 系。
- 推论：统一引用的第③形态＝**可序列化的"引用 DTO"**（携带稳定 ID 等），经 Nexum RMI/`NetMessage` 传输；Nexum 只负责"送达某 Host/会话/peer"，实体寻址由本引擎定义。

### Q17: 统一引用的定位与三形态语义 Completed
- 决策：**a** —— 内核级统一引用类型（`Orc` 内新增，包裹 `Ref<T>` 并携带稳定 Id）。
- 子决策 **Q17a**：**u1** —— 三形态是同一逻辑引用的三种表示（union＋解析器），非三个独立类型。

### Q19: 稳定 ID 的跨计算机一致性 Completed（方向）
- 决策：**n2/n3 方向** —— **确定性生成 / 复合键**（对局种子＋确定性序号，或"对局实例 ID＋卡定义 ID＋序号"复合），使各端可算出同一 ID；现有"ID 水位线"确定性自增为基础。
- 备注：需与 Q20 拓扑配合——"对局实例 ID"本身也须跨端一致（由创建方分配并同步）。
