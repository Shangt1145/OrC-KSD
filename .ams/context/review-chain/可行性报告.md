# 审查链可行性报告

> 目标（用户原述）：设计一条完整的审查链——在某个时刻，从逻辑引擎的总线开始，生成所有效果的文本视图；
> 并为此建立"编排层 / 自由逻辑层"三块序列化、编排管理器与触发器链、效果序列化。
> 本报告只做可行性判断与缺口定位，不含实现方案定稿。

## 结论（先给结论）

**整体可行，但不能按字面 100% 落地**。存在 **1 条硬边界** + **3 个必须先行定义的语义**：

- **硬边界**：引擎当前所有"逻辑本体"都是 **C# 委托**（lambda/方法组），捕获实例状态（`card`、`_chainEngine` 等），**无法从文本反序列化重建**。
  → "自由逻辑层的『我的逻辑是什么』序列化"只能做到 **稳定标识 + 代码侧注册表回指**（"这是哪段逻辑"），做不到"把逻辑写成文本、再读回来执行"。
  真正的逻辑文本化必须引入解释层（`Orc.Lua` 已存在但**尚未接入引擎**）。
- **待定语义 1**：审查链的"链" = **静态声明期关系图**（触发器为节点、handler 为边）还是 **运行期实际因果树**？后者已被 `EventStream` / `EventStreamJson` 承载。
- **待定语义 2**：序列化的目的 = **只读审查导出**，还是 **可重建**（反序列化后恢复逻辑装配）？
- **待定语义 3**：`HookID` / `TriggerID` / `HandlerID` 三者**目前均不存在**，需先定义标识空间（现有 `Trigger.Name` 只是展示名、**同名不消歧**）。

## 二、需求逐条可行性

### 需求 1：逻辑序列化（编排层 / 自由逻辑层 / 逻辑本体）

| 子项 | 可行性 | 说明 |
|---|---|---|
| "编排层"（什么时候该调用）序列化 | ✅ 可行 | 载体 = hook 列表 + `MountPriority` + `Owner` + band/priority/注册序。这些**已在 `Trigger` 内部**（`Trigger.cs:136-145`），只缺**导出 API** |
| "我该被什么调用"（反向依赖）序列化 | ⚠️ 半可行 | 静态反向边 = "哪些触发器声明了某 hook" → 由 Bus 订阅表可得（需新增枚举面）。但**运行时被谁调用**（跨触发器嵌套调用）只能靠运行期观测 |
| "我的逻辑是什么" 序列化 | ❌ 有硬边界 | 见结论：委托不可文本化。只能"标识 + 代码回指" |
| 初始化收集底层触发器 HookID | ⚠️ 需新建 | `TriggerRegistry` 覆盖不足（见矛盾 C3）；hook 无注册表；需新增 HookID 定义与登记 |
| 效果订阅"包裹 handler ID"存入字典 | ✅ 可行且方向正确 | 需在 `Trigger.Register` 上引入 `handlerId` 参数（加性重载），或引入独立登记面 |
| handler 声明"可能触发的触发器" | ✅ 可行（须手工） | 无法静态提取（闭包体内隐含，见矛盾 C4）；只能新增**声明式 API** |

### 需求 2：编排管理器 + 触发器链

- ✅ **可行**。静态图模型：节点 = 触发器（含 HookID/TriggerID/分层），边 = handler（含 HandlerID、band、priority）+ "handler → 声明其会触发的触发器"边。
- ✅ "特定触发器形成的触发器链" = 从该节点沿声明边做可达性遍历（BFS/DFS）。
- ⚠️ 但需先定义：链是**声明期可达图**还是**运行期实际调用序列**；且 **Bus 无法覆盖主动效果**（见矛盾 C5），起点必须改为"引擎卡牌登记 + 效果实例"而非纯 Bus。
- ⚠️ 需要"编排管理器"的**承载位置**定夺：扩展现有 `TriggerRegistry`，还是新建独立管理器。

### 需求 3：效果序列化（主触发器 + 挂载触发器 HookID + 预制体声明）

- ⚠️ **半可行**，且对**主动效果不成立**（主动效果主触发器不可挂载、无 HookID，见矛盾 C1）。
- 被动效果可序列化为：`{ effectId, mainTrigger: { hooks: [...], events: [...] }, injections: [{ targetTriggerId, band, priority, handlerId }] }`。
- ⚠️ "预制体"是**新概念**，需定义：是"可复用触发器/效果模板"？还是"除主触发器外需一并挂载的其它触发器（子触发器）声明"？
- ⚠️ 现状连"效果 → 注入了哪些 handler 到哪些触发器"都**不可反查**（`_rollbacks` 只留闭包），需先补登记面。

## 三、代码实际行为与需求陈述的矛盾（先暴露，不暂记）

**C1 · 主动效果没有"HookID"**
- 陈述原文：「效果可以序列化为，一个主触发器和其需要挂载的触发器的 HookID」。
- 代码实际：主动效果（指令）主触发器 `Kind=Active`，构造期声明 hooks 被**拒绝**（`src/Orc/Core/Trigger.cs:120-124`），且主动效果**不参与装载/挂载**（`src/Orc/Cards/Effect.cs:11,306-310`）。
- 结论：对主动效果，"主触发器 + 挂载 HookID"模型不成立；`Orc.Game` 中唯一生产级效果 `DeathrattleEffect` 也是**动作型、不经订阅**（`src/Orc.Game/Cards/DeathrattleSystem.cs:43,114`）。

**C2 · 效果的注入关系已丢失，无法反查**
- 陈述原文：「所有 handler 和触发器都要在引擎的某个管理器处记录关系」。
- 代码实际：`Effect.Inject` 内部只登记撤销闭包 `_rollbacks.Add(() => target.Unregister(registration))`（`src/Orc/Cards/Effect.cs:88-89`），**目标触发器对象与句柄未被保留**；触发器自身事件表 `_events` 为 private。
- 结论：现状**无任何途径**从效果反查"它注入了哪些 handler 到哪些触发器"，必须先补登记面。

**C3 · "底层触发器"实际覆盖远小于总线**
- 陈述原文：「游戏引擎初始化时，收集所有底层触发器的 Hook ID，并在引擎内维护底层触发器」。
- 代码实际：`TriggerRegistry` 只登记 4 个指挥流程触发器（`src/Orc.Game/Match/Match.cs:414-417`）；其余带 hook 的被动触发器（防御归零检查、HQ 归零检查：`src/Orc.Game/Commanding/CommandManager.cs:164-180`；再触发接收：`src/Orc.Game/Cards/RetriggerSystem.cs:87-92`；每个被动效果的生命周期触发器）**都只 `Bus.Mount`，不登记进 `TriggerRegistry`**。且登记条目只有 `{Trigger, Layer}`，无 HookID。
- 结论：需要"覆盖全部已挂载触发器"的登记路径，或改为从 Bus 反向枚举。

**C4 · handler "会触发哪个触发器" 无法静态提取**
- 陈述原文：「允许 handler 声明自己可能会触发的触发器（不强求社区的动态 handler 声明）」。
- 代码实际：下游调用隐含在闭包体内（如 `UnitCard.HandlePlayChainAsync` 内调 `unit.DeployTrigger.InvokeAsync`，`src/Orc.Game/Cards/UnitCard.cs:84`；`Inject` 的 handler 内容同样不可见）。
- 结论：只能由作者**显式声明**；这与用户"不强求动态 handler 声明"一致，但意味着静态图**天然不完备**。

**C5 · "从总线开始" 无法枚举到全部效果**
- 陈述原文：「从逻辑引擎的总线开始，生成所有效果的文本视图」。
- 代码实际：主动效果不挂总线（C1）；词条内嵌效果经独立通道挂载（`DeathrattleKeywordComponent.EmbedEffect`，`src/Orc.Game/Cards/DeathrattleSystem.cs:36`）。
- 结论：起点应为"`LogicEngine.Cards` → `Card.Effects` + 词条内嵌效果 + Bus 订阅"，Bus 只是其中一个投影面，不是全集。

**C6 · 无 HookID / TriggerID / HandlerID 定义**
- 陈述原文：多处使用 "Hook ID"、"handler ID"。
- 代码实际：hook 是开放字符串、无注册表（`src/Orc/Core/Bus.cs:7`）；触发器只有 `Name`（展示名，**同名不消歧**，见 `.ams/context/CONTEXT.md` "触发器" 条）。
- 结论：三者标识空间需先行定义，否则"链"与"序列化引用"无稳定锚点。

## 四、可行方案骨架（建议，待 grill 定稿）

1. **标识层**：为 `Trigger` 引入稳定 `TriggerId`（引擎内自增或 Guid）；为注册项引入 `HandlerId`（`Trigger.Register` 加性重载）；为 hook 引入注册表（`HookId` = 规范化字符串 + 首次登记序）。
2. **登记层**：新增/扩展"编排管理器"，在 `Register` / `Inject` / `Mount` 三个动作处**集中登记** `(HookId → TriggerId → HandlerId → 声明下游 TriggerId)` 关系，并允许从效果反查注入面。
3. **导出层**：编排管理器提供 `Export()`（文本/JSON）；审查链 = 从指定 TriggerId 出发的可达子图；被动效果序列化 = 需求 3 结构；主动效果另立形态（动作型，无 hook）。
4. **运行期侧**：复用 `EventStreamJson` 已有能力，作为"实际调用链"补充。

## 五、风险与工作量

| 风险 | 说明 |
|---|---|
| 标识稳定性 | `Trigger.Name` 同名问题必须先解决，否则序列化引用歧义 |
| 反序列化不可行 | 若要求"读回文本即恢复逻辑"，则必须先引入 handler 工厂注册表（ID→工厂），且逻辑本体仍来自代码 |
| 静态图不完备 | 动态/社区 handler 的边靠声明，声明缺失即图断裂（需明确"缺失边"的表示） |
| 改动面 | 触及内核 `Trigger`/`Bus`（加性 API）+ 游戏层效果系统；需遵守 P1/P2 与既有加性扩展惯例 |

## 六、待对齐的决策点

1. 审查链语义：静态声明图 / 运行期因果树 / 两者并存（Q1）。
2. handler 逻辑本体的序列化深度：标识层 / 文本化 / 混合（Q2）。
3. 序列化目的：只读导出 / 可重建（Q3）。
4. 标识空间方案：TriggerId / HandlerId / HookId（Q4）。
5. 效果序列化对主动效果的形态（Q5）。
6. "预制体"定义（Q6）。
7. 编排管理器承载位置（Q7）。
